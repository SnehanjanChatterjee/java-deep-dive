## Define what one measured operation includes

“How do ArrayList.contains and HashSet.contains compare for a middle-position hit and a miss at sizes sixteen and 1024?” defines operations, inputs and cases. “Which collection is fastest?” leaves the required semantics and workload unspecified.

The supplied experiment measures one membership query against an already built container. If an application constructs a set for one lookup, that lookup-only result cannot answer its total-cost question. First profile the real application to choose a relevant target; a faster tiny operation may have little end-to-end effect.

## Trace setup and one lookup invocation

Trial setup builds both containers using the selected size. For a hit, key is size/2; for a miss it is minus one. A call to listContains then scans its prepared list, while setContains performs a hash membership query. Both return the boolean so the harness consumes the result. Neither measured method constructs/populates a container.

At size sixteen, a middle hit is not the same scan workload as a first-element hit or a miss. Integer hashing/equality and cached boxing ranges are part of this selected workload. It does not represent arbitrary long Strings, custom expensive equality, adversarial collisions, concurrent mutation or insertion cost.

## Explain each harness control

| Control | What it changes | What it does not establish |
| --- | --- | --- |
| State with Scope.Thread | Independently owned state per benchmark thread | Behavior under an application's shared contention |
| Param | Selected sizes and hit/miss cases | A representative production distribution by itself |
| Setup at trial level | Build once outside measured calls | Total cost of constructing a collection |
| AverageTime and ns output | Mean time per operation under the configured harness | End-to-end request p99 |
| Warmup | Execute before recorded iterations so profiles can evolve | One universal point when all JVM behavior is stable |
| Measurement iterations | Repeated recorded work | Immunity to an unrealistic question |
| Forks | Fresh JVM processes | Elimination of every machine/workload influence |

The annotation processor produces harness code; simply invoking a benchmark method in an ordinary main is not equivalent. A profiler can help explain allocations or running paths; a score alone does not establish its cause.

## Read a real short-run scoreboard as an exercise

The following is a selected earlier JMH 1.37 capture on JDK 25.0.5. It used **one fork, one 200 ms warmup iteration and one 200 ms measurement**, overriding the source's longer configuration. This is a harness smoke record for learning output fields, not a reliable performance comparison.

```text
Benchmark                     (scenario)  (size)  Mode  Cnt  Score   Error  Units
LookupBenchmark.listContains         hit      16  avgt       4.601          ns/op
LookupBenchmark.setContains          hit      16  avgt       1.264          ns/op
```

Read the first row as the average-time score reported for this hit-at-size-sixteen lookup-only case in that short configuration. The last unit is nanoseconds per operation. The second row describes a different membership implementation under those same listed inputs. A blank Error does not mean zero uncertainty; this tiny record supplies no useful estimate of repeatability across a substantial experiment.

The supported conclusion is that the harness constructed and executed those cases and reported those scores. It does not establish a universal collection ranking or a reusable speedup. Use the declared full warmup/measurements/forks, inspect variation and profiles, and record runtime/flags/collector/input distribution before making a workload-specific performance claim. Do not select the fastest sample as the result.

For a deliberate smoke execution, the command can override with `-wi 1 -i 1 -w 200ms -r 200ms -f 1`; keep that purpose distinct. Run `-h` and `-lprof` to inspect supported options/profilers.

## Avoid changing the optimizer's question accidentally

Dead-code elimination can remove an unused computation; constant folding can replace work known in advance. Returning a result lets JMH consume it, and Blackhole handles multiple independent values. These controls do not make constant/contrived inputs representative.

Large manual repetition loops can expose optimizations different from independent application calls. Invocation-level setup can dominate tiny measured operations. Moving construction into the benchmark can be correct for a total-cost question, but label it as a different experiment. Compare required observable semantics rather than removing a publication or copy only from the apparently faster branch.

Shared benchmark-scoped state can model contention only when the operation is valid under that sharing. Unsynchronized mutable containers do not become a valid concurrent workload because a harness starts several threads. Thread-scoped data can conversely hide contention that the actual application experiences.

## Complexity and application relevance

An array scan can benefit from locality; a hash lookup pays hash/equality and table-access costs. Their scaling models differ as size grows, while a crossover under one workload requires measurement. A microbenchmark cannot establish request tail latency under queueing, I/O and arrival patterns. Throughput, mean operation cost and percentile latency answer different questions.

## Exercise and complete reference interpretation

Explain exactly what setup excludes, why the returned boolean matters, and what hit/miss distribution is measured. The complete LookupBenchmark source/project is the reference implementation. The decoded scoreboard above is the worked result-reading exercise.

To study a one-off collection conversion, create a separately named construction-plus-lookup benchmark rather than relabeling the lookup-only score. To study shared contention, change state ownership deliberately and preserve a valid synchronization contract. A useful report states the actual question and its practical limits rather than claiming the harness validated the application design.

## Start with one symptom and one question

A request is slow. Is it calculating, waiting for a lock, waiting for I/O, queued without a worker, or stopped for runtime coordination? Each hypothesis needs different evidence. A thread dump captures stacks/states at a point in time. A heap dump captures object relationships. JFR records configured events over an interval. None is a universal explanation for every symptom.

Begin with a controlled program whose cause is known. Then use the evidence to recover that cause, rather than guessing the cause from an unfamiliar tool label.

## Capture evidence while the relevant phase exists

Compile and start a recording before contention begins:

```bash
javac DiagnosticLab.java
java -XX:StartFlightRecording=name=study,settings=profile DiagnosticLab
```

In another terminal, substitute the program's printed PID:

```bash
jcmd <pid> help
jcmd <pid> Thread.print -l
jcmd <pid> GC.class_histogram
```

The PID is a placeholder, not literal angle-bracket shell syntax. Attach only to this controlled process. Help reports the target VM's supported commands and impact. The class histogram can pause/request collection depending on command options/runtime; choose it because it answers a specific question, not as a harmless universal probe.

After collecting the blocked state, press Enter at the first program prompt. While the program remains at its second prompt, capture the completed recording:

```bash
jcmd <pid> JFR.dump name=study filename=study.jfr
jcmd <pid> JFR.stop name=study
jfr summary study.jfr
jfr print --events jdk.JavaMonitorEnter,jdk.ThreadPark study.jfr
```

Press Enter at the second prompt to finish. Dumping before release can omit the still-incomplete monitor-enter event. Start recording before acquisition begins: starting midway through an already blocked operation may miss that event.

An alternative on Unix-like HotSpot systems uses a startup filename and dump-on-exit, avoiding a live attach requirement for exporting the recording:

```bash
java -XX:StartFlightRecording=name=study,settings=profile,filename=study.jfr,dumponexit=true DiagnosticLab
kill -QUIT <pid>
```

Send QUIT only to the printed PID of this owned lab while it is at its first prompt; HotSpot prints a thread dump. Release the two prompts and read the completed file after normal exit. The following worked excerpt was obtained through that controlled thread-dump/recording path. Availability/permissions and platform signal behavior remain target-specific.

## Connect the blocked contender to its owner

These selected lines come from the lab on JDK 25.0.5. Headers and unrelated library frames are omitted; object identities and line numbers can vary between captures.

```text
"study-owner"
   java.lang.Thread.State: WAITING (parking)
    at java.util.concurrent.CountDownLatch.await(java.base@25.0.5/CountDownLatch.java:230)
    at DiagnosticLab.hold(DiagnosticLab.java:16)
    - locked <0x0000000342aa6978> (a java.lang.Object)

"study-waiter"
   java.lang.Thread.State: BLOCKED (on object monitor)
    at DiagnosticLab.contend(DiagnosticLab.java:23)
    - waiting to lock <0x0000000342aa6978> (a java.lang.Object)
```

Match the monitor identity **within this dump**. Waiter requests the same object owner retains. Owner's WAITING state describes its latch park; it does not mean the application monitor was released. Unlike Object.wait on that monitor, CountDownLatch.await does not release unrelated monitor ownership.

There is no dependency from owner back to waiter: main releases the latch on Enter. This is deliberate contention with a release path, not a deadlock cycle. Repeated samples before release can establish persistence during that interval. Observing the blocked acquisition disappear after release is the discriminating follow-up.

## Read a completed JFR monitor event

```text
jdk.JavaMonitorEnter {
  monitorClass = java.lang.Object (classLoader = bootstrap)
  previousOwner = "study-owner" (javaThreadId = 29)
  eventThread = "study-waiter" (javaThreadId = 30)
  stackTrace = [
    DiagnosticLab.contend() line: 23
    java.lang.Thread.run() line: 1474
  ]
}
```

These selected fields connect the same owner, waiter, monitor class and acquisition method. Timestamp, address and duration are intentionally omitted: the wait duration is controlled by the release prompt and is not an application performance result. Do not assume every tool's address field is the identical representation of the heap monitor identity shown by another tool.

An empty event list is not proof no contention occurred. Events may be disabled, shorter than a threshold, outside the recorded interval, or incomplete when exported. JFR execution samples concern sampled running stacks; a repeatedly parked worker can contribute wall-clock latency while consuming little CPU.

## Choose heap and native evidence for memory questions

A histogram groups object counts/shallow bytes by class. It cannot identify the owner keeping arrays alive. A supported `jcmd <pid> GC.heap_dump study.hprof` captures a local heap graph; inspect dominators and paths to roots in a heap analyzer to locate static RETAINED → list storage → arrays. Shared paths complicate retained-size interpretation. The dump can pause the target/request collection and can contain application data.

A heap dump does not record every historical allocation. Allocation events/profiles supply different evidence, with sampling limitations. For process growth while heap stays stable, investigate stacks, metaspace, direct/native buffers and mappings. If using Native Memory Tracking, enable it at startup with the supported option, such as `-XX:NativeMemoryTracking=summary`, then inspect `jcmd <pid> VM.native_memory summary`. It does not account for every native-library allocation.

Thread.print serves this platform-thread monitor scenario. A virtual-thread-heavy program needs version-supported facilities such as Thread.dump_to_file where available. Read the selected runtime's output contract instead of expecting one dump format to enumerate every kind of task.

## Exercise: separate observation, hypothesis and conclusion

The complete lab is the reference implementation. State three observations: waiter is blocked at contend, owner holds the matching monitor while parked on a latch, and a completed monitor-enter event names that owner/waiter after release. The supported causal explanation is this controlled ownership interval. A general incident needs correlation with its workload and time window.

For a high-CPU incident, collect running samples and process/thread CPU evidence. For retention, compare equivalent phases and root paths. Change one hypothesis-relevant factor for a follow-up experiment. A plausible story from one sample is not yet a demonstrated application bottleneck.

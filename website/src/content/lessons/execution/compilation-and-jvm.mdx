## Separate writing, compiling and running

The greeting begins as text in HelloJava.java. Saving the file does not execute it. The compiler javac reads that source, checks that it is legal Java and produces HelloJava.class. The java launcher then starts an application JVM that can load the compiled class and invoke main. The greeting appears when the running program executes println.

<JavaExample file="HelloJava.java" output={"Hello, Java!"} />

Keep this familiar program unchanged. From the directory containing HelloJava.java, run:

```bash
mkdir -p out
javac -d out HelloJava.java
java -cp out HelloJava
```

Mkdir creates the destination directory. Successful javac compilation writes out/HelloJava.class and normally prints no message for this example. The java command uses out as its classpath and HelloJava as the class name. It prints Hello, Java!. The next chapter develops packages and classpath roots; here out simply keeps generated files separate from source.

## Follow the source, artifact and execution

<JvmVisuals client:visible model="compilation" />

Choose Successful build and step forward. The class file exists before this application main starts. It contains bytecode, the JVM's instruction format, plus information describing the class and its members. Bytecode is different from the native machine instructions of a particular processor. The runtime handles execution on the selected platform; you do not need individual instruction names to understand this pipeline.

Loading makes a required class definition available to the JVM. Linking checks and prepares that definition; initialization performs the required class initialization before main runs. The detailed rules come later. For this first program, the useful order is **source → compiler checks → class file → application JVM loads the class → main → output**.

A compiler can check the print call without carrying it out. Javac does not execute HelloJava.main or print its greeting. Likewise, javap can inspect a class file without running it; its bytecode walkthrough follows ordinary methods and objects in JVM foundations.

## Know what the JDK supplies

| Term | Responsibility in this exercise |
| --- | --- |
| JVM | Executes the compiled program according to the virtual-machine contract |
| Java runtime environment | Combines the JVM with the platform libraries and support needed to run the program |
| JDK | Supplies development tools such as javac, java and javadoc, together with the runtime needed here |

These are responsibilities, rather than three tools that must be launched in succession. The JDK is the development kit you install; the JVM is the execution engine used when the application runs. An IDE arranges the same kinds of compilation and launch operations while often hiding the generated-file location and selected JDK.

## Distinguish a failed compilation from an old artifact

Select Failed edit, old class in the visual. Its source excerpt changes the text to Changed and omits the semicolon. Javac rejects that edit, so this one-file syntax failure produces no replacement class for the new source. Its diagnostic is compiler output, not a greeting from main.

An old HelloJava.class can still remain from an earlier successful build. If you ignore the failure and launch that class, the old program can print Hello, Java!. The launcher is executing the old artifact; it is not proving the edited source compiled. Keep generated files in a known output directory and check compilation success before interpreting a run.

## Practice: stop after compilation

Run only mkdir and javac. Should the greeting have appeared? What file would this small program need on a compatible runtime if the source were no longer present?

## Explain portability at the correct boundary

The class file is a binary format for a compatible JVM, rather than a machine-code executable for one processor. An appropriate JVM implementation supplies the operating-system/processor-specific execution machinery. Source syntax, required class-file version and available libraries still have to match the selected runtime. A portable format does not make a missing dependency, newer API or platform-specific native library appear automatically.

Compilation checks the program against what the compiler can see. Launch starts a separate execution using its own classpath and runtime. This is why javac and java versions both matter, and why moving only a class file without the definitions it needs can fail later. For this greeting, no third-party dependency or native library is needed; keep that ordinary path clear before investigating loading and linking failures.

<details>
<summary>Must javac print Hello, Java! to prove the compilation succeeded?</summary>

No. Successful javac normally produces the class file without running main or producing that application output. The launcher subsequently invokes main, and that invocation prints the greeting. A tool's own diagnostic output is different from the application's output. The stepwise model records those two responsibilities separately.

</details>

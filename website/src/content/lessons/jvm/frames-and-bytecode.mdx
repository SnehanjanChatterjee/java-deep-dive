## A call creates an execution frame

A Java expression such as `value * 2` hides several execution steps: obtain the input, obtain two, multiply and return the result. **Bytecode** makes those steps explicit as instructions for the **Java Virtual Machine (JVM)**. Reading a small compiled method explains how source-level values become the inputs and results of individual operations.

One method invocation's working state is a **frame**. It keeps parameters/local values and a temporary calculation stack. Calling another method creates another frame on the thread's JVM stack; returning completes that invocation and resumes the caller, possibly supplying a result. The thread's stack contains frames, while the operand stack **inside one frame** contains calculation values.

An object and a frame have different lifetimes. A frame belongs to one invocation; an object can remain reachable after the method that created it returns. Two calls to the same method have independent local variables. Two threads can call the same method while sharing references to some of the same objects.

Start with an operation already familiar from Java methods:

<JavaExample file="ExecutionFramesDemo.java" output={"6"} />

`main` passes the value 3. `twice` computes 3 × 2 and returns 6. The caller then passes that result to `println`. At the Java level, this is ordinary argument passing and return. Bytecode makes the intermediate operations explicit.

## Compile and inspect the artifact you actually run

Save the source as ExecutionFramesDemo.java and use:

```bash
mkdir -p out
javac -d out ExecutionFramesDemo.java
java -cp out ExecutionFramesDemo
javap -classpath out -c -p ExecutionFramesDemo
```

`javac` produces a class file. `javap -c` prints its bytecode instructions; `-p` includes private members if present. Inspection does not execute the method. Inspecting the class in `out` avoids accidentally reading another version from an IDE output directory.

For this method, the important instruction sequence is:

```text
0: iload_0
1: iconst_2
2: imul
3: ireturn
```

The number before each instruction is its bytecode offset, not a source line number. A compiler can generate different instruction choices for other source expressions. The specification defines what an instruction means; it does not require every compiler to emit one preferred source-to-bytecode translation.

## Trace the local array and operand stack

A **local-variable array** is the frame's indexed storage for parameters and local values. One indexed position is called a **slot**. An **operand** is an input value for an instruction; the **operand stack** holds such inputs and intermediate results in last-in-first-out order. Push adds a value to its top, and pop removes the top value. These are JVM execution structures, not java.util collection objects.

In this static method the first int argument occupies local slot zero. `iload_0` means load the int from that slot, copying it onto the operand stack. `iconst_2` pushes int constant two; `imul` performs int multiplication; `ireturn` returns an int. The load does not remove or change the local.

| After operation | Local slot 0 | Operand stack, bottom → top | Reason |
| --- | --- | --- | --- |
| Enter method | 3 | empty | Argument is available as a local |
| iload_0 | 3 | 3 | Copy the argument onto the stack |
| iconst_2 | 3 | 3, 2 | Push the constant |
| imul | 3 | 6 | Consume two ints and push their product |
| ireturn | completed frame | result travels to caller | Return the top int |

<ConceptAnimation client:visible model="bytecode" />

The stack is last-in-first-out: the most recently pushed operand is consumed first when an instruction needs it. Here imul consumes both ints and pushes their product. Ireturn transfers the top int to the caller and completes this invocation. It does not write the product back into local slot 0.

Main waits for twice's result before it can pass that value to println. Returning from twice completes that invocation, while main remains active. A second call creates another independent invocation with its own argument local. Recursion repeats the same rule: each call has its own frame until the base case stops further calls and the results return outward.

Local slots and the operand stack are parts of the JVM model, not measured memory addresses. The earlier stack-and-heap chapter separated these invocation values from object state. More advanced member-invocation instructions, verification and optimized physical frames are studied after class loading.

## Preserve operand order for subtraction

Multiplication is commutative, so reversing its operands can hide a tracing mistake. ExecutionFramesDemo also declares `difference(int left, int right)`, returning left minus right. Inspecting it with the same javap command yields loads of local zero and local one, followed by isub and ireturn.

| Operation for difference(9, 4) | Locals | Operand stack, bottom → top |
| --- | --- | --- |
| Enter | left=9, right=4 | empty |
| iload_0 | unchanged | 9 |
| iload_1 | unchanged | 9, 4 |
| isub | unchanged | 5 |
| ireturn | invocation completes | caller receives 5 |

Isub consumes the top right operand four and the earlier left operand nine, then computes nine minus four. It does not compute four minus nine merely because four is popped first. Reversing the arguments gives minus five in a different invocation. The matching tests cover both orders and ordinary int overflow; the main demonstration still prints six so the first trace remains unchanged. [JVMS isub](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-6.html#jvms-6.5.isub)

An instance method also needs a receiver, conventionally in local slot zero, shifting its first explicit argument to later slots. A static method has no implicit receiver, as twice/difference here demonstrate. Long/double values occupy two local slots under the JVM model; a source variable name therefore is not a universal one-to-one physical slot map. Detailed slot reuse and optimized reconstruction follow in advanced bytecode linkage.

## Bytecode exercises and explained answers

<details>
<summary>What does twice(-3) return, and which local is changed?</summary>

It returns -6. The argument local remains -3 while the operand stack computes the product. Returning a result does not assign that result back into the caller's argument variable.

</details>

<details>
<summary>What changes if multiplication exceeds the int range?</summary>

Ordinary Java int multiplication uses the specified wrapping integer behavior. For example, twice(1 &lt;&lt; 30) produces Integer.MIN_VALUE. Replacing the operation with Math.multiplyExact adds an overflow exception contract and changes the program being inspected.

</details>

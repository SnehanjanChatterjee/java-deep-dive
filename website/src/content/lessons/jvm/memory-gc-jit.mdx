## A small live set can create a large allocation workload

A request repeatedly replaces temporary buffers. Another component stores every historical request in a map. Both allocate, but their memory problems are different. The first may generate high churn with bounded retained state; the second can slowly accumulate an unwanted live graph.

Allocation rate measures storage demanded over time. Retained/live size concerns what remains reachable at an observation phase. The reachability lesson traced the paths; this chapter uses a concrete owner to distinguish replacement from growth before examining whole-process budgets.

## Trace replacement and growth under one static owner

<JavaExample file="CoreRetentionLab.java" output={"16\n16\n32\n0"} />

Load(0,16) stores sixteen byte arrays under sixteen keys. Loading that same range again allocates replacements but keeps cardinality sixteen; the map drops its old value references. Loading keys sixteen through thirty-one instead adds sixteen mappings and grows retained ownership to thirty-two. Clear removes the map's mapping references.

The output reports this owner's logical mappings, not exact heap bytes or immediate collection. A former value can remain reachable through another alias. The source's 64 KiB buffers make a retaining path easy to recognize without making count a complete heap-size measurement.

## Inspect a retaining path without inventing collection timing

Run `java CoreRetentionLab hold` to pause before clear. Use jcmd to identify this controlled process and ask its supported commands. A histogram can show byte arrays exist; a heap graph can connect class/static map → entry → value. A dominator/root-path analysis answers who retains them, while an allocation profile answers where new arrays were created.

Shallow size counts an object's own storage. Retained size describes the dominated graph under an analyzer's definition. Shared paths mean removing one apparent owner may not free the whole graph. Compare equivalent workload phases instead of treating every high occupancy reading as a leak.

## Budget more than the heap

| Category | Typical contents | A distinct question |
| --- | --- | --- |
| Heap | Ordinary instances and arrays | Allocation churn or retained graph growth? |
| Thread stacks | Invocation/execution state | Deep recursion or too many threads? |
| HotSpot Metaspace | Class metadata | Retired loaders or generated classes retained? |
| Code cache | Compiled code/runtime stubs | Compilation/storage pressure? |
| Direct/native storage | Direct buffers, native libraries and VM state | Process memory growing while heap is stable? |
| Mapped resources | File-backed mappings | Address space versus resident pages? |

Xmx limits Java heap, not whole-process memory. Reserved address space, committed storage and resident pages are different observations, so do not add arbitrary reported categories as if they all measured the same quantity. A constrained process needs headroom for native/runtime/operating-system work as well as live heap objects.

An OutOfMemoryError for Java heap differs from inability to create a native thread or metadata pressure. Raising Xmx may help one heap-capacity problem while reducing room for native categories. An overly small heap can increase collection work; neither a universally larger nor universally smaller heap is the diagnosis.

## Allocation paths and cleanup contracts

HotSpot commonly uses thread-local allocation buffers for efficient small-object allocation. Other sizes and collector paths differ. A new expression is not proof of one physical allocation after optimization. The dedicated garbage-collection and compilation chapters trace those implementation mechanisms and evidence separately.

WeakHashMap's weak keys can remain indirectly retained when strongly held values refer back to them. Soft references do not implement a predictable eviction/expiry SLA. Phantom references and cleaners support cleanup coordination; a cleaner action capturing its referent can defeat cleanup. Deterministic close still owns files, sockets and native resources with prompt release requirements.

## Find what is reachable before reclaiming storage

The reachability lesson supplied a root set and followed object identities. A tracing collector applies that kind of graph reasoning to a running JVM. Objects reachable through the relevant root/reference rules remain live; an isolated cycle does not become live merely because its objects refer to each other.

This separates two questions: which storage is no longer needed, and how the runtime reuses it while preserving valid references? Collector names describe different implementations of those responsibilities, not different application ownership rules.

## Trace marking and movement on one small graph

Suppose a live root reaches a list, the list reaches A/B, and an unrelated C/D cycle has no root path. Mark the root-reachable list and payloads once. The isolated cycle is not discovered. If the list removes A but another root still reaches A, it remains live; deleting one edge is not enough.

A nonmoving reclaiming phase can make unreachable storage reusable. A moving collector instead copies selected live objects, updates the references that must name their new locations, and reuses the vacated storage. Compaction reduces fragmentation by organizing survivors. These are algorithmic models; a particular collector combines them with barriers and synchronization rules.

For movement, call A’s old location L1 and its destination L2. After copying A, both a root reference to A and B’s field referring to A must continue to identify that same logical object. Repairing only the root would leave B’s path stale. A collector can update references directly or use its documented barrier/indirection protocol; the symbols L1/L2 are a teaching model, not measured addresses. Reuse of the old storage follows only after the required protocol keeps those references valid.

## Run bounded retention with allocation churn

The static window holds sixteen buffers. Each iteration creates a 64 KiB array and replaces one slot. After the window fills, a replacement removes that owner's reference to the older buffer while keeping the live owner cardinality bounded. The final byte total counts retained payload lengths, excluding array headers, the outer array and other runtime objects.

This workload creates allocation pressure without deliberately retaining every historical buffer. It therefore complements CoreRetentionLab, where adding new keys grows a retaining owner. A short log showing a small post-collection occupancy is evidence about that run, not proof that every application using similar arrays has no leak.

<span id="read-logs-without-inventing-a-cause"></span>
## Read a real G1 event field by field

On a selected JDK 25 HotSpot runtime, the following controlled command produced the excerpt below:

```bash
javac GarbageCollectionWorkload.java
java -Xms32m -Xmx32m -XX:+UseG1GC -Xlog:gc GarbageCollectionWorkload
```

```text
[0.011s][info][gc] Using G1
[0.077s][info][gc] GC(0) Pause Young (Normal) (G1 Evacuation Pause) 18M->2M(32M) 0.507ms
[0.077s][info][gc] GC(1) Pause Young (Normal) (G1 Evacuation Pause) 14M->2M(32M) 0.132ms
```

These are observed teaching records, not promised pause times. The timestamp is JVM uptime. GC(0)/GC(1) identify different collection events. Pause Young names a young collection, and G1 Evacuation Pause identifies its moving/evacuation activity. In the first event the reported occupancy changes from about 18M to about 2M within a 32M heap capacity; these rounded figures are not exact payload-byte accounting or whole-process resident memory.

The 0.507ms duration describes that recorded pause, not average operation time, request p99 or the complete cost of concurrent GC work. The second event has a different pre-collection occupancy and pause. Comparable low post-collection occupancy is consistent with this bounded owner; a leak investigation would still need repeated equivalent phases and actual retaining paths.

<span id="zgc-concurrent-work-with-headroom-requirements"></span>
## Generations avoid repeating unnecessary discovery work

Many workloads create objects that die soon. A generational collector can focus frequent work on a younger subset while managing longer-lived data differently. Surviving data may move/promote under the selected policy. Not every allocation follows one universal young-to-old journey: large objects, optimizations and collector-specific paths differ.

An old catalog can acquire a reference to a young object. Collecting only young storage must still find that incoming reference, even if the old catalog is not otherwise rescanned completely. Write barriers and card/remembered-set mechanisms record relevant cross-region information. The optimization trades bookkeeping cost for avoiding a full-heap scan on each local collection.

HotSpot commonly allocates small objects through thread-local allocation buffers. This fast path does not make allocation free or apply to every size/collector path. Allocation rate and retained live size remain separate quantities.

## G1: regions, marking and evacuation

G1 divides the heap into regions. Young evacuation copies survivors during stop-the-world phases. Concurrent marking gathers liveness information while application work can continue, with coordinating pauses. Mixed collections can collect young regions and selected old regions. A pause target is a goal, not a real-time deadline.

Humongous allocations depend on region sizing/thresholds. Promotion/evacuation pressure, insufficient headroom and fallback collections can disrupt expected latency. The word concurrent does not mean every collector phase runs without stopping application threads. For more detail, enable version-supported `-Xlog:gc*,safepoint` and decode the chosen runtime's event fields rather than reusing one release's format blindly.

<span id="choosing-a-collector-from-a-workload"></span>
## ZGC and workload tradeoffs

ZGC performs much marking and relocation concurrently, using barriers/metadata so application references remain valid during that work. It still needs CPU and free-space headroom to keep up. Allocation stalls and non-GC application waits can cause poor latency despite short individual pauses. On the JDK 25 baseline ZGC is generational; its older non-generational mode was removed in JDK 24.

Serial, Parallel, G1 and ZGC balance throughput, pauses, CPU and footprint differently, with availability/defaults depending on runtime/platform. Choose from workload goals and evidence rather than a universal ranking. Changing collector, heap and application code together makes causal interpretation harder.

## Exercise and complete interpretation

Explain why the static buffer window stays at sixteen entries while allocating replacements. Then decode every first-event field and identify which claim needs other evidence: reclaimed occupancy, retained owner, or request latency. The program supplies the complete workload; the explanations above supply the worked interpretation.

For retention, run CoreRetentionLab with hold and locate its static map's root path. Allocation profiles identify where new arrays are made; heap graphs identify who keeps them. Weak/soft references and cleaners are specialized contracts, not generic repairs for unclear ownership or a replacement for deterministic external-resource close.

## The same bytecode can execute through different paths

The frame chapter followed arguments and operand operations. A JVM can interpret that bytecode, collect execution profiles, and compile suitable frequently executed methods/loops into machine code. Optimization changes implementation work while preserving the required values, exceptions and synchronization behavior.

HotSpot's tiered compilation can gather profiles and later create more optimized versions. A method may have several compilation records; there is no universal invocation count that defines JIT. On-stack replacement can compile a hot loop while its invocation is already running.

## Examine two different observable operations

LocalScore constructs a Pair and immediately reads its fields. PublishedScore additionally stores the Pair through a volatile static reference. The checksums match numerically, but the operations are observably different: publishing that reference constrains the optimizer in a way the local calculation does not.

For a localScore call with seed three, trace the data before considering an optimization:

| Source step | Data needed by the result |
| --- | --- |
| Enter localScore | seed is 3 |
| Construct Pair | left is 3; right is 4 |
| Read fields and calculate | 3 × 31 + 4 is 97 |
| Return | Caller receives 97 |

Inlining can expose those constructor assignments to the caller’s optimizer view. If object identity and escape requirements permit, useful state can be represented directly as scalar values rather than a materialized Pair. This explains the possible transformation; the later log analysis asks which compiler decisions were actually observed.

If the compiler can see through the local calls, inlining exposes the constructor/field arithmetic. It may represent fields directly and eliminate a materialized allocation where identity/escape semantics permit. That is a hypothesis to investigate. The two printed booleans prove matching checksums and a published reference, not allocation elimination or a speed difference.

## Capture compilation and inlining records

For a controlled HotSpot investigation, compile the source, then run:

```bash
javac -d out CoreHotLoop.java
java -Xbatch -XX:+UnlockDiagnosticVMOptions -XX:+PrintCompilation -XX:+PrintInlining -XX:CompileCommand=compileonly,CoreHotLoop::localScore -XX:CompileCommand=quiet -cp out CoreHotLoop
```

CompileOnly deliberately restricts the experiment; it is not normal application tuning. Xbatch requests foreground compilation, making this teaching trace easier to follow. The following selected records were observed with Java 8-compiled source on JDK 25. Unrelated exclusion messages and several nested decisions are omitted.

```text
15    3    b  3       CoreHotLoop::localScore (26 bytes)
                              @ 9   CoreHotLoop$Pair::<init> (7 bytes)   inline
                              @ 14   CoreHotLoop$Pair::access$100 (5 bytes)   inline
                              @ 21   CoreHotLoop$Pair::access$200 (5 bytes)   inline
15    4    b  4       CoreHotLoop::localScore (26 bytes)
16    3       3       CoreHotLoop::localScore (26 bytes)   made not entrant: not used
                              @ 9   CoreHotLoop$Pair::<init> (7 bytes)   failed to inline: unloaded signature classes
```

Read a method record across columns: uptime, compilation ID, flags, compilation tier, then method and bytecode length. IDs three and four refer to different compilations of localScore. The b flag accompanies blocking compilation here. Tier three is profiled compilation and tier four is the more optimized tier in this selected HotSpot configuration. The 26 bytes describe bytecode length, not allocation size or execution time.

The indented @ numbers identify call-site bytecode offsets and the following decisions. The first compilation reports inlining of the constructor/accessor paths. The access$ names are compiler-generated access bridges in this Java 8 class-file translation, not methods authored in the example. Other compiler targets can translate this access differently.

The later compilation reports a failed constructor inlining attempt with its stated reason. Do not turn a source method's small size into a promise that all compilations inline it. Made not entrant means that older compiled version is no longer entered for new calls; the line alone does not prove a speculative deoptimization or a correctness problem. This excerpt also does not establish the number of allocated objects.

## Profiles, guarded assumptions and deoptimization

Inlining exposes constants and relationships across a source call boundary, enabling more than saved call overhead. A call site repeatedly seeing one receiver type can support guarded specialization. A changed receiver distribution or newly loaded implementation can invalidate optimized assumptions. Deoptimization reconstructs a valid execution state and permits continued execution/recompilation.

## Escape analysis and the evidence boundary

An object can escape through a return, field store, callback or retained alias. Incomplete inlining can limit the compiler's view. Scalar replacement may avoid materialization, and later deoptimization can require reconstructing objects when semantics demand it. Nonescape is not a general promise that objects move to the native stack.

To determine actual allocation behavior, use appropriate allocation/generated-code evidence under the recorded workload. A suspiciously low timing alone cannot establish elimination. A short program may also exit before a predicted compilation occurs. Report the compiler decision observed rather than inventing the optimization expected.

## Keep optimizer effects in a measurement model

Dead-code elimination removes irrelevant work; constant folding replaces known results; hoisting can move invariant work outside a loop. Manual repetitions can create a different optimizer workload from independent application invocations. Warmup changes profiles/compilation; it is not one universally sufficient waiting duration.

Compiled code occupies code-cache memory outside the ordinary heap. Metadata, native buffers and stacks contribute other categories. Runtime coordination/safepoints can occur for reasons other than GC. Collector choice, flags and system load can affect an experiment even with identical source.

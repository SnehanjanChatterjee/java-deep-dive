## Class loading turns a binary definition into a usable runtime type

A **class loader** is the runtime facility that finds a class’s binary definition and makes that type available to the JVM. A class file describes a type; loading it is different from constructing an object of that type. One loaded Account class can support thousands of Account objects.

The JVM then links the definition: it checks structural constraints, prepares class-level storage and resolves required symbolic references. Initialization executes the required static initializers. These are separate stages, so a class can be loaded without its static blocks having run. We will first observe that distinction in one ordinary program, then examine loader identity and initialization failures.

## Using a class and initializing its state are different events

A compiled program names classes, fields and methods in its class file. Before executing a relevant operation, the runtime needs a definition of the named type and must enforce the class-file/linking rules. Static initialization is another step: it runs the class-level initializers that establish static state when an active use requires them.

## Loading, linking and initialization are distinct

| Step | What it establishes | What it does not establish |
| --- | --- | --- |
| Loading | A runtime type definition from binary form | That static initializer bodies already ran |
| Verification | Applicable class-file/type-safety constraints | Arbitrary business correctness |
| Preparation | Class-level storage and specified initial/default state | Execution of ordinary source initializer expressions |
| Resolution | Symbolic references are linked to runtime definitions under access/loader rules | That every possible method path was eagerly resolved |
| Initialization | Required static field initializers and blocks execute | Construction of every future instance |

Verification, preparation and resolution form linking. Some resolution can occur lazily. The static initializer processes source initializers in their specified order after required superclass initialization. Instance fields/initializers and constructor bodies belong to individual object construction.

Constructing an instance, invoking an appropriate declared static method or accessing a nonconstant static field can trigger initialization. Reading an inherited static field concerns the declaring type. Creating an array of a reference type does not itself initialize that component class. Class literals and explicit loading without initialization differ from active use.

## Run loading without initialization and inspect a failed class

`Class.forName(name, false, loader)` requests a runtime definition without requesting its initialization. The boolean flag is the important difference from an active field use. The experiment first reads a constant, explicitly loads the definition, then reads a method-computed static value. A second class deliberately fails its initializer: compare the first failed active use with a later one, rather than assuming initialization is retried like an ordinary method.

<JavaExample file="CoreInitializationLab.java" output={"7\nloaded without initialization\ninitialized\n42\nfirst initialization failure\nlater erroneous class"} />

Class.forName with initialize=false requests the definition without deliberately initializing Holder. Reading nonconstant VALUE then runs initialize and prints initialized before 42. The constant read still precedes both events.

Broken's initializer throws IllegalStateException. This first active use reports ExceptionInInitializerError. The class becomes erroneous in that loading context, so a later active use reports NoClassDefFoundError instead of retrying initialization. The latter error can therefore describe an earlier initialization failure, not only a missing class file. Preserve the original causal failure.

## Inspect the caller's actual class file

Run `javap -c -p InitializationOrder` against the output directory used for execution. Look for the constant instruction and the later new/invokespecial construction path. Replace CONSTANT with a method-computed value, recompile, and compare the caller's field access. Bytecode offsets, local slots and operand-stack behavior are developed in the preceding frame chapter.

A public compile-time constant can be copied into a separately compiled client. Replacing only the library class may leave that client using its old literal until recompiled. A runtime accessor has a different compatibility/lifetime contract. Symbolic method references can similarly fail at runtime if a deployed library differs from the one used for compilation.

## Class identity and loader boundaries

For ordinary named classes and interfaces, runtime identity depends on the binary name and defining class loader. Two plugin loaders can define incompatible types called plugin.Item even when the names/bytes match. An initiating loader may delegate to another defining loader. Common parent delegation is a policy, not a universal mandate for every custom loader.

Modern runtimes distinguish bootstrap, platform and application loaders. Class.getClassLoader may represent bootstrap loading with null. Live loaders/thread-context-loader references and registries can retain classes plus their static graphs after a plugin is logically retired. Diagnose artifact and loader identities rather than comparing source names alone.

## Distinguish lookup failure, initialization failure and loader conflict

| Symptom | Stage to inspect | Useful evidence |
| --- | --- | --- |
| ClassNotFoundException from explicit loading | Requested definition cannot be found by that loading operation | Requested binary name and the chosen loader's search inputs |
| ExceptionInInitializerError | Static initialization ran and failed with a wrapped non-Error cause | Earliest causal exception and initializer code |
| Later NoClassDefFoundError for an erroneous class | A required class could not be initialized successfully in that context | Earlier initialization failure, not just missing-file searches |
| ClassCastException despite matching printed names | Two incompatible runtime types may have different defining loaders | Both Class objects and their defining loaders |

Initialization also coordinates threads. One thread performs a class's initialization while another active user can wait for its completion. A static initializer that waits for work needing the same initialization can therefore create a liveness problem. This protocol does not make all later mutations of that class's static fields thread-safe. Initialization safety and subsequent shared-state coordination are separate contracts.

<details>
<summary>Why can reading Child.VALUE initialize Parent but not Child?</summary>

If VALUE is a nonconstant static field declared by Parent, the relevant initialization follows its declaring class, even when source qualifies it with Child. A compile-time constant can require neither initializer for that read. Determine the declaring field and whether it is a constant variable before predicting output; the spelling of the qualifier alone is insufficient.

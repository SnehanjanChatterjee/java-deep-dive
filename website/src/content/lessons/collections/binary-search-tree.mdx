## Locate a key by discarding a subtree

A hash table uses a hash to narrow candidates. A binary search tree uses order: every key in a node's left subtree is smaller, and every key in its right subtree is larger. Compare a query with the current node; equality finds the mapping, while a negative or positive result chooses one subtree.

For keys inserted as 20,10,30,25,40, searching for 25 compares with 20, then 30, then 25. Searching for 27 follows the same first two edges, goes right from 25 and reaches an empty child. No later scan is needed: the ordering invariant excludes every discarded subtree.

## Read search and insertion before deletion

find compares the same query key with the current node's key. It ends at a match or null. put follows that path until a missing child can receive one new node. Root insertion and ordinary child insertion increment size once; replacement returns the old value without allocating another node. Every operation uses the same stable comparison relation.

keysInOrder recursively visits left, current key, then right. This produces sorted keys because every left key precedes the current key and every right key follows it. The returned ArrayList is a new container; clearing it does not clear the tree. It still shares key objects, so stable key state remains required.

## Delete a leaf, one-child node and two-child node

| Removed node | Replacement at its parent link | Why ordering survives |
| --- | --- | --- |
| Leaf | null | No surviving subtree must be attached |
| Only left child | Its left child | All retained keys already fit the old node's range |
| Only right child | Its right child | The same range argument applies |
| Two children | Successor key/value, then delete the old successor position | The least right-subtree key is the next in-order key |

To delete 20, find the minimum of its right subtree: 25. Copy 25's key/value into the root node, then remove the original successor-position node beneath 30. The mapping 20 disappears; 25 survives once. If that successor has a right child, the one-child case reconnects it. A minimum node cannot have a left child.

remove saves the original result before rewriting keys. Its call to find establishes that the recursive delete path exists. The helper returns the new subtree root on every branch; callers must assign it back to their left/right field, and the public method assigns it back to root. Size decreases only in the public method, so moving the successor is not a second logical removal.

## Reconnect a successor that has its own right child

Use keys 20,10,30,25,27,40 and delete 20 directly. The successor is 25, but its original node has right child 27. After copying 25's association into the root, deletion of that successor position returns its right child. Assigning that return to 30.left preserves 27.

Before, the right subtree is 30 with left 25 and 25.right=27. After, it is 30 with left 27. Returning null instead would silently lose 27 even though traversal could remain sorted for the values left behind. The extended test checks the exact survivor keys, not only sortedness.

The recursive call stack also explains in-order traversal. A call at 20 suspends its own visit while traversing 10's subtree, records 20 only after that returns, then enters 30's subtree. Every node is visited once, but the maximum active stack follows the tree's height. A chain and a balanced shape can have the same sorted output with different stack/search costs.

## Height determines the cost

Let h be height measured in nodes. Search/insertion/removal take O(h) comparisons; the extra search before deletion is still O(h). Traversal takes O(n) visits and O(h) recursive stack space. Ascending insertion 10,20,30,40 creates a chain of height four. In general h can be n, so core operations can be O(n), and sufficiently deep recursive operations can exhaust the stack.

A sorted output does not establish balance: the chain traverses correctly too. TreeMap adds red-black invariants and repair to bound height; its chapter develops that additional obligation.

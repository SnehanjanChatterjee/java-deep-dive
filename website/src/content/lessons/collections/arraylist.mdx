## Resizable arrays and positional order

ArrayList is a resizable array implementing List. It preserves positional order, accepts duplicate and null elements, and provides constant-time indexed access. Its logical size counts elements; capacity counts allocated reference slots. Choose it when indexed reads and traversal dominate and the application does not require thread-safe mutation.

A list's position is not an object identifier. Inserting before index 3 moves the old element at 3 to 4. References stored in the list still identify the same objects; moving a reference does not clone its referent. Implementations of List share an API but can have very different traversal and mutation costs.

ArrayList(), ArrayList(initialCapacity) and ArrayList(collection) have different inputs. The first two create size zero; the copy constructor creates real positions from the source's encounter sequence. An initial capacity of eight does not permit set(7,value) until those positions exist.

| Method | Useful meaning | Cost model for ArrayList |
| --- | --- | --- |
| get / set | Read or replace an existing position; set returns its old value | O(1) after bounds checks |
| add(value) | Append one position | Amortized O(1); an expansion can copy O(n) |
| add(index,value) | Insert, shifting the suffix | O(n−index), plus possible growth |
| addAll(values) / addAll(index,values) | Insert source sequence | Includes source size, suffix movement and possible growth |
| indexOf / lastIndexOf | First/last equality match, or −1 | O(n) equality checks |
| remove(index) / remove(Object) | Return old value / report first equal-value removal | Includes search or suffix movement as applicable |
| subList(from,to) | Live half-open range | Ownership and later structural mutation matter |
| toArray(typedArray) | Detached array container with checked runtime component type | O(n) copy work |
| ensureCapacity / trimToSize | Adjust storage policy without creating/removing elements | Can allocate/copy; not a logical-size operation |

The source inserts B,B into A,C,A, obtaining A,B,B,C,A. set at two replaces one B with D. remove("B") removes only the first remaining B. Its typed array records A,D,C,A before later list changes. Clearing subList(1,3) removes D,C from the backing sequence, leaving changed,A.

ensureCapacity(20) and trimToSize at the end preserve those two logical elements. Trimming after every append can defeat geometric growth and introduce repeated copying. It is a deliberate storage/lifetime decision, not a mandatory tidying step.

<span id="mechanics-and-tradeoffs"></span>
## ArrayList storage and growth

### Indexed operations and shifting

`get(i)` checks that i is in the logical range, then reads the backing array slot. `set(i,v)` replaces a reference and returns the old value without changing size. `add(i,v)` permits i equal to size, ensures capacity, shifts size−i references to the right, writes v and increments size. Removal shifts size−i−1 references left and clears the vacated final slot. That clearing prevents retention outside the logical sequence.

### Growth and amortized reasoning

Geometric growth copies the existing array into larger storage occasionally. A single expanding append is O(n), while n appends have O(n) aggregate copying under geometric growth, giving amortized O(1) append. Growing by exactly one would make aggregate copying quadratic. OpenJDK's growth policy is an implementation choice; the API does not promise a specific multiplier. Pre-sizing can reduce reallocation when a reliable size estimate is known, but excessive capacity wastes memory.

### Iterators and views

A structural modification changes size or otherwise structurally changes storage. Ordinary value replacement is different. Iterators use modification bookkeeping for best-effort fail-fast detection; it is not a concurrency guarantee. Structural changes to a parent outside the permitted subList protocol can invalidate a view. Retaining a tiny view can also retain its large backing list. Copy a range when independent lifetime is required.

## Iterator state, ranges and overload traps

### Explain iterator mutation as a state machine

An iterator distinguishes the next cursor position from the last element it returned. Its remove operation deletes that last returned element and becomes unavailable until another qualifying traversal. A ListIterator additionally supports backward traversal, insertion and replacement. Adding through the iterator changes its cursor relationship; it does not mean the newly added element is automatically the last-returned element removable by remove.

Fail-fast bookkeeping compares an expected modification count with the container's current structural state. It catches some misuse, including misuse in one thread. It is not synchronization, and a missing ConcurrentModificationException is not evidence that racing access was safe. Replacing a value is different from changing the logical size, but neither distinction authorizes unsynchronized access to shared mutable elements.

### Range ownership can retain far more than expected

A subList can share the entire backing list even when only a small range is visible. Retaining the range can retain storage and other referenced objects beyond that visible range. An independent `new ArrayList<>(range)` copy changes container lifetime ownership, though it still shares element objects.

The range's indexes are relative to its own bounds. Structural parent changes outside the documented view protocol can invalidate it. Do not cache a view and then freely edit the parent in another part of the program while assuming the view's original coordinates remain meaningful.

### Stable removal versus shifting repeatedly

Removing many items one at a time from the front shifts many suffixes and can make a linear-looking loop quadratic. A bulk predicate-based operation or constructing a new accepted sequence can avoid repeated positional shifts. Its correctness still depends on the predicate not mutating the source through a competing path. When a custom array implementation compacts survivors, use a read cursor and write cursor: every accepted value is copied at most once, then the discarded tail is cleared.

### Mutation exercise with an invariant

Implement removeAllMatching on the teaching SimpleArrayList. Before the scan, remember the old size. For every read index, preserve the accepted prefix at write; after the scan clear [write, oldSize), then set size=write. A throwing predicate requires an explicit failure policy: a naive compaction can leave partial changes. The dynamic-array chapter supplies a complete two-phase acceptance-plan solution that leaves container membership unchanged when the rule throws; it trades extra storage for that explicit failure boundary.

### API overload review

For List of Integer, primitive remove selects an index while remove(Object) selects value equality. For `toArray`, array component types participate in runtime checks and may reject incompatible values. Prefer an explicitly typed array construction idiom supported by the target JDK rather than unchecked casts from Object[].

<span id="common-mistakes"></span>
## ArrayList pitfalls and ownership

Use the cost model of the actual implementation; do not mistake capacity for accessible elements, or rely on a view as a snapshot. Removing elements from an enhanced-for loop through the list can invalidate its iterator. Use supported iterator removal, removeIf, or a deliberate new result container. None makes unsynchronized shared mutation safe.

## ArrayList interview questions and exercises

<details>
<summary>Why can one append be slow despite amortized O(1)?</summary>

It may allocate and copy the entire active prefix. Amortization bounds aggregate work over a sequence, not worst-case latency of one operation. If latency predictability matters, capacity planning and workload measurement are separate considerations.

</details>

<details>
<summary>How would you test a handwritten dynamic array?</summary>

Exercise empty reads/removals, insertion at zero and size, invalid negative/too-large positions, repeated growth, duplicate/null values and first/middle/last removal. Compare the whole logical sequence after each mutation, not just the final size.

</details>

<details>
<summary>Why is remove(1) surprising for a list of Integer?</summary>

The primitive int overload means index. To remove the value one, pass Integer.valueOf(1). Explain compile-time overload resolution before describing the resulting sequence.

</details>

## Solved interview and debugging practice

<details>
<summary>How can a linear loop accidentally become quadratic?</summary>

If each iteration performs a linear shift or linked-list indexed search, the total is a sum of linear costs. Count the work inside the loop, not merely the number of visible loop statements.

</details>

<details>
<summary>Why must a generic dynamic array clear its discarded tail?</summary>

The backing Object[] remains reachable. References beyond logical size can retain removed values even when iteration and size appear correct. Clearing restores the storage-ownership invariant.

</details>

<details>
<summary>Can an iterator be valid after replacing an element?</summary>

A particular implementation may not count replacement as structural, but the replaced object and concurrent access still follow their own contracts. Do not treat iterator validity as a global thread-safety guarantee.

</details>

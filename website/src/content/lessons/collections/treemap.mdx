## Maintain sorted keys while supporting range queries

Suppose a table stores labels at thresholds 10,20,30. A request at 25 needs the nearest threshold at or below it, not only an exact match. TreeMap stores keys in comparison order and implements NavigableMap: the map interface for ordered endpoint, neighbor and range operations.

The earlier BST supplied ordered search but could become a chain. TreeMap also maintains a balance rule, implemented by a red-black tree, so core operations take O(log n) comparison steps. Use its ordered API first; colors and rotations explain how the height bound is maintained later.

Natural order or a supplied Comparator defines placement and comparison-zero membership. Values need not be comparable because only keys are ordered. A comparator is part of the map's meaning, not a display-only preference.

<span id="worked-example"></span>
## Find neighbors and modify a range

Create the map, put 30,10,20 in that order, then inspect keySet: traversal is [10,20,30] because key comparison defines order. floorKey(25) asks for the greatest key ≤ 25 and returns 20. ceilingKey(25) asks for the least key ≥ 25 and returns 30. They do not insert 25.

```java
final NavigableMap<Integer, String> thresholds = new TreeMap<>();
thresholds.put(30, "high");
thresholds.put(10, "low");
thresholds.put(20, "middle");
final Integer floor = thresholds.floorKey(25);     // 20
final Integer ceiling = thresholds.ceilingKey(25); // 30
```

<JavaExample file="TreeMapExample.java" />

The keys traverse as [10,20,30]. floorKey(25) returns 20; ceilingKey(25) returns 30. floor/ceiling include equal keys, while lower/higher are strict. None requires the queried key to exist. The range includes 10 and excludes 30; removing 20 through it removes the backing mapping.

A subMap is a backed bounded view, not an independent container. An out-of-range insertion through it fails. Copying into a new TreeMap detaches container mutation while sharing key/value objects. Natural ordering rejects null keys; an explicit comparator can support a consistent null policy.

## Interpret all neighbor and range methods in the current order

<JavaExample file="NavigableViews.java" output={"ascending floor/ceiling=20/30\ndescending floor/ceiling=30/20\n[30, 20]\nnavigation snapshot=twenty\nnavigation entry update rejected\nout-of-range key rejected\nbacking keys=[10, 30]\ndescending lower/higher=30/10\nset after range clear=[30]"} />

For ascending keys 10,20,30, lowerKey(20) is 10, floorKey(20) is 20, ceilingKey(20) is 20 and higherKey(20) is 30. For query 25, floor is 20 and ceiling is 30. In descending order 30,20,10, floor(25) is instead 30 and ceiling(25) is 20: “before/after” follows the view's comparison order.

headMap/tailMap/subMap expose bounded live views. The two-argument sorted-map subMap includes its start and excludes its end; the NavigableMap overload makes each endpoint's inclusion explicit. In a descending view, endpoints must also be supplied in descending order. The source uses subMap(30,true,10,false), containing 30 and 20.

An insertion through a bounded view must satisfy its bounds. Removal through the view affects the backing map; the source removes 20 and the original keys become 10,30. A copied TreeMap has independent membership instead.

Navigational entry methods such as TreeMap.floorEntry return association snapshots that do not support setValue. The example saves twenty, replaces the backing value with updated, and the snapshot still contains twenty. This differs from a live entry obtained from entrySet for supported value updates. The container snapshot is still shallow: mutable referenced values are not cloned.

pollFirstEntry/pollLastEntry both select and remove an endpoint; firstEntry/lastEntry only observe it. Key-only neighbor methods can return null for no result. If a comparator deliberately permits a real null key, an entry result distinguishes “no entry” from “entry whose key is null.”

## Search a neighbor without scanning every entry

At 20, query 25 is greater, so remember 20 as a floor candidate and go right. At 30, the query is smaller, so search left without replacing the candidate. Reaching null proves no eligible closer key exists on that remaining path; return 20. Ceiling remembers the corresponding larger candidate.

## Add balance constraints to search ordering

A red-black representation uses red/black node colors and conceptual black empty leaves. The root is black, no red node has a red child, and every path from a node to an empty leaf has the same black count. These constraints bound height logarithmically. Sorted traversal by itself proves none of them.

A rotation preserves established key ranges. For a left rotation at X with right child Y, move Y's left subtree to X.right, make X the left child of Y, then repair parents/root. Every moved middle-subtree key was greater than X and less than Y, so in-order traversal is unchanged. A right rotation is the mirror. Recoloring changes balance state, not key identity.

## Work through outer and inner insertion cases

Insert 30 into an empty tree and make it black. Insert 20 as its red left child: no red-red conflict. Insert 10 red below 20: the parent is red and the uncle is a black empty leaf. This is an outer left-left configuration. Rotate right at 30 and recolor: 20 becomes black, with red children 10 and 30.

<Diagram client:visible definition={"flowchart LR\n A[Before: 30 black] --> B[20 red]\n B --> C[10 red: conflict]\n A -. right rotation and recoloring .-> D[After: 20 black]\n D --> E[10 red]\n D --> F[30 red]"} caption="The shape changes from a chain to a branching tree, while the in-order sequence stays 10,20,30." />

For 30,10,20, the new 20 is the right child of red 10: an inner left-right configuration. First rotate left at 10 to obtain the outer shape 30→20→10, then perform the same right rotation/recolor at 30. Mirror directions handle right-left and right-right cases.

New nodes start red so insertion does not immediately add a black count to just one path. If a red parent has a red uncle, recolor both black and the grandparent red, then continue upward. For the balanced 20-black with 10/30-red, inserting 5 triggers this recoloring; making the root black finishes the repair. A local repair can create a conflict above it, which is why the loop continues.

## Work through deletion's black-height deficit

An ordinary BST deletion first removes a leaf/one-child position, using the successor reduction for a two-child key. Deleting a red leaf changes no black count. Removing black state can leave one path short; the “deficit” is a reasoning device, not an ordinary extra key stored in the tree.

Start with 20-black and children 10-black/30-black. Delete 10. The missing left path now has one fewer black node. Its sibling 30 is black with black empty children, so recolor 30 red and propagate the deficit to 20. At the root it is absorbed; the final 20-black with right 30-red has equal black counts again.

| Sibling situation for a left-side deficit | Repair idea | What happens next |
| --- | --- | --- |
| Red sibling | Rotate left at parent; exchange relevant colors | Converts to a black-sibling case |
| Black sibling, both children black | Recolor sibling red | Move deficit upward; red parent can absorb it |
| Black sibling, near child red, far child black | Rotate sibling toward the deficit; recolor | Converts to a far-red case |
| Black sibling, far child red | Rotate parent away from deficit; recolor parent/sibling/far child | Restores black height locally and finishes |

Near/far are relative to the deficient side, not fixed “left/right” names. For an explicit near-red example, start at 20-black, left 10-black, right 30-black with 25-red as 30's left child. Delete 10. Rotate right at 30 to make 25 the black sibling, then rotate left at 20 and finish with 25-black over 20-black/30-black. The surviving key order is 20,25,30. The right-deficit cases are mirrored.

## Connect the complete BST to production TreeMap

The preceding SimpleBinarySearchTree is the complete unbalanced implementation for insertion/search/traversal/deletion. It cannot promise TreeMap's height bound. The complete TreeMapExample above uses the library contract. Production TreeMap adds parent/color bookkeeping, rotations, insertion/deletion repair, iterators, views and other Map operations.

When reading versioned OpenJDK source, follow getEntry/put for comparison placement, rotations for pointer repair, fixAfterInsertion for the cases just traced, deleteEntry for successor reduction and fixAfterDeletion for deficit repair. Annotate the invariant each branch preserves instead of memorizing method names without the states.

## Costs include comparison and result size

get/put/remove/containsKey take O(log n) comparison steps. Comparing long Strings can cost more than comparing ints. Full traversal is O(n); a bounded range query includes locating its boundary plus visiting its results. Balancing gives no concurrency or snapshot guarantee.

<span id="common-mistakes"></span>
## Keep key identity and ordering stable

A comparator returning zero for distinct IDs can replace an existing mapping. Changing ordering fields or mutable external comparator state after insertion can invalidate search paths. Avoid subtraction-based comparators. BigDecimal illustrates comparison/equality disagreement: numeric compareTo ignores scale, while equals includes it; choose a deliberate normalized key policy when those distinctions matter.

## Completed repair reasoning exercise

For 30,20,10, write the search path, identify parent/uncle colors, rotate right at 30 and recolor. Check three independent results: sorted traversal remains 10,20,30; there is no adjacent red pair; every root-to-empty path has equal black count. Checking only sorted output would also accept the original chain.

For deletion of black 10 under 20-black/30-black, perform the sibling-black/both-children-black case above. Explain why recoloring 30 is allowed only while also propagating/absorbing the deficit; simply splicing out 10 leaves unequal black paths.

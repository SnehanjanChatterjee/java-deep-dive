## Hash lookup with encounter order

A report may need fast lookup by key while preserving the order its rows first arrived. HashMap does not promise that traversal order. LinkedHashMap does: its default **insertion order** keeps the first position of each still-present key. Replacing a value does not move the key, while removing then reinserting records a new arrival.

Use a second mode for a different problem, remembering which cached entry was used most recently. **Access order** moves a successfully accessed entry to the recent end. Neither mode sorts keys alphabetically or numerically.

<span id="worked-example"></span>
## Insertion-order and access-order examples

Follow two small maps separately. In the default map, put A then B, then replace A's value: keys stay [A,B]. In the access-order map, start A,B,C, then get(A): keys become [B,C,A]. A is the same mapping in a new encounter position.

```java
final Map<String, Integer> insertion = new LinkedHashMap<>();
final Map<String, Integer> access = new LinkedHashMap<>(16, 0.75f, true);
```

The last true selects access order; 16 and 0.75f are storage sizing inputs inherited from the hash-table model. They are not a limit on live entries. Null keys/values are permitted as in HashMap.

containsKey(B) observes membership without refreshing access order, so the second map remains [B,C,A]. The next section identifies exactly which operations move a retained entry; the following link model explains how the movement occurs.


## Trace access-generating operations precisely

<JavaExample file="OrderedMapAccess.java" output={"containsKey=[A, B, C]\ngetOrDefault=[A, C, B]\nfailed replace=[A, C, B]\nsuccessful replace=[C, B, A]\nputAll=[B, A, C, D]\nentry setValue=[B, A, C, D]"} />

In access order, containsKey(A) leaves A,B,C unchanged. getOrDefault(B,...) moves the found B to the recent end, yielding A,C,B. A failed conditional replacement of A changes nothing. A successful replacement moves A, yielding C,B,A.

putAll performs accesses in the supplied map's entry encounter order. The source's update map visits C then D, producing B,A,C,D. Updating C through its live Map.Entry.setValue does not count as an access, so the same order remains.

| Operation in access order | Access effect |
| --- | --- |
| get / getOrDefault | Found mapping counts, even if a permitted value is null |
| put / putIfAbsent / compute-family / merge | Documented successful retained mapping can count as an access |
| replace methods | Count only if a value is replaced |
| putAll | One access per supplied mapping, in supplied entry order |
| containsKey / collection-view iteration / entry setValue | Do not generate access solely from that observation/view operation |

A method that reads values by iterating keySet and calling get can therefore change access order during its own traversal. Iterating entrySet and reading each entry value avoids that extra access. It is still a live view with the map's ordinary mutation/coordination requirements.

Insertion-order construction uses no access-driven movement. Replacing an existing key preserves its position; deleting then reinserting is a different history. Ordered input is also required if a copy is expected to reproduce a meaningful encounter sequence.

<span id="mechanics-and-tradeoffs"></span>
## Entry links, access hooks and eviction

### Two structures, one entry identity

The hash table locates an entry by key. Additional before/after links maintain the encounter-order chain. A new entry is registered in both structures. Replacing a value does not require a new logical key; access-order policy can move that existing entry's order position.

### Access and removal hooks

The implementation integrates order maintenance with hash-map update hooks. Moving a node detaches it from its current neighbors and attaches it at the recent end, repairing endpoints when necessary. Removing a key deletes both its bucket membership and its order links. Resizing rearranges hash-table storage without inventing a new insertion history.

### Eviction policy

removeEldestEntry can request removal after a new mapping is inserted. A capacity-bound policy returns size greater than the configured limit. Updating an existing mapping does not necessarily invoke the same new-entry eviction path. Access-order construction plus this hook yields a compact LRU exercise, but does not add expiration, deduplicated loading or concurrent ownership.

### Traversal cost and modification

Encounter-order traversal follows the linked entries rather than scanning empty buckets. It is proportional to entries visited, while HashMap traversal can include capacity. Extra links have storage/update cost. In access-order mode, get can be a structural order change for iterator purposes. A read lock that assumes every get leaves structure untouched is therefore unsuitable.

## Access-order details and cache API boundaries

### An access is defined by the contract

The access matrix above defines which operations request movement. The important implementation consequence is that an access-order get can write order links even when it only reads the stored value.

The implementation can avoid relinking an entry already at the recent end. That optimization does not justify treating cache gets as harmless shared reads: another get can move a different entry and modify order links/bookkeeping. Correct concurrency must cover all participating accesses and updates.

### Index and order remain coordinated during growth

Rehashing redistributes bucket links according to stored hashes, while encounter order is preserved through the separate entry chain. Bucket position and encounter position are different coordinates. A test that assumes encounter order equals bucket order validates an accident, not LinkedHashMap's representation.

### A subclass exposes more than eviction

A small removeEldestEntry subclass is useful to demonstrate library-based size eviction. It also inherits a large mutable Map API. Newer sequenced positioning methods can deliberately alter order, which may not fit an abstraction promising strict recency-driven eviction. Composition can expose only get/put/invalidate under the cache's contract and make ownership of loading/eviction clearer.

### Cache misses and duplicate loading

Two concurrent misses can both compute an expensive value before either installs it. Synchronizing a map's individual get and put calls does not make that whole load protocol atomic. A production cache needs a deliberate strategy for per-key load deduplication, cancellation, failure retention and resource limits. LRU ordering alone solves none of those policies.

### Exercise solution

For an insertion-order export, copy incoming entries into a LinkedHashMap and document the source encounter policy. For a recency cache, select access order, validate a live-entry bound and evict the least-recent entry only when the bound is exceeded. For a from-scratch solution, use one node identity shared by a key index and doubly linked list; updating a key must move the existing node rather than leak a duplicate order node.

The nested Cache selects access order with the third constructor argument true. Its validated capacity is a count of live mappings, not hash-table bucket capacity. removeEldestEntry compares size with that bound after new insertion. Reading A before inserting C changes which entry is oldest.

For a from-scratch coding task, use the full LinkedLruCache class, which explicitly maintains the index and doubly linked recency list. Its unlink and append methods show the link operations that a library subclass hides. The separate LRU chapter explains the combined invariant and eviction trace in detail.

A subclass using LinkedHashMap is a library-based solution. If an interviewer forbids built-in map storage or asks specifically for manual links, state that constraint and use the appropriate implementation; the two approaches should not be presented as equivalent amounts of implementation work.

<span id="common-mistakes"></span>
## Ordered-map failure cases

Do not confuse insertion order, access order and sorted order. Replacing an existing insertion-order key does not move it to the end. containsKey does not refresh access recency. Access order is not automatically thread-safe; coordinate the full lookup/relink/eviction protocol.

<span id="exercises-and-interview-questions"></span>
## LinkedHashMap interview questions and exercises

<details>
<summary>Why can get invalidate an access-order iterator?</summary>

The operation can change encounter-order links and associated modification bookkeeping. Although the associated value is only read, the container structure is updated.

</details>

<details>
<summary>Does initial capacity bound cache entries?</summary>

No. Initial hash-table capacity is a storage sizing input. Eviction requires an explicit mapping-count/weight policy, such as removeEldestEntry in the teaching cache.

</details>

<details>
<summary>Why use LinkedHashMap instead of TreeMap for insertion order?</summary>

TreeMap orders by comparisons, independent of insertion history. LinkedHashMap maintains a separate order chain, which expresses the required encounter order without sorted-key semantics.

</details>

## Solved interview and debugging practice

<details>
<summary>Why can two coordinate systems coexist in one map?</summary>

The table locates candidates by hash while separate before/after links define encounter order. Changing capacity can change bucket coordinates without changing insertion/access history.

</details>

<details>
<summary>What does removeEldestEntry fail to specify for a production cache?</summary>

It does not by itself define expiration, weighted memory bounds, concurrent access, load deduplication or failure/cancellation policy. A mapping-count eviction hook is one small mechanism.

</details>

<details>
<summary>Why might composition be safer than a public cache subclass?</summary>

It can expose only operations that preserve the cache contract, rather than inheriting order-positioning and mutation methods whose semantics were never considered by the cache API.

</details>

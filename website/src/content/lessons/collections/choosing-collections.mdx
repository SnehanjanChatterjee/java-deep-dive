<span id="concepts"></span>
## Store a changing group of values

Suppose a program receives names one at a time. An array can hold them, but its length is fixed. A collection gives the program operations for adding, removing, finding and traversing values without requiring the caller to manage storage growth.

A **collection interface** states the behavior a caller can use. An **implementation** supplies the representation and algorithms. In `List<String> names = new ArrayList<>();`, List is the contract, String is the element type and ArrayList is the selected implementation. The variable can use List operations even though its object has array-backed storage. The diamond `<>` lets the compiler infer String for the constructor.

<span id="worked-example"></span>
## Add, inspect, replace and remove

```java
final List<String> names = new ArrayList<>();
names.add("Mira");
names.add("Noor");
names.add("Mira");
System.out.println(names.size());       // 3
System.out.println(names.get(1));        // Noor
System.out.println(names.contains("Mira")); // true
names.set(1, "Ada");                    // replacement; size stays 3
names.remove("Mira");                   // removes the first equal value
System.out.println(names);             // [Ada, Mira]
```

This fragment needs imports for java.util.List and java.util.ArrayList inside a class/method. Positions start at zero. A repeated value is a separate position in a list. contains and remove(Object) use value equality; they do not mean “the exact same allocated object.” The dedicated ArrayList chapter supplies a complete runnable file and explains indexed removal separately.

## Interpret a method result before reading printed output

The list moves through [Mira], [Mira,Noor], [Mira,Noor,Mira], then [Mira,Ada,Mira], then [Ada,Mira]. Its **size** counts positions, including repeated values. set returns the old value but does not add a position; remove(Object) reports whether it removed one equal value. A list can therefore represent repeated visits or ordered work steps.

Other tasks need different contracts. A **set** represents unique membership, such as which names have appeared. A **map** associates a key with a value, such as each name with its latest score. Putting a value for an existing map key replaces that key's association rather than adding another key position.

A **queue** keeps values waiting under a removal policy. **FIFO** means first in, first out, as in a checkout line; **LIFO** means last in, first out, as in a stack of undo actions. A **deque** (double-ended queue) exposes both ends, so the operations chosen by the caller can implement either policy. A priority queue instead selects by priority.

**Encounter order** is the order in which a container presents elements during traversal. It can come from list positions, first insertion, or a comparison rule; some containers promise none. It is separate from whether duplicates are allowed.

The <a href={lessonUrl('learn/collections/collection-operations/')}>next chapter</a> follows the shared addAll, containsAll, removeAll, retainAll and toArray operations one state at a time.


## Follow the interface hierarchy

<Diagram client:visible definition={"flowchart TD\n I[Iterable] --> C[Collection]\n C --> L[List]\n C --> S[Set]\n C --> Q[Queue]\n Q --> D[Deque]\n S --> SS[SortedSet]\n SS --> NS[NavigableSet]\n M[Map: separate key-value hierarchy] --> SM[SortedMap]\n SM --> NM[NavigableMap]"} caption="Arrows mean a more specialized interface extends the interface above it. Map is separate because it associates keys with values." />

Collection supplies shared operations such as add, remove, contains, size, isEmpty and clear. List adds indexed positions and permits duplicates. Set requires unique membership. Queue defines which pending element is examined/removed next. Deque gives access at both ends. Map associates one value with each unique key; it is not a Collection. Map exposes collections of its keys, values and entries when traversal is needed.

A contract does not promise every mutator succeeds. Some operations are optional and can throw UnsupportedOperationException, as on a fixed-size or unmodifiable container. Null handling also depends on the implementation. Learn ordinary operations before relying on a specific storage model.

## Choose by the complete operation sequence

| Required behavior | Starting choice | Reason and remaining cost |
| --- | --- | --- |
| Append, traverse, read by index | ArrayList | Compact reference array; middle mutation shifts a suffix |
| Unique values, no required order | HashSet | Hash-based membership; no encounter-order promise |
| Unique values in first-appearance order | LinkedHashSet | Membership index plus maintained encounter links |
| Associate keys and values | HashMap | Exact-key lookup; no sorted or insertion-order promise |
| Sorted keys and interval queries | TreeMap | Comparison-based navigation and range views |
| FIFO queue or LIFO stack | ArrayDeque | Efficient endpoint operations; no null elements |
| Repeated least-priority selection | PriorityQueue | Heap root gives the next value; traversal is not sorted |

The chapters that follow develop each representation. This is a choice guide, not an implementation lesson. A workload repeatedly inserting into an independently located LinkedList position still pays for traversal. Finding a position and changing links are different operations.

<span id="mechanics-and-tradeoffs"></span>
## State the cost assumptions

ArrayList indexing is O(1); append is amortized O(1), while one expansion copies O(n) references. LinkedList indexed access is O(n), even though relinking at a known node is O(1). HashMap/HashSet core lookup is expected O(1) with suitable hashing and bounded key-method work. TreeMap/TreeSet take O(log n) comparison steps. ArrayDeque end operations are amortized O(1). PriorityQueue peek is O(1), offer/poll O(log n) apart from growth.

These bounds describe growth in work as n increases. They do not rank every small input or include arbitrary comparator/hashCode computation. Construction, traversal, memory locality, allocation and final output ordering belong in the full decision. Building an index for one small lookup can cost more than scanning an existing list; repeated lookups can justify it.

## Equality, order and ownership are separate choices

Hash membership uses equals/hashCode; sorted membership uses comparison-zero equivalence. IdentityHashMap deliberately uses reference identity for specialized tasks such as identity-based graph processing. EnumSet/EnumMap specialize a single enum domain. A comparator used for display sorting does not change HashSet membership; used by TreeSet it does.

A collection can expose a live view or a detached container. Neither implies a deep copy of mutable elements. The next chapter makes traversal, views and supported mutation concrete. A concurrent collection supplies particular operation guarantees; it does not make stored objects immutable or an arbitrary sequence of calls atomic.

<span id="common-mistakes"></span>
## Check the promise before replacing the structure

Replacing HashSet with TreeSet can change uniqueness as well as order. Replacing a snapshot with a view can change ownership. Observing stable HashMap output does not establish a promised order. Choosing a Queue type does not by itself provide a capacity bound or blocking backpressure.

<span id="exercises-and-interview-questions"></span>
## Worked selection exercise

For a FIFO work list, choose ArrayDeque and add at the last end/remove at the first. For the largest k scores, keep a size-k min-heap so its root identifies the weakest retained candidate; account for final result ordering. For interval lookup choose NavigableMap and declare inclusive/exclusive endpoints. For duplicate detection in first-appearance order, insert into LinkedHashSet from a source with defined encounter order.

A defensible answer states required operations, membership relation, order, mutation ownership and concurrency assumptions. It also names the operation that remains expensive.

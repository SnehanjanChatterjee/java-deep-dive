## Logical size and physical capacity

A dynamic array combines a fixed-size backing array with a logical size. Capacity describes allocated slots; size describes valid elements. Appending uses a spare slot when available and grows the backing array when it is full. Removing an element shifts later values left, preserving sequence order.

The implementation below stores ints to keep ownership and bounds rules visible. A generic version would store references and clear vacated slots so removed elements can be collected. The core invariant is 0 ≤ size ≤ capacity and every public index must fall inside the appropriate logical range.

<span id="worked-example"></span>
## Insertion and removal trace

Adding three values to a two-slot array triggers growth. Removing index 1 returns 20 and moves 30 into that position. The remaining logical sequence is 10, 30; the unused backing-array slot is not a third element.

<span id="mechanics-and-tradeoffs"></span>
## Growth, shifting and amortized analysis

Doubling growth means a particular append can copy n elements, but a long sequence of appends has linear total copying work, giving amortized O(1) append. Indexed get remains O(1). Removing at an arbitrary index costs O(n − index) due to shifting. These costs assume element reads/writes have bounded cost.

Separate boundary checks from mutation. Reject invalid indices before changing size. Compute how many elements need moving, then reduce size after the operation succeeds. This order makes it easier to reason about failure paths.

### State and invariants

For a backing array of capacity 4 and size 3, only slots 0, 1 and 2 belong to the sequence. Slot 3 is unused. The generic implementation below maintains `0 <= size <= elements.length`, stores every logical element in that prefix, and clears references outside the prefix when removing or clearing. A null element is permitted and does not mean a slot is unused; size determines membership.

An element index accepts `0 <= index < size`. An insertion position accepts `0 <= index <= size`, including the position immediately after the last element. Confusing these checks prevents valid appends or permits invalid reads. Validate before growing or shifting so rejected operations do not alter the structure.

### Explain each mutation

`add(index, value)` validates an insertion position, ensures one spare slot, then shifts the suffix right by `size - index` positions. `System.arraycopy` correctly handles overlapping source and destination ranges. It writes the new value and increments size once. Appending is the same operation at index size, so it shifts zero elements.

`remove(index)` saves the old value, shifts `size - index - 1` elements left, decrements size, and writes null into the newly vacated slot. Without that last write, an otherwise unreachable object could remain retained through the backing array. `set` replaces a logical value without changing size. `clear` nulls the active range and resets size while retaining capacity for reuse.

### Trace insertion and removal

Starting with `[10, 30, _, _]`, size 2, insert 20 at index 1. Copy one value from index 1 to 2, store 20 at 1, then set size to 3. The logical result is `[10, 20, 30]`. Remove index 1: save 20, move 30 left, reduce size to 2, clear index 2. The remaining array is `[10, 30, null, null]`.

### Prove amortized append cost

With doubling, expansion copies roughly `1 + 2 + 4 + ... + 2^k` elements over a growing sequence. That geometric sum is less than twice its next power-of-two bound, so total copying across n appends is O(n). Ordinary writes add another O(n), making amortized append O(1). A particular expanding append is still O(n). Growing by a fixed one slot instead gives `1 + 2 + ... + n`, or O(n²) aggregate copying.

Actual ArrayList growth factors are implementation policy, not a public promise to double. Our teaching version doubles and has an explicit exercise capacity limit to prevent arithmetic overflow. It reports that limit rather than accidentally wrapping a requested array length. Automatic shrinking is omitted; shrinking on every removal near a boundary would create allocation thrashing without hysteresis.

### Boundary reasoning

Try insertion into an empty list at 0, removal from empty, insertion at size, negative indexes, repeated growth, duplicate/null values, and removal at first/middle/last positions. Explain the exact number of shifted elements for each case. Capacity is a storage detail; never expose it as an extra logical element.

## Failure paths and bulk compaction

### Validate before changing representation

An element read/removal accepts indexes below size; insertion also accepts index equal to size. Both reject negatives. Perform these checks before allocating, shifting or incrementing counters. That ordering makes an invalid operation a no-op rather than a partial mutation.

Allocation can fail even for a logically valid request. A practical implementation should calculate growth without integer overflow and preserve the old backing array until new allocation/copy succeeds. The teaching capacity bound makes this branch explicit. It is a limit of the exercise, not a promise of the production List API.

### Distinguish operation atomicity from thread safety

An append implemented as several field/array writes is not a thread-safe transaction. A correctly ordered single-threaded mutation helps reason about exceptions, but another thread can still race with it unless access follows a shared protocol. Declaring size volatile does not coordinate array replacement and element insertion as one invariant.

### Bulk removal proof

A compaction scan uses read and write cursors. Accepted values are copied into the active prefix at write, and every read position is considered once. After the scan, clear the discarded reference range and set the new logical size. This can remove many items in O(n) instead of performing a separate O(n) suffix shift per removal.

A throwing predicate introduces a failure-policy question. If mutation has already occurred, the operation cannot casually promise rollback. Production implementations preserve a defined state using careful bookkeeping; a teaching extension should state whether predicate failure leaves partial changes, restores state or first computes an independent acceptance plan.

### Amortized cost is not a latency service level

A resize can allocate and copy a large array in one append. Amortized O(1) says aggregate operation work is bounded over the sequence, not that every request meets a fixed latency. If a workload knows a reliable final size, reserving capacity can reduce repeated copying; an exaggerated reservation wastes memory and can itself fail.

### Exercise solution map

For indexed insertion, validate a position, ensure room, copy size−index elements right, store and increment. For removal, save the old element, copy size−index−1 left, decrement, clear and return. For clear, null the active reference range before resetting size. For a typed backing array, explain erasure and the localized read-cast invariant instead of scattering unchecked casts through public methods.

<span id="common-mistakes"></span>
## Bounds and retained-reference mistakes

Do not expose the backing array, use capacity as the iteration boundary, or grow by one on every append. In a reference-based version, leaving stale references beyond size retains otherwise unused objects.

<span id="exercises-and-interview-questions"></span>
## Dynamic-array interview questions and exercises

### Why is amortized O(1) different from worst-case O(1)?

<details>
<summary>Explanation</summary>

Amortized analysis spreads occasional expensive growth across a sequence of operations. A single append can still take linear time when it reallocates and copies. This is not a probabilistic average over random inputs; it is a bound on the aggregate work of a sequence under the growth policy.

</details>

### Additional interview questions

<details>
<summary>How many elements move when inserting at index i in size n?</summary>

n - i elements shift right. Insertion at n shifts zero; insertion at zero shifts the entire sequence. If capacity is exhausted, growth also copies the existing array, independently of that positional shift.

</details>

<details>
<summary>Why clear the old final slot after removal?</summary>

The logical size shrinks, but the backing array remains reachable. A stale reference outside the active prefix could keep a removed object alive. Clearing the slot preserves the ownership invariant and permits collection when no other roots retain that object.

</details>

<details>
<summary>Is amortized O(1) a guarantee about one append?</summary>

No. One expanding append can be linear. Geometric growth bounds total copying across a sequence of n appends by O(n), yielding constant amortized work. This aggregate bound does not rely on random input probabilities.

</details>

### Coding exercise

Implement insertion at an arbitrary index. Add tests for empty removal, first/last positions, growth boundaries and invalid indices. Explain how a generic reference version should clear vacated slots.

## Solved interview and debugging practice

<details>
<summary>What does a volatile size field fail to solve?</summary>

The array reference, its contents and the size relationship still form a compound invariant. Another thread could observe or race with different stages. Visibility of one field does not supply atomic coordination for the operation.

</details>

<details>
<summary>Why retain the old array until allocation/copy succeeds?</summary>

Failure before replacement can leave the original logical representation intact. Replacing state too early can lose valid elements or expose an incomplete new representation.

</details>

<details>
<summary>How can bulk removal avoid quadratic shifting?</summary>

Compact accepted values in one pass using a write cursor, then clear the discarded tail once. Analyze predicate failure separately rather than claiming rollback from the happy-path algorithm.

</details>

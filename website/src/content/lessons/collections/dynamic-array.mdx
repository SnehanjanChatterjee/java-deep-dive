## Represent a growing list with a fixed array

ArrayList's public operations hide storage management. To implement a focused subset, keep an Object array and a logical size. Only indexes below size are elements; remaining slots are unused capacity. The invariant is `0 <= size <= elements.length`, with logical elements stored in the active prefix.

A null element can be valid, so null cannot distinguish membership from spare capacity. Size makes that distinction. Element indexes permit `0 <= index < size`; insertion positions also permit index equal to size. Validate those boundaries before allocating or mutating.

<span id="worked-example"></span>
## Trace insertion and removal

Starting with [10,30,null,null], size two, insert 20 at index one. Move 30 from one to two, write 20 at one, then increment size. Remove index one: save 20, move 30 back, decrement size and clear the old final reference. The result is [10,30,null,null], size two.

## Complete generic implementation

<JavaExample file="SimpleArrayList.java" output={"20\n30\n2\nnull"} />

This one-file container implements size, get, set, append, indexed insertion, removal, clear and a bulk-removal extension. It deliberately does not implement the full List contract, iterators, backed ranges, serialization or concurrency. Every typed write receives T; get localizes the Object-to-T cast. Erasure prevents allocating a direct generic T array.

## Explain each method against the representation

get validates an element index, then reads one slot. set reads/saves the prior element through that same check before writing the replacement; size does not change. add(value) delegates to add(size,value), which validates an insertion position, ensures room and uses System.arraycopy to shift size−index references right. arraycopy handles overlapping source/destination ranges correctly.

remove saves the old value, shifts size−index−1 references left, decrements size and clears the vacated slot. The saved reference remains returnable even after clearing. clear nulls the active range before setting size to zero, retaining capacity for reuse. None of these operations clones the element objects.

ensureCapacity leaves existing storage intact if room remains. Otherwise it computes a doubled array within the explicit exercise bound and replaces storage only after allocation/copy succeeds. The capacity limit is a teaching policy, not an ArrayList API limit.

<span id="mechanics-and-tradeoffs"></span>
## Prove the growth bound

Doubling copies roughly 1+2+4+... references. The geometric sum is O(n) over n appends; ordinary writes add O(n), so append is amortized O(1). One expansion is still O(n). Growing by exactly one instead copies 1+2+...+n, or O(n²). This is a bound over a sequence, not a probability average or a latency guarantee.

Actual ArrayList growth multipliers are implementation policy. Pre-sizing can avoid copying when a reliable size is known, while excessive capacity wastes memory. Automatic shrinking is omitted here; shrinking immediately around every threshold can thrash unless a hysteresis policy separates growth and shrink decisions.

## Complete bulk removal with an explicit failure policy

A repeated remove(0) can shift O(n) references O(n) times. Bulk compaction instead keeps a write cursor for accepted elements. This example first evaluates a MatchRule into a boolean acceptance plan, then compacts survivors and clears the discarded tail. It uses O(n) extra boolean storage to leave container membership unchanged if rule evaluation throws before compaction.

MatchRule is a small interface with one boolean matches(value) method. A named implementation can supply the decision without lambda syntax. The caller must not mutate this container or its membership through the rule; arbitrary reentrant/concurrent changes are outside the contract. The guarantee does not undo mutations a rule performs on element objects elsewhere.

During compaction, read scans every old position and write identifies the next accepted slot. Each survivor is copied at most once. After the scan, clear [write,oldSize), set size=write and return oldSize−write. A no-match case preserves the sequence; all matches leave an empty reusable container.

<span id="common-mistakes"></span>
## Separate exception ordering from thread safety

Checking before mutation helps preserve state for invalid indexes. It does not make append atomic across threads. Array replacement, contents and size form one invariant; a volatile size field alone cannot coordinate them. Allocation can fail, so keep old storage until new allocation/copy succeeds.

## Completed boundary and compaction exercises

<JavaExample file="SimpleArrayListTest.java" />

Tests cover growth, empty/negative/too-large positions, insertion at size, first/middle/last removal, duplicates/nulls, replacement, clear/reuse, no/all/mixed bulk matches and a throwing rule that leaves membership unchanged. Count shifted references separately from size: insertion at i moves n−i; removal moves n−i−1; a growth copy is additional work.

**Why clear after removal?** The backing array remains reachable. A stale reference outside size can retain an otherwise unused object even when logical output looks correct.

**Why not promise rollback for an in-place one-pass predicate loop?** Earlier writes may already have overwritten values before a later predicate throws. The two-phase plan here deliberately trades memory for a defined container failure boundary.

## Start with a minimal List contract

`List<T>` represents an ordered sequence of T values. Get reads a position, add appends when mutation is supported, set replaces a position, size reports its length and an Iterator visits elements with hasNext/next. ArrayList is one growable implementation. Collection internals come later; this chapter needs only those operation contracts.

Generic types are invariant: `List<Integer>` is not a subtype of `List<Number>`. If it were, code could insert a Double through the Number reference into an Integer-only sequence. Inheritance between the element types does not establish that container assignment.

## Express producer and consumer capabilities

<Diagram client:visible definition={"flowchart LR\n S[List of Integer] --> P[Read values as T]\n P --> D[Write values into consumer of T]\n D --> N[List of Number]"} caption="Bounds describe safe data flow at compile time; they do not promise an immutable or mutable implementation." />

A `List<? extends Number>` has one unknown element type bounded above by Number. Reading as Number is safe, but adding an arbitrary Number is not: the actual list might be Integer-only. A `List<? super Integer>` accepts Integer writes but reads only as Object: other existing elements might be Double in a Number list.

| View | Read as | Add safely if supported |
| --- | --- | --- |
| `List<Number>` | Number | Any Number |
| `List<? extends Number>` | Number | Only null without further information |
| `List<? super Integer>` | Object | Integer values and null |
| `List<?>` | Object | Only null without further information |

These are type permissions. An unmodifiable implementation may still reject add. An extends view can permit clearing/removal and can observe mutations through another alias; it is not immutable.

## Read copy, max and capture as separate algorithms

Start with the copy requirement: a source of Integer values should fill a destination accepting Number values. A signature demanding `List<Number>` for both would reject the Integer source. Give the transfer a named T, read from a source that produces T, and append to a destination that consumes T:

```java
public static <T> void copy(
        final List<? super T> destination,
        final List<? extends T> source)
```

For this call T can be Integer. Reading produces an Integer; a Number destination accepts it. The mnemonic **PECS** means **producer extends, consumer super**. It records this direction of data flow; it does not promise that a particular list supports mutation.

The complete program also finds a maximum and swaps two positions. Before reading max, recall that `Comparable<X>` supplies compareTo(X): a negative result means smaller, zero means equivalent in this ordering, and a positive result means greater. Integer implements this contract, so comparing 1 to 3 gives a negative result. Number itself has no compareTo method.

<JavaExample file="GenericAlgorithms.java" output={"[3, 1, 2]\n3\n[3, 1, 2]"} />

Main begins with [2,1,3]. swap(0,2) changes it to [3,1,2]; copy appends those references into an initially empty Number list. max seeds best with 3, keeps it when visiting 1 and 2, and returns 3. These are three independent algorithms, not three required steps in every generic operation.

Copy appends rather than overwriting. Its source visits are O(n); destination add determines the remaining cost. A failed add may leave earlier appends in place. Max rejects empty/null input and null elements, performs O(n) comparisons and uses O(1) auxiliary space. Swap names its otherwise unknown element type in a helper, developed below.


## Dry-run the source and destination views

Start with a List&lt;Integer&gt; [3,1,2] and empty List&lt;Number&gt;. copy's source wildcard captures a type bounded by T; reading one element as T is safe. The destination wildcard accepts T because its unknown type is a supertype of T. After the three adds, the Number destination contains the same three Integer references.

| Signature choice | Integer source accepted? | Number destination accepted? | Meaning |
| --- | --- | --- | --- |
| List&lt;Number&gt; for a number reader | No | — | Requires exactly that parameterization |
| List&lt;? extends Number&gt; | Yes | — | Read a bounded unknown subtype |
| List&lt;? super Integer&gt; for a writer | — | Yes | Write Integer into a compatible supertype container |
| List&lt;?&gt; | Yes as an unknown list | Not an arbitrary writer | Read Object without discarding generic checks |

You cannot add Double to an extends Number view because it might point to the original Integer-only list. Adding even an Integer is not generally safe either: the captured subtype might be a different Number subtype. Null is type-compatible but can still be rejected by the actual collection.

With a super Integer view, existing data might include Double if the underlying list is List&lt;Number&gt;. Reading as Integer would therefore need evidence the wildcard does not provide. Reading as Object is always safe; an instanceof check can then refine a particular runtime element.

## Keep append-copy traversal independent of destination growth

The supplied copy appends into its destination while traversing its source. Its type bounds establish safe reads and writes; they do not establish that the two references own different containers. Passing the same ArrayList as both arguments can invalidate its source iterator after an append. Distinct subList references can also share backing storage. No rollback is promised for such interference.

To append a sequence to itself deliberately, first take a structural snapshot, then traverse that independent container:

```java
final List<Integer> snapshot = new ArrayList<>(values);
GenericAlgorithms.copy(values, snapshot);
```

Starting with [3,1,2], the result is [3,1,2,3,1,2]. The snapshot's membership stays [3,1,2]. Element references are shared; the snapshot protects this traversal from structural changes, not from arbitrary concurrent element mutation. This append-copy algorithm differs from Collections.copy, which overwrites existing destination positions.

## Capture one unknown type, not several unrelated unknowns

swap accepts List&lt;?&gt;. Reading its left position yields the unknown captured type, but the source declaration cannot write that type name directly. swapCaptured introduces T for this exact list. Both saved values and both set calls now use one T.

The implementation reads both indexes before either write. A rejected second read therefore leaves the sequence unchanged. Supported set operations can still have their own failure behavior; type safety is not a transaction or a mutability guarantee.

Two independently declared List&lt;?&gt; parameters do not mean their element types are equal. A method moving an arbitrary value from one into the other needs a named shared relationship or a checked conversion, not a wildcard repeated twice.

## Explain the comparison bound instead of memorizing it

Comparable&lt;X&gt; supplies compareTo(X). A subtype can inherit comparison against its parent type. If Child extends Parent and Parent implements Comparable&lt;Parent&gt;, Child can compare to another Child through the Parent contract. Comparable&lt;? super T&gt; permits that relationship; requiring Comparable&lt;T&gt; can reject it.

An intersection bound combines required capabilities. T extends Number & Comparable&lt;T&gt; permits Number methods and comparison; the class bound, if present, comes first. This is different from choosing either type, and different from a wildcard representing one unknown argument. The first bound also determines erasure, which matters to later binary descriptors.

Number by itself supplies numeric conversions, not Comparable. A method must not call compareTo merely because its current Integer caller happens to support it.

## Practice: choose the minimum necessary permission

A method only reads numbers. Must it accept `List<Number>`? A method only inserts Integers: should it require extends Integer?

<details>
<summary>Answers</summary>

Use `List<? extends Number>` for the reader so Integer lists can participate. Use `List<? super Integer>` for the writer so Integer, Number or Object destinations can participate. Neither signature guarantees that mutation is supported or that inputs are non-null. When an API must tie an input type to a return type, use a named parameter rather than replacing every occurrence with an unrelated wildcard. PECS summarizes these read/write needs; the algorithm's contract remains the reason for the signature.

</details>

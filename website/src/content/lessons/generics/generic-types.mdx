## See the missing relationship in an Object API

Suppose a program stores a piece of text now and reads its length later. A box with an Object field can hold that text, but its get method returns only Object. The caller must cast the result to String before calling length. The cast is a runtime check, not a promise about what future writes may put into the box.

Read the first program in this order: store a String, read and cast it, replace it with Integer, then try the same String cast again.

<JavaExample file="ObjectBoxLesson.java" output={"4\nwrong value type"} />

The text has four UTF-16 code units, so the first line is 4. The later cast fails with ClassCastException; the program catches that expected failure and prints its label. The mistake was accepted at the write. We want the compiler to connect the allowed writes to the expected reads.

## Declare a type parameter, supply a type argument

A **generic type** declares a placeholder for a reference type. In this shortened declaration, T is the **type parameter**. Every occurrence refers to the same chosen type within one use of the class:

```java
public final class GenericBox<T> {
    private T value;
    public GenericBox(final T value) { this.value = value; }
    public T get() { return value; }
    public void set(final T value) { this.value = value; }
}
```

Choosing String as the **type argument** makes the constructor and setter accept String and makes get return String. The class is written once; a caller states the relationship it needs.

## Instantiate the type instead of only naming it

Follow these statements before opening the complete program:

```java
final GenericBox<String> text = new GenericBox<>("first");
text.set("second");
final String value = text.get();
```

The declaration names a reference type; new constructs an object. The diamond `<>` lets the compiler infer String here. Construction stores "first", set replaces it with "second", and get returns that same String reference without a caller cast. It does not return the original first value.

<JavaExample file="GenericBox.java" output={"second\n7"} />

The second box chooses Integer independently. Type arguments are reference types, so `GenericBox<int>` is rejected; autoboxing converts the literal 7 into Integer for this call. Try text.set(7) separately: it fails to compile at the write boundary. Null is still permitted by this box's explicit policy.

The letters have conventional meanings, not special language behavior: T for a general type, E for an element, K/V for key/value. The next program uses two letters because its two stored positions need independent types.


## Follow two independent parameters and a generic interface

<JavaExample file="GenericRelationships.java" output={"Ada:7\n4\n7.5"} />

Entry&lt;String,Integer&gt; preserves two relationships: key returns String and value returns Integer. Supplying one argument does not determine the other. Entry is this example's ordinary nested class, not java.util.Map.Entry, and its final references do not automatically define value equality or copy mutable components.

Converter&lt;F,T&gt; describes input and output types on an interface. Length implements Converter&lt;String,Integer&gt;; its convert method must accept String and return Integer under that contract. A caller uses the interface method without an Object cast. Implementing a generic interface with concrete arguments and declaring a generic method are different declarations; the next chapter develops method parameters.

NumericValue&lt;N extends Number&gt; adds an upper bound to its class parameter. The implementation can call Number.doubleValue, while value() still returns N to a typed caller. NumericValue&lt;Double&gt; therefore retains a Double result. A String type argument is rejected because it does not meet the declared bound. The conversion to double can be approximate; the bound promises an operation, not exact arithmetic or ordering.

## Separate parameter scope, object identity and null

A type parameter is in scope for the instance fields/methods of its declaration; another nested declaration can have its own independent parameter. Reusing the letter T does not make two declarations share one variable. Descriptive names can be clearer when several roles coexist.

A static field belongs to the class rather than to each parameterization. It cannot have the enclosing class's T type, and there is no separate static counter automatically created for GenericBox&lt;String&gt; and GenericBox&lt;Integer&gt;. A static generic method can declare its own parameter; that is a new scope.

Generics constrain reference types, not object lifetimes or non-nullness. GenericBox&lt;String&gt; can contain null under its declared policy. Two GenericBox&lt;String&gt; variables can alias one mutable box and see each other's replacements. A final reference prevents reassignment of that variable; it does not freeze the box.

| Declaration or operation | What it establishes | What it does not establish |
| --- | --- | --- |
| GenericBox&lt;String&gt; reference | A static String storage/result relationship | Construction of a box object |
| new GenericBox&lt;&gt;("first") | One box with inferred argument | A new runtime class for String |
| GenericBox&lt;Integer&gt; | Boxed Integer element contract | Primitive-specialized storage |
| Entry&lt;K,V&gt; | Two independently related positions | Key/value equality or deep immutability |
| NumericValue&lt;N extends Number&gt; | Number operations available inside the class | A comparable or exact numeric domain |

The runtime-representation chapter explains why ordinary parameterizations share a runtime class and where casts remain.

## Practice: identify the rejected change

After constructing `GenericBox<String>`, can `text = new GenericBox<Integer>(7)` or `text.set(7)` work? Can another variable refer to the same String box?

<details>
<summary>Answer</summary>

Both Integer changes are rejected by the declared String relationship, regardless of the first stored value. Another `GenericBox<String>` reference can alias the same box and observe replacements through set. Type safety does not make the box immutable or thread-safe. Keep raw types and unchecked casts out of this initial API; their migration and runtime implications are taught later.

</details>

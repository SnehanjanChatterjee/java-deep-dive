## Keep a static type contract without a class per argument

Earlier, `GenericBox<String>`.get returned String without a caller cast. What does the JVM actually execute? Java checks that relationship while compiling, then ordinarily represents an unbounded type parameter using Object in the class file. The compiler can insert a cast at the typed read. This translation is called **erasure**.

Think of the two views side by side; the right side explains the translation, not source you should write instead:

| Source-level relationship | Conceptual erased operation |
| --- | --- |
| T value in `GenericBox<T>` | Object storage when T is unbounded |
| String text = box.get() | String text = (String) box.get() |
| N extends Number | Number is the erased first bound |

Ordinary parameterizations of the same declaration and defining loader share a runtime class. Erasure does not turn a String box into an untyped source API: the compiler still checks its normal writes. It also does not remove boxing, casts or allocation costs.

## Preserve overriding when the parameter changes

`Mapper<T>` declares T map(T value). With T = String, StringMapper implements String map(String). At the JVM level a method's **descriptor** records its parameter and return types; after erasure the interface expects Object-to-Object. To preserve the override, the compiler adds an adapter with that erased descriptor. This generated adapter is a **bridge**; **synthetic** marks that it was generated rather than declared in ordinary source.

## Restrictions follow from the available representation

An erased T does not supply a constructor or reified component class: `new T()`, `new T[10]` and `List<int>` are not permitted. Supply a factory or an appropriate container/specialization. A static field cannot have its enclosing class's T type. Overloads differing only by `List<String>` versus `List<Integer>` clash after erasure. Changing a first public bound can affect erased binary descriptors, not only source constraints.

Object cannot be tested with `instanceof List<String>` to validate its elements. `List<?>` is reifiable and legal in that context. Since Java 16, some parameterized tests are permitted when the operand's static type already establishes the necessary generic relationship, such as testing `List<Integer>` against `ArrayList<Integer>`. That is not runtime validation of an arbitrary object's elements. Reflection can retain **declaration** generic signatures, but arbitrary list instances do not expose a universally runtime-verified element argument.

## Raw types move failures away from the unsafe write

A raw List omits its type argument and permits legacy operations that bypass generic checking. An unchecked conversion can then expose an Integer as if it were a String, failing at a later typed read. Warnings identify missing evidence; suppressing them globally is not a proof. Localize an unavoidable unchecked cast and explain the invariant controlling every write and preventing escape.

A teaching container backed by Object[] can justify a read cast when every write follows its T API. Raw aliases or an escaping array invalidate that argument. Arrays themselves are reified, so `new List<String>[10]` cannot safely enforce its promised generic component at runtime.

## Locate the unsafe write and the later failure

rawRead creates one ArrayList&lt;String&gt;, then aliases it as raw List. The raw add accepts Integer with an unchecked operation. The failure occurs later when the compiler-inserted String cast is applied to typed.get(0). The list still contains the integer reference; erasure did not dynamically enforce String at the raw write.

checkedWrite instead passes the write through Collections.checkedList(backing,String.class). That wrapper checks the runtime class at its insertion boundary and rejects the Integer before storage. bypassRead retains another alias to the raw backing list; writing through that alias bypasses the wrapper and produces the later read failure again.

A checked wrapper does not inspect every preexisting element when constructed, does not freeze mutable values, and cannot validate arbitrary nested generic arguments from only List.class. Runtime class tokens and full generic relationships are different information.

The unsafe methods' narrow suppressions are part of this deliberately failing laboratory, not a recommendation to hide warnings in ordinary code. Removing them and compiling with -Xlint:unchecked exposes where evidence was discarded. A suppression changes diagnostics, not runtime behavior.

## Read the bridge descriptor

For Mapper&lt;T&gt;, the erased method accepts/returns Object. StringMapper's handwritten String-to-String method does not by itself have that descriptor. Its generated bridge accepts Object, casts to String, invokes the concrete method and returns the result as Object.

| Caller input | Bridge action | Handwritten body reached? |
| --- | --- | --- |
| Valid String through Mapper&lt;String&gt; | Cast succeeds, delegate | Yes |
| Incompatible object through a raw Mapper | Cast fails | No |
| Null, if allowed by target body | Reference cast accepts null | Target policy decides later behavior |

Bridge generation preserves overriding under erased dispatch. It does not create a new specialized runtime class for each argument. The same defining-loader declaration supplies the ordinary GenericBox runtime class across its parameterizations; other loaders and reflection declaration signatures are separate questions.

## Generic varargs combine two representation models

A varargs parameter is an array, but a generic element parameterization is erased. Aliasing that array as Object[] can allow an incompatible parameterization and pollute the heap. @SafeVarargs asserts an implementation has been reviewed for safe operations and exposure; it adds no runtime element checking. Do not apply it merely to quiet warnings.

## Explain why an array-store check cannot catch every generic mismatch

polluted receives a List&lt;String&gt;[]-shaped varargs array whose runtime component class is List. Its Object[] alias stores a List&lt;Integer&gt;; the array can check that the value is a List, but cannot enforce its erased String argument. The later typed read inserts a String cast and fails. This is heap pollution, not proof that the JVM ignores array component classes.

@SafeVarargs would be false for that implementation. It must not be added merely because the source compiles. In Java 8 the annotation is available on eligible static/final methods and constructors; Java 9 also permits private instance methods. It asserts reviewed safety of the varargs use and exposure, rather than adding per-element runtime validation.

A List&lt;List&lt;String&gt;> API can preserve nested write checking without exposing a generic array. A reifiable List&lt;?&gt;[] is also a different type from List&lt;String&gt;[]: it says each row has an unknown argument and does not promise String elements. Neither a cast nor a raw alias can manufacture that missing guarantee.

## Rejected declarations and safe alternatives

| Attempt | Why it fails or needs unchecked evidence | Alternative |
| --- | --- | --- |
| new T() | No runtime constructor contract for the type variable | Supply a value or an explicit creation strategy |
| new T[n] | Erased T is not a reified component class | Use a container or a correctly typed array factory |
| new List&lt;String&gt;[n] | Runtime array class cannot enforce String arguments | List&lt;List&lt;String&gt;> or a correctly constrained reifiable view |
| overload on List&lt;String&gt; versus List&lt;Integer&gt; alone | Both erase to the same parameter descriptor | Different operation names or a genuinely different signature |
| Object instanceof List&lt;String&gt; | Cannot verify arbitrary element arguments | List&lt;?&gt; plus explicit element checks when the boundary requires them |
| Raw List as an “any list” API | Discards checks for legacy compatibility | List&lt;?&gt; when the element type is genuinely unknown |

Compiler-inserted casts, boxing and concrete data-structure work can still cost time/storage. Erasure avoids a separate specialized class per argument; it is not a universal promise that generic programs have no runtime costs.

## Practice: distinguish a raw type from a wildcard

Are List and `List<?>` interchangeable ways to say any list? Can @SafeVarargs repair an implementation writing incompatible Lists into its argument array?

<details>
<summary>Answer</summary>

No. `List<?>` keeps an unknown but checked element relationship and prevents arbitrary insertion; raw List bypasses parts of generic checking for legacy compatibility. SafeVarargs cannot repair unsafe code. Remove the unsafe write or escaping alias, then review the whole implementation before asserting safety. An unchecked-warning suppression should be as narrow as the independently justified invariant.

</details>

## A typed container can still expose mutable elements

A schedule should remember the dates supplied at construction even if its caller later edits them. That is an **ownership** promise: the schedule controls the state that determines its value. A type such as `List<Date>` only says what kind of elements may be read and written; it does not make that promise for us.

There are two things to protect: the list's **membership** (which references it holds, in what order) and each referenced Date's mutable timestamp. Date is used here because setTime visibly changes an existing object. Its number is milliseconds from the epoch; calendar conversion is not needed for the experiment.

Trace one input Date initially holding 1000:

1. The constructor allocates a new list and a new Date with the same timestamp. Internal and caller dates now have equal values but separate identities.
2. The caller changes its original Date to 2000. The schedule's private Date stays at 1000.
3. The accessor returns another copied Date. Changing that returned object to 3000 leaves the private Date at 1000 again.

<JavaExample file="ImmutableSchedule.java" output={"1000\n1000\ntrue"} />

copyDates implements both boundaries: new ArrayList creates independent membership; new Date(date.getTime()) copies each value. Collections.unmodifiableList returns a view that rejects list writes through that view. Here it wraps a private copy, so no caller retains a mutable alias to that backing list. The final true compares two independently constructed schedules with the same timestamp.

Each copy takes O(n) time and space. For new date/time models, immutable Instant values can eliminate the per-element Date copy; the next sections separate that decision from copying the container.


## Write the ownership promise separately from the element type

| API result shape | Container membership | Mutable element state |
| --- | --- | --- |
| Original List&lt;Date&gt; | Shared | Shared |
| unmodifiableList(original) | Live backing membership visible | Shared |
| new ArrayList&lt;&gt;(original) | Independent membership | Shared Date objects |
| Supplied copyDates result | Independent, unmodifiable structure | New Date for each copied timestamp |

The schedule constructor and accessor use the last row. A caller can mutate a Date returned by dates(), but it is a detached object; the stored state is unchanged. Wrapping the original list alone would not protect against the caller's list edits or date edits. Returning the internal Date references would also reopen that state even if the returned container were unmodifiable.

This is value copying under a known Date contract: read a timestamp and construct a Date. A generic &lt;T&gt; copy method cannot invent a correct deep-copy rule for arbitrary T. Some values are immutable and shareable, some own external resources, some graphs have cycles/shared identities, and some require domain validation during reconstruction. Specify a strategy rather than assuming Cloneable or a cast solves every case.

## Nested containers add another ownership level

A copied List&lt;List&lt;Integer&gt;> can retain the original mutable row objects. Per-row copying detaches those row structures. Integer elements are immutable, so no element clone is needed for that stated model. List&lt;List&lt;Date&gt;> would still share mutable Date values unless those are copied too.

An unmodifiable outer container does not prevent a retained inner alias from changing a row. Conversely, making every row unmodifiable over the original backing rows can still expose changes through the raw original aliases. Copy and wrapper decisions must be applied at the level the API promises to own.

The nested-collections chapter supplies complete independent-row and frozen-set examples after the collection operations are taught. This chapter's schedule keeps one container level and one mutable element level visible before adding those structures.

## Equality and hashing need the same stable state

ImmutableSchedule compares the stored date values, not the identity of its private list. Copies constructed independently at timestamp 1000 compare equal and hash the same state. Because callers cannot mutate the private Date values through constructor/accessor aliases, those equality inputs remain stable.

A record's generated equality uses its component types' equality rules. List equality is element-based, but an array component normally compares by array identity unless the value model overrides it. A record containing a list or array is not automatically a deep snapshot. The modern example makes that difference explicit with defensive arrays and a List.copyOf boundary.

An immutable-value result still needs appropriate publication if shared between threads. Type parameters, final component references and unmodifiable wrappers describe different parts of the contract; none substitutes for a missing cross-thread handoff protocol.

## Practice: replace Date with an immutable element

Which copies remain necessary when a schedule stores immutable Instant elements? Is an unmodifiable view over the caller's mutable list sufficient?

<details>
<summary>Answer</summary>

Copy the container structure so later caller additions/removals cannot change the schedule. Sharing immutable element references is safe under that value contract; per-element cloning is unnecessary. An unmodifiable view alone still observes caller mutations and is not a detached snapshot. On Java 8, copy into a private ArrayList and wrap it; on Java 10+ List.copyOf provides a structural snapshot with its documented null policy. Concurrency and safe publication are additional concerns rather than guarantees inferred from a wildcard or wrapper.

</details>

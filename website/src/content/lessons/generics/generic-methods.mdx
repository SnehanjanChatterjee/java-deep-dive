## Give one invocation a type relationship

A utility may need to return the same kind of value it receives without belonging to a generic class. For example, assigning identity("Java") to a String should retain String, while identity(7) should retain Integer. Returning Object would discard that useful information.

A **generic method** declares its own type parameter before the return type:

```java
public static <T> T identity(final T value) {
    return value;
}
```

The first T declares the parameter, the second names the result type, and the T beside value names the input type. In `String text = identity("Java")`, the argument and assignment context permit T = String. The method returns the supplied reference unchanged; there is no cast or conversion in its body. A separate call can choose Integer.

<JavaExample file="GenericMethods.java" output={"Java\n7\nAda"} />

The explicit form `GenericMethods.<Integer>identity(7)` places the argument after the qualifier and before the method name. It is usually unnecessary when inference has enough information. The literal is boxed into Integer. The third line comes from first on a two-element String array; it reads position zero, "Ada".


## Preserve input/output information

First receives T[] and returns its first T component. A String[] therefore produces a String result. It rejects a null array and an empty array because neither supplies a first component. A present first component can itself be null, following the stated policy. The operation takes O(1) work and storage once the array exists.

Compare returning Object instead: callers would need casts even when the array's element type is already known. A named type parameter is useful when multiple positions must share a relationship. An unbounded wildcard instead represents an unknown type; later API-boundary chapters explain when that is appropriate.

## Transform an input type into a different output type

Now turn the array ["Java", "JVM"] into lengths [4, 3]. One type variable cannot express both roles precisely: the input is String and the output is Integer. `Transformation<F,T>` names an interface whose apply(F) method returns T. The named StringLength implementation supplies that behavior; lambdas are not needed here.

The result uses `List<T>`, an ordered sequence. `ArrayList<T>` is its growable implementation: new creates an empty sequence, add appends one element, and printing the list shows its elements in order. No list lookup or internal representation is needed for this loop.

For the first input, apply("Java") returns 4, then add stores that Integer. For the second, apply("JVM") returns 3 and add appends it. Only after those two steps does the method return the new list.

<JavaExample file="GenericTransform.java" output={"[4, 3]\n[4, 3]\n[Java, JVM]"} />

The method declares &lt;F,T&gt; before List&lt;T&gt;. Its F[] parameter supplies source elements; Transformation&lt;F,T&gt; turns one F into one T; the result keeps T. StringLength implements the String-to-Integer relationship, so both the inferred call and explicit &lt;String,Integer&gt; call return List&lt;Integer&gt; containing four and three. The source String[] remains unchanged.

Read the loop as a type trace:

| Position | Type in this invocation | Role |
| --- | --- | --- |
| values | String[] | Source array |
| value in the loop | String | One input passed to apply |
| operation | Transformation&lt;String,Integer&gt; | Input/output contract |
| operation.apply(value) | Integer | One result |
| result | List&lt;Integer&gt; | New encounter-ordered container |

The method allocates O(n) result positions and invokes the operation once per input. Its total cost includes the supplied operation. Empty input produces an empty result. A null array or operation is rejected; this StringLength implementation also rejects a null string. If a callback fails, the private partially built result is not returned, but the method cannot undo side effects the callback performed elsewhere.

Unlike identity, this transformation needs two letters because input and output can differ. Writing &lt;T&gt; for both would wrongly require the String input and Integer output to share one type parameter. The wildcard chapter later makes signatures more flexible when a callback consumes a supertype or produces a subtype.

## Keep a method parameter independent from its class parameter

A generic class can contain a non-generic method using its class T, and it can contain a generic method declaring a different U. A method is generic because it declares type parameters, not merely because List appears in its return type. For example, List&lt;String&gt; names() is not itself a generic method.

Explicit arguments constrain the invocation rather than converting arbitrary values. GenericMethods.&lt;String&gt;identity(7) is rejected; it cannot turn Integer into String. Ordinary casts and type inference are also different mechanisms. Inference finds a type satisfying all available constraints; it does not insert a domain conversion like Integer.toString.

Target context matters. String value = identity(null) can infer String. With var on Java 10+, identity(null) without that target has a broader inferred result; the runtime value being null does not later change the static type. A direct var value = null has no inferable initializer type.

## Inference combines constraints

An invocation must satisfy its arguments, bounds and assignment target together. The compiler does not wait for later assignments to choose a different type. Constructor diamond and method inference both operate at compile time.

A bound establishes operations the implementation may use. An unconstrained T supports Object's contract, not arbitrary methods that happen to exist on one caller's type. A method that calls doubleValue must declare an appropriate Number bound rather than relying on one successful Integer example.

## Practice: explain a useful and a useless type parameter

Would `<T> void print(T value)` need a named T if the body only calls println and the result contains no relationship? Why is T useful for first?

<details>
<summary>Answer</summary>

A simple Object parameter can express that unconstrained print operation; a named type parameter adds no useful relationship there. First uses T in both its input and return type, preserving information callers need. Generic methods are a design tool for relationships, not a requirement to replace every Object with a letter. First(new String[0]) still fails according to its empty-input contract: compile-time type safety does not establish nonempty data.

</details>

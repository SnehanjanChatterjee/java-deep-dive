## A request value belongs to an operation

**Context** is data associated with one operation and needed by several calls, such as a request identifier included in a report. The identifier lets outputs from different methods be associated with that request. The first design question is how those methods receive it and how long they should be able to access it.

Begin with ordinary parameters. Report receives the identifier, forwards it to format, and format uses it in the result. This makes the dependency explicit without any special thread mechanism:

<JavaExample file="ContextParametersLesson.java" output={"request-42: report"} />

Both report and format declare the context, making it visible in their method contracts. A **context carrier** is a mechanism through which callees can access that value without every intermediate method forwarding a parameter. ThreadLocal is one such mechanism, with a lifetime tied to the executing thread. Learn its ordinary association first, then examine why that lifetime differs from a reused worker's individual tasks.

<span id="thread-state-versus-task-state"></span>
## Thread state and task state have different lifetimes

A **ThreadLocal key** is the ThreadLocal object used to get/set a value for the **current thread**. A **binding**, or association, is that thread's current value under the key. Different threads using the same key can have different bindings; set and remove affect only the caller's association.

Think of one shared question with an answer maintained separately for each thread. Get can call an initializer to supply that thread's first answer, so it is not always a side-effect-free presence test. The next program gives one key an initializer returning zero; main changes its own answer to seven while a worker initializes and changes its separate answer.

## Observe one key with two independent associations

<JavaExample file="ThreadLocalIsolationLesson.java" output={"0\n1\n7"} />

Main installs seven for one ThreadLocal key. A newly started ordinary worker uses that **same key object**, but its get initializes its own association to zero. It changes its own value to one, records it, and removes its association in finally. Main joins and still reads seven from main's association, then removes that association too.

ThreadLocal does not assign one process-global value to its key. Main setting seven is also not inheritance into an ordinary ThreadLocal association. Conversely, if values themselves reference one deliberately shared mutable object, separate associations do not clone that object or protect its fields.

Remove affects only the calling thread. Main cannot clean a reused worker's binding merely by calling remove after a Future completes; install/restore/remove must run at the worker's task boundary. This is why the wrapper below executes finally **around the action on that worker**, rather than only around submission by the owner. ## Implement scoped restoration on a reused worker

A pool can reuse one worker for task A then task B. If A installs request context and forgets to remove it, B can see stale state. A private static key restricts access but does not make its value expire at task return.

Here a **scope** is the dynamic duration of one withContext action. Save the previous binding on entry, install the action's value, then restore the previous binding in finally. Nested actions temporarily shadow their caller's value. Restoring, rather than always removing, is what lets an outer action continue with its own context after an inner action returns or throws.

<JavaExample file="ThreadContextLesson.java" output={"outer\ninner\nouter\nnull"} />

The one-worker service makes reuse deliberate. WithContext captures the previous value, installs a non-null new value, invokes the action, then restores in finally. When there was no previous value it removes the association. When an outer binding existed, it restores that value rather than erasing the caller's context.

The first task observes outer, then inner, then outer again. A later task on the same worker sees null, proving the outer boundary removed request state before reuse. A larger pool could accidentally select a fresh worker and hide a leaked binding. Main retrieves the first task's completion before observing the next task.

## Context capture is a separate operation

The wrapper's invariant is about the calling thread. Creating a lambda while a context exists does not automatically make an executor capture that dynamic association. If propagation is required, capture the intended immutable value at submission time, then install it around execution with restoration afterward.

Reading a ThreadLocal later from a worker cannot retrieve another thread's association. InheritableThreadLocal copies through thread-creation rules, not every submission; pooled workers may already exist. Mutable inherited values can also be shared unless copied by policy. Prefer a small immutable correlation value over retaining an entire request graph.

<span id="representation-and-reachability"></span>
## Representation and retained values

A **strong reference** can keep an object reachable and therefore ineligible for garbage collection. A **weak reference** alone does not keep its referent alive. In OpenJDK, a thread-associated map weakly references keys while values remain strongly referenced. A live key can retain its value, and a stale entry's value can remain until cleanup processes it after key reclamation. Weak keys are therefore not a complete cleanup policy.

Remove clears only the current association and permits reclamation only if no other owner retains the value. A small forgotten binding can retain a large object graph. Virtual-thread-per-task execution changes reuse, but expensive per-thread caches can multiply across large numbers of threads. Cheap executions do not make their application values free.

## Exercise and complete restoration solution

Make an inner action throw, catch that failure inside the outer action, and observe outer again; after the task, the reused worker should see no prior binding. Unconditionally remove in the inner finally would incorrectly erase outer.

<JavaExample file="ThreadContextLessonTest.java" />

These supporting assertions exercise the complete wrapper. Its non-null policy lets null mean no previous application binding. A contract supporting present-null versus absent needs a sentinel or explicit state representation. Neither ThreadLocal nor a scoped carrier replaces explicit parameters when those are clearer. The scoped-value chapter later supplies a language-library-managed bounded binding for the appropriate use case.

## Thread state versus task state

ThreadLocal associates a value with a thread rather than with a method invocation or submitted task. Two threads accessing the same ThreadLocal key can have different values. Calling get can initialize a per-thread value through the key’s initialization policy; set and remove affect the current thread’s association.

A thread pool reuses threads across tasks. A value installed by task A can therefore still exist when task B runs on that worker. Task context needs an explicit lifetime even if the ThreadLocal key is private and static. Private access restricts readers but does not automatically remove old values.

<span id="worked-example"></span>
## Trace nesting on a reused worker

A single-worker executor guarantees the demonstration tasks reuse one worker. The first task binds outer, temporarily binds inner, then restores outer. When that task exits its outer boundary, a later task reads null. The output separates nesting restoration from cleanup before worker reuse.

Unconditionally calling remove in every nested finally would erase the outer binding. Conversely, never removing would leak the outer value into later tasks. The wrapper must know whether it is establishing an outermost binding or temporarily shadowing an existing one. This example rejects null values, allowing null to consistently mean no previous application binding.

<span id="mechanics-and-tradeoffs"></span>
## Context lifetime and retention

### Representation and reachability

A ThreadLocal key provides access to a thread-associated map entry. In OpenJDK, entries weakly reference keys, while their values are ordinary strong references. A long-lived worker can therefore retain task state through a still-live key, or retain a stale entry’s value until cleanup processes that entry after its key becomes unreachable. Weak keys alone are not a complete leak-prevention policy.

remove explicitly clears the current thread’s association and can permit the value to be reclaimed when no other owner retains it. It is not an instruction to clear every thread’s value or every other key. A ThreadLocal value that itself contains a large graph can make a small forgotten association an expensive retaining path.

### Scope and failure restoration

A scoped wrapper reads the previous binding, sets the new value, invokes the action and restores in finally. If no previous value existed under this example’s non-null binding contract, it removes instead of storing null. If a previous value existed, it restores that value. The invariant is that after withContext returns or throws, the calling thread sees the same application binding it had on entry.

This is a convention implemented by ordinary Java code, not automatic language dynamic scoping. Every path that installs the context must follow it. A callback that hands work to another executor does not automatically transfer the binding’s lifetime or cleanup ownership.

### Capture and propagation

If propagation across a task boundary is necessary, capture the intended immutable context value at submission time and install it around execution with restoration afterward. Reading the submitting thread’s ThreadLocal later from a worker does not retrieve the original thread’s association. Avoid retaining an entire request graph when only a small correlation value is needed.

InheritableThreadLocal copies through thread creation rules, not every executor submission. A worker often exists before a task is submitted, so inheritance does not implement per-task propagation. A mutable inherited value can also be shared unless the policy copies it; inheritance is not automatic deep isolation.

### Virtual threads and scoped values

Virtual-thread-per-task execution changes thread reuse, but creating an expensive per-thread cache for each of many virtual threads can multiply memory use. Cheap threads do not imply cheap application values. ThreadLocal remains useful for some independently mutable per-thread state, while Java 25 ScopedValue expresses bounded context bindings with controlled structured inheritance.

Neither mechanism replaces explicit parameters when those parameters are the clearest contract. Use a context carrier to reduce accidental plumbing only when its ownership/access rules remain easier to reason about. Do not let hidden ambient state decide security-sensitive behavior without a clear validated boundary.

## Implement scoped restoration

<JavaExample file="ThreadContextLesson.java" output={"outer\ninner\nouter\nnull"} />

withContext validates its arguments before changing state. It captures the current association, installs the new value, executes the Runnable, then restores or removes in finally. The public current method exposes only the current thread’s association. No collection is shared between workers by this wrapper itself.

The main method waits for the first submitted task to complete before submitting/observing the second result. A one-worker pool makes the no-leak observation meaningful; using a pool of many workers could accidentally choose a fresh worker and hide a leaked value. Finally shuts down the explicitly owned executor.

The wrapper forbids null application bindings. If an API must distinguish a present-null binding from no binding, a plain get-null check is insufficient; design an explicit sentinel/state representation. The example also does not automatically capture context for asynchronous child work.

<span id="common-mistakes"></span>
## Context propagation mistakes

Do not use ThreadLocal as global mutable state, rely on weak keys for immediate value reclamation, or treat inheritance as executor-task propagation. Do not remove an outer binding from an inner scope. A get call can initialize a value, so it is not always a side-effect-free probe for presence.

<span id="exercises-and-interview-questions"></span>
## ThreadLocal interview questions

<details>
<summary>Why does a single-worker test expose leaks better?</summary>

It ensures a later task reads the exact worker association left by the previous task. A large pool might run the observation on another thread and falsely suggest cleanup worked.

</details>

<details>
<summary>What must happen if the action throws?</summary>

The wrapper finally restores the previous binding before propagating the original failure. Cleanup should not silently convert failure into success or leave task state attached to the worker.

</details>

<details>
<summary>Why not call remove unconditionally in nested scope?</summary>

A valid outer value may have existed before the inner scope. Removing would destroy that caller context rather than restoring the entry state.

</details>

<details>
<summary>Does InheritableThreadLocal solve async propagation?</summary>

No. Thread creation and task submission are different events. Reused executor workers do not re-inherit the submitting caller context on each task.

</details>

<details>
<summary>When does scoped value fit better?</summary>

When sharing bounded, preferably immutable call context through a dynamic operation, with deliberate inheritance through structured task scopes. Per-thread mutable caches have a different model.

</details>

### Coding exercise and solution

Add an inner action that throws IllegalStateException. Catch that failure in the outer action and assert current is still outer; after the complete task, assert the reused worker sees null. Then implement an explicit capture wrapper: snapshot a non-null String before submission and call withContext inside the submitted Runnable. The solution must restore the worker’s previous state even when the wrapped task fails.

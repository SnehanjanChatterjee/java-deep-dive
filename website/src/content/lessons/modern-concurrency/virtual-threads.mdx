## Virtual threads and scarce resources

Virtual threads are JVM-managed threads designed to make large numbers of blocking tasks easier to express. They do not make CPU-bound code execute faster merely by increasing thread count. A virtual thread is still a Thread with lifecycle, interruption and stack-trace behavior, but its scheduling is not one permanently dedicated operating-system thread per task.

Resource limits remain: a database pool, remote service or file-descriptor budget can be exhausted even when threads are inexpensive. Limit the scarce resource directly rather than pooling virtual threads as though they were expensive workers. CPU-intensive tasks still compete for available processors.

## Separate scheduling from admission

The Java 8-compatible example uses a Semaphore to express the underlying resource bound independently of thread count. Modern virtual-thread code can use the same conceptual limit. The permit is released in finally, so failure does not permanently reduce capacity.

<span id="mechanics-and-tradeoffs"></span>
## Scheduling, pinning and context lifetimes

Scoped values, final in Java 25, express bounded sharing of immutable context along a dynamic call scope. They differ from arbitrary mutable ThreadLocal state. Structured concurrency treats related subtasks as a unit with coordinated lifetime and failure handling; in Java 25 it is preview functionality and requires the appropriate flags.

Pinning guidance is version-sensitive. Java 24 changed monitor handling so ordinary blocking inside synchronized code no longer causes the same pinning behavior described for Java 21–23. Native/foreign interactions and other runtime constraints still need investigation. Use the target JDK's diagnostics instead of repeating older blanket advice.

### Mounting is scheduling, not parallel execution capacity

A platform thread is generally tied to an operating-system thread. A virtual thread is scheduled by the JVM onto a carrier platform thread while it runs. Supported blocking operations can unmount it so its carrier can execute another virtual thread. A virtual thread executing CPU work still occupies execution capacity; adding thousands does not create more processors. Stack and task state still consume memory, even when suspended work is cheaper than thousands of dedicated OS threads.

<Diagram client:visible definition={"sequenceDiagram\n participant V as Virtual thread A\n participant C as Carrier\n participant B as Blocking operation\n V->>C: mount and run\n V->>B: supported blocking I/O\n Note over V,C: A unmounts, carrier can run another task\n B-->>V: completion makes A runnable\n V->>C: remount on an available carrier"} caption={"Supported blocking can release a carrier. Use one virtual thread per task rather than pooling them to protect a connection limit. Bound connections or other scarce resources directly with a pool/semaphore. Cheap waiting still needs deadlines, cancellation, queue/in-flight limits and overload handling: otherwise an application can retain unbounded request state.

### Pinning guidance must name the JDK

| Release | Relevant behavior |
| --- | --- |
| Java 21–23 | Blocking while holding a synchronized monitor can pin a carrier |
| Java 24+ | Monitor implementation changes remove that common synchronized-block pinning cause |
| Java 25 | Native/foreign call paths and runtime constraints can still matter; investigate the actual blocking path |

Do not mechanically replace all synchronized blocks with ReentrantLock based on advice for an older release. A long critical section still serializes contenders regardless of pinning. Use JFR events and version-appropriate thread diagnostics for observed symptoms.

### Scoped values are bounded context bindings

ScopedValue is final in Java 25. `ScopedValue.where(KEY, value).run(action)` binds a value during the action's dynamic execution; methods called within it can read through the same accessible key. A nested binding can shadow the value, and exiting restores the outer binding even after exceptions. Outside a binding, get fails; isBound allows an explicit policy.

The binding is immutable, but an object stored in it can still be mutable. Prefer immutable context values. Scoped values avoid arbitrary long-lived set/remove protocols for this use case, while ThreadLocal remains useful for some per-thread mutable state. Ordinary newly created threads do not automatically inherit every scoped binding. StructuredTaskScope supports controlled inheritance from its owning scope; do not assume an arbitrary executor callback has captured the dynamic scope.

### ThreadLocal lifetime and retained state

ThreadLocal associates a value with a thread, rather than with one method invocation. In a reused platform worker, leaving a request-specific value installed can retain data and expose stale context to later work. Use a try/finally remove policy when a task owns a temporary binding. ThreadLocal map keys are weak, but retained values can still survive until stale entries are cleaned or the thread ends; weak keys alone are not a complete leak-prevention policy.

InheritableThreadLocal copies context at thread creation, not automatically at every executor submission. Virtual-thread-per-task execution changes thread reuse but can multiply expensive per-thread values across large task counts. Scoped values address bounded context propagation; they do not replace every use of mutable thread-local state.

### Structured concurrency: Java 25 preview

Related child tasks belong within an owning scope. The Java 25 default `StructuredTaskScope.open()` policy waits for successful results or responds to failure by cancelling siblings. `fork` starts subtasks; `join` establishes the policy's outcome; successful Subtask.get retrieval follows joining. A failure is reported through FailedException with its cause. The API differs from earlier preview versions, so old ShutdownOnFailure examples should not be presented as Java 25 code.

Closing waits for child threads to finish. Cancellation requests interruption, which cooperative subtasks must honor. A child stuck in an uninterruptible action can delay close indefinitely; structure does not force unsafe termination. Owner-thread restrictions and scope lifetime rules prevent casual sharing of a scope as a global executor.

```bash
javac --enable-preview --release 25 StructuredConcurrencyDemo.java
java --enable-preview StructuredConcurrencyDemo
```

Only the structured-concurrency example here requires these preview flags. Records, virtual threads, gatherers, FFM and scoped values are stable on the Java 25 baseline.

### Complete resource-limit experiment with actual virtual threads

<JavaExample file="modern/VirtualResourceLimitLesson.java" output={"maximum=2\ntotal=42\npermits=2"} />

Six tasks run through a virtual-thread-per-task executor while a semaphore protects two resource permits. The first two admitted tasks signal entered before waiting for release. This coordination establishes occupancy two without using timing guesses. active is incremented only after acquisition and decremented in an inner finally; permits are released in the outer finally after successful acquisition. A task interrupted before acquire succeeds never releases a permit it did not own.

The maximum counter observes occupancy rather than controlling admission. The semaphore enforces the actual invariant. Waiting for every Future result establishes that all successful work and its cleanup completed before the final permit count is printed. The release guard in finally prevents exceptional main-thread paths from leaving the demonstration workers waiting forever.

This is a correctness experiment, not a performance comparison. The output proves the stated admission bound under the coordinated program; it does not claim more throughput or lower latency than platform threads. External services also need deadlines, request limits and failure policies that match their own behavior.

<span id="common-mistakes"></span>
## Virtual-thread assumptions

Do not equate more virtual threads with more CPU capacity, assume external pools become unlimited, or teach preview APIs without a version label. ThreadLocal values can become expensive when multiplied across very many threads.

## Virtual-thread interview practice

### Why is a semaphore still useful with virtual threads?

<details>
<summary>Explanation</summary>

Thread creation cost and downstream service capacity are separate constraints. A semaphore can bound simultaneous access to a scarce resource even when many tasks wait cheaply. The permit lifetime should match actual resource use, and cancellation/failure paths must release acquired permits.

</details>

### Additional interview questions

<details>
<summary>Why can many virtual threads still exhaust memory?</summary>

Each task retains stack/state and application objects, and waiting requests can accumulate without an admission bound. Virtual threads reduce some thread costs; they do not impose an automatic limit on accepted work or downstream resources.

</details>

<details>
<summary>Should Java 25 code replace every synchronized block to avoid pinning?</summary>

No. Java 24 removed the common monitor-held blocking pinning issue. Long critical sections still serialize access, and native/runtime paths can still matter. Diagnose the actual JDK and observed path rather than applying older blanket advice.

</details>

<details>
<summary>Can closing a structured scope forcibly kill an uncooperative child?</summary>

No. Cancellation uses cooperative interruption, and close waits for children to finish. An uninterruptible or cancellation-ignoring child can delay closure. Scope structure makes ownership visible; it does not provide unsafe forced termination.

</details>

### Coding exercise

On Java 25, run independent blocking tasks using a virtual-thread executor and limit a simulated downstream service with a semaphore. Compare task count, maximum concurrent resource use and elapsed time. Keep structured-concurrency variants explicitly marked preview.

### Coding exercise with reference solution

Implement six virtual-thread tasks sharing two resource permits. Establish occupancy two with a latch, wait for every result and prove all permits are restored. VirtualResourceLimitLesson is the complete reference solution. Identify the exact successful-acquire region before placing release in finally; a blanket release after an interrupted acquire would inflate capacity.

## Many tasks are waiting rather than calculating

A request calls another service and waits for its response. With a dedicated platform thread, that request retains an operating-system-thread resource while blocked. A large number of mostly waiting requests can need many more concurrent task lifetimes than the machine has processors.

Virtual threads make a thread-per-task programming style economical for suitable blocking work. They preserve familiar sequential calls, exceptions, interruption and stack traces. They do not make a CPU calculation faster just because more task threads exist. Understand the task's blocking behavior before changing its execution mechanism.

The program uses the stable Java 21 API and needs no preview flags. Compile with a JDK supporting Java 21 or later.

A virtual thread is a real Thread with lifecycle and interruption status; it is not merely a callback name. It is also a daemon thread, so an owner must keep the process alive while required task work remains. Joining or owning an executor lifetime makes that obligation visible.

## Trace a blocking task on carrier threads

A platform thread is generally tied to an operating-system thread. The runtime schedules a virtual thread onto a carrier platform thread while it runs. During supported blocking operations, it can unmount, leaving the carrier available to execute another virtual thread. When the operation becomes ready, the task becomes runnable and can later mount on an available carrier.

<Diagram client:visible definition={"sequenceDiagram\n participant A as Virtual task A\n participant C as Carrier\n participant I as Supported blocking operation\n A->>C: mount and execute\n A->>I: begin blocking wait\n Note over A,C: A can unmount and the carrier runs other ready work\n I-->>A: operation becomes ready\n A->>C: mount on an available carrier and resume"} caption="Suspension preserves the task's execution state. Resumption need not use the same carrier, and no extra processor is created." />

A virtual thread doing continuous CPU work still occupies execution capacity. Suspended stacks/task objects also retain memory. This is a scheduling/resource model, not a promise that every operation unmounts or every task uses less memory under every workload.

The executor creates a new virtual thread per submitted task. Three tasks report entry before waiting on release. Main observes all entry signals, releases the work, and retrieves every result. Entered proves the milestone, not that every task has already reached one exact Thread.State at the observation instant. Finally opens release on an exceptional owner path, while closing the owned executor accounts for its task lifetimes.

This experiment demonstrates concurrent task ownership and blocking coordination. It does not time the scheduler or prove a throughput improvement. In an application, use representative blocking calls and measure the actual workload rather than generalizing from arithmetic or sleep timing.

## Separate scheduling from scarce-resource admission

<JavaExample file="modern/VirtualResourceLimitLesson.java" output={"maximum=2\ntotal=42\npermits=2"} />

Six task lifetimes share two resource permits. The first two admitted tasks signal entered before waiting for release, establishing occupancy two. Active increases only after acquisition and decreases in its inner finally; the permit is released by the outer finally after successful acquire. A task interrupted before acquisition releases nothing.

Maximum observes resource occupancy; Semaphore enforces it. Retrieving every Future accounts for completed work/cleanup before final permit observation. Cheap waiting still needs deadlines, request/in-flight bounds and overload policy, otherwise many retained requests can exhaust memory.

Do not pool virtual threads to mimic a connection limit. Create one virtual thread per task and bound the connection/service itself. A connection pool may already enforce its own capacity. The Java 8 comparison below demonstrates only permit accounting, not virtual-thread execution:

## Pinning and diagnostic guidance must name the runtime

Blocking while holding a synchronized monitor could pin a carrier on Java 21–23. Java 24 changed monitor handling to remove that common cause. On the selected modern runtime, native/foreign interactions and other constraints can still matter. Read the actual target JDK's guidance and diagnostics before applying migration advice.

A long critical section still serializes contenders even when the carrier can be released. Replacing every synchronized block with ReentrantLock based on older pinning advice is not a general performance strategy. Use suitable JFR/thread-dump facilities and recorded workload evidence. Thread.getAllStackTraces covers platform threads rather than enumerating all virtual task lifetimes.

## Why related tasks need an owner

A parent operation often needs several independent results before it can return. Ordinary task submission makes concurrency easy to start, but ownership harder to finish: who cancels siblings after failure, who responds when the caller is interrupted, and who waits for cleanup? Related work should not accidentally survive the operation that requested it.

Structured concurrency associates these children with a lexical scope. The opening thread owns that scope; child lifetime is bounded by its closing boundary. The outcome policy decides what joining means—such as all children succeeding or selecting a successful result. Closing accounts for the actual child threads, rather than merely combining result handles.

This fits related subtasks of one operation, not every independently scheduled background activity. A periodic maintenance service can have an intentionally longer owner lifetime. The design question is the relationship between work and its owner, not whether every asynchronous API must disappear.

Try-with-resources closes the scope on both normal and exceptional paths, so the method cannot leave its child threads unaccounted for merely because a later statement throws.

<span id="mechanics-and-tradeoffs"></span>
## Scope states, policies and cancellation

### Java 25 lifecycle rules

Only the owner invokes fork, join and close. Forking after joining and repeatedly calling join violate the selected API's lifecycle rules. A scope is not a reusable global executor; opening another operation normally creates another scope with its own children and outcome.

The default open policy requires successful completion or reports failure. A failed child causes sibling cancellation to be requested. Other Joiner policies support other aggregate outcomes, so the join result and cancellation trigger depend on the chosen policy. They do not remove ownership or the requirement to finish child cleanup.

These rules target Java 25's preview API. Earlier previews used different construction/policy classes; examples built around ShutdownOnFailure are not interchangeable with this release's open/Joiner API.

### Outcome selection versus thread termination

An operation can select failure while a child is still responding to interruption. Cancellation is cooperative: an interruptible wait can throw, while ignored interruption or noninterruptible native work can delay termination. Close waits for child threads to finish. It cannot safely force arbitrary Java code to stop or roll back an external effect already performed.

A configured scope timeout similarly bounds outcome selection but is not permission to abandon children still cleaning up. Define interruption and resource-release behavior inside every child, especially around connection permits, files and remote requests. A semaphore release belongs only after acquisition succeeded.

### Context inheritance and resource ownership

Scoped-value bindings can be inherited through the documented structured-scope mechanism and lifetime checks. This is different from assuming an arbitrary executor captures ambient context. Keep inherited values immutable where practical; a fixed binding does not make its referenced object thread-safe.

A lexical task tree also does not create a database transaction or a general rollback mechanism. If one child performs a remote write before another child fails, cancelling siblings cannot establish that the write never occurred. The application still owns idempotency, compensation and the final operation contract.

`started` makes the failure child wait until its sibling has entered work. Without that coordination, the sibling could be cancelled before reaching the intended wait, producing a different demonstration. The sibling waits interruptibly and always signals `cleaned` from finally. The owner catches FailedException outside the resource block, preserving the failed child's cause. <span id="common-mistakes"></span>
## Recognize lifetime mistakes

Do not read a subtask result as if fork itself proved success, share the scope between arbitrary owners, or swallow interruption in a loop. Do not mistake an exceptional joined outcome for an instantaneous guarantee that remote work has ceased. Keep preview flags and release information with the example instead of teaching it as a stable Java 8 API.

A child should release its own acquired resources. The scope owns task lifetime, but cannot infer an application's connection/permit ownership. Double release after a failed acquire can violate a resource bound even though the task tree eventually terminates correctly.

<span id="exercises-and-interview-questions"></span>
## Explain and implement the task lifetime

<details>
<summary>How does this differ from CompletableFuture.allOf?</summary>

allOf represents aggregate completion but does not by itself own child threads or request sibling cancellation. A structured scope adds owner/lifetime and outcome-policy constraints. Neither abstraction replaces operation-specific cleanup or a remote-service cancellation protocol.

</details>

<details>
<summary>Why can close take longer than a timeout outcome?</summary>

A child may still be responding to cancellation or may not be interruptible at its current point. Outcome selection and termination are distinct. The owner cannot continue beyond close until the scoped child threads have finished.

</details>

<details>
<summary>Why is the start latch important in the failure solution?</summary>

It establishes the state the lesson intends to demonstrate. A fast failure otherwise could cancel a child before it began waiting. Coordination creates a reproducible causal trace without claiming deterministic task scheduling in general.

</details>

<details>
<summary>Can a child safely release a semaphore in every finally?</summary>

Only after it successfully acquired the corresponding permit. An InterruptedException before successful acquire means there is no permit to release. Track the acquired region structurally or with explicit ownership state.

</details>

<details>
<summary>What changes when a different Joiner policy is selected?</summary>

The condition for a joined outcome, result shape and cancellation trigger can change. The scope still has an owner and a closing boundary. Read the selected policy's contract rather than assuming every join means all successful results are available.

</details>

### Coding exercise and complete solution

Implement two children where one fails after an interruptible sibling starts. Preserve the cause, cancel related work and demonstrate cleanup before returning. StructuredFailureLesson above is the complete reference solution. Explain each latch and the placement of the catch outside try-with-resources.

For an extension, give each child a semaphore-protected resource and test interruption before acquisition versus after acquisition. Keep the resource-count invariant separate from the task-termination observation. Replacing the first child's wait with code that ignores cancellation deliberately demonstrates why structured lifetime cannot provide forced safe termination.

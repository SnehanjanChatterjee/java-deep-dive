## One operation needs two related results

**Structured concurrency** organizes related subtasks so their execution lifetimes are owned within one parent operation's scope. The **parent** needs the final answer; its **children** perform pieces of work needed for that answer. A **scope** is the object and code boundary managing the children it starts.

Suppose the parent needs two independent values. Starting both is easy with ordinary submissions, but the parent must also observe failures, decide when to cancel a peer, respond to its own interruption and account for cleanup. The structure makes those responsibilities belong to the operation's try-with-resources boundary rather than letting child threads escape its finished lifetime.

In the selected API, opening a scope identifies its owning thread. Fork starts child work and returns a Subtask outcome handle. A **Joiner** is the policy deciding what result or failure join selects. The default policy requires successful results from all children; a child failure selects failure and requests cancellation of peers.

Keep **join** and **close** distinct. Join waits for the selected policy outcome; close accounts for actual child-thread termination before the owner leaves the resource boundary. Cooperative tasks must still release their own resources, and a child ignoring interruption can delay that close. The first program uses two successful children before the failure/cancellation examples add those branches.

This fits work related to one operation. A long-running maintenance service can legitimately have a different owner and longer lifetime. The code targets the Java 25 **preview** API, which requires matching compile/run flags and can change between releases.

## Follow failure into sibling cleanup

Under the default policy, FailedException reports the selected task failure and retains its original cause. The next program makes the failure child wait until its peer entered, so we can distinguish a failure outcome, a cancellation request and actual sibling cleanup.

<JavaExample file="modern/StructuredFailureLesson.java" output={"child failed\ncleanup remaining=0"} />

One child reports started then waits interruptibly. The failure child waits for started before throwing, ensuring this experiment demonstrates cancellation of entered work rather than only cancellation before entry. The selected failure requests sibling interruption. The sibling's finally records cleanup. The owner catches FailedException outside the resource block, so that catch runs after scope closure has accounted for child termination.

## Scope states, policies and cancellation

In this Java 25 API, only the owner invokes fork, join and close. Forking after join or repeatedly joining violates lifecycle rules. A scope is not a reusable global executor. The default policy waits for success or reports failure while cancelling siblings. Joiner policies support different aggregate outcomes, so join can have a different result shape or cancellation trigger under a deliberately selected policy.

Earlier preview examples using ShutdownOnFailure are not interchangeable with this API's open/Joiner design. Those release details belong here after the task ownership mechanism, not before the first thread concept.

Cancellation uses cooperative interruption. A child ignoring it or blocked in a noninterruptible operation can delay close indefinitely. A configured timeout can select an outcome without guaranteeing that all child cleanup already finished; close still accounts for those child threads. The scope cannot safely force arbitrary code to stop.

## Choose a result policy for interchangeable candidates

Sometimes a parent needs **both** results. Sometimes either of two interchangeable sources can answer its one question. Those are different policies; the first completion might be a failure and therefore is not necessarily the desired answer.

<JavaExample file="modern/StructuredFirstSuccessLesson.java" output={"fallback"} />

Select validates both Callable references before opening a scope. It uses the Java 25 preview anySuccessfulResultOrThrow Joiner, forks the candidates and returns join's selected String. Main's first candidate throws through a finally that opens failurePath; the second waits for that signal before supplying fallback. The signal establishes that the failing body reached its abrupt-exit path, not that the framework has already processed its completion. The try-with-resources boundary closes before select returns to its caller, accounting for remaining child lifetimes even after a successful result has been selected.

| Candidate outcomes | This first-success policy |
| --- | --- |
| Failure and success | Return the successful value |
| Two successes | Select one permitted successful outcome; no fixed winner asserted |
| Two failures | Throw FailedException with one actual failure cause |
| Selected success while another child remains active | Request cancellation and account for child termination during closure |

If cancellation already occurred before a later fork can start work, that subtask need not execute its body. Do not require a side effect from every forked candidate. A peer ignoring interruption can still delay close, and a timeout cannot manufacture its cleanup.

Compile/run with the same `--enable-preview --release 25` / `--enable-preview` flags as the earlier scope examples. This is a preview-specific spelling of the stable ownership question: which result policy justifies ending the parent's work, and who accounts for the children that remain? ## Context and external resources remain explicit

The supported scope mechanism captures scoped bindings when opening and permits controlled child inheritance under its lifetime rules. Keep values immutable where practical: the binding does not freeze an object.

Each child must release its own acquired permits/files/connections. The scope does not infer application resource ownership, and an interrupted acquire must not be followed by an extra release. It also creates no remote transaction: if one child already wrote externally, another's failure cannot establish that write never happened. Compensation/idempotency belong to the operation's domain contract.

CompletableFuture.allOf represents aggregate result completion without automatically owning child threads or cancelling siblings. A structured scope adds owner/lifetime and outcome constraints. Both still require operation-specific resource and failure policies.

## Exercise and complete reference solution

Create two children where one fails only after its interruptible sibling enters. Preserve the failure cause and demonstrate sibling cleanup before returning. `StructuredFailureLesson` is the complete solution. Explain started versus cleaned, and why the catch is outside try-with-resources.

For a resource extension, place acquire before each release-owning finally and keep the permit invariant separate from the child-termination observation. Replacing the interruptible wait with cancellation-ignoring work changes the cleanup/close behavior; structure cannot provide unsafe forced termination.

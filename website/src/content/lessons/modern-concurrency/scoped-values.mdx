## A faraway method needs context from its caller

The ThreadLocal chapter began with `ContextParametersLesson`: report forwards a request identifier to format. Explicit parameters keep this dependency visible. When many intermediate methods only forward context, a bounded implicit parameter can avoid repetitive plumbing while retaining a clear entry/exit lifetime.

ScopedValue binds an accessible key to a value during the dynamic execution of an action and methods it calls. It is a final API in Java 25. This lesson needs no preview flags. Its basic call-scope mechanism does not require creating any new thread.

## Trace a binding through two ordinary method calls

<JavaExample file="modern/ScopedValuesDemo.java" output={"false\nrequest-42\nfalse"} />

REQUEST is a key, not one globally assigned request string. Before the action, isBound is false for the current thread. Where(REQUEST, "request-42").run invokes report inside a binding. Report calls format without a forwarding parameter, and format reads REQUEST.get. Both calls execute within the action's dynamic scope.

When the action completes, REQUEST is unbound again. Normal and exceptional exits restore the earlier association automatically; there is no matching set/remove convention for the application to remember. Get outside a binding needs an explicit policy, such as isBound or another documented retrieval method.

## Scope, nesting and exceptional restoration

<JavaExample file="modern/ScopedNestingLesson.java" output={"outer\ninner\nouter\nbound=false"} />

The outer action sees outer. A nested where binds the same key to inner and then throws. Exiting that inner dynamic scope restores outer before the surrounding catch runs. Exiting the outer boundary leaves the key unbound.

This resembles an implicit method parameter: access follows execution within the dynamic call scope. It is not automatic capture of every ambient value into a lambda object. Ordinary lexical variable capture and a dynamic context binding are different mechanisms.

## Immutable binding and data ownership

The association cannot be assigned a different value while inside that binding. A referenced object can still be mutable. Share immutable context where practical, or synchronize access to a deliberately mutable value. An immutable association is not deep immutability.

Code that holds the key can read its bound value. Keep that key accessible only to the intended authority, often a private static final field. Making every key globally accessible weakens that access boundary. Neither scoped values nor ThreadLocal should invisibly decide a security-sensitive operation without a clear validated contract.

<span id="threadlocal-lifetime-and-retained-state"></span>
## Compare ThreadLocal and structured inheritance

ThreadLocal can hold independently mutable per-thread state and requires deliberate restoration/removal for task context on reused workers. Its weak map keys do not guarantee prompt value cleanup. Scoped values fit bounded one-way transmission to callees; they do not mechanically replace all mutable caches or explicit method parameters.

An arbitrary executor task or manually created thread does not inherit a binding merely because its lambda was created inside the action. In the documented Java 25 structured-scope mechanism, bindings are captured when the scope opens and inherited by its children within the required lifetime. The next chapter teaches that preview task-scope API independently. Forking outside its supported binding/lifetime structure can fail structure checks.

## Exercise and complete reference solution

Bind outer, enter inner, throw, catch inside outer and verify restoration before final unbinding. `ScopedNestingLesson` is the complete solution. Explain which method calls are inside each dynamic action and why the binding is restored without a finally/remove written by the caller.

If an asynchronous callback needs context, first identify its owner and lifetime. Do not assume the callback captured the dynamic binding. Retaining only a small immutable context value also avoids accidentally keeping an entire request graph alive.

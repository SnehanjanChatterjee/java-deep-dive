## A task can fail after submission succeeds

A submitted task has two separate events: the service accepts its work, then the computation selects an outcome. **Exceptional completion** means the computation finished by throwing rather than producing its normal value. Its Future preserves that failed outcome for the caller to observe later.

Suppose a Callable calculating a score throws IllegalArgumentException for invalid input. Future.get reports an **ExecutionException**, a wrapper whose cause is that original task failure. The owner can inspect the cause, propagate it with context, or apply a deliberate recovery rule. An arbitrary replacement score would hide the failed calculation.

The program below first observes that failed result, then submits a healthy calculation to the same service. Follow acceptance → task failure → Future failure → get's cause before comparing execute, rejected submissions or multi-task failure policies. A try/catch surrounding only submit cannot observe a task exception reported later through this Future.

## Execute and submit expose failures differently

An uncaught exception from a Runnable passed directly to execute can reach the worker's uncaught-exception handler. Submit normally uses a FutureTask wrapper that catches the task's failure and records it for get. Ignoring that handle can make a failed task look quiet. Replacing submit with execute changes the observation channel; it is not a generic repair for missing error handling.

A worker's termination, a latch reaching zero, and a successful computation are different facts. CountDown in finally can signal failure as well as success. A caller must validate results before combining them.

## Distinguish rejection from failure inside accepted work

| Point | What can fail | Who observes it |
| --- | --- | --- |
| Submission | Rejection before normal acceptance | Submitting caller, according to the executor's policy |
| Callable or Future-wrapped Runnable body | Computation throws | Future.get reports ExecutionException with its cause |
| Plain execute Runnable body | Uncaught task failure escapes that execution | Caller if invoked inline; otherwise the facility's hooks/worker uncaught policy |
| Owner waiting in get | Owner is interrupted | That waiting caller receives InterruptedException |

A successful submit return establishes a handle, not a successful computation. A task's InterruptedException captured as an ExecutionException cause is also distinct from interruption of the caller doing get. Preserve that cause so the owner can decide what failed.

A submitted task's failure is normally captured by its Future wrapper, so an uncaught-exception handler alone is not a complete failure-observation strategy. Keeping every Future but never retrieving or otherwise observing its failure is another form of losing errors. For several independent tasks, define whether to inspect all outcomes, cancel remaining work after a selected failure, or collect partial results. A latch countdown supplies none of these domain policies. [Future outcome contract](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Future.html)

## Combine admission, completion and failure deliberately

The next example combines already familiar permits and completion signals with a **failure holder**, one safely shared cell initially containing null. AtomicReference supplies an indivisible compareAndSet operation: install this failure only if the cell is still null. It records one cause without overwriting an earlier one. Each worker owns an independent result slot. A semaphore bounds the illustrated resource region; release occurs only after acquire succeeds. An outer finally counts termination even when the worker is interrupted. Main awaits the signals, checks the failure holder, then combines the slots.

AtomicReference here is one safely shared failure cell. compareAndSet from null records a first failure without replacing an earlier one; the later atomics chapter develops this conditional-update primitive. That holder is for outcome reporting, while the successful latch await publishes ordinary slot writes. Neither responsibility should be inferred from the other.

The program's finite resource work and interruptible wait permit explicit interruption/join cleanup. These assumptions do not establish a bounded termination promise for arbitrary callbacks. Futures often package success/failure more directly than a separate latch and holder; understanding the separate channels explains what the abstraction is doing.

## Exercise and complete solution

Make a submitted task fail with a meaningful cause, observe the cause, and still release its owned executor. `ExecutorFailureLesson` is the complete solution. A catch that returns zero without a domain rule would fabricate a valid score. A catch that throws only the message would lose the causal chain.

For several tasks, retain each handle and choose a policy: wait for every outcome, or on one failure request cancellation of related work and then account for cleanup. The Future cancellation chapter implements that distinction. Merely leaving a result list half read does not stop the other tasks.

## Keep the task while changing how it executes

An **executor** is an object to which a caller gives work for execution. Its purpose is to separate the task description from managing Thread lifetimes. Instead of constructing and starting a Thread for every activity, the caller submits a task through the execution facility's contract.

The Executor interface accepts Runnable work. **ExecutorService** adds result-bearing submission and service-lifetime operations, including shutdown. A service can use reusable **workers**, threads that execute accepted tasks; the particular implementation determines that execution policy. The broader Executor contract even permits invoking work on the caller itself.

To return a value, describe work as a **Callable**: its call method produces a result and can declare checked exceptions. The service's submit method returns a **Future**, a handle representing the task's eventual outcome. That outcome may still be pending, may become a value, or may fail or be cancelled. The handle is available before the answer necessarily is.

Follow three separate objects in the first program: a Callable multiplying 21 by two, the one-worker service that invokes it, and the Future through which main obtains 42. Calling get on that Future waits if necessary. Submission lets the caller continue independently; result retrieval is the explicit point where this main chooses to wait.

1. The service owns one worker, which it can reuse for later submissions.
2. The Callable describes multiplying 21 by two. Describing it does not execute it.
3. Submit accepts the description and returns a Future. Submission and completion are separate events.
4. Get returns the successful value, waiting if it is still pending. This main thread can therefore block even though the computation is asynchronous to submission.
5. Finally calls shutdown on the service this method created, including when get fails or the owner is interrupted.

The completed task's actions are published through successful Future.get. As with join, result retrieval supplies a completion boundary. Neither get nor join reconstructs an update lost by an incorrectly shared algorithm inside the task.

## Match submitted behavior to its result shape

| Submission | Behavior contract | Successful Future result |
| --- | --- | --- |
| submit(Runnable) | `void run()` | null |
| submit(Runnable, suppliedResult) | `void run()` | The supplied result after successful completion |
| `submit(Callable<T>)` | `T call()` | The value returned by call |

A Runnable can still mutate application state or fail; void only describes its method's return type. A Callable can declare checked exceptions and return a value. Neither interface schedules itself. Calling `call()` directly is legal and runs on the caller, just as calling run directly does. Passing behavior to submit is the separate scheduling step.

The Future returned by submit is a result handle, not the worker Thread. Getting null from a successfully submitted Runnable does not mean the task never executed. Getting a supplied object does not mean the task created that object. Completion and the result type must be interpreted together. ## Know which outcome get reports

A successful get returns the value. ExecutionException means the task threw; its cause is the original failure. CancellationException means the handle was cancelled. InterruptedException means the **waiting caller** was interrupted. A timed get can throw TimeoutException without changing the underlying task. The next chapters work through these outcomes separately.

`execute` accepts a Runnable and has no result handle. `submit` wraps work so failures can be observed through its Future. Discarding that Future can discard the only intended failure observation path; a lack of an exception on the submitting thread does not establish task success.

## Own the service lifetime

`shutdown` stops accepting new submissions while allowing accepted work to finish. It returns without waiting for all workers. `awaitTermination` can then wait with a chosen bound. `shutdownNow` requests interruption and returns queued work that never commenced; it does not safely kill arbitrary code. A caller using a shared service supplied by another owner should not shut it down as if it had created it.

In this tiny successful program get observes its only result before normal shutdown. A real service needs the failure, cancellation and termination policy developed next. Avoid creating a new pool for each request; define an owner with the appropriate lifetime.

## Executor contracts and ownership

An Executor separates task submission from thread creation. ExecutorService adds lifecycle and result-bearing task operations. Runnable models work without a result; Callable returns a value and can throw checked exceptions. A Future represents a pending computation, not a promise that the task has started or that cancellation can forcibly stop it.

Thread-pool design includes worker count, queue capacity, rejection policy, task duration and downstream limits. An unbounded queue can hide overload until memory pressure grows. A caller waiting on a Future may still be blocked even though task execution is asynchronous.

<span id="mechanics-and-tradeoffs"></span>
## Capacity and completion policies

CompletableFuture distinguishes transformation from flattening: thenApply wraps a function result, while thenCompose chains a function that already returns a future. allOf represents combined completion but does not collect typed results automatically. Failure propagation must be designed using appropriate completion handlers rather than silently replacing every failure with an arbitrary default.

Timeouts bound waiting but do not necessarily stop underlying work. CompletableFuture cancellation does not provide the same interrupt behavior as every ExecutorService Future implementation. CPU-bound pools, blocking workloads and nested task dependencies have different starvation risks. Preserve context and ownership explicitly across asynchronous boundaries.

### ThreadPoolExecutor admission order

For an ordinary running pool, submission first tries to create a worker if fewer than corePoolSize workers exist. Otherwise it tries to queue the task. Only when queuing cannot accept it does the executor try to grow toward maximumPoolSize. If that also fails, it rejects the task. Shutdown races require additional state rechecks; the simplified decision diagram expresses capacity policy, not the entire source implementation.

<Diagram client:visible definition={"flowchart TD\n S[Task submitted to running pool] --> C{Below core workers?}\n C -->|yes| W[Try new worker]\n C -->|no| Q{Queue accepts?}\n Q -->|yes| E[Enqueue and recheck pool state]\n Q -->|no| M{Below maximum workers?}\n M -->|yes| W\n M -->|no| R[Reject]\n W --> F{Worker creation succeeds?}\n F -->|no| R\n F -->|yes| X[Execute task]"} caption={"Queue admission normally precedes growth beyond core size. With core 1, max 2 and a queue of capacity 1: the first blocked task occupies the core worker, the second queues, the third starts the second worker, and the fourth is rejected. ExecutorSaturationLab coordinates both workers with latches so the demonstration does not depend on arbitrary sleeps.

### Rejection policy is externally visible behavior

| Policy | Behavior | Risk to explain |
| --- | --- | --- |
| AbortPolicy | Throws RejectedExecutionException | Caller must handle refusal |
| CallerRunsPolicy | Submitting caller executes task if pool is not shut down | Adds caller latency; can run work on an unsuitable thread |
| DiscardPolicy | Silently discards | Lost work; a submit Future can remain incomplete |
| DiscardOldestPolicy | Drops queued oldest and retries when appropriate | Breaks queued-work expectations; poor fit for some queues |

Prefer explicit failure to accidental silent loss. Fixed-thread-pool factory executors use an unbounded work queue; a bounded worker count alone is not a bound on accepted work. Cached-thread pools can grow many workers. Define an overall in-flight-work budget, not just a pool name.

### execute, submit and Future failures

An exception escaping a Runnable passed to execute can reach the worker thread's uncaught-exception handler. submit normally wraps work in a FutureTask, which captures the failure and exposes it through ExecutionException from get. Ignoring that Future can hide failures. `get(timeout, unit)` times out the caller's wait; it does not by itself cancel the operation. `cancel(true)` requests interruption when the implementation owns a running thread, but the task must cooperate. Future.get can also throw CancellationException for cancellation.

`shutdown` refuses new work while allowing accepted work to complete. `awaitTermination` waits for termination after shutdown. `shutdownNow` requests interruption and returns queued tasks that never commenced; it does not forcibly kill workers or guarantee every returned Future is completed/cancelled. On an interrupted shutdown wait, request cancellation, preserve interruption and give cleanup ownership a clear boundary.

### CompletionStage operators by responsibility

| Operation | Purpose |
| --- | --- |
| thenApply | Transform a successful value |
| thenCompose | Chain a dependent stage without nesting |
| thenCombine | Combine two successful independent results |
| allOf | Represent completion of all supplied futures, without typed result collection |
| exceptionally | Recover from exceptional completion |
| handle | Map either success or failure into a new result |
| whenComplete | Observe either outcome while normally preserving it; observer failure can affect the dependent stage |

Non-async continuations may run in a completing thread or immediately in the attaching caller when the source is already complete. Async methods use their configured/default executor; pass one when ownership and capacity matter. `join` reports CompletionException and is not the interruptible checked-exception equivalent of get. CompletableFuture.cancel treats cancellation as exceptional completion and does not interrupt its underlying computation through the mayInterrupt flag. `orTimeout` (9+) completes the future exceptionally but does not automatically stop remote or background work.

### Fork/join and dependency starvation

ForkJoinPool uses work-stealing and supports divide-and-conquer tasks; it is not a magic fix for blocking dependencies. A single worker that submits another task to its own queue and waits for it can deadlock progress. RecursiveTask algorithms need a sequential threshold and an associative combination strategy. Pool scheduling policy, completion dependencies and scarce external resources must be reasoned about together.

<span id="common-mistakes"></span>
## Task ownership mistakes

Do not create a thread pool per request, block a single-worker pool while waiting for work queued to that same pool, or assume timeout means cancellation succeeded. Async suffixes may use a common pool unless an executor is supplied.

<span id="exercises-and-interview-questions"></span>
## Executor interview practice

### How do thenApply and thenCompose differ?

<details>
<summary>Explanation</summary>

thenApply transforms T into U. If U itself is a CompletableFuture, the result is nested. thenCompose accepts a function returning a CompletionStage&lt;U&gt; and exposes a flattened future for the dependent computation. Choose based on the function's return type, not whether its body seems asynchronous.

</details>

### Additional interview questions

<details>
<summary>Why might increasing maximumPoolSize have no effect?</summary>

With an accepting unbounded queue, submissions beyond the core size keep queuing instead of triggering extra workers. Queue admission precedes growth beyond core size. Choose worker and queue bounds together.

</details>

<details>
<summary>Why can submit hide an exception if its returned Future is ignored?</summary>

The task wrapper records the exception as exceptional completion rather than necessarily letting it reach an uncaught-exception handler. A result/failure-consumption policy is part of task ownership. Ignoring the Future can leave failures unreported.

</details>

<details>
<summary>Does a CompletableFuture timeout stop the remote request?</summary>

Not automatically. Completing a stage exceptionally or timing out a wait does not prove the underlying operation was cancelled or that a remote side effect never happened. Coordinate operation-specific cancellation and overall deadlines explicitly.

</details>

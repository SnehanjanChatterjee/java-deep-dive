## Keep the task while changing how it executes

Creating a Thread for every activity couples the task description to execution management. An Executor accepts work through a common interface. Its implementation decides whether to use an existing worker, a new execution, or even the calling thread. ExecutorService adds result-bearing submission and lifecycle management.

Runnable describes work without a returned value. Callable describes work returning a value and may throw a checked exception. A Future is a handle through which the caller later observes that computation's result or failure. Receiving the handle does not establish that the task has started.

## A first submitted result

<JavaExample file="ExecutorBasicsLesson.java" output={"42"} />

1. The service owns one worker, which it can reuse for later submissions.
2. The Callable describes multiplying 21 by two. Describing it does not execute it.
3. Submit accepts the description and returns a Future. Submission and completion are separate events.
4. Get returns the successful value, waiting if it is still pending. This main thread can therefore block even though the computation is asynchronous to submission.
5. Finally calls shutdown on the service this method created, including when get fails or the owner is interrupted.

The completed task's actions are published through successful Future.get. As with join, result retrieval supplies a completion boundary. Neither get nor join reconstructs an update lost by an incorrectly shared algorithm inside the task.

## Know which outcome get reports

A successful get returns the value. ExecutionException means the task threw; its cause is the original failure. CancellationException means the handle was cancelled. InterruptedException means the **waiting caller** was interrupted. A timed get can throw TimeoutException without changing the underlying task. The next chapters work through these outcomes separately.

`execute` accepts a Runnable and has no result handle. `submit` wraps work so failures can be observed through its Future. Discarding that Future can discard the only intended failure observation path; a lack of an exception on the submitting thread does not establish task success.

## Own the service lifetime

`shutdown` stops accepting new submissions while allowing accepted work to finish. It returns without waiting for all workers. `awaitTermination` can then wait with a chosen bound. `shutdownNow` requests interruption and returns queued work that never commenced; it does not safely kill arbitrary code. A caller using a shared service supplied by another owner should not shut it down as if it had created it.

In this tiny successful program get observes its only result before normal shutdown. A real service needs the failure, cancellation and termination policy developed next. Avoid creating a new pool for each request; define an owner with the appropriate lifetime.

## Continue from one result to coordination and graphs

The next lessons develop task failures, cancellation and pool capacity from this submitted-result model. Completion graphs follow once each Future outcome is understood. A counter shared by several workers additionally needs the atomic-update protocol taught in the atomics chapter; completion waiting alone does not supply that update.

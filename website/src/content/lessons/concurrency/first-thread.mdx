## Give an execution some work

A `Runnable` is an object describing an action with no arguments and no returned result. Its `run()` method is the action. A `Thread` object represents one thread lifetime and provides operations such as start and join. Constructing that object does not create a running execution. Calling its `start()` requests the separate execution that invokes the action; calling `run()` directly invokes an ordinary method on the caller's execution.

Keep three things distinct: the task description, the Thread object used to control one lifetime, and the execution that runs statements. The same Runnable can be called directly by main, passed to a new Thread, or later submitted to an executor. Each choice gives a different owner/execution arrangement without changing the Runnable interface.

The lambda below creates one Runnable. It prints the name of the thread **currently executing** the action. Creating the lambda does not invoke it.

Compile with `javac ThreadBasicsDemo.java`, then run `java ThreadBasicsDemo`. Follow the statements in order:

1. `task` holds the action. `Thread.currentThread()` is evaluated when the action runs, not when the lambda is created.
2. `task.run()` is an ordinary method call. Main executes the action and prints `task on main` before the call returns.
3. `new Thread(task, "lesson-worker")` constructs an unstarted Thread object and attaches the action and diagnostic name. The task has not run a second time yet.
4. `worker.start()` schedules a new execution. That execution invokes the action. Main can continue independently after start returns.
5. `worker.join()` waits until this worker terminates. It does not run the worker's task on main.
6. After a successful join, `isAlive()` is false and the final print follows the worker's print.

The output is deterministic here because the direct call finishes before start and the last print follows join. A Thread can be started at most once. Calling start again, including after termination, throws `IllegalThreadStateException`. Reuse a task description through a new execution rather than trying to restart a terminated Thread object.

The program above calls `task.run()` directly. Calling `worker.run()` directly is also an ordinary call on the current execution; it does not start that Thread object. Compare the two choices below. The selector changes both the highlighted code and the state being explained.

## Work out which output orders are legal

Now imagine main prints `main continues` immediately after start and **before** join. The worker's print and that new main print can appear in either order. Neither source placement in separate methods nor the worker's name establishes an order between them. The final print still follows the worker's termination.

### Distinguish source order from execution order

`start()` can return before the task starts, or the task can finish before main next runs. A drawing must choose one schedule to display; that choice does not prohibit the other legal schedule. The named-class and anonymous-Runnable forms in the following construction lesson implement the same separation without requiring the lambda syntax to carry the whole explanation.

| Relationship | Required order |
| --- | --- |
| Two statements executed by main | Main's program order |
| Main's start request and worker's task | Start precedes the started execution's actions |
| Direct task call and later start in main | Direct call finishes first |
| Two statements executed by the same worker | Worker preserves their program-order behavior |
| Main's print after start versus worker's first print | Either may be observed first |
| Worker completion and main after successful join | Worker completes first |

`Thread.sleep` can delay the current thread but cannot establish that another thread has started or finished. A demonstration can use sleep to represent waiting; a correctness assertion must use a real completion or coordination contract.

## A returned method and a finished worker are different

Returning from start means the start request returned, not that the worker completed. If a worker throws an uncaught exception, it can terminate without producing a successful application result. Join establishes termination, not task success. Result-bearing tasks and explicit failure observation are introduced after these basic execution rules.

`join` declares `InterruptedException`: the waiting caller can itself receive a cancellation request. This small main propagates it. The lifecycle lesson teaches how an owner coordinates cancellation and cleanup rather than treating every exception as a result.

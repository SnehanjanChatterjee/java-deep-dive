## A second operation needs the first result

A Future lets a caller wait for a value. Suppose the caller needs a user ID, then a score for that ID, then a label combined with the score. Repeated get calls can describe these dependencies by blocking a caller. CompletableFuture can instead record actions to run when their inputs complete.

First separate dependency shape from scheduling. An already completed source is useful for learning the shape without adding worker timing. A stage can complete with a value or failure; a new dependent stage has its own outcome.

## Transform, flatten and combine

<JavaExample file="CompletionStepsLesson.java" output={"42\n43\n43\nscore=43"} />

thenApply takes the successful 21 and returns the value 42. The dependent future therefore contains an Integer. Score is different: it already returns a future. thenApply(score) produces `CompletableFuture<CompletableFuture<Integer>>`; retrieving the outer result yields another future. thenCompose(score) connects to that inner stage, exposing one future of Integer. Their numeric answers match, but their result shapes differ.

The label and score are independent inputs to thenCombine. Its function runs once both successful inputs are available. None of this example creates a worker: the values were completed already, letting the caller execute suitable non-async actions immediately.

## Add an explicitly owned executor

<JavaExample file="CompletableFutureLab.java" output={"score=43\nrecovered\ntrue"} />

Now userId is obtained on the supplied executor. thenCompose starts dependent score work; label work can proceed independently. thenCombine connects the two successful results. Main waits on the final result, while workers avoid waiting for siblings queued to their own constrained pool. Finally owns executor shutdown, bounded termination waiting and interruption preservation.

## Watch independent results become usable together

The complete program above gives the combination two inputs: a score of 43 and the label score. The score still depends on its userId stage, while the score and label can complete in either relative order. Select either order and follow their value copies into the same dependent action.

One completed input is insufficient for this successful thenCombine operation. Once both are available, the function has the values it needs; it must execute and return before the result future is complete. The named result variable in the visual is an equivalent way to spell the complete program's combined expression.

The arrows represent value dependencies, not ownership of dedicated threads. This non-async continuation may execute in a permitted completing or attaching caller; it is not guaranteed a fresh worker. Its input futures retain their values when copies flow to the dependent action. The [CompletableFuture execution policy](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/util/concurrent/CompletableFuture.html) governs that thread choice independently of the dependency graph.

## Choose where a continuation runs

A non-async action may run in a completing thread or immediately in the attaching caller if the source is complete. Do not hold an application lock while attaching arbitrary behavior that can synchronously reenter application code. Async methods use their supplied/default executor; an Async suffix does not create an isolated pool or cancellation owner.

Get is an interruptible wait reporting checked ExecutionException. Join reports CompletionException for exceptional completion and is not get's checked interruption protocol. Neither should block a worker that must execute its own queued dependency.

## Recovery affects one branch

A CompletableFuture selects one completion outcome. Competing complete, completeExceptionally and cancel attempts do not each install a new history; only one wins. Dependent branches then interpret that source while selecting their own outcomes.

Handle maps either success or failure into a new outcome. Exceptionally maps exceptional completion to an alternative. whenComplete primarily observes, but a throwing observer can affect its dependent stage: an observer throwing after a successful source makes that dependent stage fail. A legitimate recovery needs a domain rule; an arbitrary zero can hide a failed calculation.

<JavaExample file="CompletionOutcomeLesson.java" output={"fallback\nsource failed=true\nobserved cause=source\nall still waiting=true\nall cause=source"} />

The source fails explicitly. One dependent branch recovers to fallback, leaving the source failed for other readers. When an already-failed source's observer also throws, the source failure remains the propagated primary cause under the documented policy. AllOf remains pending until its other input completes, then reports failure. This model does not depend on an accidental executor schedule.

## Aggregate completion is not automatic task ownership

AllOf completes after all its inputs complete and yields Void, not a typed result list. A failed input does not automatically cancel siblings. AnyOf selects one completion, which might be a failure rather than the first successful answer.

CompletableFuture.cancel selects exceptional cancellation without interrupting the underlying computation through mayInterruptIfRunning. The Java 9+ orTimeout and completeOnTimeout helpers change completion state; they do not automatically stop a remote action. One graph's result being complete does not establish every operation or cleanup ended. The structured-concurrency lesson later adds an owned child lifetime.

## Define empty aggregates and invalid composition

<JavaExample file="CompletionEdgeLesson.java" output={"empty all done=true\nempty all value=null\nempty any done=false\nnull composition=NullPointerException"} />

AllOf with no inputs has no unfinished obligation, so it is already successfully complete with null as its Void result. AnyOf with no inputs has no candidate completion to select, so it remains incomplete. The program inspects its state and deliberately does not join that empty anyOf.

A thenCompose function must return a CompletionStage. Returning null does not mean an already completed stage containing a null value: it makes the dependent stage fail. In contrast, a suitable value-returning transformation can legitimately produce a null result where the application contract permits it. Keep the **stage reference** separate from the **value held by a stage**.

**Failure exercise:** draw two dependents from one failed source, one recovering and one propagating. Recovery changes the new branch's result; it cannot rewrite what the other dependent observed from the shared source. The complete outcome example above and this edge example isolate those decisions without executor timing.

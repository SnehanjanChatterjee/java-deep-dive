## Readers need consistency but need not exclude each other

A catalog is updated occasionally and copied frequently. Two threads copying it do not change its state, so they may share read ownership. An update needs exclusive write ownership so no reader copies a partially changed representation. ReentrantReadWriteLock represents those two modes under one coordination protocol.

This can help sufficiently substantial read-dominated work. It can also add overhead or delay writers. First verify that the read path actually does not mutate the protected invariant; an access-order cache get can relink recency and therefore is not read-only.

Put validates key/value, acquires the write lock, mutates the TreeMap and unlocks in finally. Snapshot acquires the read lock, copies the map while writers are excluded, then returns an unmodifiable copy. Concurrent snapshot calls can hold read locks together. A writer waits until readers release; another reader cannot enter during active write ownership.

The earlier snapshot contains only java even after the catalog gains jvm. That is because it owns a separate map, not because a read lock remains attached to the returned value. Returning the mutable internal map would let callers bypass the whole protocol after unlock. UnmodifiableMap alone would also be insufficient if it wrapped the same mutable backing map; copying is essential here.

## Retain observation while downgrading

<JavaExample file="ReadWriteDowngradeLesson.java" output={"value=42\ncaller released=true"} />

UpdateAndRead first owns write mode, changes the value, and acquires read mode **before** releasing write mode. After the write unlock, the caller retains read ownership, so another writer cannot insert a change before the returned observation is copied. The second finally releases the read hold. The diagnostic method then confirms that this caller retains neither mode.

Releasing write first and acquiring read afterward would leave an interval in which another writer can change the value. That alternate program may still be correct under a contract permitting a refreshed value, but it does not preserve the just-written observation. Downgrading closes that specific gap.

The example is a complete small ownership trace rather than a performance test or an invitation to keep read locks around slow callbacks. Its returned primitive remains independently usable after unlock. For mutable returned objects, the original snapshot/ownership questions still apply. [ReentrantReadWriteLock downgrading pattern](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/locks/ReentrantReadWriteLock.html)

## Reentrancy, downgrading and upgrade hazards

An owning writer can acquire the read lock before releasing the write lock, downgrading while retaining protected observation. That supports a transition from mutation to a read-only phase without an unprotected gap.

Holding a read lock and waiting for write ownership is an upgrade hazard. A competing reader may do the same, leaving both retaining reads that prevent a writer. Release/reacquire with a fresh predicate check or design another atomic transition. Never assume read ownership reserves the state until an eventual write acquisition.

Fair construction changes documented lock acquisition policy under contention; it is not operating-system fairness, a latency SLA or protection from unrelated lock cycles. Each method still needs the correct interruptible/timed acquisition policy and finally release.

## Exercise and complete reference solution

Implement a sorted catalog returning stable snapshots without exposing internal mutable storage. `ReadWriteCatalog` is the complete solution. Explain why both mutation and snapshot copying follow the same read/write protocol and why a copied snapshot no longer needs its lock.

If the catalog contained mutable values, copying references would not freeze their contents. The current String values are immutable. A deeper mutable model would need immutable values, deep snapshots or another ownership policy. Before selecting this lock for performance, measure the actual critical-section size and read/write distribution.

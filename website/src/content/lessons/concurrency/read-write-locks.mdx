## Readers need consistency but need not exclude each other

A **read/write lock** has two coordinated ownership modes. Several callers may hold read mode together while observing protected state. Write mode excludes competing readers and writers while one caller changes that state. ReentrantReadWriteLock provides the paired modes under one protocol, rather than as two unrelated locks.

Consider a catalog copied frequently and updated occasionally. Copying its entries is read-only work, so several copies can proceed together. Inserting a new entry requires exclusive write ownership so no copy observes a partially changed representation. Every catalog access must still use its appropriate mode.

The returned **snapshot** needs a separate ownership decision. A lock protects the copying interval; a separately allocated map keeps the returned membership stable after that lock is released. The first program returns an unmodifiable copy with immutable String values, making both boundaries visible.

Sharing read ownership can help sufficiently substantial read-dominated work, but it also adds overhead and can delay writers. First learn the copied-catalog contract before choosing this mechanism as a performance optimization.

Returning the mutable internal map would let callers bypass the whole protocol after unlock. UnmodifiableMap alone would also be insufficient if it wrapped the same mutable backing map; copying is essential here.

Classify a read by its effect, rather than its method name. An access-order cache get can relink recency and therefore mutate its representation. Such an operation does not qualify for shared read ownership merely because it returns a value.

## Retain observation while downgrading

**Downgrading** means moving from exclusive write ownership to shared read ownership while continuously retaining protection. Acquire read mode before releasing write mode, so another writer has no intervening opportunity to replace the value being observed.

<JavaExample file="ReadWriteDowngradeLesson.java" output={"value=42\ncaller released=true"} />

UpdateAndRead first owns write mode, changes the value, and acquires read mode **before** releasing write mode. After the write unlock, the caller retains read ownership, so another writer cannot insert a change before the returned observation is copied. The second finally releases the read hold. The diagnostic method then confirms that this caller retains neither mode.

Releasing write first and acquiring read afterward would leave an interval in which another writer can change the value. That alternate program may still be correct under a contract permitting a refreshed value, but it does not preserve the just-written observation. Downgrading closes that specific gap.

The example is a complete small ownership trace rather than a performance test or an invitation to keep read locks around slow callbacks. Its returned primitive remains independently usable after unlock. For mutable returned objects, the original snapshot/ownership questions still apply. ## Reentrancy, downgrading and upgrade hazards

An owning writer can acquire the read lock before releasing the write lock, downgrading while retaining protected observation. That supports a transition from mutation to a read-only phase without an unprotected gap.

An **upgrade** would move from read-only ownership to write ownership. ReentrantReadWriteLock does not support acquiring write mode while retaining only read ownership; even that caller's own read hold prevents the write acquisition. Competing readers attempting the same thing can leave both waiting while retaining their reads. Release/reacquire with a fresh predicate check or design another atomic transition. Read ownership does not reserve the state until an eventual write acquisition.

Fair construction changes documented lock acquisition policy under contention; it is not operating-system fairness, a fixed latency guarantee or protection from unrelated lock cycles. Each method still needs the correct interruptible/timed acquisition policy and finally release.

## No slot exists between producer and consumer

A **SynchronousQueue** transfers an element by matching one producer's insertion with another thread's removal. This matched transfer is a **handoff**. Either participant can arrive first and wait, but acceptance requires the peer operation; there is no intermediate stored queue slot.

This is useful when a producer should meet a receiving consumer instead of leaving accepted work in a buffer. By comparison, an ArrayBlockingQueue of capacity one can accept one stored item while no consumer is taking it. Zero-buffer handoff and capacity-one storage therefore express different admission policies.

The ordinary program first tries to offer a value with nobody receiving, then starts a consumer and performs a timed offer that can match its take. Follow the insertion result separately from the consumer's later processing. A successful transfer does not acknowledge that later processing completed.

Although it implements BlockingQueue, inspection describes no stored collection: size and remainingCapacity are always zero. Participants can still be waiting with pending operations, and those waits can retain application state. Read zero as no buffered elements, rather than as no work or no waiting callers.

## Transfer does not acknowledge business processing

After take returns, the consumer may perform an expensive operation or fail. The producer's successful offer does not establish that this later processing succeeded. If an acknowledgement is required, model it separately through a result handle, reply channel or domain-specific protocol.

The handoff copies an object reference and supplies the documented publication relationship for actions before insertion and after access/removal. It does not clone mutable data or prevent the sender retaining an alias. The application still decides which participant may mutate the payload after transfer.

Interruption and timed expiry report incomplete waiting, not an invented payload. As with other BlockingQueues, null is prohibited. There is no universal close operation; finite batches, interruption or explicit terminal messages need their own ownership rules.

## Handoff changes executor admission

ThreadPoolExecutor can use a SynchronousQueue as its work queue. With no receiver ready, an offer cannot simply store the task for later. The pool then considers creating a worker up to its maximum or applying rejection policy. This is why a cached-style pool can grow workers rather than accumulate buffered tasks.

A direct handoff does not itself bound active tasks or downstream resource usage. A large maximum can still create too many platform Threads. A small maximum can reject immediately under pressure. Design the entire admission policy, not just the queue type.

Fair construction influences the order of waiting producers/consumers under the documented policy. It does not promise a fixed end-to-end processing order after transfer or reserve a processor for an awakened participant.

## Exercise and interview questions

**Can size reveal a producer waiting to transfer?** No. Size describes stored elements; this queue stores none.

**Is it equivalent to a capacity-one queue?** No. Capacity one can accept an unmatched item into storage. Zero-buffer transfer requires the peer operation.

**Does a successful put mean the consumer finished processing?** It establishes the transfer, not the result of subsequent application work.

Use the complete reference program to replace the timed offer with put. In the ordinary successful path the same value is received, but the owner loses the explicit waiting allowance. Keep an interruption/termination policy for the case where the consumer never arrives.

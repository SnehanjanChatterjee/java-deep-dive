## Split the calculation before choosing a scheduler

To sum an array, workers can accumulate into one shared counter, but then every addition needs coordination. A different design gives each task a disjoint range, computes a local sum, then combines completed results. Parallelism is possible because the data ownership and combination are explicit.

A RecursiveTask returns a value; RecursiveAction represents work without one. ForkJoinPool supplies scheduling for these related tasks. The algorithm still needs a base case, a lawful partition and a combination operation.

## Trace disjoint range sums

For `[1,2,3,4,-5]` and threshold two, range [0,5) splits at two. The left [0,2) sums one plus two. The right [2,5) splits into [2,3), sum three, and [3,5), sum minus one. Three plus two is the final five.

## Implement a recursive range sum

<JavaExample file="ForkJoinRangeSum.java" output={"5\n0"} />

Sum validates null input and a positive threshold, creates an explicitly owned pool and invokes the root. Compute loops sequentially when the range fits the threshold. Otherwise it calculates a midpoint, forks the left task, computes the right directly, joins left and combines.

Forking makes work available; it does not guarantee another worker starts it immediately. Computing one branch locally avoids creating unnecessary task handling for both halves. An empty input returns the additive identity zero. Every recursive child is smaller, so a positive threshold ensures the base case is reached.

The input array is shared read-only by contract. A final array reference does not prevent a caller from mutating its elements; keep the input stable until completion or design a snapshotting API. Each task's accumulator is local, avoiding a shared mutable total.

## Work-stealing and combination laws

On the selected OpenJDK implementation, workers have associated work queues and can steal available tasks from others. Typical local processing and stealing use different queue ends, supporting local nested work and exposing older tasks. Exact queue mechanics are implementation details. Join can involve pool-specific helping, rather than behaving exactly like an arbitrary blocking Future.get.

Useful arithmetic is O(n). With balanced splitting and leaf threshold k, the tree has roughly O(n/k) leaves. Scheduling/allocation overhead, processors and memory bandwidth limit speedup. Splitting tiny work into many tasks can cost more than it saves; threshold choice needs measurement.

The combination must match the operation. Integer-array sums into long fit the source's supported domain. Floating-point addition can vary with grouping through rounding, while subtraction is not an associative reduction. A legal task tree does not make an unlawful regrouping correct.

## Blocking, failure and ownership

A fork/join worker blocked on an unrelated socket or application lock cannot necessarily execute available work. ManagedBlocker can cooperate with pool management in suitable designs; it is not unlimited capacity or a generic I/O adapter. The common pool also serves other facilities. The source uses an owned pool and closes its lifetime after invocation; a reusable service would usually reuse an owned pool across calls.

A subtask's failure is observed through its completion/join path. ForkJoinTask cancellation does not promise interruption of running computation, and arbitrary siblings do not gain structured cancellation merely because their tasks form a recursion tree. Long-running algorithms need deliberate cancellation checks. Do not shut down the common pool as though the application alone owns it.

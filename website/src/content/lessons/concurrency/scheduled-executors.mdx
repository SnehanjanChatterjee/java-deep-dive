## A scheduled time makes work eligible

ScheduledExecutorService adds delayed and periodic execution to task submission. A relative delay determines when work becomes eligible, not a promise that it begins at that exact wall-clock instant. An occupied worker, process scheduling, GC pauses or a slow earlier task can delay actual execution.

A one-shot schedule has one result. A periodic schedule represents a continuing sequence whose successful executions do not normally complete its Future. The owner must define how cancellation, exceptional completion and executor shutdown end that sequence. Ignoring the handle can hide a failed periodic job just as ignoring a submitted Future can hide an ordinary task failure.

## Fixed rate and fixed delay answer different questions

| Policy | Next eligibility is based on | If work is slower than the requested interval |
| --- | --- | --- |
| scheduleAtFixedRate | Initial schedule plus successive period multiples | Later executions start late; one sequence does not overlap itself |
| scheduleWithFixedDelay | Completion of the previous execution plus delay | Each completion is followed by the declared delay |
| Repeated independent schedule calls | Each separately submitted delay | Overlap is possible unless another protocol prevents it |

For a nominal period of one second and a task taking 1.5 seconds, fixed rate does not create another simultaneous execution of the same periodic sequence just to meet the missed second. Fixed delay waits its delay after completion. Do not turn this reasoning example into a precise production timing guarantee; the scheduler can add further delays.

## Complete cancellation and failure example

<JavaExample file="ScheduledWorkLab.java" output={"cancelled=true\nfailed runs=1"} />

The first method waits until three invocations have reached their signal, then cancels the periodic handle. A countDown occurs inside the callback and does not itself prove that invocation has returned. It does not assert that exactly three callbacks ran: a further callback can race before cancellation is selected. It reports the cancellation result state instead of publishing an invented timing measurement. cancel(false) does not interrupt an already running invocation.

The second method increments a counter and throws on its first execution. The periodic Future becomes exceptional, get reports ExecutionException and later executions of that sequence are suppressed by contract. The method validates the cause and reports one run. It does not catch the exception and continue scheduling as if the task had succeeded.

Both methods own their executor lifetime and have bounded demonstration guards. Finally requests shutdown and waits for termination. These five-second bounds expose a broken example; they are not recommended service-level deadlines for arbitrary applications.

## Failure is part of the periodic API contract

An exception escaping a periodic invocation stops subsequent invocations of that scheduled sequence. If the application intends some failure categories to be retried on later periods, it must handle those specific failures inside the task and report them under an explicit policy. Blanket catch-and-ignore would preserve apparent activity while hiding a permanently broken operation.

A successful periodic invocation does not make Future.get return a per-tick value. Get normally keeps waiting until cancellation or failure ends the sequence. Separate monitoring/results are needed if callers require one observation per tick. A Future being done means an outcome exists, not necessarily that the background job succeeded.

## ScheduledThreadPoolExecutor storage and cancellation

ScheduledThreadPoolExecutor uses delayed work ordering with worker capacity controlled principally by corePoolSize. Its delayed queue is unbounded, so setting maximumPoolSize does not turn it into an ordinary bounded-admission ThreadPoolExecutor. Scheduling unlimited distinct tasks can still retain memory even if the workers are few.

By default a cancelled delayed task can remain queued until its delay expires. setRemoveOnCancelPolicy(true) requests prompt removal of cancelled tasks, which can matter for many long-delay tasks. This is a retention policy, not proof that a running invocation has rolled back or finished cleanup.

Shutdown behavior for delayed and periodic work is configurable. Read the selected policies when ownership moves between components; do not assume every pending task continues or every accepted one is immediately cancelled. Explicitly account for result handles and resources when shutting down.

## State sharing between executions

ScheduledThreadPoolExecutor guarantees that successive executions of one fixed-rate or fixed-delay sequence do not overlap, and provides the documented happens-before relationship from earlier to later executions. They may use different worker threads. This supports one sequence's task state under that contract; other threads concurrently reading/mutating that state still need a sharing policy.

Independently scheduled jobs can overlap. A read-modify-write shared by several jobs does not become atomic merely because the jobs were scheduled on a service with a familiar name. A one-thread scheduler serializes its executions but a blocking job can delay every other scheduled job on it.

## Interview questions and solutions

<details>
<summary>Why did a repeating job run once and then disappear?</summary>

Inspect the returned ScheduledFuture and its exceptional cause. An uncaught task exception suppresses later executions of that sequence. Adding more workers does not repair this outcome. Decide which failures should terminate the job and which can be handled and reported inside it.

</details>

<details>
<summary>Does fixed rate guarantee one start per wall-clock second?</summary>

No. It establishes a nominal period progression and eligibility. Actual execution can be delayed, and one sequence does not overlap itself to compensate for slow execution. Calendar scheduling in a time zone is a different requirement from relative periodic intervals.

</details>

<details>
<summary>Why can periodic Future.get wait forever during healthy operation?</summary>

Successful ticks do not end the sequence. The handle represents continuing scheduled work, not one result per tick. Use cancellation, failure monitoring or a separate observation channel according to the lifecycle contract.

</details>

<details>
<summary>What does the reference coding exercise establish?</summary>

ScheduledWorkLab demonstrates at least three tick signals followed by selected cancellation, and a separate failing sequence with exactly one attempted invocation. It deliberately avoids assertions about nanoseconds, exact callback order across independent jobs or rollback after cancellation.

</details>

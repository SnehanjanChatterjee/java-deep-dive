## Correct individual updates can still wait forever

**Safety** means a forbidden state does not occur, such as an invalid account balance. **Liveness** asks whether an operation can eventually make useful progress. A program can protect each update correctly yet leave its workers unable to finish.

A **deadlock** is a closed waiting dependency: each participant needs something that another participant in the cycle retains, and none can make the required next step. For two-account transfers, both balances need protection while the debit and credit occur together. That creates a need to acquire two monitors.

Now let transfer A→B acquire A then B while an opposing transfer B→A acquires B then A. If the first owns A and the second owns B, each requests what the other retains. The problem is the acquisition order, rather than arithmetic or a missing synchronized keyword.

We will draw that unsafe dependency without launching an indefinitely deadlocked program, then run the repaired transfer implementation. A stable common lock order removes this account-only cycle while preserving the protected balance update.

## Draw a wait-for graph before changing locks

A **wait-for graph** follows a waiting execution to the resource it needs, then to the execution retaining that resource. Continue following those dependencies. Returning to the starting execution exposes the cycle. The drawing below labels both the retained accounts and the next requested accounts.

Here left and right identify two account objects and their monitors. A and B identify executions. The **held** list records acquired monitors; **requested** identifies an acquisition not yet completed. For the common-order variant, the selected pair has `left.lockOrder < right.lockOrder`, so both transfer directions choose left first. Transfer direction and lock acquisition order are separate decisions.

The unsafe trace stops at the closed dependency cycle. The complete runnable solution below always uses the repaired order, so it can demonstrate opposing transfers without leaving an indefinitely deadlocked worker behind.

The classical deadlock conditions are mutual exclusion, holding resources while waiting for more, no forced resource preemption and circular wait. This framework helps identify a repair without abandoning the protected invariant. A single WAITING thread does not establish these conditions.

Each Account has a stable ordering key. Transfer chooses first/second by that key, independent of money direction, then acquires both monitors in that order. Opposing transfers therefore agree which lock comes first. Under this account-only protocol, the cycle above cannot form.

Validation rejects null and nonpositive amounts. Same-account transfer is a no-op under the declared contract. Insufficient funds returns false before mutation. AddExact computes the credited balance before debiting, so overflow preserves both original balances. The two assignments occur with both monitors held.

An individual balance getter locks its own account, but two separately obtained balances are not one atomic total during live transfers. Main joins workers before summing the final balances. A live combined total would need both locks in the same ordering protocol.

## Lock ordering has scope and preconditions

Every path acquiring these locks must obey the order. A callback that acquires another lock can introduce a larger cycle outside the account pair. Keep locked regions small and avoid unknown callbacks/slow I/O. Fair locks do not remove cycles or guarantee bounded latency.

Ordering identifiers must be stable and unambiguous. IdentityHashCode can collide and needs a tie protocol if used for ordering. This teaching example uses generated keys under a practical no-exhaustion assumption; production domains can use established immutable unique identifiers or another explicit total ordering.

## Include implicit locks in the ordering proof

An instance synchronized helper acquires its receiver's monitor even if the caller does not write an explicit synchronized block. A static synchronized helper acquires the Class monitor. If a transfer holding account A invokes a callback that acquires some registry lock, and another path holds that registry while requesting A, the larger program can recreate a cycle despite consistent ordering between account pairs.

List **all** acquisitions in a path, including callbacks, blocking I/O and task-result waits. For example, a worker holds the sole permit, starts a child needing that permit, then waits for the child. The resource cycle is parent → child completion → permit → parent, even without opposing monitor names.

**Repair exercise:** move the callback outside the acquired region when it does not require protected state, passing an immutable captured result. If it must participate atomically, extend the common protocol and reason about the new lock order. A timeout can report a stuck operation but does not create the missing worker/permit or undo external effects. ## Timed attempts, starvation and livelock

Starvation means one operation repeatedly fails to obtain service while others progress. Livelock means participants keep reacting without completing, such as two synchronized retry loops that repeatedly release and try again together.

Timed tryLock can let an operation abandon acquisition, but it must release every lock it did acquire. Aggressive opposing retries can livelock. **Backoff**, delaying or adapting retry attempts, can reduce repeated collisions; it does not supply a universal progress proof. Carry one monotonic overall budget across multiple acquisition attempts rather than granting each the full timeout again.

A timeout says what the owner stopped waiting for, not that remote effects rolled back or unrelated work terminated. Resource ownership and task lifetime still matter.

## Diagnose actual blocking evidence

Repeated thread dumps can connect a requested monitor to its owner. ThreadMXBean.findDeadlockedThreads detects supported monitor/ownable-synchronizer cycles, not every application/task/distributed dependency. A normally parked consumer awaiting work is different from a closed ownership cycle.

A single pool worker can submit a child then wait while that child is queued behind it. Similarly, a task can retain the only semaphore permit while waiting for a child needing that permit. Draw task and resource dependencies together; changing a lock timeout does not create a worker or permit.

## Exercise and complete reference solution

Describe the opposing A/B schedule, then repair every transfer with a common stable lock order. `OrderedTransferLab` is the complete solution. Explain conservation after completion, same-account behavior, insufficient funds and overflow before mutation. An intentionally deadlocked non-daemon process is unnecessary for learning the repaired algorithm.

For an investigation, repeated stacks plus ownership/cycle evidence support a deadlock hypothesis. A thread state label alone cannot distinguish ordinary waiting, starvation, lock cycles or executor capacity dependencies. The diagnostic lab later connects actual stacks and monitor identities.

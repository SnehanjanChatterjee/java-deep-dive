## A program can make progress on several activities

A **process** is a running instance of a program, with resources managed by the operating system. Starting `java` launches a Java Virtual Machine, or **JVM**, in a process. A **thread** is one ordered path of execution inside that process: it records which instruction to execute next and which method calls have not yet returned.

The application normally enters `main` on a thread already created by the runtime. If main calls `buildReport`, main's thread now executes that method. Another method call continues the same path; it does not create an additional thread.

Why introduce another path? Suppose reading a file must wait for input. That call is **blocking**: its caller cannot continue past the call until it returns. A second thread can answer a user action during the wait. The activities can make progress over overlapping lifetimes; this is **concurrency**. We will distinguish it from simultaneous execution on separate processors below.

The design question comes before the API: what can proceed independently, and what data must those activities share? Threads allow overlap, while the program remains responsible for coordinating shared changes.

## Compare process and thread boundaries

**Multiprocessing** organizes work across multiple processes; **multithreading** uses multiple threads within a process. Either arrangement can make concurrent progress on one core or run work in parallel when execution resources permit.

| Arrangement | State boundary | Communication |
| --- | --- | --- |
| Two separate java launches | Separate JVM processes with their own Java heaps and runtime state | Exchange data through an explicit mechanism such as files, pipes or sockets |
| Two threads in one JVM | Separate call stacks within the same process | Can hold references to the same Java objects |

One JVM's object reference is not automatically a usable reference in another JVM. Deliberate shared-memory mechanisms also need their own data protocol. Process separation changes the memory boundary; programs can still need coordination over shared external resources such as files. Avoid treating either design as automatically faster. [Process and thread resources](https://docs.oracle.com/javase/tutorial/essential/concurrency/procthread.html)

## Trace two stacks referring to one object

A **call stack** records one thread's unfinished method calls. Each active call has a **frame** holding its parameters, local variables and the information needed to return to its caller. Calling a method adds a frame; returning removes that call's frame.

Imagine main calls `buildReport`, which calls `readFile`. Its stack records those unfinished calls. A **worker** is an additional thread doing application work; it can have `run`, `refreshView` and `render` on its own stack. The next lesson explains the conventional run entry method. Returning from render resumes the worker's caller; it does not return into main's readFile invocation.

Local variables in these invocations belong to their own execution. A local variable containing an object reference can still point to a shared object. Two local references named `report` do not create two independent reports. Conversely, two threads can work on separate objects without sharing mutable application state at all.

This distinction will explain a counter bug later: each worker's loop index can be private while the counter object is shared. Before writing threaded code, draw which state is independently owned and which object identities cross execution boundaries.

## Concurrency and parallelism describe different things

With one available processor, a scheduler can run some of A, then some of B, then return to A. Their lifetimes overlap even though only one is executing instructions at an instant. That is concurrency through interleaving. With multiple processors, A and B can execute at the same instant; that is parallelism.

| Situation | What a second thread may accomplish | Remaining limit |
| --- | --- | --- |
| A waits for an input/output (I/O) operation | B can do independent work | The device/service still has finite capacity |
| A and B both calculate continuously | Work may use multiple processors | Thread count does not create processors |
| A and B update the same mutable object | Both can access the object | A coordination policy is required |

A context switch preserves execution state so a thread can resume later. The scheduler does not promise to switch after every source line, in creation order, or fairly enough to justify a correctness argument. Programs must not require a lucky schedule.

## Trace two executions on one processor

A machine does not need two processor cores to have two live threads. For example, one core can execute main's first statement, switch to a worker's first statement, then return to main. That is concurrent progress through overlapping lifetimes. Parallel execution additionally means work runs at the same time on different execution resources.

| Chosen time slice | Execution | Statement completed |
| --- | --- | --- |
| 1 | Main | Start worker |
| 2 | Worker | Calculate a local intermediate value |
| 3 | Main | Perform independent work |
| 4 | Worker | Finish its calculation and return |
| 5 | Main | Receives confirmation that the worker ended |

The next lesson uses join to obtain that completion confirmation. This table is one legal illustrative schedule, not a fixed time-slice duration or a promise that every eligible thread gets the next turn. A single core still needs coordination when operations interleave on shared state. **CPU-bound** work mostly performs processor calculations; two such calculations do not automatically finish sooner merely because they use two Threads. Blocking work can benefit from overlapping waits, while actual speed depends on the workload and available resources. [Java's execution and synchronization model](https://docs.oracle.com/javase/specs/jls/se8/html/jls-17.html)

## Exercise: identify ownership before starting threads

A program has two worker methods. Each declares `int index`, and both receive the same `ArrayList<String>` reference. Are the indexes shared? Is the list shared? Would constructing another local variable pointing to that list isolate it?

<details>
<summary>Worked answer</summary>

Each invocation has its own `index`. Both references name the same list object, so list mutation is shared. Assigning another reference copies the reference value, not the list. Separate independently owned lists, an immutable input, or an appropriate shared-state protocol can change the ownership model. Merely changing local variable names cannot.

</details>

## Thread-safe calls can still lose a frequency update

A **ConcurrentHashMap** stores key/value mappings with operations designed for concurrent callers. A **per-key atomic update** combines a decision and change for one mapping into an indivisible operation. This is useful when threads update independent counts, cached entries or other mappings without making every map action part of one global transaction.

Suppose java currently maps to zero. Two callers can each get zero, calculate one and put one. All four individual calls can meet their own thread-safety contracts while the composed increment loses an update. As with the earlier Counter, the whole read/compute/write must be expressed as one supported operation.

Merge provides that operation for the frequency example. `merge("java", 1, Integer::sum)` installs one when absent; otherwise its addition function combines the existing count with one atomically for that key. Follow two completed workers making these updates before examining other conditional methods or the underlying hash-table bins.

The map also supplies compute, putIfAbsent and conditional replace/remove. It rejects null keys and values, allowing a null retrieval to mean absence. Those contracts still concern individual supported operations: an invariant spanning several keys needs a larger shared protocol.

## Implement per-key counting

<JavaExample file="ConcurrentMapExample.java" output={"2000\n2000\n2000\nnull rejected"} />

Two submitted workers each call merge("java", 1, Integer::sum) one thousand times. On absence, merge installs one; on an existing value, it atomically combines the old value with one. There is no caller-controlled get/put gap. Main retrieves both Future results before reading the final 2000.

PutIfAbsent then returns the existing 2000 and leaves it unchanged; the following get still reports 2000. A null insertion throws before creating a valid mapping. These results demonstrate contracts, not a particular update order or throughput.

A non-null retrieval reporting an update has the documented happens-before relationship with that update for the key. Iteration, aggregate size and putAll are not a whole-map point-in-time transaction. A size observed during modifications is unsuitable as a hard admission check.

## Trace the difference between separate and combined operations

| Operation sequence | Interference interval | Better expression when it matches the invariant |
| --- | --- | --- |
| containsKey then put | Another caller can insert between them | putIfAbsent |
| get count then put incremented count | Both callers can use the same old count | merge or compute |
| get expected value then replace | Value can change before replacement | conditional replace |
| Update key A then key B | Readers can see the intermediate state | A larger shared protocol |

Keep the mapping/remapping functions passed to computeIfAbsent, computeIfPresent, compute and merge short. They must not modify this same map during computation; return the desired value and let the enclosing operation perform its update. Blocking computation can delay competing updates. Detectable recursive update cycles can throw IllegalStateException, but detection is not a guarantee that every invalid recursive dependency fails promptly. [Computation restrictions](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/ConcurrentHashMap.html)

ComputeIfAbsent returning null creates no mapping; a thrown exception leaves this attempt unestablished. These outcomes allow a later invocation to compute again, as the next program demonstrates.

## Follow absent, failed and installed callback outcomes

<JavaExample file="ConcurrentMapCallbacksLesson.java" output={"absent after null=true\nfailure=calculation failed\nabsent after failure=true\ninstalled=42\nexisting=42\ncallback calls=3"} />

The first computeIfAbsent returns null, leaving no mapping. The second throws a declared calculation failure, which the caller records; it also leaves the key absent. A later attempt returns 42 and installs it. Another computeIfAbsent on that present mapping returns the existing value without invoking the supplied failing function.

This sequential experiment demonstrates why atomic callback execution does not mean one callback invocation for the lifetime of a key. An absent/null/failed/removed mapping permits another attempt under its contract. Do not place an external once-only action such as payment inside a map callback and infer a business delivery guarantee.

The local calls array is confined to this experiment; it is not an example of an unprotected shared counter. For a concurrently used callback, captured mutable state requires its own protocol. Returning a value or throwing is separate from modifying the map from inside the callback, which violates the computation restrictions above. ## Bins, publication and resizing

A **bin** is the table position and associated nodes used for keys routed to that hash location. On the selected OpenJDK implementation, an ordinary empty-bin update can install a node using **compare-and-set (CAS)**: change the shared slot only if it still contains the expected value, with the check and change as one atomic action. An occupied ordinary bin coordinates updates around its head after checking the observed bin still belongs to that table slot. Tree bins use additional coordination. Reads normally follow published node references without acquiring the same update lock; user hashCode/equals can still introduce their own blocking/cost.

<Diagram client:visible definition={"flowchart TD\n P[Per-key put] --> B{Observed bin}\n B -->|empty| C[CAS-install node or retry]\n B -->|ordinary occupied| L[Coordinate, validate bin and update]\n B -->|forwarding node| N[Follow/help replacement-table transfer]\n L --> R[Publish supported mapping update]\n C --> R"} caption="This is a conceptual subset of modern update paths, not a replacement for the full JDK table/resize algorithm." />

During resize, forwarding nodes identify transferred bins. Threads can route toward the replacement table or help transfer. The invariant preserves discoverability through the supported protocol, not one global instantaneous table version. Size accounting can reflect transient concurrent state.

The fixed Segment-array architecture describes older implementations. ConcurrencyLevel is a retained sizing hint, not a promise to create exactly that number of segments/locks or permit exactly that many writers. Private node/control details should always name their source baseline.

## Callback and value ownership

Publishing an ArrayList value through the map does not protect later list.add calls. A map of LongAdder values can suit contended statistics, but sum during updates is not one exact linearizable admission decision. An invariant spanning keys needs a common lock or atomically replaced combined state followed consistently by every participant.

The atomics chapter develops CAS loops and **ABA**, the history where a value changes A→B→A so an equality test alone cannot reveal the intermediate change. A conditional update does not make unrelated fields one transaction, and retry computations must avoid repeatable external side effects. A consistently used synchronized map wrapper can be correct, with its documented complete traversal/compound-operation locking protocol.

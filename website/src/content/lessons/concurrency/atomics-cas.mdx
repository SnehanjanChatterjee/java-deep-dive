## A budget needs an indivisible decision and update

An **atomic variable**, such as AtomicInteger, supplies documented indivisible operations on one shared value. The operation needed here is **compare-and-set**, abbreviated **CAS**: replace the current value only if it matches an expected value, with comparison and replacement performed as one atomic transition.

Why make the update conditional? A budget has three units remaining and two callers each request two. Both can read three and judge their request affordable. A separate check followed by set could let both report success. The invariant instead requires validation and subtraction to take effect together.

Each attempt reads the **expected** amount into its previous local, then checks whether the request fits that observation. Only after the check passes does the compareAndSet call evaluate its **candidate** argument, previous minus units. CAS succeeds only if the shared value still matches expected at the comparison. If it differs, CAS returns false without installing the candidate. This budget's loop rereads, rechecks and recalculates after such a failure.

First follow the Budget method and its successful/too-large requests. The complete file also contains a reference-plus-version experiment for **ABA**, the history A→B→A that a value-only comparison cannot reveal. Its final false output is explained after the ordinary CAS loop and retry trace.

## Carry a stale expected value into the comparison

The expected value is a local observation, not a reservation of shared state. In the first case below the budget starts at two and both callers request one unit. A succeeds, B's stale comparison fails, then B rereads and can succeed with a new candidate. The second case uses the earlier three-unit budget and two-unit requests: rereading discovers that B's request no longer fits, so it returns false without another update.

## Match atomicity to the whole invariant

| Required operation | Suitable starting protocol | Why |
| --- | --- | --- |
| Publish one completed immutable snapshot | Volatile reference | Ordered publication; no competing conditional update required |
| Increment one exact counter | Atomic increment or common lock | One indivisible read/modify/write |
| Reserve only when remaining capacity is sufficient | CAS loop or common lock | Validation and mutation share one taking-effect point |
| Transfer between several mutable fields | Common lock or CAS of one immutable combined state | Individual atomic fields do not combine themselves |
| Aggregate contended statistics | LongAdder/LongAccumulator when their observation contract fits | A live sum need not be a linearizable admission decision |

AtomicReference.compareAndSet compares the expected reference by identity, not equals. A logically equal newly allocated object is still a different expected reference. Conversely, observing the identical old reference again can hide an A→B→A history; value/reference equality alone does not encode a version. This motivates the stamp example below.

No row supplies a universal speed ranking. Locking algorithms can deadlock under a bad acquisition policy, and CAS retry algorithms can livelock or starve an individual contender under an unsuitable surrounding protocol. Prove the invariant and progress assumptions before measuring an alternative. [Atomic package memory and operation contracts](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/atomic/package-summary.html)

## Keep retries free of external side effects

The calculation may run several times. Sending an email, charging an external account or decrementing another ordinary counter inside it could repeat despite one successful reservation. Atomic update functions have the same retry concern. A side effect after successful CAS still needs its own delivery/failure policy; an in-memory atomic update is not a distributed transaction.

For relationships spanning fields, CAS one immutable combined state or use a common lock. Independent CAS operations on two balances do not make a transfer indivisible.

## ABA is history hidden by equality

The source also observes reference A with stamp zero, changes A→B→A with stamps one/two, then attempts a stale update. Reference identity is A again, but the old stamp fails. AtomicStampedReference compares both together.

Every participant must follow the stamp policy; omitting advancement can defeat it. A finite stamp can wrap and is not unlimited history. Garbage collection removes some raw-pointer reclamation hazards while logical A→B→A histories can still matter in object algorithms.

## Memory effects, progress and counter choice

Familiar AtomicInteger get/set/CAS operations have their documented ordering effects. Additional plain/opaque/acquire/release methods have weaker contracts; do not substitute them into a stronger proof mechanically. Exact API availability and implementation should be labeled when studying those modes.

Lock-free means algorithm-wide progress, not a guarantee that each caller completes within a bounded number of steps. Wait-free is stronger. Using an atomic variable does not establish either property for the whole algorithm.

A **spin lock** repeatedly tests or attempts to acquire an ownership flag instead of parking while waiting. It can use CAS and still depend on the current owner releasing that flag: if the owner pauses, contenders can keep retrying without entering the protected region. A CAS primitive therefore does not turn an ownership lock into a lock-free algorithm. The budget loop instead attempts one conditional state update without retaining an ownership flag around later work. [Atomic ownership and waiting example](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/locks/LockSupport.html)

AtomicLong can return the exact value assigned by one increment, useful for sequences with an overflow policy. LongAdder spreads contention over cells; concurrent sum is not one linearizable snapshot. It suits statistics rather than hard resource limits or unique IDs.

## Distinguish a shared variable from a shared cache line

A **cache line** is a hardware unit used to hold and coordinate nearby memory locations in processor caches. **Cache coherence** keeps those cached locations consistent under the hardware's protocol. With an invalidation-based protocol, a core writing a line can require other cores' copies to be invalidated, even when their code uses a different location in that line.

**False sharing** is that unnecessary contention between logically independent locations. Consider two frequently written counters: A alone writes left and B alone writes right. Assume, for this conceptual example, that both locations occupy one coherence line and the workers run on separate cores. The counters can be logically correct while their stores compete for that line's write permission. [Intel's false-sharing discussion](https://www.intel.com/content/dam/develop/external/us/en/documents/gdma-2-165938.pdf#page=74)

<Diagram client:visible definition={"flowchart TD\n W[Independent writers: A writes left; B writes right] --> L[One assumed cache line contains both locations]\n L --> P[Stores can compete for the same line write permission]"} caption="A concept map of false sharing: independent variables can occupy one coherence unit. The boxes do not specify JVM field offsets, line size, event timing or measured traffic; the table below traces a hypothetical store sequence." />

| Illustrative store | left / right afterward | Why unrelated code can still contend |
| --- | --- | --- |
| A writes left = 1 | 1 / 0 | A needs permission to write their common line |
| B writes right = 1 | 1 / 1 | B's line permission can invalidate A's copy |
| A writes left = 2 | 2 / 1 | A can need the line again despite never using right |

All three writes are retained; this is different from the lost-update bug. With independent single writers and result reads after join, such fields can be data-race-free while their actual placement still causes false sharing. Volatile or atomic access does not by itself guarantee separation into different lines. Hardware coherence is also not a substitute for the Java Memory Model's ordering rules.

Actual line size, placement and generated stores depend on the hardware, JVM and optimization. Correct totals do not establish that false sharing occurred. If the access pattern permits it, accumulating locally and publishing less often can reduce shared stores. Layout isolation/padding has memory costs and needs representative evidence; allocating separate objects alone does not promise separate cache lines. [OpenJDK 25 layout-isolation rationale](https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/jdk/internal/vm/annotation/Contended.java)

**Interview check:** two threads repeatedly update the same counter. That is true sharing and needs an atomic update protocol. Two separate counters placed in one line can instead have a performance interaction despite correct independent updates. This example reports no measured speedup, cache misses or padding benefit.

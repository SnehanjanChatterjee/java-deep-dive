## A budget needs an indivisible decision and update

A budget has three units remaining. Two callers each request two. A separate read/check followed by set can let both report success from the same old three. The invariant requires an indivisible validate-and-decrement, not just a visible read or individually atomic assignment.

compareAndSet checks an expected value and installs a replacement as one atomic transition. If another caller changed the value, it returns false. The caller must reread and recompute; its earlier observation no longer authorizes a reservation.

## Keep retries free of external side effects

The calculation may run several times. Sending an email, charging an external account or decrementing another ordinary counter inside it could repeat despite one successful reservation. Atomic update functions have the same retry concern. A side effect after successful CAS still needs its own delivery/failure policy; an in-memory atomic update is not a distributed transaction.

For relationships spanning fields, CAS one immutable combined state or use a common lock. Independent CAS operations on two balances do not make a transfer indivisible.

## ABA is history hidden by equality

The source also observes reference A with stamp zero, changes A→B→A with stamps one/two, then attempts a stale update. Reference identity is A again, but the old stamp fails. AtomicStampedReference compares both together.

Every participant must follow the stamp policy; omitting advancement can defeat it. A finite stamp can wrap and is not unlimited history. Garbage collection removes some raw-pointer reclamation hazards while logical A→B→A histories can still matter in object algorithms.

## Memory effects, progress and counter choice

Familiar AtomicInteger get/set/CAS operations have their documented ordering effects. Additional plain/opaque/acquire/release methods have weaker contracts; do not substitute them into a stronger proof mechanically. Exact API availability and implementation should be labeled when studying those modes.

Lock-free means algorithm-wide progress, not a guarantee that each caller completes within a bounded number of steps. Wait-free is stronger. Using an atomic variable does not make an entire algorithm lock-free if it blocks elsewhere.

AtomicLong can return the exact value assigned by one increment, useful for sequences with an overflow policy. LongAdder spreads contention over cells; concurrent sum is not one linearizable snapshot. It suits statistics rather than hard resource limits or unique IDs. False sharing describes independent hot writes sharing coherence granularity; investigate a real profile/benchmark before padding or weakening an exact invariant.

Implement the nonnegative budget and reject invalid/oversized requests without mutation. `AtomicCounterLab` is the complete solution. Under contention, successful one-unit reservations plus remaining must equal initial capacity after completion. Do not assert how many retries one thread happened to perform.

## Combine an atomic counter with completion coordination

<JavaExample file="LatchCoordination.java" output={"2"} />

Each worker atomically increments one shared counter and decrements a completion latch in finally. The atomic operation protects the update; the latch establishes that both task bodies ended before the owner reads. The latch does not itself combine a separate get and set into one increment, and it does not collect worker failure causes. Retain task result handles when success/failure matters as well as completion.

## Stop needing a result without abandoning its work

A caller submits work, then no longer needs its result. Cancelling the Future changes the result handle's selected outcome. If interruption is requested and supported, it also asks a running task to stop. Neither step proves that cleanup has finished or that a remote side effect was undone.

Use one owner to answer four questions: who observes failure, who requests cancellation, who releases acquired resources, and who accounts for termination? Adding a timeout without answering them merely changes how long one caller waits.

## Trace cancellation and cleanup

<JavaExample file="TaskCancellationLesson.java" output={"true\ncancelled result\ncleanup finished"} />

Started makes the task reach its intended interruptible wait before main cancels. Without it, the task might be cancelled before it began, demonstrating a different case. Cancel(true) selects cancellation and requests interruption. Get now throws CancellationException; it cannot deliver an ordinary Integer result from this cancelled handle.

The worker separately leaves its wait and executes finally, counting down cleanup. Main waits for that acknowledgement before reporting cleanup finished. A successful cancellation can therefore precede resource cleanup. Finally also opens release and requests executor shutdown if main takes an exceptional path.

## Interpret every get outcome

| Outcome | What it establishes | What the owner must decide |
| --- | --- | --- |
| Value | Successful computation result | How returned mutable data may be shared |
| ExecutionException | Task failed | Preserve/interpret its cause |
| CancellationException | Handle was cancelled | How to account for remaining work |
| InterruptedException | Waiting caller was interrupted | Propagate or preserve cancellation at its boundary |
| TimeoutException | This bounded wait expired | Whether to cancel or keep observing the task |

IsDone includes failure and cancellation. Cancel(false) can cancel an already running FutureTask without interrupting its runner; the computation may continue while its result is no longer delivered through that handle. Cancel(true) requests interruption if cancellation succeeds with a known runner. A task can ignore that request or be in a noninterruptible action.

## Share one deadline across dependent waits

For a parent operation with 500 milliseconds remaining, assigning a fresh 500 milliseconds to each of three waits permits a longer total operation. Track a monotonic start/deadline and recompute remaining budget before each wait. A timeout is not a statement that remote work stopped. Wall-clock adjustments make currentTimeMillis unsuitable for measuring elapsed budgets.

Shutdown stops new acceptance; shutdownNow additionally requests interruption and returns queued Runnable objects that did not start. Those returned wrappers are not an automatic report that all corresponding Futures were cancelled/completed. Deliberately account for removed work and its result handles.

## Recompute remaining time instead of restarting a timeout

Take a monotonic start measurement and an allowed elapsed budget. Before each acquisition or result wait, calculate `remaining = budget - (System.nanoTime() - start)`. If remaining is nonpositive, apply the parent's expiry policy instead of starting another full-duration wait. Use durations within nanoTime's documented elapsed-comparison range and avoid converting a small remainder down to an accidental zero that another API interprets as unbounded.

For an illustrative 500 ms budget, an admission wait consuming 120 ms leaves about 380 ms for the result wait, rather than a fresh 500 ms. Those numbers demonstrate accounting, not a measured execution. A bounded wait can still return early for failure/interruption, and scheduler delay can make an actual return later than an ideal timer deadline.

**Cancellation cases:** a task cancelled before entry may never run its body/finally. A running task that honors interruption can execute finally after the handle is already cancelled. A running task ignoring interruption can continue. The task body is therefore responsible only for resources it actually acquired; an owner needs a separate policy for queued work that never entered. ## FutureTask completion internals

A manually constructed FutureTask is both Runnable and Future. It remains unexecuted until a thread or executor invokes run. The task description, its result handle and its executing thread are distinct objects/responsibilities.

On the selected OpenJDK source baseline, FutureTask has state, outcome and runner fields. It distinguishes NEW, transient COMPLETING, NORMAL, EXCEPTIONAL, CANCELLED and interruption-request transitions. Completion publishes an outcome and releases parked waiters. These are private implementation states, not Thread.State labels or a promise that every Future implementation uses the same representation. Read this state machine after understanding the public outcomes above.

## Exercise and complete reference solution

Cancel a running interruptible task, require get to report cancellation, and separately observe finally cleanup. `TaskCancellationLesson` is the complete solution. Explain why started and cleanup cannot be one latch: one establishes entry before cancellation, while the other acknowledges work performed after cancellation.

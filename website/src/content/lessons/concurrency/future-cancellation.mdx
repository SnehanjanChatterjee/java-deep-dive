## Results and task ownership

A Future is a handle to one computation’s eventual result. It separates submitting work from observing completion. The result can be successful, exceptional or cancelled. It does not mean the task has started, and its completion state is not a universal observation that all underlying side effects have ceased.

Runnable describes work without a returned value; Callable returns a value and can throw a checked exception. ExecutorService.submit normally wraps either in a FutureTask. FutureTask implements Runnable as well as Future: its run method owns execution and completion publication, while get waits for and interprets that outcome. A manually created FutureTask does not execute until some thread invokes run or an executor runs it.

Define ownership before adding a timeout: who observes failure, who requests cancellation, who releases resources, and who waits for termination? A fire-and-forget submission that discards its Future can lose the application’s only failure observation path.

<span id="worked-example"></span>
## Trace cancellation and cleanup

A worker begins an interruptible wait and signals that it has started. The caller cancels its Future with interruption requested. Calling get now reports CancellationException. Separately, the worker exits its wait through InterruptedException and executes a finally block that signals cleanup. The caller waits for that cleanup signal before declaring resource ownership finished.

These events are intentionally observed separately. Cancellation can make get report cancellation before a task’s finally block finishes. A real task could catch interruption, ignore it or be stuck in a noninterruptible operation. The result handle cannot safely force arbitrary Java execution to stop.

<span id="mechanics-and-tradeoffs"></span>
## FutureTask completion internals

### State and result publication

OpenJDK 25 FutureTask uses a state field, an outcome and a runner reference. Execution records a returned value or thrown failure, publishes a terminal state and releases waiting threads. Its internal transitions distinguish NEW, transient COMPLETING, NORMAL, EXCEPTIONAL, CANCELLED and the interruption-request transition. These are implementation states, not the same names as Thread.State or every Future implementation’s public state API.

A waiting thread can park until completion or a waiting deadline. Completion unparks waiters. Successful get supplies a memory-consistency edge from the completed task’s actions to the caller’s subsequent actions. A caller that observes a pending task through unrelated fields has not thereby established the same publication proof.

### Interpret get outcomes precisely

| Outcome | Meaning | Caller responsibility |
| --- | --- | --- |
| Returned value | Successful computation result | Use the value under its own mutation/ownership contract |
| ExecutionException | Task failed | Inspect/preserve its cause and apply the operation’s failure policy |
| CancellationException | Handle was cancelled | Do not treat this as a successful null result |
| InterruptedException | Waiting caller was interrupted | Propagate or preserve cancellation according to the boundary |
| TimeoutException | This bounded wait expired | Decide separately whether to cancel work or continue observing it |

`get(timeout, unit)` does not alter the task merely because the caller stops waiting. `cancel(false)` can cancel a FutureTask that is already running without interrupting its runner; the computation may continue even though its result will no longer be delivered through the cancelled handle. `cancel(true)` requests interruption if cancellation succeeds while a runner is known. It is neither rollback nor an external-service cancellation protocol.

### Deadlines versus independent timeouts

Suppose a parent operation has 500 ms remaining and performs three dependent waits. Giving each wait a fresh 500 ms timeout permits a much longer total operation. Track an overall deadline with a monotonic time source, calculate remaining budget before each wait, and define what happens when no budget remains. Do not derive elapsed durations from wall-clock time, which can be adjusted.

Executor shutdown and task cancellation are separate lifecycle operations. shutdown rejects new submissions but permits accepted work to finish. shutdownNow requests interruption and returns queued work that never began. Those returned Runnable objects are not automatically a report that all corresponding application Futures have been cancelled. Ownership code must deliberately complete, cancel or otherwise account for work removed from the queue.

`started` prevents the example from accidentally demonstrating only cancellation before start. `release` supplies an interruptible blocking point. `cleanup` is a distinct lifecycle acknowledgement, signalled in finally even when the task fails or is interrupted. Bounded latch waits make a broken demonstration fail explicitly rather than hang forever.

The Future result is deliberately not read as an Integer after cancellation. Its get call reports cancellation regardless of the Callable’s potential return value. Finally releases the latch and requests executor shutdown, ensuring the demonstration does not retain a blocked worker on an exceptional caller path. The task body does not swallow InterruptedException; the submit wrapper records task termination while cancellation still determines the Future’s selected outcome.

<span id="common-mistakes"></span>
## Cancellation mistakes

Do not interpret isDone as successful completion: failure and cancellation are also done. Do not describe Future.cancel as guaranteed task termination. Do not catch ExecutionException and throw only its message, losing its cause. A timeout should not silently become an empty success result. Interrupting one caller waiting on get does not automatically cancel the task it was waiting for.

<span id="exercises-and-interview-questions"></span>
## Future interview questions

<details>
<summary>Can a cancelled task still change application state?</summary>

Yes. Cancellation changes the result handle’s state and may request interruption. A running task can already have performed effects or can continue if it does not cooperate. Place cancellation checks at meaningful boundaries and define idempotency/compensation for external effects.

</details>

<details>
<summary>Why can submit failures appear silent?</summary>

FutureTask captures task exceptions as exceptional completion. If no owner retrieves or otherwise reports that outcome, an uncaught-exception handler need not receive it. The application must own observation.

</details>

<details>
<summary>What happens if cancel loses a race with success?</summary>

Cancellation returns false once completion prevents it. The successful result remains available. Always handle the returned boolean rather than assuming a cancellation request won.

</details>

<details>
<summary>Does get publish results from the task?</summary>

Successful result retrieval has the documented task-to-caller happens-before guarantee. This does not automatically make a returned mutable object safe for later concurrent writes.

</details>

<details>
<summary>When should interruption be restored?</summary>

When a boundary cannot propagate InterruptedException but is abandoning work in response, restore the current thread status before returning/throwing an appropriate wrapper. Do not restore and blindly retry forever.

</details>

### Coding exercise and solution

Implement an owner that submits one task, waits until it starts, cancels its result, observes CancellationException and waits separately for cleanup. The complete TaskCancellationLesson source above is the reference solution: started establishes the state, cancel selects the result outcome, get observes it, and cleanup acknowledges the worker's finally path.

For an extension, hold cleanup on a second latch and prove that cancellation can be observed before that latch is released. Preserve bounded waits and unconditional release guards; never infer task cleanup from isDone.

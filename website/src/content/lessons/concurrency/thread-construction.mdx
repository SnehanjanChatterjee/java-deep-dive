## Describe work before choosing an execution

The first program supplied a small task with a lambda. A larger task may need a name, constructor arguments or helper methods. Its behavior can still be described separately from the Thread that will execute it. `Runnable` supplies that behavior contract: an object provides a run method, and some caller chooses when to invoke it.

One choice is to define a **Thread subclass**: a class extending Thread and overriding its run method. The other is **composition**: construct an ordinary Runnable object and pass it to a Thread. In composition, the Thread uses the supplied object's behavior rather than requiring the task class to inherit its lifetime-control methods.

A named Runnable class, an anonymous Runnable class and a lambda are three spellings of that supplied behavior. An **anonymous class** creates an implementation without giving the class a reusable source name. The lambda expresses the single operation more compactly. All four forms below still need start for an independent execution and join for the demonstrated completion observation.

The mental model stays the same across the syntax: identify the object containing the behavior, identify the Thread whose lifetime is started, then join that same Thread before using its finished work.

## Run four complete forms

The example creates four threads and one four-element answer array. Each worker writes a different element. Main starts every worker, joins every worker, then prints array order. The displayed order comes from the printing loop, not a scheduler promise that the subclass ran first.

| Form | Behavior lives in | Thread construction |
| --- | --- | --- |
| Named Thread subclass | Overridden `NamedWorker.run()` | `new NamedWorker(answers)` |
| Named Runnable class | `NamedTask.run()` | `new Thread(new NamedTask(answers), name)` |
| Anonymous Runnable | The inline object's overridden `run()` | Pass `anonymous` to a Thread |
| Lambda Runnable | Lambda body implementing `run()` | Pass the lambda to a Thread |

`NamedWorker` invokes `super(name)` to name its Thread object. `NamedTask` holds the answer-array reference and writes index one when invoked. The anonymous class supplies a small unnamed implementation. The lambda supplies the same functional-interface behavior without the class declaration syntax. Its captured array reference is effectively final; the referenced array remains mutable.

The four joins establish that every corresponding write happened before main inspects the answers. Four different array elements are different variables. If two workers instead updated the same ordinary element with read/modify/write, their construction style would provide no protection against a lost update.

Runnable's method returns void and does not declare checked exceptions. Its implementations cannot add a new checked exception to that method's signature. Thread implements Runnable too, which is why a Thread subclass can override run; it does not make every Runnable object a started Thread.

## Prefer composition when the behavior is the reusable part

A Runnable class can already extend another class; Java permits only one class superclass. It can also be submitted to an executor later without treating a Thread object as a reusable task container. A Thread subclass can be useful when the Thread itself needs specialized behavior, but subclassing does not confer extra concurrency or make its fields automatically safe.

One Runnable instance can be passed to two distinct Threads. Both invocations then refer to the same Runnable object and its instance fields, while each invocation has its own parameters and local variables. Two separate Runnable instances can still share the same referenced counter. Inspect object relationships rather than counting class declarations.

Avoid constructing `new Thread(aThreadSubclass)` as a routine way to start the subclass. Thread implements Runnable, so the expression is legal, but it creates a second Thread object. Starting the outer object invokes the inner object's `run()` on the **outer execution**; it does not start the inner Thread's own lifetime. A later `inner.join()` is therefore the wrong completion handle for that outer execution.

## Interview questions

**Does implementing Runnable create a thread?** No. It supplies a method implementation. A caller can invoke it directly, or an execution facility can invoke it.

**Does a lambda make the code parallel or faster?** Its syntax establishes neither property. Execution is chosen by the caller/facility; performance requires a workload and measurement.

**Can one Thread be started for each invocation of a reusable Runnable?** Create a fresh Thread for each required lifetime. A terminated Thread cannot be restarted, even when its Runnable would be reusable.

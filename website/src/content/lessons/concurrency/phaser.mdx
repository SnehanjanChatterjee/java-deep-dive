## The participant set can change

A **Phaser** coordinates repeated rounds of work while allowing the expected participant count to change. Each round has a **phase number**. A **registered party** is one logical participant promising an arrival in the current phase; it is not a Thread object automatically tracked by the library.

Think of a progress board with two counts: how many parties are registered, and how many of those have not arrived yet. Registration adds a promised arrival. Arrival records that a party finished this phase. Arrival-and-deregistration also removes that party from future phases. When the required arrivals are accounted for, the phase can advance under the phaser's policy.

This is useful when a parent discovers child tasks dynamically. It can register each child before starting it, wait for their current work, then continue after completed children leave. A fixed-party barrier would require the same participants to keep returning, while this board explicitly records changes.

The first program uses one parent and two children for one phase. Follow its registration, result writes and departures before studying separate arrival/wait operations or custom phase policies. An unfulfilled registration remains a missing arrival and can keep everyone else waiting.

## Register before a child can complete

The Phaser begins with one registered parent. The parent registers each child **before** starting it. Otherwise the last currently known participant could advance a phase before the new child was represented. Keeping the parent registered also prevents the task group from terminating while children are being assembled.

The initial three means parent plus two children. Each child writes its own result slot and calls arriveAndDeregister in finally. Main calls arriveAndAwaitAdvance: it reports its own arrival and waits until the remaining children arrive. Their deregistrations let the phase advance while leaving only the parent registered. Joining then accounts for actual worker termination.

The parent reads the completed slots, observes one remaining registered party, then deregisters itself. With the default termination policy, no parties remaining terminates the Phaser. That terminal state is distinct from forcibly stopping a thread.

## Dry-run registration and a disappearing participant

For one legal schedule, let the children arrive before the parent. Begin phase zero with the parent registered: registered=1, unarrived=1. Register two children before starting them: registered=3, unarrived=3. Each child's arriveAndDeregister records its phase-zero arrival **and** removes its future registration. After both children, only the parent's arrival remains. The parent's arrival completes phase zero and permits advancement under the phaser's policy. The complete program does not require that arrival order.

Arrival does not inherently wait. `arrive()` returns the arrival phase; a participant that must wait can subsequently await advancement from that phase. `arriveAndAwaitAdvance()` combines those responsibilities. Calling arrive twice for one conceptual contribution violates the application protocol; registration is an accounting contract, not a scheduler that prevents mistaken calls.

Registration after a phase has already advanced joins the phase selected by the API's coordination, not an earlier phase a caller hoped to join. That is why this program registers children before they can run. The registered parent keeps the intended first phase from completing prematurely.

Use the interruptible/timed advancement API when the waiting caller needs that policy. The convenience arrive-and-await form does not throw InterruptedException. Termination makes waiting operations return their termination indication; it still does not interrupt or join child threads. ## Separate arrival from waiting

| Operation | Records this party's arrival? | Waits for phase advance? | Remains in later phases? |
| --- | --- | --- | --- |
| arrive | Yes | No | Yes |
| arriveAndAwaitAdvance | Yes | Yes | Yes |
| arriveAndDeregister | Yes | No | No |
| awaitAdvance | No | Yes, if the phase has not advanced | Does not change registration |

Do not call two arrival operations for the same logical party in one phase. AwaitAdvance takes an observed phase number; another thread may already have advanced by the time the caller waits. Use the returned phase/termination state instead of assuming a universal monotonically unbounded count.

The simple arriveAndAwaitAdvance wait is not an InterruptedException-producing API. When interruption/deadlines are required, arrange arrival deliberately and use awaitAdvanceInterruptibly with the observed phase and desired waiting policy. The owner must still decide how abandoned participation is repaired.

## Termination and failure ownership

ForceTermination releases relevant phase waits with terminal state. It does not interrupt application threads, release their permits or roll back partial results. A failed child still needs a failure channel. As with a latch, finally signaling participation prevents a hang but does not convert failure into a valid result.

OnAdvance is the hook run when the last required party arrives; it can customize phase action/termination policy. Keep that policy short and consistent with registered arrivals. **Tiered phasers** arrange child phasers under a parent, allowing groups to coordinate through a tree. That can reduce contention for large participant sets, but the optimization follows a correct registration/arrival protocol.

## Exercise and complete solution

Model a parent with two dynamically registered children, then remove both children and finish the parent. `PhaserLesson` supplies the complete solution. Identify the state if one child forgets arriveAndDeregister: main can remain waiting because that promised arrival is missing. Prematurely deregistering before writing its result instead permits main to continue without that promised work.

For repeated phases, participants that remain call an arrival operation once per phase; those leaving deregister at their final phase. Draw the registration and arrival counts for each phase before adding new threads.

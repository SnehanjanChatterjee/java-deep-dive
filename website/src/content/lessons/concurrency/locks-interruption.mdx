## Lock ownership and acquisition modes

A synchronized block acquires an object's monitor and releases it when the block exits, including exceptional exit. Reentrant locks allow the owning thread to acquire the same lock again. Explicit Lock APIs add capabilities such as interruptible acquisition, timed attempts and multiple condition queues.

Interruption is a cooperative cancellation signal. Some blocking methods throw InterruptedException and clear the interrupted status. A method that cannot propagate the exception should usually restore the status when abandoning work, rather than silently swallowing cancellation. An interrupt does not forcibly roll back partially completed business operations.

<span id="worked-example"></span>
## Coordinating termination without timing guesses

A fixed-size executor runs independent tasks and a latch records completion. await waits for all signals without guessing timing. Shutdown is performed in finally so the program does not keep worker threads alive accidentally.

<span id="mechanics-and-tradeoffs"></span>
## Conditions, cancellation and lock invariants

Conditions must be checked in a loop because a wakeup is not proof that the desired state holds. With intrinsic monitors, wait atomically releases the monitor and suspends, then reacquires it before returning. notify does not release the lock immediately. Calling wait without owning the monitor is invalid.

Keep the protected invariant clear: all participating reads and writes must follow the same protocol. Lock ordering helps avoid deadlock when multiple locks are needed. Holding locks during slow I/O or calling untrusted callbacks while locked can cause contention or reentrancy problems.

### Monitor ownership is attached to an object

An instance synchronized method locks its receiver. A static synchronized method locks the declaring Class object. Two instances have different monitors, so synchronizing on one does not protect data also accessed under another. Reentrancy lets a thread reacquire a lock it already owns; each acquisition must still be matched by release. Monitor exit happens even when a synchronized block throws.

Thread states describe different kinds of waiting: BLOCKED is associated with entering an intrinsic monitor; WAITING can represent wait, join or parking; TIMED_WAITING includes bounded waits and sleep. RUNNABLE does not guarantee the thread is consuming CPU at that instant. Thread state alone cannot establish the root cause of an incident.

### Wait for a predicate, not a notification

The queue example uses one shared monitor for slots, head, tail and size. `put` loops while full; `take` loops while empty. `wait` releases that monitor and reacquires it before returning. It does not release unrelated locks the thread holds. `notifyAll` makes waiters eligible to contend; it does not immediately transfer ownership or guarantee the awakened thread sees its desired predicate true.

<JavaExample file="BoundedQueueDemo.java" output={"first\nsecond\nthird"} />

For capacity 2, put A then B makes head and tail both zero with size 2. Taking A advances head to 1, clears slot 0 and reduces size. Putting C writes slot 0 and wraps tail. Size distinguishes full from empty when head equals tail. Both the predicate check and mutation must occur under the same lock; checking outside and then acquiring the monitor creates a race.

### Explicit locks and separate condition queues

```java
lock.lockInterruptibly();
try {
    while (size == capacity) {
        notFull.await();
    }
    // Update the protected queue state.
    notEmpty.signal();
} finally {
    lock.unlock();
}
```

This is a guarded-operation excerpt: lock is a ReentrantLock, and both Conditions are created from it. Separate notFull/notEmpty wait sets let a producer signal a consumer rather than wake all kinds of waiter. Await still belongs in a while loop. Place the try after successful lock acquisition; otherwise an interrupted acquisition could execute an invalid unlock. ReentrantLock's ordinary lock is not an interruptible acquisition. Fairness can reduce barging but adds overhead and does not promise perfect task scheduling.

### Cancellation is a protocol

`interrupt()` sets a cooperative signal. Many blocking operations throw InterruptedException and clear the status. `Thread.interrupted()` tests and clears the current thread's status; `isInterrupted()` observes a thread's status without clearing it. CPU work must check cancellation at suitable points. Some I/O or native work has different interrupt behavior; cancellation is not a forced rollback.

If a method can propagate InterruptedException, let its caller own the policy. If a Runnable boundary cannot propagate it, restore status with `Thread.currentThread().interrupt()` and stop or clean up as intended. Do not restore and then blindly retry an interruptible operation forever. Acquired resources belong in finally; interruption before a successful semaphore acquire must not release a permit that was never acquired.

### Deadlock, starvation and livelock

Deadlock requires a dependency cycle, such as A holding lock X while waiting for Y and B holding Y while waiting for X. A global lock order can break that cycle. Starvation means some work repeatedly fails to gain service; livelock means active participants keep reacting without progress. Timed tryLock and retry can avoid permanent waiting but still create livelock without a disciplined retry policy.

### Select the coordination primitive

CountDownLatch is a one-shot completion count. CyclicBarrier coordinates reusable phases among a fixed participant set. Phaser supports evolving participants/phases. Semaphore bounds concurrent access to a resource. A latch signal should occur in finally when it represents task termination, while failure information needs its own propagation path: “all tasks finished” does not mean “all tasks succeeded.”

## ReentrantLock internals and fairness boundaries

A ReentrantLock has an exclusive owner and a reentrant hold count. A contending caller can enter an acquisition queue and park until it can retry. AbstractQueuedSynchronizer supplies common state/queue machinery, while the lock's acquisition policy decides whether an attempt succeeds. Do not describe the queue as transferring an application's data directly between threads; the successful lock/unlock protocol orders access to that data.

Fair construction affects the documented acquisition policy under contention, but does not make OS scheduling fair or remove deadlock cycles. Untimed tryLock can acquire opportunistically even on a fair lock. A timed/interruptible acquisition has a different contract. Choose the required timeout and cancellation semantics before selecting the method.

Condition.await requires ownership of its associated lock. It releases the lock state for waiting and restores ownership before returning. signal moves an eligible waiter toward reacquisition; it does not let the waiter skip the lock or assume the predicate remains true. Separate notEmpty and notFull queues allow the program to signal a relevant class of waiter. Closure changes both predicates and therefore wakes both queues in the example.

put acquires interruptibly and enters its unlock-owning try only after acquisition succeeds. poll includes acquisition waiting in the requested budget, then carries remaining nanoseconds through each condition wait. It rejects negative timeouts and null TimeUnit rather than silently changing policy. Zero-time polling can still deliver a value if the lock and item are immediately available; otherwise it returns null. That null can mean timeout or closed-and-empty under this deliberately compact API, so a richer production result type would be needed if callers must distinguish them.

The producer waits while occupied and open, then rejects closure before assigning. The consumer clears the slot before signaling notFull. close wakes both condition queues. As with the intrinsic-mailbox version, already accepted data is drainable after closure. Method completion and every exceptional body exit release the acquired lock in finally. Timeout is not a hard real-time guarantee because scheduling and reacquisition remain outside the application's exact control.

<span id="common-mistakes"></span>
## Ownership and timeout mistakes

Do not catch InterruptedException and continue as though nothing happened. Do not use if instead of while around a condition wait. Avoid protecting writes with one lock and reading under another.

## Read/write locking and optimistic validation

ReentrantReadWriteLock permits multiple read owners while excluding write owners. It can improve a workload dominated by sufficiently substantial read sections; it can also add overhead or delay writers. A read path must actually be read-only with respect to the protected invariant. Do not classify an access-order cache get as read-only when it relinks recency state.

A writer can acquire the read lock before releasing its write lock to downgrade while retaining protected observation. Attempting to upgrade by holding a read lock and waiting for the write lock can deadlock progress when competing readers also retain reads. Release/reacquire with a fresh predicate check or choose a different atomic transition. StampedLock's conversion APIs provide different mechanisms and still need validation.

StampedLock is not reentrant and has no ordinary thread ownership model. An optimistic read permits interference: copy the relevant primitive fields into locals, validate the stamp, and discard/reread under a real read lock when validation fails. Do not traverse an inconsistent mutable graph or call unknown methods before validation. A successful stamp validation establishes the documented consistency relationship for that interval; an invalidated optimistic observation must not be used as a trusted snapshot.

## Locking interview questions and exercises

### Why can notifyAll be necessary even when only one item is added?

<details>
<summary>Explanation</summary>

Several waiters may be waiting for different conditions on the same monitor. Waking an arbitrary one can leave the thread able to make progress asleep. notifyAll wakes contenders to recheck their conditions under the lock. Explicit Conditions can separate wait sets but still require loop-based checks.

</details>

### Additional interview questions

<details>
<summary>Does wait release every lock held by the thread?</summary>

No. It releases the monitor on which wait was invoked and must reacquire that monitor before returning. Holding another lock while waiting can block progress or contribute to a deadlock.

</details>

<details>
<summary>Does notifyAll immediately let a waiter execute its guarded operation?</summary>

No. The notifying thread still owns the monitor until it releases it. Waiters then contend to reacquire it and recheck their predicates. Another participant can consume the state change first.

</details>

<details>
<summary>Why put unlock in finally after acquisition succeeds?</summary>

All body exits must release the acquired lock, including exceptions. If acquisition itself throws InterruptedException, no lock was acquired; an unconditional unlock from an incorrectly placed finally would be invalid.

</details>

## Use an explicit lock when acquisition itself needs a policy

The monitor mailbox already supplies exclusion and guarded waiting. ReentrantLock gives the same kind of ownership with additional acquisition operations: an ordinary lock, an interruptible acquisition, or a timed attempt. It can also create separate Conditions for consumers waiting for data and producers waiting for space.

The state invariant stays the same. Switching the API does not repair a predicate checked outside the lock or a read performed under an unrelated lock.

## Acquire first, then enter the release-owning try

```java
lock.lockInterruptibly();
try {
    while (value != null && !closed) {
        notFull.await();
    }
    // Recheck closure, store the item, then signal notEmpty.
} finally {
    lock.unlock();
}
```

The excerpt assumes lock is a ReentrantLock and notFull is its Condition. Acquisition is before try because an interrupted acquisition has no lock to release. Once acquired, every normal or exceptional body exit must unlock. Ordinary `lock()` does not provide the interruption behavior of `lockInterruptibly()`.

Reentrancy means the owner can acquire the same lock again, increasing its hold count. Matching unlocks are still necessary. This is useful when a protected method calls another protected method; it does not make unknown callbacks safe.

## Implement a timed condition mailbox

<JavaExample file="ConditionMailbox.java" output={"null\nmessage\nnull"} />

Put waits on notFull while occupied and open, rechecks closure, stores the value, then signals notEmpty. Poll waits on notEmpty while empty and open, clears a delivered slot, and signals notFull. Close changes both predicates, so it signals all waiters on both Conditions. Every check and state transition is under the same lock.

Poll's first null is an immediate empty result. The second call returns message. After closure and draining, null is the terminal result. This compact API intentionally uses null for both timeout and terminal emptiness; a richer result type would be needed to distinguish them. Null data and invalid timeouts are rejected.

Await belongs in a while loop for the same reasons as Object.wait: a spurious return or competing consumer can leave the predicate false. A Condition is associated with its lock; ownership is required. A separate condition wait queue is different from the lock's acquisition queue.

## Carry one time budget across acquisition and waiting

Poll converts the supplied duration to nanoseconds and captures a monotonic start time. Its timed tryLock consumes part of that budget. After acquisition, the remaining budget excludes elapsed acquisition time. Each awaitNanos return supplies the remaining wait estimate, which is carried into the next predicate check.

Zero timeout can still deliver an immediately available value if acquisition succeeds; otherwise it returns null. A timeout is a waiting policy rather than a hard real-time return deadline. A notification never grants a fresh full timeout. The complete source implements these cases rather than leaving them as an unsolved extension.

## Fairness and implementation boundaries

A fair ReentrantLock influences its documented acquisition policy under contention. It does not make operating-system scheduling fair, guarantee end-to-end latency, or eliminate cycles involving other locks. Untimed tryLock can acquire opportunistically even on a fair lock. Select the exact acquisition contract before relying on fairness.

AQS supplies internal state/queue machinery; the later implementation chapter explains that machinery after latches and permits. <a href={lessonUrl('learn/concurrency/read-write-locks/')}>Read/write locking</a> and <a href={lessonUrl('learn/concurrency/stamped-lock/')}>optimistic validation with StampedLock</a> have different contracts and their own focused chapters. They are not additional modes to enable blindly on this mailbox.

## Exercise and complete reference solution

Implement interruptible put, timed poll and drain-on-close using separate notEmpty/notFull Conditions. `ConditionMailbox` is the complete solution.

## Ask what must become true before a thread continues

A lock answers who may access protected state now. Other coordination problems need a different question: have all results arrived, has every participant finished this phase, or is capacity available for one more resource user? An API name alone does not establish that it represents the required condition.

Consider two report workers and a service with two connections. Main may need both report results; workers may synchronize at repeated calculation phases; each service call may need one connection. Those are three distinct protocols, even when the same program uses all of them.

<span id="choose-the-question-being-synchronized"></span>
## Choose the smallest matching contract

| Required condition | Utility | State change that permits progress |
| --- | --- | --- |
| N one-time signals have occurred | CountDownLatch | Count reaches zero and stays there |
| Every fixed participant reached this round | CyclicBarrier | Current generation trips; a new one begins |
| The currently registered participants reached a phase | Phaser | Phase advances as registrations/arrivals permit |
| One of a fixed number of resource slots is available | Semaphore | Successful acquisition consumes a permit |

The following chapters teach each through a complete program. A comparison table is useful only after you can state the underlying predicate. A semaphore does not collect results. A latch does not limit how many calls run simultaneously. A barrier does not create missing executor workers.

## Trace a combined operation before combining APIs

A worker first acquires a connection permit, writes its own result slot, releases the permit, then reports completion. Main waits for all completion signals and checks failures before combining results.

<Diagram client:visible definition={"flowchart TD\n A[Acquire resource permit] --> B[Perform resource work]\n B --> C[Release acquired permit in finally]\n C --> D[Signal task completion in outer finally]\n D --> E[Owner observes every result or failure]"} caption="Admission, completion and failure reporting are separate responsibilities. An acquired permit must be released even when work fails." />

If the task throws after acquiring, releasing the permit remains necessary. If it is interrupted before acquisition succeeds, releasing would create an extra permit. If a completion count means termination, every termination path must count down; successful completion is still a separate outcome.

## Avoid a dependency that cannot be scheduled

With two workers and a barrier requiring three tasks, the first two tasks can occupy the pool while the third stays queued. The barrier cannot advance because no worker is available for that third participant. Increasing a wait timeout does not create execution capacity.

Likewise, a worker retaining the only permit while waiting for a child that needs the same permit creates a resource dependency. Draw the work and resources together. Coordination utilities do not remove liveness reasoning.

## Exercise with explained selection

Choose a utility for each problem: wait for four file-check tasks once; combine two array partitions after every iteration; accept a changing number of child activities; allow at most three simultaneous remote calls.

<details>
<summary>Worked answer</summary>

Use a latch initialized to four for the one-time signals, a two-party barrier for the repeated fixed phases, a phaser with explicit registration/deregistration for changing participants, and a semaphore with three permits around actual remote resource use. Give every case a failure/termination policy. A plain semaphore bounds concurrency, not calls per second; rate limits also need time/replenishment semantics.

</details>

Study the complete solutions in the next four chapters, then revisit their shared machinery in AQS. No custom synchronizer is needed to use these library contracts correctly.

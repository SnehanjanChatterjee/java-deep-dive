## Ask what must become true before a thread continues

A **coordination utility** is a library object that remembers progress or available capacity and lets callers wait for a specified condition. It saves an application from writing every state counter and guarded-wait loop itself. A lock controls access to protected data; these utilities answer questions such as when enough work is finished or when another resource user may enter.

Consider two report workers and a service with two connections. Main needs one completion **signal** from each worker before combining results. A repeated calculation instead needs a **phase**, one round that every participant must finish before the next begins. A service call needs a **permit**, one unit of permission to use limited capacity, then returns it after use.

These are different kinds of remembered state. A one-way count can stay at zero forever after completion. A reusable barrier needs a new **generation**, or round, each time its participants meet. A changing participant set also needs **registration**, explicit accounting for who is expected to arrive. Use those questions to understand the comparison rather than choosing by an unfamiliar class name.

## Choose the smallest matching contract

| Required condition | Utility | State change that permits progress |
| --- | --- | --- |
| N one-time signals have occurred | CountDownLatch | Count reaches zero and stays there |
| Every fixed participant reached this round | CyclicBarrier | Last required arrival completes the round; a new round begins |
| The currently registered participants reached a phase | Phaser | Phase advances as registrations/arrivals permit |
| One of a fixed number of resource slots is available | Semaphore | Successful acquisition consumes a permit |
| Two participants have each brought a value to swap | Exchanger | A matched pair receives each other's value |

The following chapters teach each through a complete program. A comparison table is useful only after you can state the underlying predicate. A semaphore does not collect results. A latch does not limit how many calls run simultaneously. A barrier does not create missing executor workers.

## Classify the state, not just the waiting method

A latch with count two remembers two one-way completion signals even if its owner has not called await yet. A two-party barrier instead requires participants to meet in the same generation. A semaphore with two permits can repeatedly lend and recover two admissions. A phaser adds registered arrivals and generation changes; deregistration changes future participation. An Exchanger pairs two callers and returns each caller's peer value.

This distinction predicts behavior. Calling countDown twice can permanently open one latch. Calling release twice can add semaphore permits, even from a different caller, so erroneous extra releases can destroy a capacity invariant. Repeated barrier arrivals belong to separate generations rather than two stored credits for any future waiter.

**Selection exercise:** two producers finish forever and the owner needs both completion signals: latch. The same two workers must finish every repeated round before advancing: barrier. Variable child tasks join and leave phases: phaser. Only two database operations may hold resource slots at once: semaphore. Two participants swap buffers at a boundary: Exchanger. The focused chapters run each contract independently before combining them. [Java 8 coordination package](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/package-summary.html)

## Trace a combined operation before combining APIs

A worker first acquires a connection permit, writes its own result slot, releases the permit, then reports completion. Main waits for all completion signals and checks failures before combining results.

<Diagram client:visible definition={"flowchart TD\n A[Acquire resource permit] --> B[Perform resource work]\n B --> C[Release acquired permit in finally]\n C --> D[Signal work milestone in outer finally]\n D --> E[Owner observes every result or failure]"} caption="Admission, milestone publication and failure reporting are separate responsibilities. An acquired permit must be released even when work fails." />

If the task throws after acquiring, releasing the permit remains necessary. If it is interrupted before acquisition succeeds, releasing would create an extra permit. Define what each completion signal means and perform the required result writes or cleanup before signalling. A countdown publishes that preceding milestone; the task can still have return/framework code afterward, and its worker thread may continue. Actual thread termination requires an appropriate observation such as join. Successful computation is another distinct outcome. ## Avoid a dependency that cannot be scheduled

Every required arrival needs a path that can actually make progress. Before adding a waiting utility, identify the work that will satisfy its condition and any resource that work needs. **Liveness** asks whether useful progress eventually occurs; remembering a condition alone does not establish it.

## Exercise with explained selection

Choose a utility for each problem: wait for four file-check tasks once; combine two array partitions after every iteration; accept a changing number of child activities; allow at most three simultaneous remote calls.

<details>
<summary>Worked answer</summary>

Use a latch initialized to four for the one-time signals, a two-party barrier for the repeated fixed phases, a phaser with explicit registration/deregistration for changing participants, and a semaphore with three permits around actual remote resource use. Give every case a failure/termination policy. A plain semaphore bounds concurrency, not calls per second; rate limits also need time/replenishment semantics.

</details>

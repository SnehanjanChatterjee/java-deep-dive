## Choose the question being synchronized

A lock protects state ownership. A latch answers whether a one-time count of signals has completed. A barrier aligns a fixed group at a reusable phase boundary. A phaser generalizes phase participation with registration/deregistration. A semaphore limits concurrent admission to a resource. Calling all of them locks hides the differences that determine correctness.

| Primitive | Core state | Typical task | Important limitation |
| --- | --- | --- | --- |
| CountDownLatch | Count monotonically reaches zero | Wait for N tasks' completion signals | Cannot reset |
| CyclicBarrier | Fixed parties and reusable generation | Repeated parallel computation phases | One broken participant can break a generation |
| Phaser | Registered/unarrived parties and phase | Dynamic multi-phase participation | Registration and arrival are a protocol |
| Semaphore | Available permits | Bound simultaneous use of a resource | No automatic ownership or release tracking |

Begin with the invariant. Is work allowed after all results exist, after every party reaches a phase, or only when a permit is held? A construct selected by a familiar name can express a different condition from the required one.

<span id="worked-example"></span>
## Completion publication is not failure propagation

A CountDownLatch signal after writing a result can publish that write to a successful await observing completion. The latch does not collect exceptions. If countDown means task termination, put it in finally, and preserve failure through a Future, an explicit result type or a separate failure holder. Otherwise a task can fail and either leave await stuck forever or be mistaken for successful completion.

A fixed pool can deadlock progress if its running tasks wait at a barrier whose remaining parties are still queued behind them. The synchronization primitive cannot manufacture an available worker. Count admitted parties and execution capacity together. Likewise, a latch's initial count must match actual signals on every success/failure path.

<span id="mechanics-and-tradeoffs"></span>
## CyclicBarrier generation behavior

A barrier's await registers arrival and waits for other parties in that generation. The last arrival can run a barrier action before releasing the others. A failed action or an interrupted/timed-out participant can break the generation, causing peers to receive BrokenBarrierException. Do not catch that exception and proceed as though the coordinated phase succeeded.

Resetting a barrier is not equivalent to repairing all application state. Parties from different logical iterations can be mixed if the reset/retry protocol is uncontrolled. Prefer cancelling and recreating the whole computation when that gives a clearer recovery boundary. A barrier action must not wait for work that requires a party still held at the same barrier.

## Phaser registration and arrival

Register parties before they can cause a phase to advance unexpectedly. arrive records arrival without waiting. arriveAndAwaitAdvance combines arrival with waiting for phase change; arriveAndDeregister also reduces future participation. A missed deregistration can leave future phases waiting for a party that will never arrive, while premature deregistration can advance before its promised work completes.

Not all waiting forms are interruptible. awaitAdvanceInterruptibly supplies an interruptible phase-wait API; a method's name and contract must be read rather than assuming every wait throws InterruptedException. Terminating a phaser releases relevant waits with termination state, but does not forcibly stop application threads or release their other resources.

<span id="common-mistakes"></span>
## Semaphore permits, fairness and over-release

A permit is not tied to the acquiring thread like a ReentrantLock's ownership. Releasing from another thread can be part of a legitimate handoff protocol. The semaphore does not automatically detect an extra release, however, so an unconditional finally release after failed acquire can exceed the intended concurrency limit.

Fair semaphores favor established queue order under the documented acquisition rules; untimed tryAcquire can still barge. Fairness does not promise equal CPU scheduling or exact end-to-end response times. A binary semaphore differs from a reentrant owner-tracked lock: recursively acquiring its only permit can block the same thread rather than increase a hold count.

### Coding exercise: bound a simulated downloader

Use a fixed permit count around actual resource use, acquire before entering the release-owning finally, and propagate interruption. Collect task failures explicitly. A correct solution does not keep a scarce permit while waiting for unrelated child work that itself needs a permit. Decide whether timeout includes waiting for a permit, the resource action, or the entire operation.

<span id="exercises-and-interview-questions"></span>
## Interview questions with worked answers
<details>
<summary>Why does countDown belong in finally?</summary>

When the count means task termination, every completion path must signal. Success needs separate result validation. If the count instead deliberately means successful tasks, a failure/cancellation path must still prevent the owner from waiting forever under a mistaken initial count.

</details>

<details>
<summary>Can a semaphore implement a rate limit?</summary>

A plain permit count bounds concurrent admission, not operations per time interval. A rate policy also needs time/replenishment semantics. Returning a permit immediately after a fast action does not enforce an hourly or per-second quota.

</details>

<details>
<summary>Why can a barrier hang in a correctly sized task group?</summary>

The executor may have fewer available workers than parties, or another dependency may occupy them. Some parties can remain queued while running parties wait for them. Analyze execution capacity as well as barrier count.

</details>

<details>
<summary>Why does forceTermination not stop worker computation?</summary>

It changes the phaser coordination state and releases relevant waiters. Threads still own their execution and external resources; cancellation and cleanup remain cooperative responsibilities.

</details>

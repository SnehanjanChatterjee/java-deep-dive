## One worker can execute several tasks

A **worker pool** is a set of threads reused to execute submitted tasks. One worker can finish task A and then execute task B, so each task's completion does not have to end that worker's lifetime. The application instead owns the longer-lived execution service.

An **executor factory** is a helper method constructing a service with a chosen policy. The name newSingleThreadExecutor selects one active worker at a time; newFixedThreadPool selects a different worker-count policy. Before comparing those names, run two successive tasks through one owned service and follow when that service is shut down.

The example supplies a ThreadFactory, a creation callback that receives the worker Runnable and returns an unstarted Thread. It gives any worker created for this service a readable diagnostic name. The executor still starts and manages that worker.

After the ordinary batch, compare what can accumulate under each factory. A **work queue** holds accepted tasks waiting for a worker. Bounded workers and bounded waiting storage are different resource decisions. Queueing, synchronization, allocation and context handling have costs, so reuse alone is not a workload-independent speed guarantee.

## Compare the factory policies

| Factory | Ordinary policy | Resource question |
| --- | --- | --- |
| newFixedThreadPool(n) | Up to n active workers; shared unbounded work queue | How much waiting work/state may accumulate? |
| newSingleThreadExecutor() | At most one task active; unbounded queue; worker replacement if needed | Can one slow task delay every later task? |
| newCachedThreadPool() | Reuse idle workers or create as needed; idle workers expire | What limits simultaneous platform-thread growth? |
| newScheduledThreadPool(n) | Delayed/periodic eligibility on scheduled workers | How many delayed jobs and their captured objects may remain queued? |
| newWorkStealingPool() | Work-stealing pool with target parallelism | Is the workload suitable for decomposition and this ordering policy? |
| newVirtualThreadPerTaskExecutor(), Java 21+ | New virtual Thread per task | What limits requests, memory and the actual scarce downstream resource? |

Fixed describes the worker limit, not a finite accepted-task limit. Cached describes reuse, not a bound on thread creation. Scheduled delay does not bound delayed storage. Work-stealing does not promise first-in-first-out (FIFO) execution. A virtual-thread executor is not a conventional pool of reused virtual workers.

Most factory-created platform workers are created when needed rather than all being eagerly started at construction. A single-worker service also does not promise one immortal Thread object: a failed worker can be replaced while the service continues. Code needing worker identity or task context must account for this distinction.

The later pool-admission lesson traces an explicitly bounded ThreadPoolExecutor. Choose that when the application needs a defined worker/queue/rejection policy instead of assuming a factory name supplies it.

## Match shutdown to the real owner

A request handler using an application-owned shared executor must not call shutdown after its one request. That would reject the next request's submission. The application/component owning the executor instead closes it when that component ends. A short command-line batch can legitimately own a shorter service lifetime, as this program does.

Do not close an executor owned by a framework or the common ForkJoinPool just because your task finished. Conversely, creating an owned executor and forgetting shutdown can keep non-daemon workers alive and retain application state. Ownership must be part of the design, not guessed from whether a program appears to exit during one run.

| Operation | Establishes | Does not establish |
| --- | --- | --- |
| shutdown | Stop accepting new work; process accepted work under policy | All work is already finished |
| shutdownNow | Attempt to interrupt active work; return not-started queued tasks | All tasks honored interruption or their Futures were completed |
| awaitTermination | Wait for termination or return on timeout/interruption | Initiate shutdown by itself |
| Future.get | Observe one task outcome | The shared service has ended |

## Exercises and interview questions

**A web request shuts down its injected executor. Why does the next request fail?** The service lifetime was incorrectly tied to one task. Retain the shared service under its component owner and close it at component termination.

**Is newSingleThreadExecutor equivalent to starting one plain Thread once?** It accepts multiple submissions, queues them, supplies task-result handles and can replace a failed worker. One plain Thread's run method has only its own single lifetime.

**Does a fixed pool prevent overload?** Its workers are bounded, but its unbounded queue can retain arbitrarily many accepted tasks. The application needs a queue/admission policy as well.

For the complete exercise, inspect runBatch and locate the executor owner, both result observations, the rejection boundary after shutdown, and the termination wait. Then explain why moving second.get into a task running on the same sole worker could create a capacity dependency if that child is queued behind it.

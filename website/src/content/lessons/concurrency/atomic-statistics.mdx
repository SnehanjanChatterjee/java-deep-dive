## Statistics and admission answer different questions

**Aggregation** combines contributions into a summary, such as a total or maximum. LongAdder accepts additive contributions and exposes their combined sum. LongAccumulator accepts a combining function and an **identity**, the starting value that leaves a contribution unchanged when combined with it. Zero is the identity for addition; Long.MIN_VALUE works for the maximum of long values.

This fits statistics such as recorded events or observed sizes. A resource budget asks a different question: may **this** caller consume capacity now? That requires the indivisible conditional decision from the CAS lesson. A live statistics observation is not a replacement for that admission protocol.

The first program uses two workers, each contributing 1, 2 and 3, and observes a sum and maximum after joining both. Begin with that completed accounting. Then examine what changes when readers ask for a summary while contributors are still updating.

## Observe completed contributors

<JavaExample file="AtomicStatisticsLesson.java" output={"sum=12\nmaximum=3"} />

Both workers use the same two aggregate objects. Each contributes 1, 2 and 3. LongAdder therefore records two copies of six, giving twelve. LongAccumulator uses Long::max with Long.MIN_VALUE as its identity, giving maximum three.

The loop variable value is local to each invocation. The aggregate references captured by the shared Runnable refer to the same two objects. Main starts both workers and joins both before reading either result. This is a **quiescent** boundary: updates have stopped, so the outputs include every completed contribution.

| Contribution | Additive aggregate | Maximum aggregate |
| --- | --- | --- |
| Initial state | 0 | Long.MIN_VALUE |
| One worker's 1, 2, 3 | 6 | 3 |
| Both complete | 12 | 3 |

The table is an arithmetic accounting trace, not a claimed update order between workers or a view of private cells. The aggregate is allowed to group contributions differently while respecting its supported function contract.

Under **contention**, multiple threads compete to update the same shared location. These implementations can distribute contributions over multiple variables or cells, trading a more involved observation for less competition on one location. That mechanism is worth evaluating for a workload, rather than a universal claim that it beats AtomicLong.

## A live sum is not one atomic snapshot

LongAdder.sum while updates occur is not an atomic snapshot of every contributing variable at one instant. It is useful for statistics, but `if (sum() < limit) increment()` cannot enforce a hard limit. Two callers can both decide to proceed, even apart from the aggregation observation's limitations.

The same caution applies to reset and sumThenReset while writers remain active. Reset-based reporting needs a quiescent/owned interval or an explicitly acceptable approximate collection policy. An aggregation API does not decide where application reporting periods begin and end.

AtomicLong.incrementAndGet can supply the value assigned by one atomic increment, which can support sequences under an overflow policy. LongAdder.increment does not return a unique new sequence number. Choose the operation whose contract expresses the required invariant.

## The reduction function needs laws

**Associativity** means regrouping inputs does not change the result; **commutativity** means changing their order does not change it. LongAccumulator may regroup and retry applications of its function. Use a side-effect-free function, which does not change external state, with a valid identity and suitable combination laws. Commutativity matters when encounter order is not defined. Maximum with Long.MIN_VALUE fits: max(identity, x) is x, and grouping/order do not change the maximum.

Subtraction is not an associative reduction: `(10 - 3) - 2` differs from `10 - (3 - 2)`. Sending a message from the function is also wrong because evaluation can be retried. Integer addition needs an overflow policy, and floating-point aggregation may differ with grouping because of rounding. Do not infer a business guarantee from the word accumulator alone.

## Exercises and interview questions

**What is maximum before any contributions?** The configured identity, Long.MIN_VALUE. If absence is a meaningful domain state, model it explicitly instead of presenting the identity as an observed sample.

**Can sum equal twelve before both joins?** It may, but an accidental intermediate value is not a completion proof. Joins establish that these owned contributors ended before final observation.

**Should a connection limit use LongAdder?** Use a suitable permit or atomic conditional-state protocol. Statistics may observe admission; they should not replace its indivisible decision.

The complete reference solution is AtomicStatisticsLesson. Change each worker to contribute 2 and 4: the final sum becomes twelve and maximum four. Explain why an unchanged total can coexist with a changed maximum; the two aggregates answer different questions and are not one atomic multi-field snapshot during updates.

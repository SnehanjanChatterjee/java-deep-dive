## A sleeping worker needs a way to stop

Suppose a worker periodically checks for work. Its owner no longer needs it. Returning from the owner's method does not cancel the worker, and interrupting does not forcibly unwind arbitrary Java code. A reliable design gives the worker a cancellation signal it understands and keeps an owner responsible for observing termination.

The first-thread lesson introduced create/start/join. Here we add one operation: `interrupt`, a cooperative request. The task must either inspect the interrupted status or use an operation whose contract responds to interruption.

The worker checks its current thread's interrupted status before each wait. `Thread.sleep` is interruptible. If the request arrives while sleeping, sleep throws InterruptedException and clears the status as part of that reporting path. The catch restores the signal and lets execution leave the body. Finally records cleanup on either path.

Main can interrupt before the worker first sleeps, between the status check and sleep, or while sleep is waiting. Each is handled: the loop can observe the status, or sleep can report it. The program does not need to prove the worker was sleeping at the instant of the request. After join, main can read the ordinary cleanup field using the termination publication rule already studied.

The one-second sleep represents an interruptible wait; it is not the cancellation latency guarantee. Scheduling can delay both the owner and worker. A task stuck in a different operation needs that operation's specific cancellation contract.

## Read states without guessing timing

| Thread.State | Useful interpretation | What it cannot prove |
| --- | --- | --- |
| NEW | Created but not started | That calling run directly starts it |
| RUNNABLE | Executing or eligible to execute | Continuous CPU use |
| BLOCKED | Waiting to enter an intrinsic monitor | Every kind of lock wait |
| WAITING | An indefinite supported wait, join or park | Deadlock by itself |
| TIMED_WAITING | A bounded supported wait or sleep | An exact return-to-execution deadline |
| TERMINATED | Execution ended | Application success |

getState is a changing diagnostic snapshot. A ReentrantLock contender can park rather than appear BLOCKED. NEW before start and TERMINATED after a successful join are stable boundaries; sampling a state after an arbitrary sleep is not a coordination technique.

## Interruption is a cooperative protocol

`thread.isInterrupted()` observes a thread's status without clearing it. `Thread.interrupted()` observes **and clears the current thread's** status. Accidentally consuming that signal can make a later layer miss cancellation.

A method declaring InterruptedException can usually propagate it. A Runnable boundary cannot throw that checked exception to its caller; it commonly restores the status and finishes. A layer deliberately consuming cancellation can have another documented policy. Restoring the status and blindly retrying the same interruptible wait can create a busy failure loop.

For CPU work, check `Thread.currentThread().isInterrupted()` between bounded chunks. The chunk size controls where the program can respond. Finish the current valid state transition before returning; an interrupt is not rollback for an already completed side effect.

## Design a termination policy

A bounded join limits how long the owner waits; a timed-out join does not establish that the worker ended. Report the remaining work or transfer ownership deliberately. Do not claim that a call to interrupt safely terminates arbitrary code.

A daemon thread does not keep the process alive after the non-daemon threads terminate. It is therefore unsuitable as the only owner of essential shutdown work. Virtual threads are daemon threads; their scheduler is studied later. A terminated Thread cannot be started again.

Sleep does not release monitors held by the caller. Wait releases its target monitor and reacquires it before returning; the guarded-waiting chapter develops that different protocol. Yield is a scheduling hint, not fairness or publication. Unsafe stop/suspend-style mechanisms are unsuitable for preserving invariants and can leave invalid state or retained locks.

## Exercise and worked answer

Replace sleeping with processing one bounded chunk, then checking cancellation. State where the last completed chunk commits its result, which resources finally releases, and which owner joins the worker. A correct answer returns when interrupted, keeps the last committed result valid, and does not silently report all requested chunks as complete.

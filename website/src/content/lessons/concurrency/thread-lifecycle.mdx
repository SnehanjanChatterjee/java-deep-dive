## A sleeping worker needs a way to stop

The **lifecycle** of a thread is the progression from an unstarted object, through its started execution, to termination. **Cancellation** is an application decision to stop needing some work. The thread's **owner** is the code responsible for starting it, requesting cancellation when needed and accounting for its eventual end.

Returning from the method that started a Thread does not itself end that Thread's execution. Its task needs to reach a return or other terminating outcome under the program's lifetime policy.

Suppose that owner starts a worker which periodically waits before checking for more work. If the owner wants to stop it, the worker needs a way to notice the request and leave its run method. Java supplies an **interruption status**, an on/off flag associated with each Thread. Calling interrupt requests interruption; the task chooses a response at a safe point.

There are two ordinary response paths in the program below. A status check can notice the request before a wait. An **interruptible** wait such as Thread.sleep can instead report the request by throwing InterruptedException. The worker responds by leaving its body through finally cleanup, then main joins to observe termination. This is cooperative cancellation: the request and the actual end are separate steps.

## Complete lifecycle and cancellation example

<JavaExample file="CooperativeStopLesson.java" output={"terminated=true\ncleanup=true"} />

The worker checks its current thread's interrupted status before each wait. `Thread.sleep` is interruptible. If the request arrives while sleeping, sleep throws InterruptedException and clears the status as part of that reporting path. The catch restores the signal and lets execution leave the body. Finally records cleanup on either path.

Main can interrupt before the worker first sleeps, between the status check and sleep, or while sleep is waiting. Each is handled: the loop can observe the status, or sleep can report it. The program does not need to prove the worker was sleeping at the instant of the request. After successful join, main can observe the worker's completed write to the ordinary cleanup field. The memory-model chapter later derives the formal termination-publication rule behind this familiar completion pattern.

The one-second sleep represents an interruptible wait; it is not the cancellation latency guarantee. Scheduling can delay both the owner and worker. A task stuck in a different operation needs that operation's specific cancellation contract.

## Separate lifecycle state from scheduler vocabulary

Thread.State has six enum values. A diagram may informally separate ready-to-run from currently running, but both can fall under Java's RUNNABLE category; RUNNING is not an additional Thread.State constant. Likewise, a description such as not running is too broad to replace BLOCKED, WAITING and TIMED_WAITING, which describe different reasons for lack of execution.

These are Java virtual-machine states, rather than a direct inventory of operating-system scheduler states. A drawing may choose one path through them, while an actual worker can pass through a state between diagnostic observations. The table below uses the API's actual enum vocabulary. [Thread.State definitions](https://docs.oracle.com/javase/8/docs/api/java/lang/Thread.State.html)

## Read states without guessing timing

A **monitor** is Java's built-in object lock: one thread can own it while executing a protected region. The synchronization chapters teach its use. For this lifecycle table, it is enough to know that BLOCKED specifically describes a thread waiting to enter such a monitor; other waiting mechanisms have different state labels.

| Thread.State | Useful interpretation | What it cannot prove |
| --- | --- | --- |
| NEW | Created but not started | That calling run directly starts it |
| RUNNABLE | Executing or eligible to execute | Continuous CPU use |
| BLOCKED | Waiting to enter an intrinsic monitor | Every kind of lock wait |
| WAITING | An indefinite supported wait, such as join | A dependency cycle or permanent lack of progress by itself |
| TIMED_WAITING | A bounded supported wait or sleep | An exact return-to-execution deadline |
| TERMINATED | Execution ended | Application success |

GetState is a changing diagnostic snapshot. Library locks such as ReentrantLock can suspend a contender using a different waiting mechanism, called parking, rather than putting it in BLOCKED. Their later chapters explain that mechanism. NEW before start and TERMINATED after a successful join are stable boundaries; sampling a state after an arbitrary sleep is not a coordination technique.

## Interruption is a cooperative protocol

`thread.isInterrupted()` observes a thread's status without clearing it. `Thread.interrupted()` observes **and clears the current thread's** status. Accidentally consuming that signal can make a later layer miss cancellation.

A method declaring InterruptedException can usually propagate it. A Runnable boundary cannot throw that checked exception to its caller; it commonly restores the status and finishes. A layer deliberately consuming cancellation can have another documented policy. Restoring the status and blindly retrying the same interruptible wait can create a busy failure loop.

For CPU work, check `Thread.currentThread().isInterrupted()` between bounded chunks. The chunk size controls where the program can respond. Finish the current valid state transition before returning; an interrupt is not rollback for an already completed side effect.

## Design a termination policy

A bounded join limits how long the owner waits; a timed-out join does not establish that the worker ended. Report the remaining work or transfer ownership deliberately. Do not claim that a call to interrupt safely terminates arbitrary code.

A daemon thread does not keep the process alive after the non-daemon threads terminate. It is therefore unsuitable as the only owner of essential shutdown work. Virtual threads are daemon threads; their scheduler is studied later. A terminated Thread cannot be started again.

Sleep does not release monitors held by the caller. Wait releases its target monitor and reacquires it before returning; the guarded-waiting chapter develops that different protocol. Yield is a scheduling hint, not fairness or publication. Unsafe stop/suspend-style mechanisms are unsuitable for preserving invariants and can leave invalid state or retained locks.

## Exercise and worked answer

Replace sleeping with processing one bounded chunk, then checking cancellation. State where the last completed chunk commits its result, which resources finally releases, and which owner joins the worker. A correct answer returns when interrupted, keeps the last committed result valid, and does not silently report all requested chunks as complete.

<JavaExample file="ChunkedCancellationLesson.java" output={"completed=3\nchecksum=15150\ncleanup=true"} />

Each chunk computes 1+…+100 into an invocation-local subtotal, then commits that complete 5050 to checksum and advances completed. Status is checked before another chunk begins. There is no sleep, wait or checked exception causing a CPU loop to stop automatically.

The demonstration raises a controlled request **inside the worker after its third commit**, giving a reproducible output. An external owner can call the same Thread's interrupt; the next checkpoint responds to that request, but which chunk it reaches depends on timing. The program does not claim an externally requested cancellation always stops after exactly three chunks.

Five requested chunks and three completed chunks are separate facts. Finally records cleanup even for zero chunks or a request at entry. Main joins before reading the ordinary fields. The Worker constructor permits -1 to disable this controlled request; that variant completes all requested chunks unless another caller interrupts it. The next interruption lesson demonstrates the consuming and non-consuming flag APIs independently.

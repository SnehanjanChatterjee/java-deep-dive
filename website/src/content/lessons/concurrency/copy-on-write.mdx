## A listener traversal needs stable membership

**Snapshot iteration** means one iterator keeps the element membership it captured when created. CopyOnWriteArrayList provides this for a thread-safe list: updates publish a replacement membership array, while an existing iterator continues through its earlier array.

This is useful for a listener registry. A **listener** is an object invoked when an event occurs; a **dispatcher** walks the registered listeners and calls them. If a new listener registers halfway through one dispatch, the dispatcher can finish using its captured membership while a later dispatch sees the update.

Picture array version one holding references A/B, then version two holding changed/B/C. Keeping version one alive lets its iterator finish with A/B. The references in either array can still identify mutable objects; a membership snapshot is not a historical copy of every object's fields. The first program demonstrates both distinctions before examining the publication mechanism.

This tradeoff fits small read-mostly registries with infrequent membership changes. A large frequently changed list pays copying and allocation costs. Choose the observation contract first, then measure whether the workload justifies those costs.

## Array publication and iteration

The implementation holds a current array in a volatile field. Readers capture a reference. Writers take turns changing membership, construct replacement storage and publish it. Never mutating a published array is the crucial representation invariant; the volatile reference alone would not make arbitrary in-place element writes safe.

Appending to n elements normally copies O(n) references and uses O(n) temporary storage. Ordinary positional get is O(1). Specific calls can optimize cases such as setting an identical reference, so do not assert a new allocation for every conceivable method path.

An iterator owns an array reference and cursor. Iterator.remove and list-iterator remove/set/add are unsupported: changing a historical array would not define a coherent current-list edit. Keeping an iterator alive can retain its old array and removed element references after the current list no longer contains them. Reachability, not the time of remove, controls reclamation.

## Compare iterator contracts and compound operations

ArrayList/HashMap fail-fast detection is best effort and supplies no sharing protocol. ConcurrentHashMap-style weak consistency can reflect some concurrent changes without a single snapshot. Synchronized wrappers require their documented complete traversal locking. Avoid the vague label fail-safe; state what the traversal can observe.

Two thread-safe get calls need not select one array generation if a writer changes membership between them. Use an iterator/toArray snapshot when a stable membership set is required, or a larger protocol when multiple objects must agree. AddIfAbsent is an atomic membership operation; contains followed by add leaves a race. Equality implementations can themselves be costly or introduce surprising side effects.

## Register once without a contains/add race

For a listener registry, two callers can both observe contains(listener) as false and then both add it. Each call can be thread-safe while the composite decision permits duplicates. AddIfAbsent represents the complete conditional membership change under the list's update protocol.

If caller A successfully registers listener L and caller B then performs addIfAbsent(L), B reports no new insertion. A dispatcher that captured its iterator **before** registration still uses the earlier array; a later dispatcher can capture the new membership. Unregistering L similarly cannot remove L from an already captured iterator. Decide whether a callback already selected by a dispatch is allowed to finish after unregistration.

Snapshot membership is especially useful when callbacks run outside the membership-update lock. It does not make each callback safe to invoke concurrently or freeze a mutable listener's fields. Keep listener behavior/state ownership separate from registration.

A subList is a backed range with a stricter boundary than a snapshot iterator. Its documented semantics become undefined if the backing list is modified outside that view, including a replacement through set, rather than only a size-changing update. Do not rely on a particular later exception or a stable historical view after that invalidation; use an iterator/toArray when snapshot membership is required. [CopyOnWriteArrayList view contract](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/CopyOnWriteArrayList.html#subList-int-int-)

## Exercise and complete reference solution

Capture an iterator, replace/append membership, then compare the old traversal with the current list. Add one mutable element and explain why the snapshot still returns its changed contents. `SnapshotIterationLesson` is the complete solution.

To implement the principle, serialize writers, copy before changing, publish one volatile array reference and never expose that array for arbitrary mutation. A complete List additionally needs bounds, bulk, iterator and failure contracts; this explanation does not claim to replace the production implementation.

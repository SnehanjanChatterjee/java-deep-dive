## A worker limit does not bound accepted work

Suppose one request arrives while every worker is busy. A pool may queue it, create another worker if policy allows, or refuse it. A queue absorbs a burst; it cannot create sustained processing capacity. If arrivals continue faster than completion, an unbounded queue converts overload into growing latency and retained request state.

ThreadPoolExecutor combines core size, maximum size, queue capacity/type, keep-alive, thread factory and rejection policy. Learn their combined admission decision rather than treating a factory name such as fixed as a complete resource bound.

## Trace admission and rejection

Use core one, maximum two, and queue capacity one. Hold accepted workers at a latch so they cannot accidentally finish during submission.

| Submitted task | Decision | State afterward |
| --- | --- | --- |
| A | Below core size: create worker | One active worker |
| B | Core occupied: enqueue | One active, one queued |
| C | Queue full: grow toward maximum | Two active, one queued |
| D | Queue full and maximum reached | AbortPolicy rejects D |

## Follow the admission algorithm

An unbounded accepting queue usually keeps queuing beyond core size, so increasing maximumPoolSize alone may not add active workers. A SynchronousQueue stores no buffered tasks, making handoff/growth decisions different. Successful offer is followed by lifecycle rechecks because shutdown can race with admission; queued work also needs an available worker.

## Rejection is externally visible behavior

| Policy | Saturated running pool | Consequence to design |
| --- | --- | --- |
| AbortPolicy | Throws RejectedExecutionException | Explicit refusal |
| CallerRunsPolicy | Executes on submitting thread | Caller latency; an unsuitable caller may block |
| DiscardPolicy | Drops silently | Submit-produced Future can remain incomplete |
| DiscardOldestPolicy | Drops queued head and retries | Changed ordering/loss; poor fit for some queues |

CallerRunsPolicy discards during shutdown. A rejection handler returning normally does not prove execution occurred. Retries, result handles, shutdown and overload all need a policy. Do not describe a pool as backpressure without stating who waits or refuses work.

## Workers, retrieval and termination

On the OpenJDK source baseline, runWorker executes tasks and getTask retrieves more, using take or timed poll according to idle-worker policy. Keep-alive normally concerns excess workers; allowCoreThreadTimeOut changes core-idle behavior. An empty queue alone does not establish termination.

The lifecycle distinguishes accepting work, draining accepted work after shutdown, interruption/stopping, and completed worker termination. AwaitTermination waits for that actual transition. The internal control representation coordinates run state and worker count rather than treating a flag write as instant thread death.

A ThreadFactory can name workers and configure uncaught-error policy. A factory returning null can prevent worker creation. beforeExecute/afterExecute hooks must not break workers; a Future-wrapped task can capture a failure without passing it directly as afterExecute's Throwable. Observe the actual task representation.

## Exercise and complete solution

Reproduce A/B/C/D admission with explicit worker milestones and AbortPolicy. `ExecutorSaturationLab` is the complete solution. Explain the effect of substituting an unbounded queue: B, C and D can keep queuing instead of forcing growth/refusal. Explain separately how shutdown racing with queue insertion affects acceptance.

CPU work competes for processors; blocking work also competes for downstream resources. No universal CPU-count formula replaces representative workload analysis. Do not create a new pool per request or let a single worker wait for a child queued behind itself.

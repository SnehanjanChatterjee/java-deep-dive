## A worker limit does not bound accepted work

A **ThreadPoolExecutor** is an execution service combining reusable worker threads with a queue of accepted tasks waiting to run. Its **admission decision** determines what happens to each newly submitted task: run it on a worker, store it for later, or apply a rejection policy.

Three settings explain the ordinary decision. **Core size** is the worker-count threshold below which a new task normally causes worker creation. Once that threshold is reached, the pool tries its work queue. **Queue capacity** limits stored waiting tasks. **Maximum size** limits growth when the queue cannot accept another task; a larger maximum does not make the pool skip an available queue slot.

This matters during overload, when work arrives faster than it can be completed. A queue can absorb a burst while retaining each task's state; an unbounded backlog can keep increasing waiting time and memory use. A finite worker count alone therefore does not define a finite accepted workload.

Start with core one, maximum two and one queue slot. The example uses ArrayBlockingQueue as fixed-capacity task storage and AbortPolicy as the rule that throws when the pool refuses a task. Familiar latches keep workers busy long enough to follow each decision. Idle-worker timeout, alternate handlers and source internals come after that ordinary admission trace.

An unbounded accepting queue usually keeps queuing beyond core size, so increasing maximumPoolSize alone may not add active workers. A SynchronousQueue stores no buffered tasks, making handoff/growth decisions different. Successful offer is followed by lifecycle rechecks because shutdown can race with admission; queued work also needs an available worker.

## Change one capacity choice and predict admission again

Keep core one and maximum two, but make the queue capacity two. With workers held at release, A creates the core worker, B and C enqueue, D creates the second worker only after the queue is full, and E would be rejected. Increasing maximum alone does not make B skip an available queue slot.

Now use an accepting unbounded queue: after A, later tasks normally keep queueing, so the maximum of two does not make a second worker appear solely because backlog exists. With a direct-handoff SynchronousQueue, there is no stored slot for B; when handoff cannot match an idle worker, admission considers growth or rejection instead.

These dry runs assume a running pool, successful thread creation and the stated held-worker milestones. Shutdown races and ThreadFactory failures are additional branches in the real algorithm. Core workers need not all exist at constructor return; prestart APIs deliberately change that behavior. Core is also not an absolute floor when core timeout is enabled. ## Rejection is externally visible behavior

| Policy | Saturated running pool | Consequence to design |
| --- | --- | --- |
| AbortPolicy | Throws RejectedExecutionException | Explicit refusal |
| CallerRunsPolicy | Executes on submitting thread | Caller latency; an unsuitable caller may block |
| DiscardPolicy | Drops silently | Submit-produced Future can remain incomplete |
| DiscardOldestPolicy | Drops queued head and retries | Changed ordering/loss; poor fit for some queues |

CallerRunsPolicy discards during shutdown. A rejection handler returning normally does not prove execution occurred. Retries, result handles, shutdown and overload all need a policy. **Backpressure** feeds capacity pressure back to upstream submitters so they can slow or otherwise respond. If that is the intended behavior, state exactly which caller waits, performs work or observes refusal.

## Workers, retrieval and termination

On the OpenJDK source baseline, runWorker executes tasks and getTask retrieves more, using take or timed poll according to idle-worker policy. **Keep-alive** is the idle-time allowance used when workers are eligible to time out. It normally concerns excess workers; allowCoreThreadTimeOut changes core-idle behavior. An empty queue alone does not establish termination.

The lifecycle distinguishes accepting work, draining accepted work after shutdown, interruption/stopping, and completed worker termination. AwaitTermination waits for that actual transition. The internal control representation coordinates run state and worker count rather than treating a flag write as instant thread death.

A ThreadFactory can name workers and configure uncaught-error policy. A factory returning null can prevent worker creation. beforeExecute/afterExecute hooks must not break workers; a Future-wrapped task can capture a failure without passing it directly as afterExecute's Throwable. Observe the actual task representation.

## Avoid a dependency that cannot be scheduled

With two workers and a barrier requiring three tasks, the first two tasks can occupy the pool while the third stays queued. The barrier cannot advance because no worker is available for that third participant. Increasing a wait timeout does not create execution capacity.

Likewise, a worker retaining the only permit while waiting for a child that needs the same permit creates a resource dependency. Draw the work and resources together. Coordination utilities do not remove the need to prove useful progress.

## Exercise and complete solution

Reproduce A/B/C/D admission with explicit worker milestones and AbortPolicy. `ExecutorSaturationLab` is the complete solution. Explain the effect of substituting an unbounded queue: B, C and D can keep queuing instead of forcing growth/refusal. Explain separately how shutdown racing with queue insertion affects acceptance.

CPU work competes for processors; blocking work also competes for downstream resources. No universal CPU-count formula replaces representative workload analysis. Do not create a new pool per request or let a single worker wait for a child queued behind itself.

## Name the operation before choosing the container

A **concurrent collection** is a container whose documented operations support access by multiple threads. Its **contract** specifies which changes are indivisible, how traversal behaves during updates, which order is preserved and whether storage or waiting is bounded. The class name alone cannot choose those requirements for an application.

Start with the complete operation. A frequency table needs one indivisible increment for a key. A work queue needs a rule for empty and full storage. A listener registry, a list of callbacks invoked for events, may need one stable membership set throughout a dispatch. All share data, but each needs a different observation or update guarantee.

The familiar monitor remains a useful baseline: guard the complete state transition with one lock and check its waiting predicate. First trace a tiny bounded queue using that principle, then compare the library contracts that specialize it. Two individually safe method calls still leave an interference interval unless their larger operation has its own protocol.

## Trace storage and application ownership separately

At FIFO capacity two, inserting first and second fills storage. Removing first frees a slot; third can reuse that physical position while logical order remains second, third. Bounded queued storage does not bound running producers, waiting requests or downstream connections. A larger request may hold memory before insertion and after removal.

FIFO means first-in-first-out: the earliest accepted stored element is the next removed. The teaching queue uses an array as a ring. Head identifies the next removal position, tail the next insertion position, and size counts occupied slots. Indexes wrap from the last slot back to zero. One monitor guards those fields and their empty/full predicates.

An operation is **linearizable** when its effect can be placed at one point between its invocation and return while preserving the specified sequential behavior. That point is its **linearization point**. A protected queue insertion/removal can supply such a transition; a changing aggregate observation or an iterator may have a weaker contract. Ask which operation is guaranteed, rather than applying one label to every method on a class.

## Choose a contract for a concrete problem

| Problem | Candidate | Why the contract matters |
| --- | --- | --- |
| Shared independent key counts | ConcurrentHashMap merge/compute | One supported per-key update is atomic; several keys are not a transaction |
| Bounded FIFO producer-consumer pipeline | ArrayBlockingQueue | Put/take can wait; timed offer can refuse admission |
| Immediate nonblocking FIFO endpoints | ConcurrentLinkedQueue | Poll reports emptiness; there is no built-in capacity/waiting policy |
| Shared ordered keys and neighbors | ConcurrentSkipListMap | Comparison-based navigation; range views remain backed and concurrent |
| Read-mostly stable listener membership | CopyOnWriteArrayList | Iterator captures an array; mutations copy references |
| Invariant spanning arbitrary objects/calls | One common lock or combined immutable state | All participating accesses must use the same larger protocol |

Each container has a focused chapter and complete usage example. AtomicInteger/AtomicReference and LongAdder address different scalar-state questions in the later atomics chapter; a statistics sum is not a hard admission decision.

## Compare iteration guarantees

**Traversal** is a sequence of observations, such as advancing an iterator through elements. A snapshot fixes the captured membership, a weakly consistent traversal can reflect some concurrent updates, and fail-fast detection tries to report unsupported structural change. These policies describe different observations; exception detection is not the mechanism that makes a shared algorithm safe.

| Container family | Traversal model | What it means |
| --- | --- | --- |
| Ordinary ArrayList/HashMap | Best-effort fail-fast | Detection is not a thread-safety protocol |
| CopyOnWriteArrayList | Captured array membership | Later structural updates do not change that iterator |
| ConcurrentHashMap/linked queue/skip list | Weakly consistent | Traversal tolerates updates without one global point-in-time snapshot |
| Synchronized wrapper | Documented mutex protocol | Caller must coordinate complete traversal where required |

The loose phrase fail-safe hides important differences. A snapshot array still points to the same mutable elements. A weakly consistent view can reflect some updates without representing one historical map.

## Hold a synchronized wrapper's mutex for a traversal

Collections.synchronizedMap protects individual operations through a **mutex**, a mutual-exclusion lock. Here the returned wrapper object's monitor is that lock. Iterating is a sequence of operations, so its documented traversal protocol requires synchronizing on the **returned map wrapper** across the whole traversal:

```java
final Map<String, Integer> counts = Collections.synchronizedMap(new HashMap<>());
counts.put("java", 2);
synchronized (counts) {
    for (final Map.Entry<String, Integer> entry : counts.entrySet()) {
        System.out.println(entry.getKey() + "=" + entry.getValue());
    }
}
```

This excerpt assumes the displayed Map, Collections and HashMap imports; it illustrates the mutex protocol rather than launching competing tasks. Keep the original backing map private so another caller cannot bypass the wrapper. Synchronizing only on entrySet, an iterator or a separately created Object does not acquire the wrapper's specified mutex.

The same common lock can cover a compound read/check/update when all participants follow it. Copying a live HashMap into a new HashMap without coordination does not make that traversal safe. Choose a documented concurrent traversal or obtain the required stable observation under its actual guard. [Collections synchronizedMap traversal contract](https://docs.oracle.com/javase/8/docs/api/java/util/Collections.html#synchronizedMap-java.util.Map-)

## Do not compose guarantees that were never promised

A concurrent map holding ArrayList values does not make concurrent list.add safe. A get followed by put can lose an update despite each call being thread-safe. An unbounded queue does not enforce backpressure. A sorted concurrent map does not reserve an entire range atomically. Synchronizing only writes while making uncoordinated ordinary reads does not provide a complete protocol.

Null policy, equality/comparison cost, callback duration, contention and retained storage also matter. A complexity label alone does not decide latency. A consistently shared coarse lock can be correct when the full invariant needs exclusion; concurrent primitives are useful when their individual contracts fit.

## Exercise with explained choices

A consumer must wait when no work exists and producers must not queue beyond 100 items. Choose a bounded BlockingQueue and an explicit termination policy. Replacing it with ConcurrentLinkedQueue plus `if (size() < 100)` is insufficient: the check and insertion can race, and size itself can require traversal while changing.

For a frequency map, use an atomic merge rather than get/put. For stable callbacks over an infrequently changed registry, consider a copy-on-write snapshot while giving mutable listener objects their own policy.

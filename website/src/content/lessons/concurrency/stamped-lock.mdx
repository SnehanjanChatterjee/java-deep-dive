## Read two coordinates that a writer changes together

A **StampedLock** coordinates read and write access using **stamps**, long-valued tokens returned by its operations. A stamp identifies a held lock mode or an optimistic observation for that lock. The matching API uses it for unlock, validation or attempted mode conversion; it is not the protected data itself.

Its distinctive option is an **optimistic read**: copy a small amount of state without acquiring read ownership, then validate whether a write acquisition invalidated that observation. The local copies are **tentative**, meaning they must not be trusted yet. If validation fails, discard them and reread under a real read lock.

Use a point with x and y changed together. Distance from the origin depends on one consistent pair: (3,4) gives five and (6,8) gives ten. A reader must avoid acting on a mixture. The ordinary distance method copies the coordinates, validates, falls back if necessary, then calculates from its selected locals.

Optimistic access deliberately allows overlap with a writer. It therefore fits a carefully limited copy-and-check operation, rather than arbitrary traversal or side effects through temporarily inconsistent objects. First follow the point program; the second experiment then forces a rejected validation without depending on a racing schedule.

## Force the validation-failure branch

<JavaExample file="StampedValidationLesson.java" output={"tentative=0\nvalid=false\nselected=42"} />

The caller obtains an optimistic stamp and copies zero. It then deliberately acquires write mode, changes the protected element to 42 and releases write mode before validating the old stamp. Validation must reject that interval. The fallback obtains genuine read ownership and rereads 42, which becomes the selected result.

This single-thread experiment isolates the version/validation rule. It does not claim to have forced two threads to race or measured contention. In a real optimistic reader, an intervening writer can create the same invalidation, and tentative fields must remain unused until the observation is validated or replaced by a protected reread.

Validation does not retain ownership afterward. A writer may acquire immediately after successful validation, so the reader should calculate from the validated local copies rather than return to unprotected fields and assume the stamp reserved them. A valid past interval and a lock held over future accesses are different guarantees. [StampedLock validation contract](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/locks/StampedLock.html#validate-long-)

## A stamp is not reentrant thread ownership

StampedLock has a different ownership model from ReentrantLock and is not reentrant. Holding a write stamp and calling a method that tries to acquire another incompatible stamp can prevent progress. Unlock requires the matching valid stamp/mode. Do not transfer familiar reentrant-lock assumptions mechanically.

Conversion APIs can try to change modes, but a failed conversion must be handled without using an invalidated assumption. Releasing and reacquiring allows intervening writers, so recheck the protected predicate. An optimistic stamp of zero cannot authorize a successful optimistic observation.

Avoid callbacks, inconsistent graph traversal or externally visible side effects before validation. If the tentative operation throws or already acts on inconsistent data, validating afterward cannot undo that behavior. Primitive-field copying is a deliberately small example with a clear fallback.

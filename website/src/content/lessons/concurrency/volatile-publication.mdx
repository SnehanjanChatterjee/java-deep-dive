## A reader needs one complete configuration generation

A writer updates base price and fee. A reader must use the pair from one generation. Making two independent fields volatile does not combine two writes into one replacement: a reader can capture an old base and new fee between those writes.

Instead, construct one immutable Snapshot containing both fields and publish one volatile reference. Each reader captures that reference once and reads its fields through that one local value. The object groups the invariant; volatile supplies the publication boundary.

## What volatile guarantees

A volatile write happens-before subsequent reads of that variable under the synchronization rules. With program order and transitivity, ordinary initialization before publication becomes visible following the observing read. This is a rule about allowed observations, not an invitation to describe every cache instruction literally.

Calling read twice can legitimately select different generations. Writing two volatile fields does not create an atomic record. Making an array reference volatile does not make every array element volatile. A volatile count++ still has a read/compute/write interference interval.

## Final fields and construction escape

Correctly constructed final fields have specific initialization-safety guarantees. A final reference to a mutable array or list does not protect its later contents. Retaining and exposing an externally mutable array would also defeat this Snapshot's intended immutability.

Do not publish this from an unfinished constructor through a callback, listener registration or started thread. Another execution can observe the object before its invariant is established. Construct privately, validate, then publish the completed value at an explicit boundary.

## Double-checked locking and initialization holders

A lazy shared Service can use a volatile reference, one local fast-path read, a synchronized initialization block and a second null check inside that block:

```java
private static volatile Service instance;
static Service instance() {
    Service local = instance;
    if (local == null) {
        synchronized (Service.class) {
            local = instance;
            if (local == null) {
                local = new Service();
                instance = local;
            }
        }
    }
    return local;
}
```

This is an advanced pattern excerpt assuming a compatible Service type and a deliberate single-instance policy. Without the inner check two contenders can construct; without volatile, unlocked readers lack the intended publication edge. Mutable Service methods still need their own sharing policy.

Class initialization can often express lazy one-time construction more simply through a static holder. Its initialization/failure rules are developed in JVM internals: retrying an ordinary constructor failure and remembering a class-initialization failure are different policies. Lazy initialization is not automatically the right default.

## Exercise and complete reference solution

Repair two separately volatile configuration fields so each operation reads one consistent generation. `VolatilePublicationLab` is the complete solution. The essential steps are grouping, validation, one volatile replacement and one captured reader reference. If writers calculate a replacement from the current state, they can still lose each other's updates; use a common lock or CAS over the whole immutable state for that different problem.

A volatile reference does not repair a mutable map key whose equality/hash fields change; key identity and later mutation remain separate contracts. A volatile cancellation flag is useful only if work checks it. A thread blocked in an unrelated operation also needs that operation's cancellation mechanism. The lifecycle chapter adds cooperative interruption and cleanup.

## A consumer cannot take a message that does not exist

A lock protects an update while a thread owns it. A consumer that finds an empty mailbox needs another capability: stop using execution capacity until a producer changes the state. Sleeping while holding the mailbox monitor prevents the producer from entering. Repeatedly checking without waiting wastes work and does not create a correct handoff.

`wait` lets the consumer release the target monitor and suspend. Before it returns, the consumer must reacquire that monitor. The mailbox fields record the condition; notification merely makes waiters eligible to try again.

## A condition is state, not an event

The general pattern checks a predicate and changes state under the same monitor:

```java
synchronized (monitor) {
    while (!predicate()) {
        monitor.wait();
    }
    performGuardedChange();
}
```

The names stand for state operations guarded by monitor. A notification delivered before wait is not remembered as a credit. Checking the durable predicate under the lock handles that case: if a value already exists, there is no reason to wait.

## A notification is not a stored message

If a caller owns an object's monitor and invokes notify when nobody is waiting, the call returns without storing a credit for some future wait. Calling notify or wait without owning **that object's** monitor instead throws IllegalMonitorStateException. Synchronizing a different object does not satisfy this requirement.

This explains a classic missed-signal bug: a producer notifies, then a consumer starts and unconditionally waits. No future notifier need exist. The correct consumer checks a persistent guarded predicate first; if the item is already present, it proceeds without waiting. The producer changes that predicate under the same monitor before notifying.

Notify selects one arbitrary waiter; the contract does not promise a random distribution, oldest waiter or the worker with the right predicate. NotifyAll makes all waiters eligible to compete, but does not itself guarantee fairness or prevent every form of starvation. The odd-even/three-thread lesson applies these rules to a finite sequence, including the final wakeup and cancellation branches. [JLS wait sets and notification](https://docs.oracle.com/javase/specs/jls/se8/html/jls-17.html#jls-17.2)

## Why wakeup requires a while loop

A notification does not reserve the item. Another consumer can reacquire first and remove it. Spurious wakeups are also permitted. In both cases the awakened thread must check again. Notify/notifyAll retain the notifier's ownership until it exits; they do not hand the lock to a selected consumer.

Each object can serve as a monitor. A synchronized instance method locks its receiver; a static synchronized method locks the declaring Class object. Calling wait/notify without owning the target monitor throws IllegalMonitorStateException. Wait releases only its target monitor, not every other lock held by the thread. Monitors are reentrant, but callbacks under a lock can still observe a temporarily broken invariant or introduce another lock dependency.

Here value and closed form one guarded invariant. Null is rejected as data because it represents an empty slot. Put waits while occupied and open, then rechecks closure before writing. Take waits while empty and open; it drains accepted data after closure and returns null only when closed and empty. Close sets the flag and wakes both producer and consumer populations.

NotifyAll is useful because one wait set contains different predicates. Waking an arbitrary producer when only a consumer can progress can leave useful work asleep. Separate Conditions in the next chapter target distinct waiter populations.

## Interruption, timeouts and exercise solution

Interrupted waits propagate InterruptedException rather than inventing a delivered value. Normal contended synchronized entry is not an interruptible acquisition; interrupting a BLOCKED entrant does not make entry throw. Removal is not successful processing: acknowledgement/retry for a larger operation needs another contract.

For a timed guarded wait, retain one monotonic remaining-time budget and recheck the predicate after every return. Restarting the full timeout after notification can exceed the intended budget. Scheduling and monitor reacquisition can still delay actual return.

The primary exercise is a one-slot drain-on-close mailbox. `MonitorMailbox` is the complete solution: explain both while conditions, why closure is rechecked after put's wait, and why close notifies every kind of waiter. Use an established BlockingQueue in application code when its contract fits; this teaching implementation is intentionally smaller.

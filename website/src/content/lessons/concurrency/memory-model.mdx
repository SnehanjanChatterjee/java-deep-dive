## A correct final value needs both update and observation rules

The counter lesson established two requirements. A monitor protects each complete increment, and join waits for the worker's completion. The Java Memory Model supplies the language rules for which writes another thread may observe and what ordering relationships constrain those observations. It explains why these protocols work across supported compilers and processors.

It is not a physical heap diagram or a claim that every thread owns a separate copy of every field. A call stack explains invocation ownership; the memory model explains permitted shared-memory observations.

## Start with one ordinary result after join

<JavaExample file="JoinPublicationLesson.java" output={"42"} />

The result field is ordinary, not volatile or atomic. There is one writer. Main does not read until join returns successfully. All worker actions happen-before the actions after that successful join, so the write of 42 is published to the subsequent read.

Removing join changes two things: main might run before the write, and the program loses this termination-publication edge. Merely waiting a convenient number of milliseconds establishes neither requirement. Replacing the field with an atomic type alone would not wait for work to occur.

## Construct a happens-before proof

Happens-before is an ordering relation between actions. Draw the worker's write, the successful join boundary, then main's read. The edge proves that this read follows the completed writer under the language rules, rather than relying on an observed wall-clock order.

<Diagram client:visible definition={"flowchart LR\n W[Worker writes result 42] --> E[Worker terminates]\n E -->|successful join| J[Main continues]\n J --> R[Main reads result]"} caption="Worker completion observed through join publishes preceding actions. This is an ordering proof, not a model of literal cache transfers." />

| Relationship | Ordered actions |
| --- | --- |
| Program order | Earlier actions of one thread precede its later actions for memory-model reasoning |
| Thread.start | Caller actions before start precede actions in the started thread |
| Successful termination detection through join | Worker actions precede the observer's actions after join |
| Unlock then later lock on the same monitor | Protected writes become visible to that acquiring thread |
| Transitivity | If A precedes B and B precedes C, A precedes C |

In the synchronized counter, every increment acquires the same receiver monitor. An earlier owner's unlock orders its protected update before a later owner's locked read/update. Different monitor identities do not supply that relationship. Future retrieval and coordination utilities later provide their own documented publication boundaries.

## Separate visibility, ordering and atomicity

Visibility concerns which writes a reader can observe. Ordering concerns relationships between actions. Atomicity concerns whether a complete operation can be treated as indivisible relative to competing operations. A completed ordinary-field write can be safely observed after join without making a future two-worker increment atomic.

The earlier chosen lost-update schedule shows the distinction. Two callers can both read zero, then both write one, even if individual reads/writes are visible. Protect the whole read/modify/write with one protocol. An invariant spanning two balances needs more than an independent atomic update of each field.

A race condition means correctness depends on uncontrolled relative timing. A **data race** is the narrower memory-model situation of conflicting accesses to the same variable, at least one a write, not ordered by happens-before. Individually thread-safe map calls can still form a check-then-act race; their separate guarantees do not combine into a transaction.

## What correctly synchronized reasoning permits

A correctly synchronized program has the JMM's sequential-consistency guarantee: it can be reasoned about through interleavings consistent with thread program order. Implementations can still optimize as long as required observations are preserved. Happens-before does not demand a literal machine instruction for every source expression.

A data race removes this convenient guarantee. It does not make every imaginable behavior legal: intra-thread semantics and the model's other constraints still apply. Ordinary reference/most primitive reads and writes are individually atomic, while the specification permits some non-volatile long/double accesses to be treated as halves. None of those individual-access rules makes a compound operation atomic.

The next chapter adds volatile publication to exchange an immutable snapshot before the writer terminates. Final fields have construction-specific initialization guarantees; they do not freeze mutable referents or protect later updates. Keep construction, publication and later mutation as separate boundaries.

## Exercise with a complete reference solution

Why is the ordinary result in `JoinPublicationLesson` correct? Identify one writer, no concurrent read, termination detection through join, and the read afterward. Why is a counter shared by two incrementing workers a different problem? Their updates can overlap before either terminates.

`SharedStateLesson.countSafely` is the complete repaired two-worker solution. Trace both the monitor's exclusion/publication and main's completion boundary. An output matching the expected value in one racy run proves neither contract.

Actor/outcome tools such as jcstress can search for unexpected outcomes; failure to observe an outcome does not prove it forbidden. The advanced atomics chapter revisits a barrier-forced lost update after those coordination mechanisms are familiar.

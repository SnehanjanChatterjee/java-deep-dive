## Three workers share two resource slots

A **Semaphore** maintains a count of available **permits**, units of permission to enter some operation. Acquire takes a permit when available; release returns one under the application's protocol. With no permit available, an ordinary acquire waits interruptibly until permission becomes available.

The purpose is **admission control**: decide how many callers may use a limited resource at once. A program might have many threads while a remote service permits only two simultaneous calls. One shared Semaphore initialized to two can represent those two slots, provided every caller follows the acquire/use/release protocol.

The mental model is a resource with two available places, rather than two special worker threads. Any worker can acquire a place, perform the actual service operation and return the permit. A waiting worker owns no place yet. Keep the permit around resource use, allowing unrelated work to happen outside that region.

First read the ordinary acquired-region pattern. The complete three-worker experiment then adds familiar latches solely to make the maximum simultaneous use observable without timing guesses.

## Put finally around the acquired region

```java
permits.acquire();
try {
    useResource();
} finally {
    permits.release();
}
```

Acquisition is before the try whose finally releases. If acquire throws InterruptedException, no permit was acquired. Entering an unconditional release finally before successful acquisition would increase capacity incorrectly. The full program below applies this rule and also cleans up its latch-controlled workers on an exceptional owner path.

## Run a coordinated admission experiment

<JavaExample file="PermitLesson.java" output={"maximum=2\npermits=2"} />

There are three workers and two permits. The first two admitted workers count down entered, then wait on release while retaining their permits. The third cannot pass acquire yet. Main waits for both entered signals, establishing occupancy two without guessing elapsed time. It then opens release, allowing all workers eventually to finish.

Occupancy's synchronized enter/leave methods record active users; they do not control admission. Semaphore is the mechanism enforcing the bound. The maximum is two because main establishes two admitted users and the two-permit budget prevents a third concurrent user. After joining every worker, availablePermits is two again.

A Semaphore does not track permit ownership like a ReentrantLock. A different thread can legitimately release for a handoff protocol, but accidental extra releases are not automatically rejected. A one-permit semaphore is not a reentrant mutex (a mutual-exclusion lock): the same thread acquiring again can wait for its own retained permit.

## A permit can publish data without being an ownership lock

Start a semaphore at zero permits. A producer writes payload 42 and then releases one permit. A consumer successfully acquires that permit and then reads payload. The release/acquire memory effect can publish that preceding write; the producer and consumer need not be the same thread.

That ownerless design also explains a danger: release does not check that this caller previously acquired. With initial capacity two, acquire changes available permits to one and one matching release restores two. A second erroneous release raises availability to three; the semaphore does not preserve the original resource capacity for the application.

For this resource-lending example, only a caller whose acquire succeeded enters the finally responsible for release. An InterruptedException before acquisition grants no permit to return. A multi-permit acquire also needs its full requested count; several small callers and one large caller can interact differently under fairness policy. Untimed tryAcquire has documented barging behavior even for a fair semaphore. These are acquisition rules, not end-to-end task completion guarantees. [Semaphore ownership and memory effects](https://docs.oracle.com/javase/8/docs/api/java/util/concurrent/Semaphore.html)

## Capacity, fairness and rate are different

A plain count limits simultaneous admission. It does not enforce calls per second: a fast task can acquire/release many times within a time interval. Rate limiting requires a time/replenishment policy as well.

Fair construction influences documented acquisition order under contention. Untimed tryAcquire can **barge**, meaning it takes an available permit ahead of already waiting callers. Fairness does not guarantee equal CPU service or equal response latency. Timed tryAcquire bounds the waiting policy; the parent operation should decide whether its deadline includes admission, resource work and cleanup.

A worker retaining the only permit while waiting for a child that needs it can prevent progress. Permits cannot manufacture downstream capacity. Virtual threads later change the cost of waiting; they do not change this resource invariant.

## Exercise and complete reference solution

Run three tasks with two permits, establish two simultaneous admitted users, then prove all acquired permits are returned. `PermitLesson` is the complete solution. Main's entered signal proves a milestone; joining proves the workers ended. Reading a convenient count before cleanup would not establish restoration.

For an interrupted acquisition, the correct answer records cancellation and releases nothing. For failure after acquisition, release exactly once in finally. An external write performed before failure may still need compensation; returning a permit does not undo that write.

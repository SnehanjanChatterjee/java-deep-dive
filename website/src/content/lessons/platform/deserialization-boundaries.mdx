## Check representation, graph and value separately

Native reconstruction can invoke class-specific behavior and consume resources before application code uses the final value. Prefer deliberately designed external formats and validation for untrusted boundaries. Where native serialization is required, a narrow type policy, bounded input and graph limits complement domain validation; none substitutes for the others.

## Trace the five boundaries in decode

Decode rejects a null input and byte arrays above its limit before constructing ObjectInputStream. The per-stream filter checks depth, reference count, array length and bytes consumed. Those checks run even when serialClass is null, because a callback without class information can still carry graph metrics.

The filter allows the expected Score class and rejects other reported classes. UNDECIDED for a classless event is not a blanket allow-list entry. readObject then reconstructs the representation. Score's private readObject calls defaultReadObject and checks the restored 0..100 invariant, throwing InvalidObjectException if invalid. Finally, decode checks that the returned top-level object is actually Score.

<Diagram client:visible definition={"flowchart LR\n B[Bound input length] --> F[Filter class and graph metrics]\n F --> R[Restore representation]\n R --> V[Validate Score state]\n V --> T[Check root type]\n T --> U[Use expected value]"} caption="Each step establishes a different property of the eventual value." />

A root-type check is still needed because filter callbacks are not a universal final-result type assertion. readResolve and other hooks can change conventional reconstruction behavior; a broad package allow-list admits more behavior than a narrow type policy. Filters should reflect the actual use context. Context-specific filter factories can establish policies for multiple components; adding a filter does not validate every allowed class's semantics.

## Compatibility does not replace validation

Declare serialVersionUID deliberately for a native-serializable type. Keeping the same UID permits particular compatibility processing, but a newly added field can restore to a default that violates today's invariant. Changing a UID merely to silence an error discards the question of how stored data should evolve.

A serialization proxy can represent a type using a restricted intermediate form and reconstruct through a controlled invariant boundary. It still needs a format/type/resource policy. Constructor validation remains insufficient for conventional Serializable classes whose fields are restored outside the ordinary constructor path.

## Practice: classify four defenses

Which check rejects an oversized byte array? Which catches restored score -1? Which proves the root is Score? Which authorizes the caller to change a score?

<details>
<summary>Answer</summary>

The pre-stream byte-length check handles the first, Score.readObject's invariant check the second, and the explicit instanceof root check the third. None authorizes a caller: authentication/authorization belong to the application operation boundary. Matching UID, a valid graph and a valid score can all coexist with an unauthorized operation. Test rejection categories independently rather than asserting only a message containing rejected.

</details>

## Separate a rejected graph from a rejected value

| Input variation | Expected failure boundary | Why another check is insufficient |
| --- | --- | --- |
| Excessive byte array before parsing | Pre-stream size limit | A root-type test comes too late to bound that allocation |
| Unexpected reported class | Type filter | A matching top-level type would not constrain every nested type |
| Excessive references/depth/array length | Graph/resource limit | A small set of class names can still describe an enormous graph |
| Score outside its invariant | readObject validation | The allowed Score class name says nothing about its field values |
| Unexpected final root | Post-read type check | Substitution hooks can affect the resulting object |

The supplied filter rejects a resource-limit violation before deciding a class-specific status. Reversing that order and returning ALLOWED immediately for Score would skip graph checks for that callback. UNDECIDED is a status passed to the surrounding filter policy; it is not a synonym for rejected, nor proof that some other policy rejects every unlisted event.

<details>
<summary>Is keeping serialVersionUID constant enough to add a new positive quantity field safely?</summary>

No. An older stream may have no value for the field, so zero can be restored under a compatible representation evolution. Decide how to migrate that data or reject it if the new invariant cannot be satisfied. Validation belongs on the reconstruction path as well as ordinary construction. A serialization proxy can centralize reconstruction, but still needs input and graph boundaries.

</details>

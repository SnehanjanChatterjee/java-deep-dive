## Obtain an executable operation with an explicit type

A Method represents reflective member metadata. A MethodHandle is a typed executable reference, which can also be adapted or composed. Its MethodType specifies the return type and parameter types. Lookup performs access checks when creating the handle; passing the resulting handle can transfer the capability to invoke its target.

<JavaExample file="MethodHandleLesson.java" output={"6\n8\nwrong signature"} />

FindStatic requests twice on this class with signature `(int)int`. This lookup can access its own private method. The first call supplies an int argument and explicitly requests an int return, matching the handle exactly and returning six. Main declares Throwable because the invocation APIs can propagate the target's failures; a production boundary should handle its intended contract deliberately.

## The call site's return type matters

InvokeExact matches argument **and result** types, rather than asking whether a runtime value could fit some wider type. The `(int)` cast on its call contributes to that descriptor. An uncast call used as an Object expression requests Object, which does not exactly match int. This is signature-polymorphic invocation, not ordinary overload selection among Java methods named twice.

The attempted exact call with 4L has a long argument, so WrongMethodTypeException occurs before twice can perform its multiplication. A target's own ArithmeticException would be a different failure after successful invocation shape checking.

## Adapt intentionally instead of relying on hidden conversions

AsType constructs an adapted handle accepting short and returning long. Its invocation widens short 4 to the target's int input, then widens the int result 8 to long. The new handle still requires its own exact `(short)long` shape at invokeExact. Adaptable invoke can apply permitted conversions, but is not a universal way to accept arbitrary objects.

FindVirtual differs from findStatic: the requested method type describes the member's parameters/result, while the obtained handle also needs the receiver as an invocation argument. BindTo can bind an appropriate receiver and remove that parameter. Keep receiver, arguments and result visible when writing down the invocation type.

## Keep access and performance claims precise

A lookup has a defined access context. Handles do not automatically bypass module readability or package openness. Do not pass a privileged private-member handle to code that should not possess that capability. A handle is immutable, while its target can still mutate state or require coordination.

Lookup frequency, adaptation and call-site stability affect optimization. Measure an actual invocation pattern before claiming handles always outperform reflection or direct calls. A cached handle can avoid repeated lookup without proving every remaining cost disappears.

## Practice: diagnose two failures

An exact invocation uses long where the handle expects int. A correctly shaped call instead supplies Integer.MAX_VALUE to twice. Are these the same error?

<details>
<summary>Answer</summary>

No. The first fails the invocation type relationship with WrongMethodTypeException. The second reaches Math.multiplyExact and fails with ArithmeticException because the int result would overflow. Changing a cast can fix an invocation descriptor, but cannot make an overflowing mathematical result fit the declared numeric domain.

</details>

## Write the type through each adaptation

| Operation in the example | Incoming type | Resulting handle type |
| --- | --- | --- |
| findStatic twice | Lookup requests int result, one int input | `(int)int` |
| asType | Request short input and long result | `(short)long` |
| exact adapted call | The call site supplies short and requests long | Executes with those exact declared types |

The shown adaptation performs short-to-int widening before the target and int-to-long widening afterward. Every short value doubled fits int, so this particular `(short)long` adapter cannot overflow twice's multiplication. The original `(int)int` target, or an `(int)long` adapter, can still receive an int whose doubling overflows before any return widening. Adapting a result type cannot recover a mathematical result that the target never represented.

Handles can be composed as well as converted. `filterArguments` places a conversion/filter in an input position; `filterReturnValue` applies a compatible operation to a result; `guardWithTest` selects between compatible targets. Derive the full input/result shapes before composing them. These operations build invocation objects, not a promise that a new thread or dynamic Java overload search will run. [Handle combinators](https://docs.oracle.com/javase/8/docs/api/java/lang/invoke/MethodHandles.html)

<details>
<summary>What changes when a virtual handle is bound to one receiver?</summary>

The unbound handle needs the receiver in addition to the member's explicit parameters. Binding a compatible receiver supplies that argument in advance, so it disappears from the resulting invocation type. The target still acts on that same receiver and can mutate its state. Handle immutability therefore does not imply target immutability or automatic thread safety.

</details>

## Foreign memory is storage accessed outside ordinary Java object fields

The **Foreign Function and Memory API (FFM)** provides supported access to memory regions and native functions outside ordinary Java object operations. Native storage is often outside the garbage-collected Java heap, so its location, representation and lifetime need an explicit model. The stable API begins in Java 22.

A **memory segment** is a bounded view of storage. An **arena** owns the lifetime of certain allocations. A **layout** describes how values occupy bytes. We will allocate one int, write and read it while its owner is open, then observe why retaining a segment reference cannot authorize access after close. Native function calls follow only after those memory concepts.

## Give native storage an explicit owner

The first program needs only one int, not a native library. Create an arena, allocate a segment using the Java-int layout, store 42 at byte offset zero and read it before close. Keep the segment reference after leaving the owning block and attempt another read. That last operation demonstrates lifetime checking: the variable can still exist after permission to access its storage has ended.

<JavaExample file="modern/ForeignMemoryDemo.java" output={"42\nclosed"} />

`Arena.ofConfined` creates an explicitly closeable arena owned by the current thread. `allocate` reserves storage for one int layout. `set` writes 42 at byte offset zero, and get reads it while the arena remains open. Try-with-resources closes the arena. The retained segment reference still exists, but access is rejected because the storage lifetime ended. Reachability is not ownership permission.

## Separate byte offsets from Java array indexes

<JavaExample file="modern/ForeignLayoutLesson.java" output={"0:4\n7\nclosed"} />

The point layout has two named Java-int members. X is at byte offset zero and y at four. The code derives those offsets through layout paths rather than scattering constants. It writes three and four, then reads their sum seven. The same segment becomes invalid when its arena closes.

Struct members follow one another; a layout does not guess an external native format's padding. A byte followed by an aligned int may need an explicit padding layout. Layouts also describe byte order and alignment. A slice is a view sharing storage and scope, not an independent allocation that extends the arena lifetime.

## Trace the ownership graph of a slice

Suppose an arena allocates eight bytes for the two-int point. A slice covering bytes four through seven identifies the y region. Reading offset zero from that slice means the original segment's y location, not a copied int. A write through either view can be seen through the other while access remains valid. Closing the arena invalidates both views; keeping the slice reference cannot keep a closeable arena open.

| Check | Concrete failing situation | Repair to reason about |
| --- | --- | --- |
| Bounds | Four-byte read beginning too near the segment end | Correct the byte range and layout size |
| Alignment | An int layout used at an incompatible location | Match actual representation/alignment |
| Lifetime | Access after arena close | Keep the owner alive for the actual use, then close it |
| Confinement | Another thread accesses a confined segment | Choose an appropriate arena and synchronization policy |

A heap-backed segment from an array and a native allocation are different storage kinds using the same access model. An Arena does not convert an ordinary Java object graph into native structs automatically. Each external representation needs explicit layouts and ownership. [Segment access and storage kinds](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/foreign/MemorySegment.html)


## Diagnose confinement separately from races

Confined arenas restrict access and closing to their owner thread. Shared arenas allow access from multiple threads, but do not make a read-modify-write operation atomic or remove the need for synchronization. Global arenas have unbounded lifetime; automatic arenas depend on reachability-based cleanup. Choose a lifetime model deliberately rather than keeping all memory permanently global to avoid closing errors.

Bounds, alignment, wrong-thread and closed-scope failures describe different violated contracts. Check them before involving a native library. A valid Java segment does not prove arbitrary native code uses the pointer safely.

## A foreign function adds an ABI contract

The **Application Binary Interface (ABI)** specifies native data representations and how calls pass arguments/results on a particular platform. A **calling convention** is part of that contract, including how registers/stack positions are used. A **symbol** is a named native entity, such as an exported function, which a lookup resolves to an address.

A **downcall** goes from Java to native code. An **upcall** lets native code invoke a Java callback through a generated entry point. These directions are separate from allocating memory or compiling ordinary Java bytecode with a JIT.

### Derive a binding from a small native signature

Suppose an owned native library exports this C function:

```c
int twice(int value) { return value * 2; }
```

This is a binding walkthrough, not an already installed native library. The native implementation, its built library and matching platform ABI must exist before invocation. For the chosen input 3, that C body computes 6; do not infer Java's overflow/exception rules for arbitrary C arithmetic.

| Binding step | Information it establishes |
| --- | --- |
| Find symbol twice in the intended library | Obtain the native function address |
| Obtain the linker's canonical C int layout | Use the ABI's representation of int |
| FunctionDescriptor.of(cInt, cInt) | Describe one C int parameter and one C int result |
| linker.downcallHandle(address, descriptor) | Create an invocation handle with the derived Java carrier types |
| `(int) handle.invokeExact(3)` | Supply an int and request the matching int result |

For this supported C-int mapping, the Java handle type is `(int)int`. The layout descriptor describes the native signature; MethodType describes the Java invocation shape. A matching-looking function name supplies neither of those type guarantees. Keep the library lookup's arena alive while calls can use its symbol addresses. [Native linker and canonical layouts](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/Linker.html), [symbol lookup lifetime](https://docs.oracle.com/en/java/javase/22/docs/api/java.base/java/lang/foreign/SymbolLookup.html)


Linker connects a symbol and FunctionDescriptor to an invocable MethodHandle. A downcall must match the actual native return/argument layouts, calling convention and ownership. Native code can retain a pointer after the Java call returns; its arena must outlive the actual native use. An upcall similarly needs a callback lifetime and a defined exception policy.

Native access permission is a separate JDK/module launch policy for restricted operations. Inspect the selected JDK's documented --enable-native-access requirements for actual native linking rather than adding flags to explain a simple arena-allocation example. JNI and FFM are interoperability mechanisms, not substitutes for ordinary Java collections.

## Practice: retain a slice beyond close

Does slicing a live point segment keep its x field accessible after the original arena closes? Does a shared arena make `read + 1; write` an atomic increment?

<details>
<summary>Answers</summary>

No to both. The slice shares the original scope, so closing invalidates it as well. Sharing changes thread-access permission; a compound update still needs a coordination policy. For a native API that stores a pointer, prove the owner and release protocol before handing over memory. A successful single call does not establish that retained pointers or callbacks remain valid.

</details>

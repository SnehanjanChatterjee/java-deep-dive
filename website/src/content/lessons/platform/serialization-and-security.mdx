## Serialization converts structured state into a representation

**Serialization** encodes structured data into a representation that can be stored or transmitted. **Deserialization** reconstructs data from that representation. Native Java object serialization is one particular binary protocol, implemented through ObjectOutputStream and ObjectInputStream; it is different from formats such as JSON.

An object graph contains both values and reference relationships. Two people may share one Address object, so restoring identical field text is not enough to describe whether sharing was preserved. We will serialize a small known graph, compare original and restored identities, and then study omitted fields, constructors, stream handles and reconstruction hooks.

## Represent an object graph as bytes

Native Java serialization writes a graph of objects, rather than only copying a top-level object's field text. Serializable is a marker interface enabling that protocol. ObjectOutputStream traverses eligible fields and records references using handles; repeated references can remain shared in the reconstructed graph.

The example below creates its bytes locally from a known graph. It is an observation of identity and field behavior, rather than a general invitation to deserialize arbitrary external input.

## Decide which state belongs to the representation

Default serialization includes eligible non-static, non-transient instance fields. Static fields belong to the class. Transient session is omitted and returns to its reference default null in this ordinary Serializable example. Transient is not encryption: the same value might still be written through another field or a custom write method.

A referenced nonserializable object can cause NotSerializableException during graph traversal. Handles preserve sharing and support many cycles; serializing each repeated reference independently would produce a different ownership graph. Read and write operations must agree on ordering and types when a custom protocol writes additional data.

## Reconstruction is not an ordinary constructor call

For conventional Serializable classes, normal constructors do not simply rerun for every serializable class. The first nonserializable superclass's accessible no-argument constructor participates while serializable fields are restored. Constructor validation alone therefore does not establish restored invariants.

Records use their canonical constructor during their special serialization protocol and ignore certain conventional custom hooks. Enums have their own identity-based serialization rules. Externalizable supplies an explicit format/construction protocol, including public no-argument construction, rather than automatically becoming a safer version of Serializable.

SerialVersionUID participates in representation compatibility. A mismatch can cause InvalidClassException; a match does not prove new defaults or changed business invariants are meaningful. The next chapter separates compatibility, graph filtering and invariant validation.

## A stream remembers objects it has already written

One ObjectOutputStream has a handle table. If the same ordinary object is written again, the stream can write a back-reference to its earlier representation instead of serializing its newly mutated fields. This preserves identity within a graph, but surprises code that treats repeated writeObject calls as independent snapshots.

### Trace the repeated roots

| Step | Original value | Stream action | Restored result |
| --- | --- | --- | --- |
| First write | 1 | Write a new object and assign its handle | First root contains 1 |
| Mutate, then write again | 2 | Reuse the existing handle | Second root is the same restored object, still containing 1 |
| reset, then write | 2 | Forget old stream handles and write a fresh representation | Third root is distinct and contains 2 |

`reset()` resets stream bookkeeping; it does not clone or reset the original Java object. The matching input stream observes the reset marker. Repeatedly creating output-stream headers in the middle of one logical stream is a different operation and can corrupt the reader's expected protocol. Long-lived streams also retain handle bookkeeping, so choose a deliberate message/snapshot boundary. [Output-stream handles and reset](https://docs.oracle.com/javase/8/docs/platform/serialization/spec/output.html)

### Compare three reconstruction mechanisms

Final does not override transient. `TransientFinalValue` assigns its final transient field from a constructor argument, so it is not a constant variable. Its ordinary value is 12, but the reconstructed field is zero because default serialization omits it and normal construction does not reassign it. A literal-initialized constant field can be inlined into a reading expression, disguising the omitted underlying field. Do not generalize that constant-folding observation into a rule that every final field is serialized despite transient.

`ExternalScore` implements Externalizable. Its public no-argument constructor runs during reconstruction; `readExternal` then reads the explicit format version and score, rejects an unknown version or an out-of-range score, and only then assigns the field. `writeExternal` writes those two ints in the corresponding order. Externalizable gives control over the representation, so omitting a field or writing data in another order changes the protocol. It does not automatically apply the default field-selection rules.

`CustomScore` uses ordinary Serializable fields. Its constructor establishes the initial score and transient label during normal construction. During reconstruction, private `readObject` first calls `defaultReadObject`, validates the restored value and rebuilds `label`. Constructor validation alone would miss this path. The read hook must have the required signature; an unrelated public method with a similar name is not an automatic callback.

`CanonicalToken.readResolve` substitutes its canonical instance as the reconstruction result. This explains why its copied result has canonical identity; ordinary Serializable reconstruction did not acquire a universal singleton guarantee. For appropriate singleton domains, enum serialization already preserves the named enum constant's identity. [Input hooks and substitution](https://docs.oracle.com/javase/8/docs/platform/serialization/spec/input.html)

### Choose a representation, rather than serializing memory addresses

Serialization is a general encoding idea; native Java object serialization is one specific binary protocol. JSON needs an agreed schema and does not automatically preserve arbitrary Java aliasing, constructors, field types or cycles. A serializer can represent a graph using explicit IDs when identity matters. Deep copying can also use explicit constructors/mapping; it does not inherently require serialization.

Casting the result of readObject checks its runtime type. The cast does not create a new Student or convert an unrelated object into one. Likewise, serialVersionUID is a compatibility identifier, not a key or proof that restored state is valid. These distinctions matter when explaining a file-based serialization example in an interview.

<details>
<summary>Why is a new field zero after reading an older serialized representation?</summary>

With a compatible class evolution, a newly added field can receive its default value when no corresponding value exists in the old stream. A field initializer in the ordinary constructor path is not a reliable migration mechanism for conventional Serializable reconstruction. Validate the resulting state and use an intentional compatible read/migration policy, or reject representations that cannot satisfy the new invariant. Matching UIDs alone does not fill in a meaningful business value.

</details>


## Practice: preserve sharing or make two copies?

If each restored Person had an independent Address with identical city text, would that be the same graph behavior? Does marking session transient guarantee secrecy?

<details>
<summary>Answer</summary>

No. Equal field text is different from shared identity; changing a mutable shared Address would affect both people, while independent addresses would diverge. Transient only changes default representation eligibility and does not provide confidentiality. Design a deliberate external format when crossing a trust boundary, and apply bounds/validation separately rather than treating a matching class name or UID as evidence of safe data.

</details>

## Add a boundary above packages

A package organizes type names and access. A named module additionally declares dependencies and which packages it exposes. Requires establishes readability; exports permits ordinary access to public API in a package; opens enables deep reflection under its scope. Finding a public class file on disk does not establish all three relationships.

JPMS is available from Java 9. This exercise uses real module descriptors, rather than presenting an ordinary Java 8 interface as though it executed module resolution.

The directory immediately below the module-source-path root names each module. From the repository root:

```bash
mkdir -p out
javac -d out --module-source-path java-examples/modern/jpms -m study.service,study.client
java --module-path out -m study.client/study.client.Main
```

Output is Hello Mira. Study.client reads study.service, which exports study.api. Main imports Greeter and calls its public method. This service class is an ordinary exported API; a ServiceLoader service additionally uses the uses/provides metadata from the preceding chapter.

## Diagnose the missing permission

<Diagram client:visible definition={"flowchart LR\n C[study.client] -->|requires| S[study.service]\n S -->|exports| A[study.api public API]\n R[Deep reflection] --> O[Appropriate opens contract]"} caption="Readability, ordinary exports and reflective openness answer different access questions." />

Remove the client's requires and compilation loses readability. Restore it, then remove the service's exports: the package is not exported to the client. Neither failure means Greeter.greet executed and returned the wrong text. Restore both before continuing.

Exports does not grant deep reflection into private members. Opens does not permit ordinary source imports from an otherwise unexported package. Qualified exports/opens restrict the relevant permission to named consumers. Package/member access rules still apply within these module rules. Add-exports and add-opens are distinct explicit migration options, not interchangeable fixes for an unexplained access failure.

## Explain transitive and optional dependencies

If A requires B and B requires C, A does not automatically acquire B's readability of C. Use requires transitive when B's exported API deliberately exposes types from C to consumers. Requires static makes a dependency required at compilation but optional at runtime; using that absent dependency during execution can still fail. A descriptor declares relationships and does not bundle dependency classes into an application artifact.

A modular JAR on the classpath belongs to the unnamed module rather than enforcing its descriptor as a named module. A plain JAR on the module path can become an automatic module. Prefer a stable Automatic-Module-Name over relying on a filename-derived name during migration. Split packages across named modules can prevent resolution/access; repair package ownership rather than adding arbitrary opens.

## Practice: choose a narrow repair

An ordinary public API call works, while a framework's private-field reflection fails. Should every package be exported?

<details>
<summary>Answer</summary>

No. Ordinary access and deep reflection have different contracts. Confirm the framework's target declaration, then provide only the intended reflective openness if that access belongs to the design. Exporting unrelated packages does not solve a missing private-access permission. Review readability and package visibility separately. Runtime-image packaging builds on this resolved graph in the next chapter; native memory has a separate lifetime model.

</details>

## Protect confidentiality and reject modified ciphertext

Encryption hides plaintext, while an authenticated-encryption construction also detects unauthorized modifications under its key and protocol. AES-GCM supplies authenticated encryption with associated data. Java's Cipher API expresses the transformation as AES/GCM/NoPadding; specifying the mode avoids relying on a provider's unspecified default choice.

<JavaExample file="CoreAuthenticatedEncryption.java" output={"message\ntamper rejected"} />

Main creates a fresh ephemeral AES key and one 12-byte nonce from SecureRandom. Transform creates a Cipher, initializes encryption or decryption with that key and GCM parameters, and performs doFinal. Decrypting the original ciphertext reproduces message. Flipping the final ciphertext/tag byte makes authentication fail with AEADBadTagException.

## Read the parameters as protocol obligations

GCMParameterSpec's 128 here is the tag length in **bits**. The nonce array is 12 bytes. These values serve different roles; neither is the plaintext length. Ciphertext includes authentication information and is not expected to equal the plaintext's byte length. Use the agreed charset only at the text/byte boundary; ciphertext is arbitrary bytes, not a String.

A nonce must not repeat for encryption with the same key. This demo encrypts once under its newly generated key, so it does not need a long-lived allocation service. A persistent service does: design key ownership, nonce uniqueness, storage/rotation, message versioning and failure policy. Random-looking bytes alone are not a proof of a correct nonce protocol.

## Bind public context deliberately

Associated data can authenticate context without encrypting it, such as a protocol version or record identifier. Supply the agreed AAD before processing ciphertext through update/doFinal. AAD is not automatically inferred from Java object fields; sender and receiver must use the same defined bytes. This example uses no AAD and demonstrates one message, rather than a complete storage/wire format.

Do not use unauthenticated decrypted data as trusted application state before authentication succeeds. Keep the original authentication failure visible at the boundary owning the operation. An encrypted, authenticated message still needs domain validation and an authorized purpose; cryptography does not decide whether a caller may perform an action.

## Practice: reuse a nonce after restart?

A service persists its AES key but resets an incrementing nonce counter to zero after every restart. Why does passing a round-trip test fail to establish security?

<details>
<summary>Answer</summary>

The same key/nonce pairs can repeat across process lifetimes, violating GCM's uniqueness requirement even though encryption and decryption still round-trip. Preserve a safe allocation state or adopt an established protocol that guarantees uniqueness across the key's lifetime. Test tampering and malformed inputs as failure paths, and review key/nonce ownership separately from ordinary functional output. Prefer established protocols and reviewed libraries over adding a custom checksum or home-made cipher composition.

</details>

## Explain every boundary in the round trip

The source's transform helper creates a fresh Cipher for one operation, selects encrypt or decrypt mode, supplies a GCMParameterSpec and calls doFinal. Creating a fresh Cipher avoids sharing its mutable operation state between these calls. It does not make reusing a key/nonce pair safe for repeated encryption. The example's key is freshly generated and used for one encrypted message.

| Part | Secret? | Required relationship |
| --- | --- | --- |
| Key | Yes | The intended encryptor/decryptor uses the correct key |
| Nonce | Need not be secret | Must satisfy the GCM uniqueness rule per encryption key |
| AAD | May be public | Sender and receiver authenticate the same defined context bytes |
| Ciphertext and tag | Can be transmitted | The receiver must reject authentication failure |

Tampering with the tag, ciphertext or authenticated context must not yield a success-like result. Catching AEADBadTagException and returning an empty string would make a failed authentication resemble a valid empty message. Keep the failure distinguishable at the operation boundary; determine externally visible error detail through the surrounding protocol.

<details>
<summary>Does converting ciphertext to a UTF-8 String make a valid storage format?</summary>

No. Arbitrary ciphertext bytes need not be valid text and a text decoding/encoding round trip can lose bytes. Use a specified binary format or a byte-preserving encoding such as Base64 when text transport is needed. That encoding supplies no additional confidentiality or authentication.

</details>

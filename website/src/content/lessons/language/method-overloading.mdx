## Choose a signature at compile time

Overloading gives methods the same name but different parameter lists. A method's return type alone cannot distinguish overloads. A simple useful pair might format one number or format a number with a width. The declared argument types decide which signature the compiler chooses; the runtime class of a reference argument does not start a new overload search.

## Apply the first successful applicability phase

For ordinary calls, first consider fixed-arity methods without boxing/unboxing. Next permit boxing/unboxing. Finally consider variable-arity invocation. Within the first successful phase, choose a most-specific applicable method.

For `pick(1)`, int widens to long in the first phase; boxing is unnecessary. An existing Integer reference matches Integer without unboxing. An empty argument list needs varargs, which supplies an empty int array. This is more reliable than a slogan about widening always beating boxing in every possible context.

## A varargs parameter is an array

`int... values` must be last and its body treats values as int[]. Passing an explicit array uses the declaration in fixed-arity form. `pick((int[]) null)` therefore passes a null array; `pick()` passes an empty array. A body that iterates must distinguish them.

An incoming varargs array can be caller-owned. Keeping it in object state can expose later mutations; copy when snapshot ownership is required. Generic varargs have additional erased-type restrictions, taught after generics. Do not introduce several unrelated varargs overloads merely to avoid choosing clear method names.

## Practice: resolve a null call

Does `pick(null)` select Integer or int[]? What changes with overloads `show(Object)` and `show(String)`?

<details>
<summary>Answer</summary>

Pick is ambiguous because Integer and int[] are unrelated reference types, both accept null, and neither is more specific. A cast communicates which contract the caller intends, without making dereferencing null safe. For show, String is more specific than Object and wins. Adding an unrelated overload can break recompilation even while existing class files continue to reference their originally chosen signature. Inheritance adds a separate runtime dispatch step; it is taught after classes and interfaces.

</details>

## Reject signatures that only appear different

Changing a parameter's name, a method's return type, its throws list or the presence of static alone does not create another overload with the same parameter types. `int read()` and `String read()` cannot coexist just because their callers want different result types. An array parameter and the corresponding varargs parameter also describe the same parameter type, so int[] and int... cannot distinguish two declarations.

Keep overload sets conceptually consistent. Methods that accept unrelated reference types can make `call(null)` ambiguous even though each declaration works separately. A cast at the call site can select one, but an API with distinct descriptive names may communicate the intent better. Assignment of the call's result happens after overload selection; it is not a license to declare conflicting ordinary signatures.

## Decide what one character means

Text from different writing systems needs more than a one-byte-per-letter model. **Unicode** provides a common system of numeric code-point values for text. A **code point** is one value in that system, often written as U+ followed by hexadecimal digits, the base-16 digits 0–9 and A–F; for example A is U+0041. A visible symbol may require one code point or a sequence of them.

An **encoding** represents those values using storage units. A **bit** is a binary digit; a **byte** contains eight bits. Java String indexing uses **UTF-16**, the 16-bit Unicode Transformation Format, whose code units are 16 bits wide. A Java char holds one such unit. A code unit, a code point and an encoded byte are therefore different quantities.

UTF-16 represents code points in its first range, the **Basic Multilingual Plane**, with one code unit. A supplementary code point outside that range uses two units called a **surrogate pair**. Thus A followed by an emoji can have String length three while containing two code points. The goal of the examples is to choose the unit your operation actually promises to count or traverse.

## Compare char traversal with code-point traversal

An indexed charAt loop and a toCharArray loop visit UTF-16 code units. For `"A\uD83D\uDE00B"`, the length is four: A, the high surrogate, the low surrogate and B. The code-point loop visits three points and advances by one, two and one code units. Casting the emoji's full int code point to char discards information; char cannot represent every Unicode point by itself.

String.chars also exposes code units, while codePoints combines valid surrogate pairs into int values. Streams are taught later; choosing a stream does not by itself choose the correct text unit. StringTokenizer splits tokens, not characters, and split with a regex is not a substitute for declaring Unicode boundaries. A simple offset loop is sufficient for this chapter.

<details>
<summary>The third code point starts at which UTF-16 index in A😀B?</summary>

Index three. A occupies index zero and the supplementary point occupies indexes one and two. `text.offsetByCodePoints(0, 2)` computes that offset without assuming every code point has width one. A code-point count is not automatically a usable substring offset. Combining accents and joined emoji can still contain several code points per user-perceived character, so neither count alone implements cursor movement for every text editor.

</details>

## Advance by the width of the code point

Keep offset as a String index. CodePointAt reads a full code point starting there; Character.charCount tells how many UTF-16 units it occupies. Character is the standard library's character utility/wrapper class. Its static helper avoids assuming that every point advances the index by one.

```java
final String text = "A\uD83D\uDE00";
for (int offset = 0; offset < text.length();) {
    final int point = text.codePointAt(offset);
    System.out.println(point);
    offset += Character.charCount(point);
}
```

The body prints 65 then 128512. At offset zero, A has width one; the next offset is one. At offset one, the surrogate pair describes a supplementary point with width two; the next offset is three and iteration ends. Incrementing by one would visit the second surrogate separately. CodePointBefore supports backward traversal from an exclusive end offset.

A grapheme cluster can contain several code points, such as a base letter plus a combining accent or a multi-part emoji. Code-point reversal preserves valid surrogate pairs but can still split a user-perceived character. Declare the unit before implementing palindrome, cursor movement or length validation. A substring boundary inside a surrogate pair can create malformed text.

## Encoding converts text to bytes

String's indexing model is different from an external file's byte encoding. **UTF-8**, the 8-bit Unicode Transformation Format, uses a variable number of bytes for a code point. Use `text.getBytes(StandardCharsets.UTF_8)` and decode with the agreed charset, using explicit imports. Arbitrary bytes need not be valid UTF-8. When invalid input must fail, configure a CharsetDecoder with CodingErrorAction.REPORT rather than replacement; the input/output (I/O) chapter develops byte/character boundaries.

Canonically equivalent precomposed and combining-accent text can compare unequal under String.equals. Normalization is an explicit domain policy. It is not automatically performed by storing text in a String, and case folding is another separate policy.

## Practice: choose the appropriate unit

A validator allows two Unicode code points. Should it reject the example merely because length is three? Does codePointCount solve a two-visible-character limit?

<details>
<summary>Answer</summary>

The declared code-point policy permits it: codePointCount is two. A visible-character policy needs grapheme segmentation and cannot substitute either String.length or codePointCount without changing its meaning. Document normalization and null policies as well. The later string-algorithms chapter implements a deliberately code-point-based reversal and first-unique search after map operations have been taught.

</details>

## Method parameters and object aliases

A Java method receives argument values. For an object argument, that value is a reference. The parameter is a new variable containing a copied reference, so it may reach the same mutable object as the caller. Mutating that object and reassigning the local parameter are different operations.

Overloading chooses among method signatures at compile time using declared argument types and conversion rules. Overriding chooses an implementation at runtime for an instance method. Neither mechanism changes Java's parameter-passing semantics. Varargs is an array-based calling convenience, not a separate collection type.

## Overload phases and virtual dispatch

### The parameter receives a copied value

For a primitive argument, the copied value is the primitive itself. For a reference argument, the copied value is a reference to the same object. Assigning the parameter changes the method's local variable. Mutating the referenced object can be visible through the caller's alias.

<Diagram client:visible definition={"flowchart LR\n C[Caller variable] --> O[User object]\n P[Copied parameter reference] --> O\n P -. reassignment .-> N[New User object]\n C --> O"} caption={"At method entry both references identify one User. Reassigning the parameter does not redirect the caller's variable."} />

The existing `rename` method writes through the shared reference. The `replace` method only redirects its own parameter. An array follows exactly the same rule: `items[0] = 9` changes its component, while `items = new int[3]` does not replace the caller's array. To replace a caller-owned value, return a new value and let the caller assign it, or use an explicitly designed mutable holder. A method that appears to swap two caller reference variables only swaps its local copies.

### How overload resolution proceeds

Overloading chooses a method **at compile time**, using argument expression types and applicable conversion rules. For ordinary calls, consider fixed-arity methods without boxing/unboxing first, then fixed-arity methods that permit boxing/unboxing, and finally variable-arity invocation. Choose the most specific applicable method within the first successful phase. This is more precise than a blanket “widening beats boxing beats varargs” slogan.

```java
static String pick(final long value) { return "long"; }
static String pick(final Integer value) { return "Integer"; }
static String pick(final int... values) { return "varargs"; }
```

`pick(1)` chooses `long`: widening works in the first phase. `pick(Integer.valueOf(1))` chooses `Integer`: reference identity conversion works without unboxing. `pick()` chooses varargs and receives an empty array. `pick((int[]) null)` selects the array form of the varargs declaration; iterating it would throw. `pick(null)` is ambiguous between unrelated reference parameter types `Integer` and `int[]`; casting null resolves which contract is requested.

Two overloads accepting `String` and `Integer` make `choose(null)` ambiguous. With `Object` and `String`, String is more specific and wins. Runtime object class does not rescue an ambiguous source call.

### Overloading and overriding interact

Suppose Parent has `show(Object)` and Child overrides it while also declaring `show(String)`. With `Parent p = new Child(); p.show("x");`, the compiler selects Parent's visible `show(Object)` signature. Runtime dispatch then executes Child's override of that signature. It does not reconsider Child's additional overload. Return type alone cannot distinguish overloads. An override can narrow a reference return type and checked exceptions, but cannot reduce access.

### Varargs and API design

A varargs declaration is represented as an array parameter and must be last. Avoid overload sets that combine several unrelated varargs types. Generic varargs can create heap pollution because the array is reified while its generic component is erased; the generics chapter explains the restrictions. Varargs arrays are mutable: retaining an incoming array can let later caller mutations change object state. Copy when snapshot ownership is intended.

Recursion creates successive method invocations with independent locals; excessively deep recursion can produce `StackOverflowError`. Iteration often makes bounded stack use easier to reason about. Neither approach changes Java's argument-passing model.

### Interview prediction exercise

Given `Object value = "text"`, overloads `format(Object)` and `format(String)` select `format(Object)`. If the selected method is virtual and overridden, dispatch can change its implementation, but never its already selected signature. State both steps in the answer.

### Trace the call in two stages

`receiver` is declared Parent, so its visible describe signature accepts Object. The argument's runtime String class does not cause an overload search in Child. After choosing that signature, virtual dispatch uses the actual Child receiver and executes Child.describe(Object). Casting the receiver to Child exposes its String overload at the next source call, producing child-string.

The final calls demonstrate the applicability phases. The int literal widens to long without boxing, so a later boxing or variable-arity candidate is not selected instead. An existing Integer matches the Integer parameter by reference conversion. An empty argument list needs the varargs form. The method bodies only report the chosen path; the selection occurs before their execution.

### Ambiguity is a compile-time result

With unrelated String and Integer overloads, a null argument supplies no most-specific winner. A cast such as `(String) null` narrows the intended overload, but does not make the resulting receiver/argument safe to dereference. Return type alone cannot distinguish two overload declarations with the same parameter signature. Adding an overload can therefore break recompilation of callers while old binaries still link to their original descriptors.

A varargs method can also be invoked in fixed-arity form by passing its array type. `choose((int[]) null)` passes a null array; `choose()` supplies an empty array. Those states require different body handling. Never collapse them into the same “zero arguments” explanation.

### Parameter ownership and exceptions

For an array or object parameter, reassignment is local while mutation through the shared reference can be visible. A final parameter prevents local reassignment; it does not prevent writing array entries or mutating fields. Returning a replacement object is the normal way to make replacement explicit in the caller.

Argument expressions complete before entering the method. If constructing the second argument throws, the method body never runs, but side effects already performed by the first argument remain. Java does not roll those effects back. This matters when overloaded factory/validation methods accept expensive or state-changing expressions.

### Coding exercise solution strategy

Draw separate columns for declared receiver type, declared argument type, chosen signature and runtime implementation. Fill the signature column before considering virtual dispatch. Then trace parameter values/aliases only for the chosen body. This order prevents the common error of mixing overload resolution with the pass-by-value model.

## Method-selection pitfalls

Do not describe object arguments as pass-by-reference. Assigning a new object to a parameter does not rebind the caller's variable. Arrays follow the same reference-value rule. Avoid confusing a final reference with an immutable object.

## Method-call interview practice

### How can a method replace the object used by the caller?

<details>
<summary>Explanation</summary>

Return the replacement, then have the caller assign that returned reference. Alternatively, a mutable holder can expose a value that is changed, but this is still mutation through a copied reference, not a change to Java's calling convention. Prefer explicit return values when replacement is the intent.

</details>

### Additional interview questions

<details>
<summary>Can a method swap two caller variables by reassigning its reference parameters?</summary>

No. It swaps only its local parameter copies. It can mutate objects both references identify, but redirecting one local reference does not redirect the caller's variable. Return a replacement result or define an explicit mutable holder contract.

</details>

<details>
<summary>Given overloads `show(Object)` and `show(String)`, which is selected for `Object x = "text"; show(x)`?</summary>

show(Object). Overload selection uses x's compile-time type. Runtime dispatch can select an override of that chosen signature on a receiver, but does not reconsider overloads using the argument's runtime class.

</details>

<details>
<summary>Why can `choose(null)` become ambiguous after an overload is added?</summary>

Null converts to unrelated reference types such as String and Integer, and neither parameter type is more specific than the other. The compiler cannot choose. Existing compiled callers can still reference the old descriptor, so source and binary compatibility differ.

</details>

## Solved interview and debugging practice

<details>
<summary>Why does casting the argument differ from casting the receiver?</summary>

Casting an argument changes the compile-time type used to choose among visible overloads. Casting the receiver changes the member set visible at that source call. Neither cast reconstructs the object; both can fail runtime compatibility checks where applicable.

</details>

<details>
<summary>Can a subclass override a static method?</summary>

A same-signature static method hides rather than overrides. Static selection is tied to compile-time qualifying type, unlike virtual instance dispatch. Calling a static member through an instance obscures that distinction and should be avoided.

</details>

<details>
<summary>What should an overload-heavy API test?</summary>

Test null-call ambiguity at compile time, primitive versus wrapper inputs, no-varargs versus explicit-array calls and overload addition effects. Runtime unit tests cannot execute a source call that the compiler correctly rejects.

</details>

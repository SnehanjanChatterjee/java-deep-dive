## Keep the client binary fixed while changing the library

A library can compile successfully while breaking a program that was compiled against its previous version. Source compatibility asks whether client source still compiles. Binary compatibility asks whether an already compiled client can link. Behavioral compatibility asks whether the operation still means what the caller expects.

This lab separates those questions with one greeting method. The original accepts String. Version two accepts CharSequence, a broader source parameter, but removes the original method descriptor. A third library retains the old descriptor and delegates to the broader overload.

<span id="worked-example" aria-hidden="true"></span>
## Read the first library and compile its client once

<JavaExample file="projects/binary-compatibility/api-v1/study/api/Greeter.java" label="Version 1: Greeter.java" />

<JavaExample file="projects/binary-compatibility/client/study/client/Main.java" label="Separately compiled Main.java" />

```bash
mkdir -p out/v1 out/client out/v2 out/compatible
javac -d out/v1 api-v1/study/api/Greeter.java
javac -cp out/v1 -d out/client client/study/client/Main.java
java -cp out/client:out/v1 study.client.Main
```

The launch prints Hello Mira. The client source passes a String, and its class file records a reference to Greeter.greet with a String parameter and String result. Keep out/client unchanged for the next launch. Commands use : between classpath roots; use ; on Windows.

<span id="mechanics-and-tradeoffs" aria-hidden="true"></span>
## Replace the runtime library without recompiling the client

<JavaExample file="projects/binary-compatibility/api-v2/study/api/Greeter.java" label="Version 2: Greeter.java" />

```bash
javac -d out/v2 api-v2/study/api/Greeter.java
java -cp out/client:out/v2 study.client.Main
```

This launch fails with NoSuchMethodError for the original String method. Broadening a parameter in source did not preserve the method descriptor that the old binary requests. The launcher finds Greeter's class, but linkage cannot find the required member.

Inspect the two library descriptors:

```bash
javap -s -classpath out/v1 study.api.Greeter
javap -s -classpath out/v2 study.api.Greeter
```

The relevant descriptors are:

```text
v1 greet(String):
(Ljava/lang/String;)Ljava/lang/String;

v2 greet(CharSequence):
(Ljava/lang/CharSequence;)Ljava/lang/String;
```

The descriptor includes parameter and return types. A String argument can be passed to CharSequence in newly compiled Java source, but the runtime does not rerun overload resolution on the old invocation to choose a different descriptor.

## Recompile separately to test source compatibility

```bash
mkdir -p out/recompiled
javac -cp out/v2 -d out/recompiled client/study/client/Main.java
java -cp out/recompiled:out/v2 study.client.Main
```

This source still compiles and the new client prints Welcome Mira. It now records the CharSequence descriptor. That successful recompilation does not repair the unchanged old out/client binary; they are different artifacts.

<span id="java-implementation" aria-hidden="true"></span>
## Retain the old descriptor through an overload

<JavaExample file="projects/binary-compatibility/api-compatible/study/api/Greeter.java" label="Descriptor-preserving Greeter.java" />

```bash
javac -d out/compatible api-compatible/study/api/Greeter.java
java -cp out/client:out/compatible study.client.Main
```

The original client now links and prints Welcome Mira. greet(String) still exists and delegates to greet(CharSequence). Its cast selects that broader overload; calling greet(name) with the unchanged String expression inside the String overload would select itself recursively.

Preserved linkage does not imply unchanged behavior: the greeting changed from Hello to Welcome. A caller requiring the original text can still be behaviorally broken. Name the specific compatibility property demonstrated, rather than calling every successful launch “fully backward compatible.”

## Compare another ordinary overload addition

<JavaExample file="CompatibleApi.java" output={"Hello Mira\nWelcome Mira"} />

This smaller source keeps the one-argument method's Hello behavior while adding a two-argument prefix variation. It demonstrates delegation inside one version. The separately compiled lab above is required to investigate what happens to old binaries.

Adding an unrelated same-arity reference overload can break source calls such as greet(null): String and Integer overloads are both applicable and neither is more specific. Existing binaries can still reference their old String descriptor. Adding a broader CharSequence overload alongside String does not create that particular ambiguity because String is more specific.

## Classify API changes precisely

| Change | Source question | Binary question | Behavioral question |
| --- | --- | --- | --- |
| Remove public method | Does caller compile? | Does old descriptor exist? | Is the operation still provided? |
| Change parameter/return descriptor | Can source adapt/recompile? | Can the old member reference link? | Does it mean the same thing? |
| Tighten input validation | Source may compile | Binary may link | Previously accepted inputs can now fail |
| Change a constant variable | Recompiled callers can see new value | Old callers can retain inlined value | Mixed versions can disagree |
| Add interface requirements/defaults | Existing implementations can conflict | Old implementations need analysis | Defaults can alter dispatch/meaning |

Binary compatibility is more nuanced than public visibility. Inheritance, erased generic descriptors, interface defaults and static/instance changes can matter. Evaluate representative consumers as separate compiled artifacts, not only the library's clean test run.

## Package the artifact actually intended for its runtime

The first project chapter establishes compile/test/package; dependency management explains the selected library graph. package creates an artifact according to plugins, install copies it into the local repository, and deploy publishes remotely. Packaging is not launching an application.

A shaded JAR can combine dependencies, but overlapping resources such as META-INF/services may require merging. Otherwise the program can compile while provider discovery changes. Preserve required dependency notices and make any source licensing choice deliberately; publication visibility is not a build setting.

A linked runtime image also needs dynamically discovered modules/resources. Static dependency analysis does not prove every reflected class, service provider or native resource is present. The module and service chapters establish those additional ownership/discovery requirements.

## Target older releases explicitly when distributing

A modern javac --release target constrains supported language syntax, class-file target and platform API together. Source/target alone can allow newer library calls into an older-format class file. On an actual older JDK, only its installed platform API is available, but third-party dependencies still need compatible bytecode/APIs.

The lab commands work with a Java 8+ JDK, using the same selected toolchain for compilation and launch. For distribution, choose the intended release and run the artifact on supported runtimes. Preview features need their matching release and flags; keep preview examples separate from stable distributable code.

## Diagnose the actual loaded code before changing declarations

For NoSuchMethodError, identify the caller's descriptor, actual loaded library version and runtime classpath order. A dependency tree explains resolution, but a custom launch can still supply a different JAR. A missing class and a missing method are different failures. Imports only affect source naming; they cannot fix already compiled linkage.

For migration, inventory dependencies and toolchains, use jdeps to inspect static/internal JDK usage, review removed/deprecated APIs, configure processors explicitly and compare warnings. Recheck serialization, charset/locale, time and concurrency assumptions where the domain depends on them. Use project-local settings instead of silently changing machine-wide configuration.

<span id="exercises-and-interview-questions" aria-hidden="true"></span>
## Completed compatibility exercise

The supplied reference artifacts demonstrate four outcomes: old client with v1 prints Hello Mira; old client with v2 fails at its absent String descriptor; old client with the retained overload prints Welcome Mira; recompiled client with v2 also prints Welcome Mira. The difference is which client binary is held fixed.

A migration note should state source/API target, actual runtime/toolchain, resolved dependency changes, removed/internal API use, processor configuration and observed behavior checks. Record unsupported or unrun combinations honestly. A library's successful clean build cannot establish compatibility for client/runtime combinations it never exercised.

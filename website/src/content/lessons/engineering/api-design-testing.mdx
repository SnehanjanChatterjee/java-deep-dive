## Contracts, ownership and variation points

An API contract includes valid inputs, output meaning, mutation/ownership, failure behavior and concurrency assumptions. Good names and small methods help readers see that contract, but a method being short is not sufficient if its dependencies and side effects are hidden. Cohesion groups behavior around a clear responsibility; coupling describes dependencies between those responsibilities.

SOLID principles and design patterns are reasoning aids rather than a requirement to create an interface for every class. Strategy separates a varying behavior; Builder helps assemble complex valid state; Adapter translates contracts. Refactoring changes internal structure while preserving intended observable behavior.

## Test boundaries and design tradeoffs

<Diagram client:visible definition={"flowchart TD\n C[Observable contract] --> S[Success and boundary tests]\n C --> F[Failure tests]\n S --> R[Refactor internals]\n F --> R\n R --> V[Verify contract is preserved]"} caption={"Useful tests protect observable behavior across refactoring instead of reproducing private implementation steps."} />

### Design around an observable contract

Consider a Checkout quote operation. Its contract says: quantities must be positive, unit prices nonnegative, amounts use one declared currency/scale, the discount policy must not return a negative total, and calculations detect overflow or apply an explicit decimal rounding policy. A quote is a calculation result, not an instruction to charge a card. Naming and return types should preserve that distinction.

A coherent design can contain an immutable input value, a pricing service and a DiscountPolicy strategy only if discounts genuinely vary. Inject Clock if rules depend on time. Return an immutable quote snapshot. Keep storage/network access behind the boundary that owns it, rather than making an otherwise pure calculation depend on global mutable singletons.

### SOLID applied to that case

Single responsibility groups pricing rules that change together; it does not demand one statement per class. Open/closed reasoning can isolate a varying discount policy, but excessive abstraction before any real variation adds cost. Liskov substitution requires every policy to honor nonnegative/valid-result guarantees. Interface segregation avoids forcing a pure calculator to implement persistence operations. Dependency inversion makes the policy boundary explicit without requiring a dependency-injection framework.

Builder is useful when constructing a valid object involves many optional inputs and cross-field validation. Adapter translates an external contract into a local one. Decorator adds behavior around the same capability. These names explain a design after the requirements are clear; they should not replace the requirements.

### Test the public behavior first

The supplied ContractExample is deliberately small enough to derive all essential categories. Its inputs are nonnegative ints and its output is their exact int sum. Negative inputs fail with IllegalArgumentException. Arithmetic overflow fails with ArithmeticException rather than wrapping. A test for `subtotal(0,4)` protects the zero boundary. A negative-input test should independently cover each argument. The overflow case protects a behavior that ordinary positive examples miss. Test names should state the contract, and assertions should not duplicate private helper calls from the implementation. The modern JUnit Jupiter API has analogous assertions and richer parameterized facilities, but imports/runtime requirements differ; do not mix test frameworks in one file accidentally.

### Use test doubles at a genuine boundary

A fake repository can model stored values deterministically; a stub clock/policy can return controlled inputs; a mock can verify an interaction when that interaction itself is the contract. Mocking every internal method makes a refactor break tests even when behavior stays correct. Do not mock BigDecimal merely to make arithmetic assertions pass. A pure pricing function often needs no mock at all.

Unit tests exercise a bounded behavior. Integration tests verify real collaboration, such as an actual file encoding round-trip. Contract tests check that independent implementations agree with an interface promise. End-to-end tests provide a smaller set of whole-flow checks. Choose the level that exposes the failure instead of testing the same formula redundantly at every level.

### Failure atomicity and ownership

Validate before mutating shared state. If an operation fails halfway through, define whether earlier effects remain, are rolled back, or are reported as partial completion. Returning an unmodifiable view can expose later mutations; return a snapshot when the API promises a fixed result. Define null handling at boundaries rather than scattering Optional and null checks without a consistent model.

Concurrency tests need explicit coordination and bounded waiting. A latch can establish the state being tested; sleep only hopes it happened. Time tests should inject Clock. Randomized/property tests should retain enough input/seed information to reproduce a failure. Coverage identifies unexecuted branches but does not prove meaningful assertions or all possible states; mutation testing asks whether deliberate small defects are caught.

### Refactoring exercise with explained outcome

Change ContractExample's internal validation helper without changing tests. Then temporarily replace addExact with `left + right`: the overflow test must fail. Temporarily remove validation for the second argument: its negative test must fail. These are discriminating assertions. A test that only checks “some result returned” would miss both defects.

### Interview follow-up

Explain an actual boundary you would introduce and what change it isolates. A strong answer connects requirements, contract, invariants, tests and tradeoffs. “Use SOLID” without a concrete responsibility or substitutability guarantee does not explain the design.

### Define the domain before the abstraction

The calculation operates in one declared currency/minor-unit domain. Unit prices are nonnegative long values; quantities are positive ints. A quote is not a payment instruction. The supplied discount policy must be side-effect-free and return an amount in 0..subtotal. Overflow is reported explicitly rather than wrapping into a plausible negative/incorrect amount.

Line's constructor establishes local validity. Its subtotal uses multiplyExact. The quote operation validates container/policy/line inputs, sums with addExact, invokes the variable discount behavior, verifies its result and creates an immutable aggregate. Quote exposes the result without retaining a caller-owned mutable line list. The only interface represents genuine varying behavior: discount policy.

### Failure behavior is observable API

A negative price or zero quantity fails at construction. A null line fails before its arithmetic is used. An invalid policy result fails before returning a quote. Arithmetic overflow is a separate failure class from invalid negative input. The method performs no storage/network operations; arbitrary side-effecting policies are outside its contract, so code review must not assume a Function-shaped type proves purity.

### Tests that discriminate defects

<JavaExample file="CoreCheckoutTest.java" />

The success test checks an exact total. The empty/full-discount cases exercise boundaries. Negative/zero/null cases test each declared invalid category. Multiplication and aggregate-addition overflow are tested separately because either implementation step can be broken independently. Replacing an exact helper with wrapping arithmetic should cause a meaningful assertion to fail.

### Refactor without changing the public promise

Validation can move into helpers or a validated value representation without tests asserting private call order. A fake external policy can supply a deterministic discount when isolation is appropriate; arithmetic itself should not be mocked. If the domain later supports multiple currencies, rounding or taxed allocations, extend the value contract deliberately rather than sprinkling doubles and nullable currency strings through existing callers.

### Design discussion

The example uses composition through a policy boundary and immutable result data. It does not introduce a factory/builder/repository for every class because those variations are not present. Explain which real change a pattern isolates and which invariant a type protects. This is a stronger interview answer than listing SOLID acronyms without connecting them to behavior.

## API design and testing pitfalls

Do not silently convert unexpected failures into empty success-like results, mock the class under test, or equate line coverage with complete correctness. Adding abstractions without a concrete variation or testing need can increase complexity.

## API contract interview practice

### What makes a regression test useful?

<details>
<summary>Explanation</summary>

It captures the externally meaningful failure and expected behavior at a stable boundary. It should fail before the correction, pass afterward, and remain valid if the implementation is sensibly refactored. Tests that merely assert internal method calls often protect the current structure rather than the requirement.

</details>

### Additional interview questions

<details>
<summary>What is failure atomicity?</summary>

It describes the externally visible state when an operation fails. Ideally a rejected operation leaves state unchanged, or its partial effects are explicitly defined. Validating inputs before mutation helps, but external side effects may require a larger consistency protocol.

</details>

<details>
<summary>Why can 100% line coverage miss a broken subtotal?</summary>

A test can execute the addition without asserting overflow behavior or exact values. Coverage measures execution, not assertion strength. An overflow test that fails when addExact is replaced with wrapping addition discriminates the intended contract.

</details>

<details>
<summary>When should a mock verify calls?</summary>

When the interaction is itself an externally meaningful contract, such as exactly one dispatch to a controlled external boundary. Verifying every private collaboration makes implementation structure the requirement and creates brittle refactoring tests.

</details>

### Coding exercise

Write success, zero, negative-input and overflow tests for subtotal. Refactor the implementation while keeping those tests unchanged, and explain which cases remain outside the chosen contract.

## Solved interview and debugging practice

<details>
<summary>Why validate the policy result after invocation?</summary>

The interface shape alone cannot enforce a discount within bounds. The quote boundary owns that invariant and must reject an invalid implementation instead of returning a negative total or silently clamping an undeclared policy.

</details>

<details>
<summary>Why test both multiplication and addition overflow?</summary>

A line amount can overflow before aggregation, or individually valid lines can overflow the total. One test does not establish both failure paths.

</details>

<details>
<summary>What remains outside this example's contract?</summary>

Multiple currencies, arbitrary rounding, persistence, payment authorization and concurrent mutation of caller inputs/policies. Those need explicit additional models/protocols rather than being implied by a small quote calculator.

</details>

## Design a quote calculation around its observable promise

A shop needs to calculate a quote from line prices, quantities and a varying discount policy. The quote is a calculation result, not a payment instruction. Before introducing classes or design patterns, state the meaning and failure behavior that callers need.

This example operates in one declared currency/minor-unit domain. Prices are nonnegative long values; quantities are positive ints. A policy returns a discount between zero and subtotal, inclusive. Overflow is a reported arithmetic failure. The returned quote is immutable and does not retain the caller's mutable list. Policies must be side-effect-free, and concurrent caller mutation is outside this small example's contract.

## Calculate the quote before naming the pattern

<JavaExample file="CoreCheckout.java" output={"2500\npolicy rejected"} />

The lines cost 1,250 × 2 and 500 × 1, producing a subtotal of 3,000 minor units. The policy returns a discount of 500, so total is 2,500. A second policy returns subtotal+1; the boundary rejects it rather than returning a negative total or silently clamping it.

Line validates its own price/quantity when constructed. subtotal uses multiplyExact for each line. quote checks its container and policy, visits non-null lines, adds amounts with addExact, invokes the policy once after accumulation, validates the returned discount and constructs Quote. Null lines or overflow fail before policy invocation. The ordinary interface shape cannot prove the policy is pure or returns a valid amount; the API must declare purity and enforce its numeric invariant.

## Assign ownership to the types that can enforce it

Line's final primitive fields preserve local validity. Quote stores only completed aggregate numbers, so later edits to the input list do not change it. DiscountPolicy represents one real variation: how much discount a valid subtotal receives. The calculation does not need a repository, network client, builder and factory merely because those pattern names exist.

If prices later support several currencies or decimal rounding, revise the value contract deliberately. Mixing raw doubles and nullable currency Strings into the existing calculation would weaken its invariants. An unmodifiable view of the input list would also be a different ownership promise from an immutable aggregate quote.

## Let tests discriminate plausible mistakes

<JavaExample file="CoreCheckoutTest.java" />

The success assertion uses an independently chosen exact result. Empty input and full discount establish boundaries. Invalid price/quantity/null input and invalid policy results establish failure categories. Multiplication overflow and aggregate-addition overflow are separate: each can fail even if the other step is implemented correctly.

Coverage says whether code executed, not whether assertions would reject an incorrect result. Replacing exact arithmetic with ordinary wrapping addition/multiplication can still execute the same lines. The corresponding overflow assertion must fail for that defect. Mutation testing systematically asks similar questions by introducing small defects and observing whether tests catch them.

Test the public behavior instead of private call order. A helper extraction should not require every test to know its name. A useful regression test captures the externally meaningful failure, fails before its correction and remains valid after a sensible refactor.

## Refactor a small contract without changing its tests

subtotal still accepts two nonnegative ints and returns their exact int sum. The final implementation delegates each input check to one private requireNonnegative helper. That internal extraction changes no input/result/failure promise.

<JavaExample file="ContractExampleTest.java" />

The same tests check an ordinary result, zero, an accepted maximum value, each negative input independently and overflow. Removing validation for just the right argument would therefore be detected independently of left validation. Replacing addExact with wrapping addition would be detected by the overflow test. The helper's private call order is not itself asserted.

## Apply design principles to an actual variation

| Principle | Decision in the quote calculation |
| --- | --- |
| Single responsibility | Group pricing rules and their input/result invariants coherently |
| Open/closed | Isolate the discount behavior when policies really vary |
| Liskov substitution | Every discount implementation must honor the same bounds/purity promise |
| Interface segregation | A pure pricing policy need not implement persistence methods |
| Dependency inversion | The calculation receives the policy contract instead of selecting a global implementation |

SOLID is a reasoning aid, not a requirement to add an interface for every class. A Strategy is the varying discount behavior already present. A Builder can help when many optional inputs and cross-field checks make construction difficult. An Adapter translates an external contract into the local one. A Decorator adds behavior around the same capability while preserving its promise. Name the real change a pattern isolates.

## Use doubles and test levels at genuine boundaries

A fake repository can provide deterministic in-memory state. A stub Clock/policy can return controlled inputs. A mock verifies an interaction when that interaction is itself meaningful, such as exactly one controlled dispatch. Mocking every private collaboration makes structure part of the test requirement; mocking BigDecimal arithmetic normally obscures the calculation.

Unit tests exercise a bounded behavior such as quote. Integration tests exercise real collaboration such as file/charset round-tripping. Contract tests check independent implementations of an interface promise. A smaller set of end-to-end checks protects whole flows. Choose the level that exposes the relevant failure rather than repeating the same formula everywhere.

Time-dependent code should accept Clock. Concurrency tests need coordination and bounded waiting; sleep only hopes a state occurred. Randomized/property checks should retain reproducing inputs/seeds. None of these techniques substitutes for a declared contract and meaningful expected behavior.

<span id="common-mistakes" aria-hidden="true"></span>
## Define failure atomicity where effects exist

This quote method builds a result without writing storage or charging a payment. If an operation performs effects and fails halfway, specify whether earlier effects remain, roll back or are reported as partial completion. Validating inputs before mutation helps, but does not itself create a distributed transaction. Optional.empty should not silently replace an unexpected failure.

## Completed design exercise

For a new discount policy, define its input/output bounds first, supply it through DiscountPolicy, and use the same quote boundary/tests to reject invalid results. A zero-discount policy is subtotal -> 0; a full-discount policy is subtotal -> subtotal. Both preserve 0 ≤ discount ≤ subtotal. A policy returning −1 or subtotal+1 violates substitutability and is rejected.

For refactoring, retain ContractExampleTest unchanged while extracting the private helper shown above. The supplied source is the completed reference. Test a future currency/rounding requirement separately after defining that new contract; the current example does not claim to cover payments, persistence or arbitrary concurrent policies.

## Evaluate substitutability with one concrete counterexample

Suppose a discount policy advertises the same interface but stores each customer's request in a global mutable collection. Its numeric return might satisfy 0 ≤ discount ≤ subtotal, yet it violates this API's stated side-effect-free requirement and can introduce retention/races. Type compatibility is only part of substitutability; preconditions, postconditions, failures and effects belong to the promise too.

A useful review starts with a table of accepted inputs and outcomes. Then choose an ordinary case, each independent invalid boundary, and a plausible implementation defect for the tests to discriminate. Null container, null element and null policy are different inputs. Likewise, multiplication overflow can occur inside a line while addition overflow occurs only when valid line amounts are combined.

<details>
<summary>Should a refactor assert that the private validator is called exactly twice?</summary>

Not for this pure public contract. That assertion would couple tests to an implementation detail and reject a valid alternative that validates inline. Assert accepted/rejected inputs and exact results instead. Interaction assertions belong where the interaction is an observable requirement, such as invoking an effectful dispatch once under a defined retry policy.

## Records and closed alternatives

A record declares a fixed set of components and supplies component accessors, equality, hashing and a descriptive string representation. Records are useful for transparent data carriers. A record component can still reference a mutable object, so records provide shallow rather than automatic deep immutability.

Sealed classes and interfaces restrict the direct permitted subtype set. They support modeling a deliberately closed family of alternatives. Pattern matching can combine a runtime type test with a scoped binding, and modern switch forms can express exhaustive handling of appropriate alternatives. These features solve different problems and should not be grouped as interchangeable boilerplate reduction.

## Record constructors and exhaustive patterns

Feature availability must be tied to a JDK: records are final from Java 16, sealed types from 17, and record patterns/pattern-switch features from 21. Use the target language specification rather than assuming every pattern form is supported because one related feature is available.

### Read a record declaration as an API

`record Range(int start, int end)` declares a final data-carrier class with private final component fields, `start()` and `end()` accessors, a canonical constructor, and generated equality, hashing and string representation. It extends Record and can implement interfaces. It cannot extend another class or declare additional instance fields. Static fields and ordinary methods are allowed.

```java
record Range(int start, int end) {
    Range {
        if (start > end) {
            throw new IllegalArgumentException("start exceeds end");
        }
    }
}
```

This compact constructor validates the parameters before generated assignments. It does not assign component fields explicitly. A normal canonical constructor declares all components and assigns the fields itself. Additional constructors must delegate to another constructor of the record. The canonical constructor's visibility must be at least as accessible as the record.

### Mutable components and generated equality

A record containing a list can normalize its component with `items = List.copyOf(items)` in a compact constructor (Java 10+ API). The copy rejects null elements and provides an unmodifiable snapshot of references; mutable elements remain mutable. An array component needs a copy on input and output when snapshots are required. Generated equality of array components uses the arrays' ordinary identity equality, not `Arrays.equals`. If array-content value semantics are required, explicitly design matching equals/hashCode implementations or use an appropriate immutable representation.

### A sealed family expresses alternatives

```java
sealed interface Reply permits Found, Missing { }
record Found(String value) implements Reply { }
record Missing(String key) implements Reply { }
```

A direct permitted subtype must be final, sealed or non-sealed; records are implicitly final. Permitted types must be in the same named module, or the same package when in the unnamed module. A non-sealed branch intentionally reopens extension beneath that branch. Choose a sealed family when enumerating alternatives makes domain reasoning clearer, not merely to prevent all extension.

### Switch, dominance and null

In Java 21+, a pattern switch can destructure record components and cover a sealed family:

```java
static String describe(final Reply reply) {
    return switch (reply) {
        case null -> "no reply";
        case Found(final String value) -> "found: " + value;
        case Missing(final String key) -> "missing: " + key;
    };
}
```

Without an applicable null label, a null selector in this pattern switch throws NullPointerException; an ordinary default does not automatically make it null-safe. A broad earlier type pattern can dominate a later narrower pattern and cause a compilation error. A guard such as `case Found f when f.value().isEmpty()` refines an alternative but does not normally cover all Found values, so include an unguarded branch where needed.

Exhaustiveness is checked against the compile-time hierarchy. Adding an alternative can require recompiling and extending switches. Separate compilation with evolved hierarchies can expose runtime mismatch paths; do not assume a previously exhaustive binary handles newly introduced data meaningfully.

## Closed alternatives and invalid-state prevention

### Choose a product or a sum of alternatives

A record groups components that are all present together: a Range has both start and end. A sealed family models alternatives: a lookup is Found with a value or Missing with a key. A single record carrying a boolean plus several nullable fields can admit contradictory states that a small alternative family excludes structurally.

The constructor is the local validation boundary. Normalize/copy record inputs there, but preserve the reconstruction expectation: building a new record from an existing record's accessor values should normally represent the same value. An accessor that invents unrelated values or exposes mutable internals undermines transparent value semantics.

### Exhaustiveness is checked against a particular world

A switch over a sealed family can cover its known alternatives without a catch-all. That makes a newly added alternative visible during recompilation. Separate compilation still matters: an older client can encounter a hierarchy evolved after it was compiled. Do not treat exhaustiveness as proof that every future binary combination is semantically supported.

A guarded pattern such as `case Found f when f.value().isEmpty()` covers only a subset. Include the remaining unguarded Found case where required. A broad earlier type pattern can dominate a narrower later one and make the latter illegal. Null handling is a separate policy: an ordinary default is not automatically an applicable null case.

### Record patterns inspect the published component API

A record pattern uses component accessors rather than bypassing the type's API to read arbitrary private fields. Nested patterns fail to match when a required nested component is null; they do not silently fabricate a default record. Keep patterns small when deep nesting obscures business cases, and name intermediate values when it improves explanation.

### When an enum is the right closed model

An enum suits a fixed set of named instances such as directions or lifecycle labels. It can implement an interface, hold immutable metadata and provide constant-specific behavior. Records suit per-instance data carriers; sealed subtypes suit alternatives with different component shapes. Using one of these features does not imply the others are always required.

### Coding solution outline

For a lookup result, define a sealed root, a Found record whose constructor rejects null and a Missing record with its own validated key. Write an exhaustive switch with explicit null policy. Test each alternative and invalid construction separately. Do not encode a failed infrastructure request as Missing unless that is truly the contract; a closed model should clarify outcomes rather than hide failures.

## Record and pattern-matching pitfalls

Do not assume a record containing a mutable array has value equality over array contents automatically. Do not use preview flags merely to silence unexplained compilation failures. A sealed hierarchy is a domain-modeling decision, not a requirement for all interfaces.

## Modern type-modeling interview practice

### Why is a record not necessarily deeply immutable?

<details>
<summary>Explanation</summary>

The component references are fixed, but referenced objects may still mutate. A record containing a mutable list can expose changes through its accessor. Copy collections at construction when snapshot semantics are intended and consider the mutability of elements as well.

</details>

### Additional interview questions

<details>
<summary>Why does a record containing int[] not automatically compare array contents?</summary>

Generated record equality follows the component equality semantics, and arrays use identity equality. Defensive copies protect ownership but do not change that equality rule. Define matching equals/hashCode explicitly if array contents form the value, or choose another immutable representation.

</details>

<details>
<summary>Does a default label make a pattern switch accept null?</summary>

Not automatically. An explicit applicable null label is needed for the intended null policy. Without it, a null selector can throw NullPointerException before ordinary default behavior applies. Exhaustiveness over non-null alternatives is distinct from null handling.

</details>

<details>
<summary>Can a permitted subtype remain extensible?</summary>

Yes, a direct permitted class can declare non-sealed, reopening extension beneath that branch. The sealed root still controls its direct alternatives. This is a domain decision, not a promise that every descendant is listed at the root.

</details>

## Solved interview and debugging practice

<details>
<summary>Does a record always need a compact constructor?</summary>

No. The generated canonical constructor is sufficient when simple component assignment is the intended contract. Add validation/normalization/copying only when the domain requires it; do not add boilerplate without a constraint.

</details>

<details>
<summary>Why might an enum be preferable to a singleton class?</summary>

An enum provides a fixed named instance model with language/runtime support for its identity and serialization behavior. It does not solve initialization side effects, mutable shared state or suitability of global access.

</details>

<details>
<summary>How does a guard affect exhaustiveness?</summary>

A guard filters matching values, so the guarded branch generally does not cover the entire underlying type alternative. The switch still needs the remaining values handled unless another applicable rule establishes coverage.

</details>

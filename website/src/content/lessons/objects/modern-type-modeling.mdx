## Declare a transparent data carrier

A **record** is a class form for a value described by a fixed set of named **components**. A Range has a start and an end; those components are its published value structure. Records make that structure explicit so the compiler can supply the routine constructor, readers, equality, hashing and text representation instead of requiring each to be handwritten.

In `record Range(int start, int end)`, the parentheses form the **record header**. The compiler supplies private final component fields and public **accessors**, start() and end(), which read them. It also supplies the **canonical constructor**, whose parameters correspond to the components in their declared order. This is a concrete API generated at compilation, not automatic validation of every combination of component values.

When a Range must have start no greater than end, write constructor validation. A **compact constructor** supplies that validation body without repeating the component parameter list or normal field assignments. The example first uses that form, then applies the already learned defensive-copy policy to a record containing an array.

Record classes are implicitly final and extend Record; they can implement interfaces but cannot extend another class or add instance fields. Static fields and ordinary methods are allowed. Records became a permanent language feature in Java 16. The Java 8-compatible immutable class from the previous chapter teaches the same ownership concerns without requiring record syntax.

No explicit assignment to this.start is needed in that compact form. A normal canonical constructor instead declares every component and assigns the fields itself. Additional constructors delegate to another record constructor. Canonical visibility must be at least as accessible as the record.

## Read the generated API before choosing a record

`Range` exposes start() and end(), not JavaBeans getStart()/getEnd() setters/getters. Its component fields cannot be reassigned by clients. A record can add operations such as length, implement an interface and declare static constants, but cannot add a hidden instance field outside its header. If a component should not be part of the published value representation, a conventional class may express that boundary better.

Component equality follows the record contract, rather than primitive `==` for every possible type. In particular, generated floating-point component comparisons treat NaN values as equal and distinguish positive from negative zero. Reference components use their equality behavior. Arrays therefore retain array identity semantics unless explicitly handled. These are independent choices from validation and copying. [Record generated-member contract](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/Record.html)

<details>
<summary>Can a compact constructor normalize parameters before implicit assignments?</summary>

Yes: a component parameter can be normalized, such as replacing text with text.trim(), and the generated assignments store the resulting parameter values after the compact body. Assigning this.component directly in that compact body is not the compact-constructor form. Validate or normalize the parameters, then allow the implicit assignment; use a normal canonical constructor when explicit field assignment is required.

</details>

## Generated methods follow component semantics

A record is shallowly immutable: fixed references can still identify mutable objects. Sample clones its array on input and output, protecting the stored values from aliases. Generated record equality would compare arrays by ordinary array identity, so Sample explicitly pairs Arrays.equals with Arrays.hashCode.

The input and output mutation attempts therefore leave its first component equal to one. A new Sample created from equal component contents compares equal. This preserves the reconstruction expectation: creating a new record from an existing record's accessor values should normally represent the same value. An accessor inventing unrelated values undermines transparent value semantics.

Record validation is a local invariant boundary, not a replacement for external authorization or I/O policy. A generated canonical constructor needs no custom body when ordinary component assignment is exactly the intended contract.

## Separate a product of components from alternatives

Range groups two simultaneously present values: start **and** end. A lookup can instead be Found **or** Missing, each carrying different data. That second shape is the subject of the next sealed-types chapter. Combining records, sealed types and patterns into one syntax trick obscures their different purposes.

## Practice: explain a record containing an array

Would input copying alone make generated equality compare two independent Sample arrays by contents?

<details>
<summary>Answer</summary>

No. Copying changes ownership, not the array equality contract. Independent copies remain different array objects. Override equals and hashCode together for content semantics, and copy on output as well if mutable components must remain private. For a list component, a structural snapshot still does not freeze mutable elements; the generics ownership chapter supplies that separate example.

</details>

## Classify an interface by the contract it supplies

An interface states what operations a caller may request, but not every interface uses the same form. Some declare several required operations, some describe one operation, and some attach a type-level tag without declaring an operation at all. These differences matter when implementing a capability and when an API interprets membership in a named type.

An **abstract interface method** requires an implementation. A **default method** already has an instance-method body that an implementation may inherit. A **static interface method** belongs to the interface itself. Once those roles are separated, the labels functional and marker can be read precisely: **functional** concerns the single-abstract-operation shape, while **marker** concerns the meaning of a type tag.

Functional does not mean the method is automatically pure or free of side effects. Marker does not mean behavior runs merely because a class implements the interface. The compiler annotation `@FunctionalInterface` checks the functional shape; the examples use named classes, so understanding them requires no lambda syntax. Later, inherited defaults raise another concrete question: what if two capabilities supply a body for the same method?

| Description | What matters | Consequence |
| --- | --- | --- |
| Ordinary capability | The required operations and their behavior | A concrete implementation fulfills the complete inherited contract |
| Functional interface | One abstract operation after the language's inheritance/signature rules | A named class can implement it; lambdas express implementations later |
| Marker type | Membership in a named type carries a defined meaning | An API can test or require that type even when it declares no operations |

The empty Tagged interface below adds a type relationship. It does not execute a tagging operation automatically. Serializable and Cloneable are standard-library marker examples whose specific APIs are developed later; implementing a marker alone does not run serialization or create a clone.

Marker membership and the behavior of apply remain separate facts.

TextOperation's default kind method is inherited behavior. Its static description belongs to the interface and is called with TextOperation.description(); it is not an inherited instance operation. An interface field is implicitly public static final, so interfaces do not provide per-instance mutable fields. Default methods can operate through an implementing object's published operations, but do not add instance-field storage to the interface.

## Count abstract operations after applying the rules

TextOperation declares apply and redeclares equals(Object), yet @FunctionalInterface is valid. A public Object-method signature such as equals(Object) does not add another functional-operation requirement. Default and static methods also do not add abstract operations. Inherited override-equivalent declarations can describe one operation rather than several unrelated ones.

The annotation asks the compiler to check the functional-interface rule; it is optional when the interface already satisfies that rule. Add an unrelated abstract method such as `int length();` and this declaration no longer qualifies. A class can still implement a nonfunctional interface normally; it simply lacks that single-operation target shape. Java 9+ also permits private interface helpers, which are implementation details rather than inherited abstract operations. [JLS interface methods and functional interfaces](https://docs.oracle.com/javase/specs/jls/se25/html/jls-9.html#jls-9.8)

## Resolve unrelated defaults at the implementing class

Left and Right both provide label(). Combined cannot silently inherit both unrelated bodies. Its explicit override makes the policy visible and uses Left.super.label() and Right.super.label() to invoke the eligible direct-interface defaults. Those qualified calls do not mean “search any ancestor for a convenient implementation.”

## Practice: add a method without confusing the contracts

<details>
<summary>Would adding a second default method destroy TextOperation's functional shape?</summary>

No. The functional shape concerns abstract operation requirements, not the total number of members. A second unrelated abstract operation would change that shape. Static and private helper methods do not become abstract instance operations. A public Object-method redeclaration receives its specified special treatment.

</details>

<details>
<summary>Can a concrete class omit one inherited abstract method because another interface supplied it?</summary>

A compatible inherited public implementation can fulfill a required signature. Otherwise the concrete class must supply a body, or the class itself must remain abstract. Merely declaring implements does not manufacture behavior. Check the full inherited contract, including access, compatible return types and checked-exception restrictions.

</details>

<details>
<summary>What should an interview answer say about a diamond of defaults?</summary>

List the eligible inherited methods first. A more-specific interface override can resolve an ancestor relationship; unrelated defaults require a class override. An inherited concrete class method has precedence. Then show the actual chosen body, rather than claiming that whichever interface appears first in implements wins. Reordering Left and Right does not choose a winner.

</details>

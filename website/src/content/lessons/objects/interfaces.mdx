## Depend on an operation rather than one concrete class

A checkout needs to ask how a price is calculated, but it should not have to know every pricing class's storage or algorithm. An **interface** is a reference type declaring a capability other code can depend on. Its **contract** describes the operations and behavior callers may request. An **implementation** supplies the code that fulfills those operations.

`interface Pricing` declares `int apply(int amount)`: receive an int amount and return an int result. This declaration states the method's shape without a body. `class DiscountPricing implements Pricing` supplies the public method body. Implements declares the type relationship; Java checks that a concrete implementation provides the required operation.

The caller can hold the object through a variable declared Pricing and request apply. It creates an actual DiscountPricing object, not an extra interface object. This separates the capability visible to the caller from the particular class doing the work, allowing a different pricing implementation to be supplied without rewriting Checkout.

The helper types are declared inside CompositionExample to keep this demonstration in one file. Static on DiscountPricing and Checkout means neither needs an enclosing CompositionExample object. Their own objects still have instance behavior and state; static nesting does not make Checkout's pricing field a static field.

Read the declarations in order. Pricing defines the method shape. DiscountPricing implements it with a named class, subtracting ten. Checkout stores a private Pricing reference supplied to its constructor. Total delegates to `pricing.apply(amount)`. In main, the concrete object is DiscountPricing, while the reference type is Pricing. A total of 100 follows the delegate and returns 90.

This intentionally small policy has no currency, rounding or lower-bound contract. A real checkout must define those rules rather than silently treating every int as a valid charge. Here the example isolates the relationship between interface, implementation and caller.

## Interface types describe what callers may ask

The declared type determines available methods at a source call. An interface-typed reference does not acquire every extra method declared by its concrete implementation. At runtime, an instance invocation reaches the implementation on the actual object. This **dispatch** selects the implementing behavior. Using one contract with different implementations is a form of **polymorphism**: callers use the common operation while behavior can vary with the actual object.

A class may implement several interfaces but extend only one class. An abstract class can hold state and partial implementation; an interface often suits a capability shared by otherwise unrelated classes. Neither automatically creates a useful abstraction. Choose the smallest contract the callers actually need.

## Separate a contract from inherited implementation

Pricing's declaration has no method body, so the implementing class supplies it. An interface can extend other interfaces, and a class can implement several independent capabilities. Implementing a public interface operation with package access is illegal: callers must be able to rely on the promised public operation. A class that leaves an abstract obligation unimplemented must itself be abstract.

Abstraction is deciding the operations a client depends on; encapsulation is controlling how a type's state and implementation are accessed. They cooperate, but neither is a percentage of hidden code. An abstract class can have constructors, per-object state and implemented methods alongside abstract methods; the <a href={lessonUrl('learn/objects/abstract-classes/')}>shared-algorithm lesson</a> develops a complete example. An interface cannot provide per-instance fields or a constructor; its default methods can provide behavior after the contract is understood. The <a href={lessonUrl('learn/objects/interface-contracts/')}>interface categories and default-conflict lesson</a> works through marker types, functional shape and inherited defaults using named classes.

<details>
<summary>Does Pricing pricing = new DiscountPricing() create both a Pricing and a DiscountPricing object?</summary>

It creates one DiscountPricing object and stores its reference in a variable declared Pricing. Interface typing changes what operations the source may request, not the object's number or concrete identity. Checkout retains another copy of that reference, allowing its total operation to delegate to the same collaborator.

</details>

## Practice: add regular pricing without changing Checkout

Implement a named Pricing class that returns the amount unchanged. Construct another Checkout and explain what varies.

<details>
<summary>Solution</summary>

```java
static final class RegularPricing implements Pricing {
    @Override public int apply(final int amount) {
        return amount;
    }
}
```

Use `new Checkout(new RegularPricing()).total(100)`, which returns 100. Checkout's code is unchanged because it invokes the Pricing contract. The supplied collaborator varies. Constructing DiscountPricing inside total would hard-code that choice and make substitution harder. Lambda notation can express some one-method interfaces later; it is not needed to understand this model.

</details>

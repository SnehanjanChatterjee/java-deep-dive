## Model alternatives with different data

A result can be a success carrying a value or a failure carrying a message. Putting a boolean and both nullable payloads into one class permits contradictory combinations: successful with an error, failed with a success value, or neither. A family of different types can instead give each outcome only its appropriate data.

A **sealed class or interface** restricts its direct subtypes to a permitted family. Here Result permits Success and Failure. A **pattern** tests an object's type/structure and can name the matched data for use in a branch. These are separate tools: sealing controls which alternatives exist; patterns inspect a particular value; a switch selects behavior for its matched case.

Start with the type-family and simple pattern-scoping rules. Then follow the complete result program, where constructor checks establish each alternative's local invariant before a pattern switch describes it.

## Read sealing independently of pattern syntax

Sealed classes/interfaces restrict direct permitted subtypes. Each direct subtype must be final, sealed or non-sealed; records are implicitly final. Permitted types must belong to the same named module, or the same package in an unnamed module. A non-sealed branch intentionally allows further extension beneath that branch.

Sealing became final in Java 17. The record patterns and pattern switch in this complete example require Java 21 or later, with no preview flags. A plain instanceof type pattern can bind a compatible value to a scoped local; a record pattern additionally deconstructs through the record component API.

## Learn flow scoping before deconstruction

A **type pattern**, such as `String text`, tests whether a value is a non-null instance of the named type and introduces a variable for the successful path. A **record pattern** additionally inspects the declared record components, such as the int inside Success. A variable introduced by a pattern is available only where control flow proves the match succeeded.

`if (value instanceof String text && !text.isEmpty())` makes text available on the right of && because that operand runs only after the match succeeds. Replacing && with || does not provide that guarantee: the right operand can run when the match failed. A pattern variable's scope follows proven matching paths, not just the nearest pair of braces.

After `if (!(value instanceof String text)) { return; }`, following statements can use text because every path reaching them matched. Null never matches that instanceof pattern. This guard style gives a safe typed local without an unchecked cast; it does not accept null as empty text or make arbitrary OR branches safe. [JLS pattern-variable scope](https://docs.oracle.com/javase/specs/jls/se25/html/jls-6.html#jls-6.3.2)

<details>
<summary>Does a sealed root mean every descendant is final?</summary>

No. A permitted direct subtype may be non-sealed, intentionally opening that branch to further descendants. A root's closed list concerns its direct permitted types; inspect each branch's declaration before asserting a finite set of concrete leaf classes. Exhaustive handling can cover an open branch with a type pattern for that branch, rather than enumerating every possible future descendant.

</details>

## Explain exhaustiveness, dominance and null separately

Describe covers the known permitted alternatives, so it needs no default for non-null Result values. Without an applicable null label, a null selector throws NullPointerException; ordinary default does not automatically make it null-safe. Add `case null -> "no result";` when absence is an allowed input policy.

An earlier broad pattern can dominate a later narrow one, making the latter illegal. A guard such as `case Failure f when f.message() != null && f.message().isEmpty()` covers only some failures; include a remaining unguarded Failure case. Nested record patterns do not fabricate defaults for null nested components.

Exhaustiveness is checked against the compile-time hierarchy. Adding a permitted alternative exposes missing cases during recompilation. An old client can still encounter an evolved hierarchy through separate compilation; a previously exhaustive binary is not a promise of meaningful behavior for every future alternative.

## Practice: add a Pending outcome

Pending carries a nonnegative retry delay. What must change beyond adding a record declaration?

<details>
<summary>Answer</summary>

Permit Pending at the sealed root, validate its delay in its constructor and add an unguarded Pending branch to every exhaustive switch during recompilation. Decide separately whether describe accepts null. Do not encode infrastructure failure as Missing or Pending merely to keep the model small: alternatives should preserve the actual outcome contract. A retry delay value does not itself authorize retrying a side-effecting operation.

</details>

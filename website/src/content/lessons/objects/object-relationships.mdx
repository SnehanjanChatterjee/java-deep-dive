## Describe the relationship before choosing fields

A reference tells which object another value identifies, but it does not by itself explain the relationship. Does the caller lend the object for one operation? Do several owners share it? Does one object create and control its mutable parts? These questions determine how constructors and accessors should handle aliases.

**Ownership** is the design responsibility for controlling an object's use, changes and useful lifetime. **Borrowing** uses a caller-owned object without silently taking over that responsibility. An **association** is the general collaboration: a Reviewer uses a Book. **Aggregation** describes a whole retaining independently usable parts: two ReadingGroups share a caller-supplied Book. **Composition** expresses stronger ownership: a Notebook creates and controls its private Pages.

Java represents all three using ordinary objects and references. The distinctions come from creation, retained aliases and exposed operations, not special allocation keywords. Trace those choices in the program before assigning the relationship label.

## Make ownership visible in construction and access

Notebook creates its own array and each Page. Allocating `new Page[size]` alone would create an array of null references; the loop constructs the individual Page objects. No caller supplies those mutable Page identities, and no accessor returns them. Write changes a selected page; read returns its immutable String value. Separate Notebooks therefore have separate mutable parts.

The constructor permits zero pages and rejects negative sizes. Every real page starts with empty text. Valid indexes are zero through size minus one; invalid indexing fails rather than silently changing another page. Null text is rejected. Each operation names a concrete invariant instead of exposing a Page setter to arbitrary callers.

Construction takes O(n) time and O(n) owned storage for n pages. An indexed read/write uses constant indexing work; the String supplied to write is shared safely because Strings are immutable. This does not imply that all arbitrary part objects could be shared safely.

## Separate a design lifetime from garbage collection

Composition says the API controls its parts' useful lifetime. **Garbage collection (GC)** separately manages memory according to **reachability**, paths from runtime-kept references through objects. Composition does not promise a cleanup callback at the closing brace or immediate memory reclamation when an owner becomes unreachable. If a mutable Page reference escaped, a client could retain it independently and undermine that ownership model. Reference reachability, rather than an aggregation/composition keyword, determines what storage can still be needed; the JVM lessons develop that memory model.

`throughRetainedOwner` makes this concrete. Local initially identifies a Book. ReadingGroup stores a copied reference in its book field. Assigning `local = null` removes only the local path. `owner.title()` still reaches the Book through a field and returns Retained. Association direction is another design choice; aggregation is not universally required to be unidirectional. [JLS reference values](https://docs.oracle.com/javase/specs/jls/se25/html/jls-4.html#jls-4.3.1), [JVMS heap](https://docs.oracle.com/javase/specs/jvms/se25/html/jvms-2.html#jvms-2.5.3)

## Practice: review a leaking accessor

<details>
<summary>Notebook adds Page[] pages() returning its field. Is the strong ownership claim preserved?</summary>

No. A caller could replace array entries or retain individual mutable Pages. Cloning only the outer array prevents entry replacement in Notebook's array, but would still expose the same Page identities. Return immutable page values or deliberate snapshots instead. Composition is a policy to enforce at every boundary, rather than a label earned solely by calling new in a constructor.

## Separate transport reads from application messages

A **frame** is one complete application message. Its **header** contains control information; its **payload** contains the message data. This protocol uses a four-byte big-endian nonnegative payload-byte length, followed by exactly that many UTF-8 bytes. Big-endian writes the most significant byte first. The accepted payload limit is 1,024 bytes.

For the text €, the complete wire bytes are 00 00 00 03 E2 82 AC: four bytes spelling the length three, then the three UTF-8 payload bytes. An empty String has header length zero and no payload. We must distinguish that complete empty frame from having no complete frame yet.

Transmission Control Protocol (TCP) provides the byte-stream transport introduced in the next lesson. Its reads can split a header or UTF-8 sequence anywhere; they do not define these application boundaries.

The parser receives a buffer already flipped for reading. It consumes complete frames and leaves an incomplete frame wholly unread for a later attempt. It does not own a socket or decide when EOF occurs.

## Read each branch against the invariant

If fewer than four bytes remain, do not consume a header. Otherwise mark the prefix position and read the length. Reject negative/oversized lengths immediately. If the body is incomplete, reset to the mark before breaking, so the next attempt begins with a coherent header.

For a complete body, slice creates a shared bounded view and limit(length) restricts decoding to this payload. The strict decoder reports invalid UTF-8 rather than replacing it. Its own position changes independently; after success, the parent advances by the body byte length. Earlier decoded frames may already have advanced input if a later frame fails; extract does not promise batch rollback.

## Track exact cursor values through the split euro sign

| Phase in the 32-byte demonstration | Position | Limit | Relevant bytes/state |
| --- | --- | --- | --- |
| After header 3 and first payload byte are put | 5 | 32 | Four-byte header followed by E2 |
| After flip | 0 | 5 | Five readable bytes |
| extract reads the header | 4 | 5 | Only one of three body bytes available |
| extract resets to its mark | 0 | 5 | Entire incomplete frame remains readable |
| compact | 5 | 32 | The same five bytes retained; append starts at 5 |
| Append 82 AC, then flip | 0 | 7 | Complete header and three-byte payload |
| Successful extraction | 7 | 7 | One String emitted; no readable suffix |

A complete empty frame consumes its four-byte header and emits an empty String. That is different from having no complete frame to emit. When multiple frames arrive together, repeat extraction from the new position. If a later frame is incomplete, reset only to that later frame's header; earlier successful frames stay consumed.

## Encode bytes before writing a length

encode converts the String through a strict UTF-8 encoder. It checks encoded payload length, allocates header plus payload, writes the byte count and body, then flips the completed output. For the euro sign it writes length three, not String.length's one. A malformed UTF-16 input such as an unpaired surrogate is rejected.

The bounded decoder view avoids a payload copy, but does not create independent storage/lifetime. Retaining a view and mutating an alias can change the same bytes. The parser's caller owns the input buffer.

## Decide when incomplete becomes truncated

While more input is expected, an incomplete frame is normal. After the source reports EOF, finish first extracts all complete frames, then rejects any remaining bytes as a truncated header/body. Empty remaining input is valid. A shorter final frame is not silently invented.

finish shares extract's failure boundary: already consumed earlier frames are not rolled back. A session owner must decide whether malformed/truncated input closes the connection or invokes an explicit recovery protocol. Retrying indefinitely against the same invalid bytes is not recovery.

The encoder first rejects text whose UTF-16-unit count already exceeds the byte budget, limiting temporary encoding work. Passing that preliminary guard is insufficient: 342 euro signs contain only 342 units but require 1,026 UTF-8 bytes, so the exact encoded-byte check still rejects them. A 341-euro-sign string plus one ASCII unit occupies exactly 1,024 bytes. Malformed surrogate input is rejected by strict encoding independently of size.

At EOF, a partial header and a partial payload are truncation failures. While input remains open, they are ordinary incomplete states. Neither compact nor a later retry repairs a negative length or malformed complete payload. This separation makes the parser independent of how a socket/channel groups its reads.

## Capacity and admission remain separate

The demonstration's 32-byte buffer fits its short frame. A real accumulator must hold an accepted frame or grow within the declared bound after validating its length. compact cannot create capacity. A full buffer with an incomplete body needs a bounded growth/rejection policy, not another read into zero writable space.

Nonblocking zero progress also needs readiness/backpressure coordination. This parser isolates protocol correctness from that transport/lifetime design rather than pretending a memory example is a complete server.

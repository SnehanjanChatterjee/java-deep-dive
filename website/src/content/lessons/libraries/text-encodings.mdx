## A byte count is not a character count

A file stores bytes; String exposes UTF-16 code units. **Encoding** turns text into bytes, and **decoding** turns bytes back into text under an agreed charset. UTF means Unicode Transformation Format: UTF-16 uses 16-bit code units, while UTF-8 encodes Unicode scalar values using byte sequences.

For the euro sign, String.length is one but UTF-8 needs three bytes, written in hexadecimal as E2 82 AC (two hex digits describe one byte). A supplementary code point can need two UTF-16 units and four UTF-8 bytes. The two counts answer different questions.

An explicit charset means the writer and reader use the same declared representation. It is not a claim that every input byte sequence is valid text. A decoder must also choose whether malformed input is rejected or replaced.

## Decode a complete bounded value

First encode the complete value: `byte[] encoded = "€".getBytes(StandardCharsets.UTF_8)`. The resulting array has length three. Decoding that whole valid sequence under UTF-8 reconstructs the original text. For input validation, decodeStrict creates a decoder with REPORT error actions so malformed input fails instead of silently changing the data.

ByteBuffer.wrap supplies the byte-array storage to this decoder API without copying it. The buffer chapter develops its cursor; this use only needs the whole bounded array as input.

The first outputs compare String.length with encoded byte length. E2 alone is only the start of the euro sign's encoding, so treating it as a complete value is rejected. It is not a different valid character.

## Distinguish encoding errors from read segmentation

A read may stop after E2 even when the remaining bytes will arrive later. Converting each arbitrary read chunk into an independent String can reject or replace valid split characters. Either retain decoder state across chunks, with correct end-of-input handling, or retain bytes until a complete protocol payload is available. The framing lesson implements the second design.

new String(bytes, charset) uses replacement behavior for malformed input under its contract. That can be suitable for best-effort display but is wrong when malformed protocol data must fail. An encoder also needs a policy for malformed UTF-16, such as an unpaired surrogate; the completed frame encoder later uses REPORT in both directions.

## Keep text normalization separate

Decoding reconstructs characters. It does not canonicalize case, Unicode normalization, line endings or domain identifiers. Locale.ROOT is useful for locale-neutral machine-term case conversion; user-facing language rules may need a chosen locale. Canonically equivalent Unicode strings can have different code-unit sequences unless the application chooses a normalization policy.

A delimiter protocol must define whether a delimiter is a byte sequence or a decoded character rule. A length prefix must state byte length versus character count. The euro sign needs length three in the UTF-8 framing protocol, even though text.length() is one.

## Carry decoder state across one-byte input chunks

<JavaExample file="EncodingBoundaryLab.java" output={"units=2, points=1, bytes=4\nreconstructed=true\nsurrogate rejected"} />

The supplementary symbol is one code point, represented by two UTF-16 units and four UTF-8 bytes. OneByteInput deliberately returns at most one byte per bulk read. InputStreamReader retains its decoder state across those reads, so the four byte fragments reconstruct the original text. Decoding each fragment independently would lose the multibyte sequence.

The Reader is a character-stream API, not a code-point iterator. Reading into a one-char array can deliver the two surrogate units in separate calls. The StringBuilder gathers those units before code-point-level interpretation. A complete code point can still be part of a larger visible grapheme; neither a byte count nor String.length counts every visible character.

### Choose strictness in both directions

| Boundary | Convenient replacement behavior | Strict policy |
| --- | --- | --- |
| Bytes to text | new String(bytes, charset) | CharsetDecoder with REPORT |
| Text to bytes | String.getBytes(charset) | CharsetEncoder with REPORT |
| Stateful byte stream to text | Reader carrying decoder state | InputStreamReader supplied with the configured decoder |

The unpaired high surrogate has no complete Unicode scalar value to encode, so the strict encoder rejects it. Replacement can be appropriate for best-effort display; it changes the data and should not silently become a protocol validation policy. Charset instances can be shared, but encoder/decoder instances carry operation state and need their own ownership.

The solution accepts complete UTF-8 and empty input, rejects a truncated multibyte sequence and a malformed continuation, and rejects null input. An empty byte array is valid empty text; it is not EOF by itself. EOF is reported by the underlying source and determines whether more bytes can still arrive.

For strict text input, call decodeStrict once the declared complete payload is present. For unbounded text streams, use a Reader/decoder with a deliberate incremental protocol rather than reading all content just to get one complete byte array.

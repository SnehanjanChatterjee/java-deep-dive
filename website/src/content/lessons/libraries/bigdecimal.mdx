## Decimal value, scale and precision

BigDecimal provides decimal arithmetic with explicit scale and precision. It is appropriate when base-ten representation and rounding policy are part of correctness, such as monetary calculations. It is immutable: arithmetic produces a new value rather than modifying the original operand.

Take the decimal spelling 1.20. Its unscaled integer is 120, its scale is 2, and its precision is 3 significant digits. The value is 120 × 10^-2. Scale describes decimal position; precision describes significant digits. They are separate inputs to later rounding decisions.

Start with ordinary arithmetic on two values:

```java
final BigDecimal left = new BigDecimal("1.20");
final BigDecimal right = new BigDecimal("3.4");
final BigDecimal sum = left.add(right);       // 4.60
final BigDecimal product = left.multiply(right); // 4.080
final BigDecimal eighth = BigDecimal.ONE.divide(new BigDecimal("8")); // 0.125
```

Each call returns a new value and leaves left/right unchanged. These exact operations retain documented preferred scales: addition uses the larger operand scale, multiplication adds scales. Division by eight terminates exactly; division by three requires a policy because no finite decimal holds its exact result. Define units and boundaries before deciding how to round that result.

## Worked arithmetic policies and exact conversion

### A decimal is an integer and a scale

Follow these ordinary operations before running the complete arithmetic catalog:

| Operation | Result | Representation to notice |
| --- | --- | --- |
| 1.20 + 3.4 | 4.60 | Exact addition preserves the preferred maximum operand scale |
| 1.20 − 3.4 | −2.20 | Subtraction uses the corresponding scale rule |
| 1.20 × 3.4 | 4.080 | Exact multiplication has the sum of operand scales |
| 1 ÷ 8 | 0.125 | The exact decimal expansion terminates |
| 1 ÷ 3 at scale 4 | 0.3333 | The explicit rounding/scale policy permits an approximation |
| 12345.67 with precision 4 | 12350 | Four significant digits can require a negative result scale |

These are exact-operation preferred-scale examples except where a context/rounding policy is specified. A MathContext can limit significant digits across an arithmetic operation; setScale controls the decimal-position representation. They are not interchangeable settings.

### Tie rounding examples

At scale one, HALF_UP maps 1.25 to 1.3, while HALF_EVEN maps it to 1.2 because the retained last digit is even. HALF_EVEN maps 1.35 to 1.4. The choice is a domain rule; do not describe one as universally more correct. UNNECESSARY asserts that rounding must not be required and throws when the exact value does not fit.

For the negative tie −1.25 rounded to one place, the full matrix is:

| Mode | Result | Rule |
| --- | --- | --- |
| UP | −1.3 | Away from zero |
| DOWN | −1.2 | Toward zero |
| CEILING | −1.2 | Toward positive infinity |
| FLOOR | −1.3 | Toward negative infinity |
| HALF_UP | −1.3 | Nearest; ties away from zero |
| HALF_DOWN | −1.2 | Nearest; ties toward zero |
| HALF_EVEN | −1.2 | Nearest; ties to an even retained digit |
| UNNECESSARY | ArithmeticException | Reject an inexact result |

UP does not mean positive infinity. CEILING and FLOOR depend on sign; the program prints each negative result so that difference can be checked.

### Division and rounding boundaries

An exact divide can reject a nonterminating decimal expansion such as 1/3. A scale-based divide specifies decimal places; a MathContext specifies significant-digit precision. Intermediate multiplication/division can need a policy even if the final display has two places. Specify whether taxes, discounts or allocations round per item, per group or at the total boundary.

The divide overload determines what precision information is supplied:

| Invocation shape | Result rule | One divided by three |
| --- | --- | --- |
| divide(divisor) | Require an exact terminating decimal | ArithmeticException |
| divide(divisor, roundingMode) | Use the dividend's existing scale | 1 gives 0; 1.00 gives 0.33 with HALF_UP |
| divide(divisor, scale, roundingMode) | Use the explicitly requested result scale | Scale 4 gives 0.3333 |
| divide(divisor, mathContext) | Use the context's significant-digit precision and rounding | Precision 4 gives 0.3333 |

The RoundingMode-only overload does not invent extra fractional places. For BigDecimal.ONE the dividend scale is zero, so rounding 1/3 to that scale yields zero under HALF_UP. The numerically equal dividend 1.00 has scale two and yields 0.33. If the domain requires a fixed result scale, state it explicitly rather than depending on an operand's spelling. The complete program prints both cases. [BigDecimal.divide overload contracts](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/math/BigDecimal.html#divide(java.math.BigDecimal,java.math.RoundingMode))

`divideToIntegralValue` obtains the integral quotient; `remainder` returns what remains after that quotient. For 7.25 and 2, the program prints quotient 3.00 and remainder 1.25. Remainder is not a general nonnegative modular operation: a negative dividend can produce a negative remainder. Dividing by zero fails independently of whether a nonzero divisor would have a terminating decimal expansion.

### Exact minor-unit conversion

For a domain whose declared minor-unit scale is two, moving 1.25 right by two places and calling longValueExact yields 125. A value with extra fractional minor units is rejected by an exact conversion unless the domain explicitly rounds first. Currencies and other decimal domains can use different scales; avoid hard-coding two as a universal money rule.

### Collection and API consequences

Representation-sensitive equals/hashCode is intentional. If an API requires numeric equivalence independent of scale, use a value model that enforces a canonical policy. A TreeMap comparison policy alone can change membership without changing BigDecimal.equals, which affects general Map expectations. Document whether returned amounts preserve input scale, are normalized or are formatted only at a presentation boundary.

## Exact arithmetic and conversion policy

### Decimal representation is part of the contract

For unscaled integer u and scale s, the value is u × 10^-s. `1.00` therefore has unscaled 100, scale 2 and precision 3. `stripTrailingZeros` on 1000 can yield unscaled 1 and scale −3: a negative scale represents a power of ten, not an invalid number. Decide whether an API preserves input scale or normalizes it.

`equals` includes scale, while compareTo can report numeric equivalence. HashSet and TreeSet can therefore produce different cardinalities from the same inputs. A normalized value model can choose another policy, but every equals/hashCode and ordering implementation must agree with that declared model. Formatting is a separate presentation step.

### Rounding is a business rule

The worked matrix above separates decimal places from significant-digit precision and makes negative tie direction visible. A MathContext applies its precision/rounding policy to an arithmetic operation; setScale chooses a result scale. Keep that policy attached to the intended boundary.

Narrowing conversions need a separate decision. intValue can discard a fractional part or overflow its target, whereas intValueExact rejects an inexact or out-of-range result. For a fixed-minor-unit long model, enforce the currency/scale and overflow rules explicitly rather than assuming the integer representation chooses them.

## Apply the arithmetic contract

For an exact minor-unit conversion, shift the decimal point according to the domain scale and use an exact integer conversion that rejects fractions/overflow. Do not silently truncate with intValue or assume every currency uses two decimal places. Perform intermediate arithmetic under the required precision and round at the declared boundary; repeated arbitrary rounding can change totals.

## BigDecimal equality and rounding pitfalls

equals includes scale while compareTo can treat different scales as numerically equivalent. Do not ignore that distinction in map/set keys. Avoid new BigDecimal(double) when the desired input is the human decimal spelling, and do not discard returned arithmetic results.

## BigDecimal interview practice

<details>
<summary>What is the difference between scale and precision?</summary>

Scale describes the decimal-position representation; precision describes the number of significant digits. A result-scale overload and a MathContext do not specify the same arithmetic policy.

</details>

<details>
<summary>Why can a numeric conversion need an Exact suffix?</summary>

A narrowing conversion may otherwise discard fractional information or overflow. An exact conversion rejects data that does not fit the promised integer domain rather than inventing a truncated value.

</details>

## Solved interview and debugging practice

<details>
<summary>What does RoundingMode.UNNECESSARY assert?</summary>

That the requested operation/result representation requires no rounding. It reports a failure when that assertion is false; it is not a request to silently keep arbitrary extra digits.

</details>

<details>
<summary>Can valueOf repair a previously rounded double?</summary>

No. It starts from the supplied double value. If an earlier calculation already lost the original decimal intent, selecting a later constructor cannot reconstruct it.

</details>

<details>
<summary>Why might a library expose an amount value rather than raw BigDecimal?</summary>

A value type can enforce currency/unit, accepted scale, rounding and equality policy consistently. BigDecimal supplies arithmetic representation but does not choose those domain invariants.

</details>

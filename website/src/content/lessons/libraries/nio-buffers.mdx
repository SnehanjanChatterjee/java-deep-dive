## Put bytes into storage, then take them out

A ByteBuffer combines byte storage with position, limit, capacity and an optional mark. A channel transfers bytes through a buffer. NIO is a family of APIs, not a promise that every operation is nonblocking.

The invariant is `0 <= position <= limit <= capacity`. Capacity is fixed for that buffer. Position identifies the next relative read/write index; limit bounds the current usable range. Relative get/put advance position. Absolute operations use an explicit index without advancing it, while enforcing their relevant bounds.

## Trace a buffer before copying a file

| Operation on capacity 8 | Position | Limit | Meaning |
| --- | --- | --- | --- |
| allocate | 0 | 8 | Whole buffer available for writing |
| putInt(42) | 4 | 8 | Four bytes have been written |
| flip | 0 | 4 | Readable range is those four bytes |
| get two bytes | 2 | 4 | Two written bytes remain unread |
| compact | 2 | 8 | Preserve unread bytes; append after them |

flip sets limit to the old position and resets position to zero. clear resets position to zero and limit to capacity, without erasing bytes. compact moves unread bytes to the start, puts position after them and restores the write limit. rewind resets position while keeping the limit. flip/clear/compact/rewind discard the mark as their contracts specify.

## Complete a blocking channel copy

<JavaExample file="ChannelCopyLab.java" output={"copied 5 bytes\nhello"} />

The outer loop reads bytes into an eight-byte buffer. flip makes the bytes just read available for output. The inner loop writes until no bytes remain; one write may consume only part. clear prepares the next read. At EOF, the source reports -1 rather than a shorter final “message.”

The copy method owns neither supplied channel. Its caller opens/closes both and cleans temporary files in finally. Copying n bytes uses O(n) transfer work and O(buffer capacity) working storage. File existence checks are not required to establish the operation's success in advance.

## Understand zero progress before using nonblocking channels

A general channel can return zero without EOF. The blocking file-channel copy is intentionally different from a nonblocking socket loop. Repeating zero-progress calls tightly can waste CPU. A selector/event loop waits for appropriate readiness, retains per-connection state and controls pending output. Readiness is not a promise that a complete application message will arrive in one call.

InputStream also allows partial reads: -1 means EOF, while a zero-length request can return zero. OutputStream and channel method contracts differ; do not transfer one interface's all-bytes assumption to another.

## Byte order, direct storage and views

putInt translates an int into four bytes in the configured byte order. Both ends of a protocol must agree. ByteBuffer starts big-endian by default. An absolute index is measured in bytes, not “number of ints.” A bounded view shares bytes while maintaining its own position/limit; a view is not a detached snapshot.

Direct buffers can reduce some native I/O copying but have allocation/lifecycle costs and are not universally faster. They do not make data thread-safe. Mapped buffers likewise bring filesystem/native lifetime considerations. Select them for a demonstrated workload instead of assuming a low-level representation is an automatic optimization.

## Completed exercise: preserve an unread suffix

Suppose four bytes are readable and only two are consumed. Calling clear loses the state identifying the unread two; later writes can overwrite them. compact moves those two bytes to indexes zero/one and sets position two. Append the next bytes there, then flip again before consuming. No additional capacity is created by compact.

Calling getInt immediately after putInt without flip reads from the current position, not from the bytes just written. The existing introductory FilesAndBuffers program demonstrates the simplest putInt/flip/getInt round-trip; the complete channel copy above applies the same state transition repeatedly.

## Observe independent cursors over shared bytes

<JavaExample file="BufferViewsLab.java" output={"absolute=20, position=0\nrelative=10, position=1\nreset position=1\nview orders=LITTLE_ENDIAN/BIG_ENDIAN\ncursors=1/2\nslice shared=99\nreadonly observes=88\nreadonly write rejected\nbig endian=16909060\nlittle endian=67305985"} />

Absolute get(1) reads20 without moving the source's position. Relative get then reads10 and advances position to1. Mark records that position; reading again advances to2, and reset returns to the recorded1. Setting a new position/limit that invalidates a mark can make later reset throw InvalidMarkException; reset is not a general return-to-zero operation.

Duplicate begins with its own copy of the cursor/limit state. Reading from it changes its position to2 while the source stays at1. Slice begins at the source's current position: its index0 identifies source index1. Writing99 through that slice changes the same byte seen through source.get(1). A read-only view rejects its own put, yet observes a later write through the source. Read-only access does not make shared storage immutable.

ByteBuffer view byte order needs deliberate attention: duplicate and slice return ByteBuffer views with the specified initial BIG_ENDIAN order, even when the source was configured LITTLE_ENDIAN. The example prints that distinction. Set the desired order on the chosen view before multibyte operations; typed views such as asIntBuffer have their own documented creation-time order relationship.

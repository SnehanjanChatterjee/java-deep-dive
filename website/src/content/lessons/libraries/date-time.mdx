## Choose the meaning before the type

An Instant identifies a point on the UTC timeline. LocalDate is a calendar date without time or zone, suitable for values such as a birthday. LocalTime is a wall-clock time. LocalDateTime combines local date and time but still lacks the information needed to identify an instant. OffsetDateTime adds a fixed offset; ZonedDateTime resolves a regional zone's rules at a particular date/time.

These types are immutable and their arithmetic returns new values. Ignoring the result of plusDays does not modify the original date. Thread-safe value objects do not decide which zone, chronology or business boundary the application intends.

A past event timestamp and a recurring future schedule need different models. Storing only an Instant can lose a future “09:00 in this region” intention; storing only a LocalDateTime can lose which past occurrence was recorded. Retain the information the domain requires rather than treating every temporal value as a formatted timestamp String.

## Zero, one or two offsets for a local time

Regional offset transitions make a local label map to zero, one or two valid offsets. A spring gap skips a local range. An autumn overlap repeats one. A normal time has one valid offset. These outcomes must be resolved before claiming a unique instant.

In Europe/Paris's historical 2024 spring transition, 02:30 on 31 March is in a gap. On 27 October, 02:30 occurs twice. Default convenience resolution can choose/adjust according to its documented rules; that does not mean the choice fits every scheduling or audit domain.

Resolve obtains the valid offsets instead of guessing from a formatted value. It rejects null inputs. An empty offset list is a gap and is rejected. A two-offset overlap uses the requested earlier/later offset or rejects under REJECT. ZonedDateTime.ofStrict then constructs using the chosen offset and zone.

Earlier/later here refers to the zone API's documented overlap offset list; state the resulting instant relationship when explaining it. The sample verifies the two resulting instants differ by 3,600 seconds while sharing the same local clock label. A user interface accepting an ambiguous local appointment should retain enough information to express the chosen occurrence.

The code deliberately rejects gaps rather than silently moving them. A different API can legitimately adjust a nonexistent time, but that is a different declared policy. Never describe either default as universally correct for all business rules.

## Duration versus Period across transitions

Duration models seconds/nanoseconds of elapsed amount. Period models calendar years/months/days. Across a one-hour spring transition, adding a calendar day to noon can preserve next-day noon while adding 24 elapsed hours reaches 13:00. A calendar day is not defined as exactly 86,400 elapsed seconds in every regional context.

For an elapsed timeout, use an elapsed-time abstraction appropriate to the operation rather than wall-clock calendar arithmetic. For a recurring local schedule, retain the zone and calendar intent. For month-end arithmetic, inspect normalization behavior: adding a month to an unavailable day can adjust according to the API; it is not the same as preserving a fixed number of days.

## Parsing and formatting boundaries

DateTimeFormatter is immutable and can be shared. A pattern is not a natural-language description: year-of-era, proleptic year and week-based year have different meanings. Resolver behavior controls how parsed fields become a valid date. When invalid dates should be errors, choose a strict contract and test invalid inputs rather than assuming a human-readable format implies strict validation.

A local timestamp's successful parsing does not provide a missing offset or zone. An ISO-looking value can therefore remain ambiguous. Machine protocols should declare a format, charset and temporal meaning. User-facing formatting should use the intended locale/zone, not whatever defaults happen to be configured on the developer machine.

Formatting is presentation. Do not sort arbitrary localized display strings as if they were a chronological representation. Compare temporal values or use a representation whose ordering contract is deliberately suitable.

## Current time and testability

Inject Clock into code that asks what time/date it is. A fixed Clock makes midnight, expiry and leap-date decisions reproducible without sleeping or editing the system clock. A single fixed instant can lie on different local dates in different zones, so the test must also establish its zone policy.

For “expires at the next local midnight,” derive the next local date in the specified zone, then resolve that date's start under regional rules. Adding 24 hours to the current instant does not necessarily reach that boundary. Some historical/regional transitions affect midnight itself, so use the API's actual zone-rule semantics rather than assuming every date begins at an unambiguous 00:00.

For measuring elapsed work in one process, wall-clock time can be adjusted. System.nanoTime supports differences for elapsed intervals and is not an epoch timestamp to persist or compare across unrelated JVMs.

## Interview questions with worked answers

<details>
<summary>Why is LocalDateTime insufficient for ordering global events?</summary>

It is a local label without a resolved offset. Different regions or repeated overlap occurrences can share it while representing different instants. Resolve/store the timeline meaning before using it as a global event timestamp.

</details>

<details>
<summary>Is an offset a replacement for a regional zone?</summary>

A fixed offset describes one relationship to UTC; a regional zone includes transition rules over time. The offset suitable for one date need not be the offset for a future recurrence in that region.

</details>

<details>
<summary>What does a strict overlap policy prevent?</summary>

It prevents silently picking one of two possible instants when the input lacks enough information. The caller can supply a policy/offset or request user clarification, depending on the application's contract.

</details>

<details>
<summary>How would you test a local-date expiry rule?</summary>

Supply a fixed Clock and explicit region, including an instant near local midnight and transition boundaries. Assert the domain date/instant result. Avoid waiting until the machine clock reaches the condition.

</details>

<details>
<summary>Why can plusMonths differ from adding a fixed day count?</summary>

Months have different lengths and calendar arithmetic has documented date-resolution behavior. A monthly billing rule is not inherently a 30-day elapsed interval. Define which rule the product promises.

</details>

## Coding exercise and solution

Implement a function returning the first valid instant of the next local date for an injected Clock. Derive LocalDate.now(clock), add one date, then call atStartOfDay with the declared zone and return its instant. If the API instead accepts a separate zone, ensure the clock supplies the intended instant and convert using that zone consistently. Test a normal day, a DST transition and different zones sharing one fixed instant.

If the domain requires rejecting any adjusted midnight rather than accepting atStartOfDay's resolution, inspect the valid offset rules and establish that stricter requirement explicitly. Replacing the call with arbitrary 24-hour addition would solve a different problem.

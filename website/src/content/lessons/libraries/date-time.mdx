## Resolve a local label into an instant

LocalDateTime contains calendar fields without an offset. OffsetDateTime adds a fixed offset; ZonedDateTime combines local fields with a regional zone's rules and a resolved offset. An offset records one UTC relationship, while a regional zone describes how that relationship changes over time.

A past recorded event and a recurring future “09:00 in this region” schedule require different models. An Instant can identify the event but lose the recurrence's local intention. A LocalDateTime alone cannot uniquely identify every past occurrence. Preserve the information the domain needs.

## A local time can have zero, one or two valid offsets

A normal local label has one offset. A spring gap skips a range, so a label in it has none. An autumn overlap repeats a range, yielding two possible instants. In Europe/Paris's historical 2024 rules, 31 March 02:30 is nonexistent and 27 October 02:30 occurs twice.

Convenience atZone normally adjusts a gap forward and chooses an overlap offset according to its documented rules. Those defaults are valid API behavior; an appointment/audit domain may require a different policy.

For the overlap, +02:00 maps 02:30 to 00:30Z, while +01:00 maps it to 01:30Z. The same displayed local fields correspond to instants 3,600 seconds apart. “Earlier/later offset” follows the zone API's list order; explain the resulting instant instead of guessing from the numerical offset alone.

## Calendar days and elapsed hours diverge

At noon on 30 March in Paris, plus Period.ofDays(1) preserves next-day noon. Adding Duration.ofHours(24) reaches 13:00 after the spring transition. A regional calendar day is not universally 86,400 elapsed seconds.

Month-end adjustments also belong to calendar semantics. A monthly billing rule is not inherently a 30-day elapsed interval. For elapsed measurements inside one process, System.nanoTime supports differences; wall clocks can be adjusted, and nanoTime is not an epoch timestamp to persist or compare across unrelated JVMs.

## Complete the next-local-date expiry exercise

<JavaExample file="ExpiryPolicy.java" output={"2024-03-31T22:00:00Z\n23\ntrue"} />

The Clock supplies an instant. The explicit ZoneId determines its local date even when the Clock itself has a different zone. nextLocalDateStart obtains that date, adds one calendar date and resolves its start with atStartOfDay(zone). It does not add 24 hours to the current instant.

The fixed clock starts at Paris midnight before the 2024 spring transition. The next local midnight is 23 elapsed hours later. isExpired defines the exact deadline as expired: !now.isBefore(deadline). A one-nanosecond-before case is therefore false, while equality and after are true.

Some historical/regional transitions affect midnight itself. atStartOfDay returns the first valid time according to zone rules. An API that must reject an adjusted midnight would need a stricter valid-offset check and a declared failure policy; arbitrary 24-hour arithmetic is not that policy.

## Worked design questions

**Can a fixed offset replace a regional zone for future meetings?** It describes one UTC relationship but not future regional transitions. Preserve the region and local recurrence when those express the requirement.

**Can an ISO-looking String lack essential information?** Yes. A local date-time can parse correctly while omitting offset/region. Parsing syntax and resolving timeline meaning are separate steps.

**Can one Clock support different regional policies?** Yes. Treat its instant as the source and convert with the explicitly requested region, as the complete expiry implementation does.

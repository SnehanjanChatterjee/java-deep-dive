## Open a file through a path

A Path describes a location in a filesystem provider. Files performs operations at that location. Merely constructing or resolving a Path does not create a file, open it or establish that it exists. Relative paths are resolved against the process's working directory when used; do not assume that directory is the source-code folder.

Use resolve to combine a parent and child, rather than concatenating platform separators. getFileName returns the last component; getParent returns the containing path when one exists. toAbsolutePath anchors a relative path, while normalize removes redundant lexical components such as dot/dot-dot without examining symbolic links.

## Separate byte I/O from character I/O

InputStream/OutputStream transfer bytes. Reader/Writer expose text characters through an encoding boundary. Buffering batches small operations; flush pushes pending output through that wrapper but does not itself promise durable storage on disk. Closing an owned writer completes its normal flushing/closure protocol.

Do not close a caller-owned stream unless the API explicitly transfers ownership. Conversely, a method that opens a file should normally close it or return an explicit owned resource with a clear caller obligation. Suppressed close exceptions follow the try-with-resources rules taught in the resource chapter.

<span id="mechanics-and-tradeoffs" aria-hidden="true"></span>
## Choose bounded convenience or streaming

For a known small file, readAllBytes/readAllLines provide convenient complete results. On Java 11+, readString/writeString provide text convenience with their documented charset defaults/overloads. Choose an explicit charset when the external format specifies one. Convenience does not make an arbitrarily large input safe to buffer.

For larger text, process a BufferedReader line by line. Files.lines returns a lazily consumed Stream that must be closed. Files.list and Files.walk also own traversal resources; use try-with-resources around them. A terminal count/collect does not waive closure.

```java
try (final Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
    final long nonblank = lines.filter(line -> !line.trim().isEmpty()).count();
    System.out.println(nonblank);
}
```

This fragment needs imports for Files, StandardCharsets and Stream, and a containing method that handles IOException. It counts under a declared trim-based blank policy; it does not modify the file or retain all lines. Directory walk depth and symbolic-link policy should likewise be explicit.

## Let the operation report its actual failure

A prior Files.exists check cannot guarantee a later open succeeds; the file can change between them. Prefer the actual operation and handle the relevant documented exception. Copy/move may reject an existing destination unless the requested options say otherwise. An atomic move is a separate option/capability, not a property of every rename across filesystems.

File authorization also needs more than a String prefix check. normalize is lexical and does not resolve symlinks. Even a normalized path starting with a permitted base can reach elsewhere through a link. Choose whether links are permitted and use appropriate real-path or secure-directory operations for the actual trust boundary.

## Match resource lifetime to traversal

Returning a Stream from inside a try-with-resources block that has already closed it is invalid ownership. Leaving Files.walk unclosed can retain filesystem resources. Assuming one read fills a requested array is also incorrect: byte streams/channels may deliver partial input, a subject developed with channels.

## Worked questions

**Is a Path a file handle?** No. It describes a location; opening is a separate operation with a separate lifetime.

**Does a charset change bytes automatically in Files.copy?** No. Copy transfers file contents; text decoding/encoding is a different operation.

**Does clear on a future ByteBuffer erase data?** No. That name concerns buffer state, not file deletion or secure erasure. The buffer chapter shows the distinction.

## Resolve names and choose open options

On one filesystem, resolving a relative child appends it to the base. Resolving an absolute child returns that child rather than forcing it inside the base. Relativize describes a route between compatible paths; it does not move a file. Different providers/root kinds may make the operation invalid. Neither resolve nor normalize proves filesystem authorization or existence.

| Option/operation | Effect to choose deliberately |
| --- | --- |
| CREATE | Create a missing file; not exclusive creation |
| CREATE_NEW | Fail if the target already exists under the operation's contract |
| TRUNCATE_EXISTING | Discard existing content when opening for appropriate writing |
| APPEND | Write at the end; do not assume cross-process record atomicity |
| REPLACE_EXISTING | Permit replacement in the specified copy/move operation |
| ATOMIC_MOVE | Request an atomic move; unsupported cases can fail |

The default options of a particular Files convenience method matter. Do not open an existing file under a truncating default while intending to append. Copy/move failures can also leave states requiring investigation; an existence precheck does not make the later operation transactional.

## Process bounded text without retaining an entire line

<JavaExample file="BoundedTextScan.java" output={"nonblank=2\ncharacter limit rejected"} />

countNonblank borrows its Reader. It processes a 512-unit buffer, retains only a count and whether the current line contains a unit greater than ASCII space, and leaves closure to the caller. CR and LF terminate a candidate line; empty/whitespace-only segments do not add to the nonblank count. At EOF, an unterminated nonblank final line still counts.

The maximum counts UTF-16 units, including line endings. The helper reads at most one unit beyond the remaining budget to distinguish exact-limit EOF from excess input, then rejects excess. It does not allocate an unbounded String for an extremely long line. Character limits, byte limits and user-visible character counts are different contracts. Processing n accepted units takes O(n) work and fixed-size working storage.

If a read fails, its IOException propagates. A zero-progress Reader is rejected rather than spun indefinitely. Some input may already have been consumed when failure occurs; this scanner does not promise stream rollback. The caller can supply an owned BufferedReader opened with Files.newBufferedReader and close it outside this helper.

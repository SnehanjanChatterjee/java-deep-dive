## Own a lifetime as well as an object

A **resource** is a facility with a lifetime that needs explicit management, such as a file or network connection used for input/output (I/O). A Java object can wrap that facility, but reclaiming the wrapper's memory is not the same operation as closing the file or connection. **Ownership** names the code responsible for ending that lifetime. A helper merely borrowing a caller's resource should not silently close it.

**AutoCloseable** is an interface declaring close. **Try-with-resources** is a try statement with resource declarations in parentheses. After a non-null resource is successfully initialized, the language calls close when leaving the body, whether it completes normally or exceptionally. Scope makes the intended lifetime visible: acquire, use, close, then continue after the construct.

Begin with the normal closing path. Then add a body failure, a closing failure and partial initialization one at a time. This separates the basic lifetime rule from the rule selecting a primary failure when several operations fail.

TraceResource implements the closing contract and prints a label in each phase. Construction completes before the body starts; use runs in the body; close runs before the statement after the try. There is no explicit close call in main because the resource declaration owns that obligation.

This in-memory teaching resource holds no operating-system facility: its close method only records the invocation. A real file/socket type defines what close releases and which later operations it rejects. The language guarantees the structured call to close; the resource type supplies that call's actual behavior. The settings-loader example below applies the same lifetime structure to a Reader.

## First observe one body and one close failure

<JavaExample file="ResourceFailures.java" output={"body\n1"} />

The resource initializes successfully. Its body throws an IllegalStateException named body. Before the catch runs, the language closes the resource; close also throws. The body exception stays **primary**, the failure propagated to the catch. GetSuppressed contains the additional close failure, retained without replacing that primary failure. GetCause instead describes why one failure was produced from another at an abstraction boundary. Cause and suppression answer distinct questions.

## Close in reverse order and preserve the primary failure

<JavaExample file="ResourceFailureTrace.java" output={"body\nclose B\nclose A\nclose B\nclose A"} />

Run(true) initializes A then B. The body fails, B closes, then A closes. It prints the primary body message followed by suppressed close B and close A. Run(false) has no body failure: B's close failure becomes primary and A's becomes suppressed. Only successfully initialized resources close; if B's constructor fails, A still closes and B is not closed by that declaration.

<Diagram client:visible definition={"sequenceDiagram\n participant C as Caller\n participant A as Resource A\n participant B as Resource B\n C->>A: initialize\n C->>B: initialize\n Note over C: body fails\n C->>B: close, retain failure\n C->>A: close, retain failure\n Note over C: catch original body failure with suppressed closes"} caption="The language preserves a body failure while recording later cleanup failures." />

A hand-written finally that throws during close can mask the original failure. Try-with-resources encodes the selection and suppression rules rather than relying on every caller to reproduce them. A null resource value is not closed, although an API can reject null before constructing a wrapper.

## Run the failure during resource initialization

<JavaExample file="ResourceInitializationLesson.java" output={"open A\nopen B\nclose A\nprimary=open B\nsuppressed=close A"} />

First is successfully initialized before second begins. B records its opening attempt and throws before its declaration acquires a completed Resource. The body is never entered. A is closed during unwinding; B has no automatic close invocation from that failed declaration. When A's cleanup also fails, the opening failure stays primary and the close failure is suppressed on it. Trace(false) in the same source exercises the successful cleanup variant.

A constructor acquiring several external resources must account for partial acquisition itself when it can fail before returning a wrapper. Try-with-resources closes successfully established resource variables, not every external thing a failed constructor touched internally. This is an ownership boundary, not merely a reversed loop over names.

## Read the closing interface's actual promise

An **idempotent** close has the same effect when repeated after the resource is already closed. AutoCloseable.close may declare Exception and is not universally required to be idempotent. Closeable narrows its checked failure to IOException and specifies that closing an already closed stream has no effect. A concrete type may promise more than its broad interface; read that type's contract before retrying close or sharing a resource between owners. In Java 9+, an existing final or effectively final local can appear as a resource (`try (reader)`); the Java 8 declarations above remain valid on later releases. [AutoCloseable](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/lang/AutoCloseable.html), [Closeable](https://docs.oracle.com/en/java/javase/25/docs/api/java.base/java/io/Closeable.html)

Checked closing obligations follow the resource variable's declared type. TraceResource.close declares no checked failure, so the normal example needs no throws clause. Declaring that variable as AutoCloseable would expose AutoCloseable.close's broader Exception contract and require catching or declaring it, even for the same runtime object. The chosen implementation does not erase the compiler's source-level obligation. [JLS try-with-resources translation](https://docs.oracle.com/javase/specs/jls/se21/html/jls-14.html#jls-14.20.3.1)

## Solved loader: open, read, validate and translate

This loader reads a network port number from text, accepting one through 65535. A **Reader** is the standard character-input abstraction; **BufferedReader** adds buffering and readLine. ReaderFactory is this example's interface for obtaining a fresh input, allowing the caller to supply a file or a controlled in-memory reader without changing the loading policy.

<JavaExample file="CheckedSettingsLoader.java" output={"8080\nCannot load port\nnot available"} />

ReaderFactory.open supplies a fresh Reader and transfers ownership to the loader. The resource declaration wraps it in a BufferedReader; closing the wrapper closes that input. ReadLine returns the first line or null for missing input. Parsing and the 1..65535 check preserve the port domain. IOException and invalid representations are translated into SettingsLoadException with the original cause.

If body and close fail, suppression attaches to the body exception **before** the outer catch wraps it. Inspect `failure.getCause().getSuppressed()`, not only the wrapper's suppressed array. An opening failure is also translated. Null factory or a null returned Reader is a rejected programming contract, rather than a successful empty configuration. The supporting test exercises opening, reading, parsing, close-only and simultaneous failures.

## Transfer lazy resource ownership explicitly

The later functional lessons introduce **Stream**, a lazily processed sequence API, and the I/O lessons use it for files. Keep one ownership rule in mind for that later use: Files.lines and Files.walk return resource-backed streams requiring closure after consumption. Returning one from inside an already closed try-with-resources scope gives the caller a closed value. Ordinary collection streams do not imply the same ownership requirement. Document who closes resource-backed results, and remember that wrappers commonly close their underlying resource.

## Practice: fail while opening the second resource

A opens, B's initialization throws X and A.close throws Z. Which exception is caught, and where is Z?

<details>
<summary>Answer</summary>

X is primary, with Z suppressed on X. B never completed initialization, so that resource declaration does not close B. This differs from B opening successfully and failing in the body. Preserve both primary and suppressed diagnostics, and do not claim an operation succeeded merely because a catch returned a default. A custom diagnostic graph formatter must also avoid cycles if it traverses arbitrary cause/suppressed relationships.

</details>

Closing a resource is separate from rejecting malformed text, and both policies need to remain visible to the caller.

## Pass a behavior to another operation

A method can receive data such as a String. It can also receive an object whose method supplies a decision. Imagine selecting text with a rule: the caller chooses the rule, while the selection operation owns traversal. A functional interface describes that one behavior through a single abstract method.

<span id="worked-example" aria-hidden="true"></span>
## Derive the lambda from its interface method

Start with the operation we want to vary: accept text containing exactly three UTF-16 code units. The interface names a method for that decision:

```java
@FunctionalInterface
interface TextRule {
    boolean accepts(String text);
}
```

A named class ThreeLetters implements TextRule and defines accepts as returning text.length() == 3. To use it, create the object and call its method through the interface:

```java
final TextRule named = new ThreeLetters();
final boolean accepted = named.accepts("cat"); // true
```

A **lambda expression** supplies that same functional-method implementation without another named class. Derive the expression from the target interface: accepts has one String parameter and a boolean result.

```java
final TextRule explicit = (String text) -> { return text.length() == 3; };
final TextRule concise = text -> text.length() == 3;
```

The arrow separates parameters from implementation. Because the target type already supplies String, the second form omits it. A single returned expression can omit braces and return. Invocation is still concise.accepts("cat"), not a new universal function-call operator.

<JavaExample file="FunctionalInterfacesLab.java" output={"true\ntrue\ntrue\ntrue"} />

Predict each line: the named rule accepts cat; the anonymous rule accepts cat; the explicit lambda accepts dog; the concise rule rejects Java because its length is four. rejects is a default method that negates accepts. A default implementation does not add a second abstract requirement, so TextRule remains functional. Null is outside this rule's contract and fails when length is read.


## Compare a named class, an anonymous class and a lambda

The complete source's second implementation is an anonymous TextRule class. It declares an override of accepts in a class body without introducing a separate source-level class name. Its first three output lines show the named, anonymous and explicit-lambda implementations accepting three-unit text. The final concise lambda rejects four-unit Java through its inherited default rejects operation.

These mechanisms can implement the same interface but are not universally interchangeable. An anonymous class can declare additional fields/methods and has its own this. A lambda supplies the functional method's behavior and uses the enclosing this. An abstract class with one abstract method is still not a lambda target: the language requires an appropriate functional interface.

## Read the parameter and result shapes

| Shape | Example interface | Invocation |
| --- | --- | --- |
| One input, boolean result | Predicate&lt;T&gt; | test(value) |
| One input, transformed result | Function&lt;T,R&gt; | apply(value) |
| One input, side effect | Consumer&lt;T&gt; | accept(value) |
| No input, produced result | Supplier&lt;T&gt; | get() |
| No input, no result | Runnable | run() |
| Same input/output type | UnaryOperator&lt;T&gt; | apply(value) |
| Two inputs, one result | BiFunction&lt;T,U,R&gt; | apply(left,right) |

`() -> "ready"` has no parameters; parentheses are required. `(left, right) -> left + right` has two parameters, so parentheses remain. For a block returning a value, each normal returning path must return a compatible value. Primitive variants such as ToIntFunction and IntPredicate use primitive results/parameters rather than boxed contracts.

The target interface supplies the type. A bare lambda does not declare a standalone nominal function type, and an ambiguous overload can need an explicit target or cast. @FunctionalInterface asks the compiler to check the interface's intent; it is not required to enable lambdas. Inherited override-equivalent declarations can form one abstract contract, while public Object methods, static/default/private methods do not add an abstract requirement.

## Check syntax against the target method

| Form | Valid purpose |
| --- | --- |
| `() -> 7` | No-argument value production |
| `value -> value.length()` | One inferred parameter and an expression result |
| `(left,right) -> left + right` | Two parameters; parentheses required |
| `(String value) -> { return value.length(); }` | Explicitly typed parameter and returning block |
| `value -> System.out.println(value)` | Void action through a compatible Consumer |

An expression-bodied method invocation returning a value can sometimes be adapted to a void action by discarding its result. For example, a List.add invocation returns boolean but can supply a Consumer action. This can make overloads accepting different functional shapes ambiguous; an explicit target variable or appropriately typed block clarifies the intended contract.

Do not mix explicitly typed and inferred parameter declarations in one lambda. Java 11 adds var parameter syntax, with its own consistent-parameter requirements; that is different from Java 10 var local variables. A block with a value result must satisfy its return-path/type rules. Statements such as loops require a block rather than pretending every body is one expression.

The Object target alone does not identify a functional method. Casting a lambda to a specific functional interface supplies a target; it does not create a universal function type. Return/input conversion must fit that interface, including boxing and primitive specialization.

## Capture a value from the enclosing method

```java
final int minimum = 3;
final Predicate<String> longEnough = text -> text.length() >= minimum;
System.out.println(longEnough.test("Java")); // true
```

minimum is a captured local value. It must be final or effectively final: a local assigned once without the final keyword is also eligible. Reassigning it after capture is rejected. A captured final List reference can still point to a mutable list; local reassignment and referent mutation are different operations.

Capturing an enclosing receiver can retain its object graph when a callback is stored in a long-lived listener collection. Fields follow their own mutation/access protocol rather than the local-variable capture rule; the method-reference chapter makes receiver evaluation observable.

## Distinguish binding a local value from sharing mutable state

Effectively final concerns assignments to the local variable, not merely statements after the lambda was written. Reassigning an initialized local before later capture can also make it ineligible. Branch assignments can still satisfy the language's definite-assignment/effectively-final rules; the compiler checks the whole relationship.

A lambda retaining a final List reference can observe later changes to that same List object. It does not receive an automatic snapshot. A field read can also observe different state on a later invocation. When callbacks cross thread/lifetime boundaries, those aliases need an explicit ownership/publication protocol.

A mutable one-cell counter can demonstrate capture, but is not a general solution to parallel aggregation. Prefer returned values, lawful collectors or an intentionally coordinated state abstraction for real concurrent work.

## Respect the callback's invocation contract

Function does not promise purity; Supplier does not promise memoization. Document when/how often callbacks run, whether they are retained/retried, thread context, null handling and failure propagation. A Function mapper cannot directly throw an arbitrary checked IOException because its abstract method does not declare it. Handle/translate the specific failure with its cause, or choose an interface that declares the intended failure.

The compiler/runtime can link lambdas using invokedynamic. Do not assume one anonymous class per expression, a fresh instance each time, stable identity, or a serializable durable representation of behavior. Serializing a callback also depends on its target interface and captured values; explicit data is usually clearer for durable commands.

## Worked exercise: add a default operation

The complete TextRule solution already includes rejects as a default operation. Implement a second rule for nonempty text as `text -> !text.isEmpty()`, then invoke accepts on empty and nonempty strings. Expected results are false and true. Calling rejects reverses those outcomes by invoking the same abstract behavior.

<span id="common-mistakes" aria-hidden="true"></span>
## Check the method being implemented

A Consumer performs an action and cannot stand in for a Function returning a result. A lambda cannot override a default method. Capturing a mutable list does not freeze it. A syntactically compatible callback can still violate a caller's lifecycle or failure assumptions.

<span id="exercises-and-interview-questions" aria-hidden="true"></span>
## Explain the code before shortening it

Given `Predicate<String> rule = value -> value.isEmpty();`, identify the target type, abstract method, parameter, expression and result. The invocation is rule.test, not rule.apply. Expanding to `(String value) -> { return value.isEmpty(); }` preserves its meaning.

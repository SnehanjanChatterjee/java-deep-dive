## Make “no result” part of an API

A search can legitimately find no matching value. Returning Optional makes that outcome visible in the method's result type. A returned Optional should itself never be null. First declare what empty means: a missing configuration value is different from a malformed present value or a failed network request.

Create a known value with Optional.of(value), a nullable boundary with ofNullable(value), or deliberate absence with empty(). of(null) fails immediately. Optional is a value-based result abstraction; do not rely on identity, synchronize on it or assume it is Serializable.

The example is a small composition, not an invocation-count experiment. The separate experiment below makes evaluation observable.

| Operation | Present | Empty |
| --- | --- | --- |
| map(f) | Apply f; null result becomes empty | Skip f, remain empty |
| flatMap(f) | f must return a non-null Optional | Skip f, remain empty |
| filter(p) | Retain only if p returns true | Skip p, remain empty |
| orElse(value) | Return present value; argument was already evaluated | Return evaluated fallback |
| orElseGet(factory) | Skip factory | Invoke factory |
| orElseThrow(factory) | Return present value | Construct and throw the supplied exception |

## Observe eager and lazy fallback

<JavaExample file="OptionalFallbackLab.java" output={"present eager: present, calls=1\npresent lazy: present, calls=0\nempty eager: fallback, calls=1\nempty lazy: fallback, calls=1"} />

Java evaluates arguments before entering a method. With orElse(fallback(counter)), fallback runs even when the value is present; its result is then discarded. With orElseGet(() -> fallback(counter)), constructing the supplier does not execute its body. Optional invokes it only for empty. Each observation gets its own counter, so prior runs cannot contaminate the result.

This difference concerns work and failures, not just speed. If the eager fallback throws, orElse is never entered even for a present Optional. A lazy fallback can still throw when absence actually requires it. Supplier does not promise memoization across separate calls.

## Compose a lookup without nesting

Suppose findAccount returns Optional&lt;Account&gt;, and Account.findAddress returns Optional&lt;Address&gt;. map(Account::findAddress) produces Optional&lt;Optional&lt;Address&gt;&gt;. flatMap(Account::findAddress) keeps one presence dimension: either a present Address or empty. Returning null from the flatMap mapper violates its contract; map instead treats a null mapped value as absence.

Optional.or on Java 9+ supplies a lazy Optional-returning alternative; orElseGet supplies a plain value. Optional.stream on Java 9+ exposes zero or one stream element for later flattening. Primitive OptionalInt/Long/Double use primitive result contracts and do not mechanically reproduce every Optional method.

## Complete the nested-lookup example

<JavaExample file="OptionalComposition.java" output={"true/true\nMain Street\nnone\nnone\nmap null becomes empty=true\nflatMap null rejected\nnull function rejected even for empty"} />

find("known") returns a present Account whose address lookup is also present. map(Account::address) therefore produces `Optional<Optional<String>>`. flatMap keeps one result layer and returns Main Street directly. no-address is a present account with no address; missing is no account. Both yield an empty address result, while null keys are explicitly rejected by this fixture rather than called a normal absence.

The program also separates a null mapped value from a null callback object. map's null result becomes empty; flatMap's null Optional result throws when invoked. A null map callback is rejected even for empty input. Skipping a body does not mean every API skips validation of the callback argument itself.

## Choose retrieval and actions deliberately

| API | Purpose | Version |
| --- | --- | --- |
| isPresent / get | Query presence / retrieve under a presence guarantee | 8 |
| ifPresent | Invoke a Consumer only for a present value | 8 |
| orElse / orElseGet | Eager-argument or lazy-supplier value fallback | 8 |
| orElseThrow(supplier) | Require a value with an explicit failure policy | 8 |
| ifPresentOrElse | Handle present and empty branches | 9 |
| or | Lazy Optional-returning alternative | 9 |
| stream | Zero/one element integration | 9 |
| orElseThrow() | Require a value with the standard empty failure | 10 |
| isEmpty | Direct absence query | 11 |

<JavaExample file="modern/OptionalOperations.java" output={"secondary\nempty branch\nabsent=true\nstream sizes=1/0\nprimitive sum=7"} />

The complete convenience example requires Java 11. or is not a general exception fallback: its supplier runs for absence, not because a previous lookup failed. ifPresentOrElse can perform distinct branch actions, but ordinary branching may be clearer when each branch owns resources or several effects.

Optional equality compares contained values, or considers two empty values equal. It does not justify synchronizing on instance identity. An Optional&lt;Integer&gt; can also be converted back into a dangerous null by orElse(null), then fail during caller unboxing. The container's non-null-value rule cannot protect a later caller-chosen null fallback.

Primitive optionals do not expose every Optional transformation method. Their stream methods require Java 9. Select them for a primitive-result API, then use their actual supported operations instead of assuming Optional&lt;T&gt; method parity.

<span id="common-mistakes" aria-hidden="true"></span>
## Retrieve only after choosing an absence policy

Calling get without a presence guarantee fails for empty. orElseThrow communicates a required value directly. ifPresent is useful for a small conditional action, but a normal if can be clearer when branches own resources or perform different side effects. Using Optional in every field and parameter can complicate a model without clarifying it.

<span id="exercises-and-interview-questions" aria-hidden="true"></span>
## Worked reasoning questions

**Why does map not invoke a mapper for empty?** There is no T to transform; absence propagates. The same rule makes a fluent chain concise, but can hide intended work if a programmer places a mandatory effect in a skipped stage.

**When should absence throw?** A find operation can return empty when no match is normal. A require operation can throw when absence violates its contract. Name and document the difference.

**Can a lazy alternative return null?** Optional.or requires a non-null Optional. The empty result is Optional.empty, not null. A plain-value fallback has its own documented null contract.

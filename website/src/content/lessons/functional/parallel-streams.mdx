## Split work without changing the result meaning

Parallel execution allows independent source partitions to be processed by different tasks. It does not change a stream into a thread-safe container. Begin with a lawful sequential reduction, then prove that splitting and combining preserves its meaning.

For [1,2,3,4], two illustrative partitions can produce totals 3 and 7, then combine to 10. A framework is free to split differently. Correctness must hold for all valid regroupings, including empty partial results, not just this drawing.

## Preserve encounter-order semantics deliberately

An ordered source can be processed out of callback order while retaining its required result order. forEach on a parallel stream does not promise encounter-order effects; forEachOrdered does, at an additional coordination cost. findFirst respects defined encounter order; findAny allows any eligible result. unordered relaxes an order requirement rather than randomly shuffling.

Stateful operations such as sorted/distinct and ordered limit can require buffering or coordination. Spliterator splitting quality and properties constrain useful partitioning. A cheap operation over a small source can cost more to split, schedule and merge than to run sequentially.

toConcurrentMap combines repeated words with a lawful count merge. groupingByConcurrent with downstream counting produces counts by length. Both are unordered concurrent reductions; a TreeMap copy is used only to display deterministic diagnostic keys after completion.

A concurrent outer map does not promise that its grouped List values are generally thread-safe for arbitrary caller mutation. The final line checks only group cardinalities after terminal completion, not incidental order within those lists. If encounter order is a value requirement, choose an ordered reduction or explicitly construct/sort the required sequence.

An ordinary nonconcurrent collector can be parallel-safe through separate partial containers. A concurrent collector can permit shared accumulation under its applicable characteristics and stream ordering conditions. Neither description implies that every arbitrary user accumulator is safe, or that changing characteristics repairs an incorrect combiner.

sequential()/parallel() configure pipeline evaluation mode, and isParallel reports that mode without consuming elements. The StreamSources program changes mode before its one terminal operation. unordered relaxes result order constraints; it neither randomizes elements nor forces another thread count. These are pipeline contracts, not a manual worker-allocation API.

## Understand execution resources

Parallel streams commonly use ForkJoin machinery; pool sharing, contention and blocking matter. Blocking I/O can occupy workers needed elsewhere. Nested parallelism is not an automatic optimization. The concurrency module later develops task pools and work stealing. Here the essential model is independent partial work plus combination, rather than a universal faster mode.

A timed wait does not establish cancellation of remote effects or complete resource cleanup. A stream pipeline is also not a substitute for an explicit bounded task protocol when admission, deadlines and lifetime are the main problem.

## Worked failure diagnoses

**A shared ArrayList loses elements.** Multiple callbacks mutate the same ordinary list. Use collect with independent accumulation or an explicit suitable concurrency protocol. Synchronizing the list can coordinate individual writes but introduces contention and does not repair an unlawful reduction formula.

**reduce(1, Integer::sum) is wrong.** One is not addition's identity. An explicit split [1,2] and [3,4] gives partial sums 4 and 8, then 12; sequential evaluation gives 11. Zero gives 10 in either case. Do not turn one observed framework partition count into an API promise.

**Sequential success, parallel failure.** Inspect supplier independence, combiner identity/associativity, finisher type and characteristics. A false IDENTITY_FINISH or incorrect merge cannot be repaired by adding synchronized.

## Explain what order is and is not preserved

For an ordered list, collecting to a list preserves the required result sequence even if independent callbacks run out of order. forEachOrdered orders its terminal actions, with the documented happens-before relationship between successive actions, but upstream map/filter evaluation can still be concurrent.

findAny may return any eligible value. findFirst must honor an encounter-first result when order exists and can need more coordination. Stateful sorted/distinct and prefix slicing add their own barriers/state. Callback side effects and thread-local assumptions can therefore make an apparently simple parallel switch change observable behavior or ownership.

## Decide whether parallelism helps

State a hypothesis about source size, per-element work, splitting, order, allocation and merge cost. Measure a representative workload with a sound benchmark. A faster small local run does not establish a general speedup. The diagnostic benchmark chapter explains measurement after the execution model is understood.

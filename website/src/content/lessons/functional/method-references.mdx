## Name an existing implementation

A parsing function already exists: Integer.parseInt converts decimal text to int. If a `Function<String,Integer>` lambda does nothing except call it, a **method reference** can name that implementation:

```java
final Function<String, Integer> longForm = text -> Integer.parseInt(text);
final Function<String, Integer> reference = Integer::parseInt;
final Integer value = reference.apply("42"); // 42
```

The target Function supplies the argument/result shape. Writing :: names the method; apply invokes it later. To understand any reference, expand it to the corresponding lambda and identify which argument supplies the receiver.

| Reference | Lambda expansion | What supplies the receiver? |
| --- | --- | --- |
| Integer::parseInt | text -> Integer.parseInt(text) | Static method; no receiver |
| text::trim | () -> text.trim() | Bound text object |
| String::trim | value -> value.trim() | First functional argument |
| ArrayList&lt;String&gt;::new | () -> new ArrayList&lt;String&gt;() | New object created per invocation |
| String[]::new | length -> new String[length] | Array length argument |

<JavaExample file="MethodReferenceLab.java" output={"42\njava\njvm\n0\n2\n4\ntrue"} />

The reference does not invoke the target body just by being declared. Calling apply/get does. A bound receiver is evaluated when the reference is created: a null receiver fails then. `() -> receiver.work()` defers that dereference until invocation. Constructor references can target different overloads depending on their functional signature.

The basic program prints 42 from parsing, java from trimming a bound String, jvm from trimming an argument String, zero from a new empty list's size, and two from a newly allocated array's length. Its final 4 and true are composed function/predicate results, developed below.

## Observe receiver evaluation, virtual dispatch and super

missing::trim evaluates a null receiver while creating the reference, so the first failure occurs before a callback object can be used. The lambda () -> missing.trim() can be created; its dereference happens only when get is called. “Method reference is a shorter lambda” describes a useful invocation shape, not permission to ignore evaluation timing.

The parent-typed receiver actually refers to Child. An ordinary bound virtual reference still reaches the child's override. Child's super::greet deliberately selects its superclass body instead, producing child/base. A bound receiver is not the same as freezing every later field value inside that object.

The final Scope experiment returns enclosing from lambda this and anonymous from the anonymous implementation's own this. Identical-looking member names can therefore resolve to different receivers. Captured context can also keep an enclosing object reachable while a stored callback remains live.

## Read additional arguments from the target type

`String::substring` can target `BiFunction<String,Integer,String>` as `(text,start) -> text.substring(start)`: the first functional argument supplies the receiver, the second the method's index. With a bound text::substring, a two-index target can instead supply only the begin/end indexes.

Constructor references also use target shape. `Supplier<List<String>>` with ArrayList&lt;String&gt;::new selects the no-argument constructor; `IntFunction<List<String>>` with that same constructor spelling selects the capacity constructor. A requested capacity still does not create list positions. `String[]::new` accepts a length and produces that runtime array component type.

## Compose transformations in a declared order

trim produces a String; length consumes a String and produces Integer. trim.andThen(length) therefore computes length(trim(input)). Function.compose reverses that relationship: f.compose(g) computes f(g(input)). The intermediate output/input types must fit.

For " java ", trim yields "java", then length yields 4. Reversing these particular functions would not type-check: length returns Integer, while trim needs String. Composition is a typed data flow, not a request to call arbitrary functions in either order.

These are the same composition contracts used with explicitly written lambdas. The method-reference spelling selects an implementation; it does not add purity, memoization, exception recovery or a different effect order. The preceding predicate/function chapter supplies complete short-circuit and consumer-order experiments.

## Reverse one comparator key or the whole policy

<JavaExample file="ComparatorComposition.java" output={"ascending=[B:10, C:10, A:20]\nboth keys reversed=[A:20, C:10, B:10]\npoints only reversed=[A:20, B:10, C:10]"} />

CollectionOrdering.Score exposes immutable id and points accessors. `comparingInt(Score::points).thenComparing(Score::id)` produces B:10,C:10,A:20. Reversing that whole comparator reverses both keys: A:20,C:10,B:10. Reversing only comparingInt before adding thenComparing produces A:20,B:10,C:10, with ascending IDs inside point ties.

The composition order is the comparison contract. Shorter syntax does not repair inconsistent equality, arithmetic overflow in a handwritten subtraction comparator, or mutable ordering state. ## Worked exercise: expand an unbound reference

`String::length` can target ToIntFunction&lt;String&gt; as `value -> value.length()`. The String argument is the receiver, and the result is primitive int. `"java"::length` instead has its receiver fixed and can target IntSupplier with `() -> "java".length()`. Predicting those invocation shapes explains why they are not interchangeable.

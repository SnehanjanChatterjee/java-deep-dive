## Turn several values into one result

A reduction combines values, such as adding invoice amounts or finding a maximum. Begin with the sequential loop: initialize a result to zero, then add every number. A stream reduction separates that initial identity from the operation that combines the current result with one more value.

For [1,2,3,4], start with total = 0, then visit the values:

```java
int total = 0;
for (final int value : values) { total += value; }
// totals: 0 -> 1 -> 3 -> 6 -> 10
final int reduced = values.stream().reduce(0, Integer::sum);
```

The initial 0 is the **identity**, an input that leaves an addition result unchanged. The combining function takes the running result and the next element. For Integer::max over the bounded int domain, Integer.MIN_VALUE is a valid identity: max(MIN_VALUE,x) equals x for every int. An identity-based reduction would return MIN_VALUE both for empty input and for a real maximum of MIN_VALUE. The no-identity overload returns Optional so those outcomes stay distinct.

For reduce(0, Integer::sum), the intermediate totals are 0,1,3,6,10. Zero is an identity: adding it changes nothing. The no-identity overload reduce(Integer::max) returns Optional because an empty stream has no maximum value to return. Using zero as a guessed maximum would be wrong for all-negative inputs.

## Require laws that survive regrouping

An associative operation produces the same meaning under regrouping. Integer addition without an overflowing domain supports this algebra; subtraction does not: (10−3)−2 is 5, while 10−(3−2) is 9. With identity one, addition is not an identity-based sum: even sequential evaluation introduces an extra one, and partitioned evaluation can introduce one in every partial reduction.

Floating-point addition has rounding effects and is not associative in the mathematical sense over all finite values. Regrouping can change low-order bits. Overflow, exceptional arithmetic and numeric domain constraints must be part of the reduction contract.

For the three-argument reduce overload, the combiner must agree with the accumulator as well as having a valid identity. For example, reducing words to total length needs accumulation of one word's length and combination of two length totals. Do not apply an element accumulator to partial results of a different shape.

## Work the three overload shapes separately

| Overload shape | State/result type | Empty policy |
| --- | --- | --- |
| reduce(identity,BinaryOperator&lt;T&gt;) | T throughout | Return identity |
| reduce(BinaryOperator&lt;T&gt;) | T throughout | Empty Optional&lt;T&gt; |
| reduce(identity,BiFunction&lt;U,T,U&gt;,BinaryOperator&lt;U&gt;) | Input T, result U | Return U identity |

<JavaExample file="ReductionLaws.java" output={"length=8\nempty length=0\ncombined=8\ninvalid identity sequential/partitioned=11/12"} />

For totalLength, the input T is String and result U is Long. Accumulation adds one text's length to a partial long; combination adds two partial longs. Java,JVM,a produce 0→4→7→8. Splitting after Java gives partial results four and four, combined to eight. Empty input contributes zero.

The compatibility law is not just “both methods return U.” For any valid partial u and element t, combining u with accumulation of t into the identity must mean the same thing as accumulating t into u. Here u + (0 + length(t)) equals u + length(t). Substituting an unrelated combiner such as max would break that relationship despite compiling.

The source also manually splits an invalid identity-one sum. Sequential output eleven and partitioned output twelve show the law failure without pretending a framework must use one particular partition count. A different parallel partitioning can produce another wrong answer; none makes one an addition identity.

Math.addExact makes the length aggregation's arithmetic failure explicit. Exact arithmetic is not automatically associative for arbitrary mixtures of signed values and exception paths: an intermediate overflow can depend on grouping. This nonnegative-length model makes its intended mathematical range policy clear.

## Distinguish reduce from mutable collection

An ordinary immutable scalar reduction returns a new result value from each combination. Appending into one shared StringBuilder/ArrayList identity mixes mutable aliasing with reduction laws. Mutable accumulation belongs in collect, which supplies independently owned containers and a lawful combiner. The next chapter begins with ordinary collector factories before implementing those pieces.

mapToInt changes Stream&lt;Integer&gt; into IntStream; sum is then a primitive terminal operation. That avoids boxed accumulation contracts, not overflow. Use long, exact arithmetic or a domain type when the supported range requires it.

## Worked exercise: choose the empty-input behavior

For a product of integers with a conventional algebraic identity, use one and multiplication; declare overflow policy. For a maximum, choose Optional or a domain-specific failure/default at the caller. For an average, retain count and total until the final division. Averaging partial averages without their counts loses information: averages of one item and one thousand items cannot be weighted equally.
